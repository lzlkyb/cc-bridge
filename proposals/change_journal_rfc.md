# RFC：变更日志 —— 把「AI 为哪个需求、出于什么原因改了哪些文件」做成开放能力

状态：**草案，方向已确认，未动代码**
日期：2026-11-12（同日三版：按会话 → 按变更集且桥管状态 → **桥只记录、状态归使用方**）
起因：NCForge 要做「按需求审查代码」。但「知道 AI 为哪个需求改了什么、为什么改」不是 NCForge 独有的需求——任何编辑器、审查工具、发版脚本都可能要。cc-bridge 只提供事实记录，**不含任何 NCForge / NC 专用字段、规则或状态**。

## 〇、已确认的决策（2026-11-12）

| # | 决策 | 理由 |
|---|---|---|
| 1 | 归属单位是**变更集（需求）**，不是会话 | 一个会话可能做几个需求，一个需求也可能跨会话 |
| 2 | 写类工具加两个可选参数：`changeSet`（需求名）、`reason`（一句话说明为什么这么改） | 显式声明没有「当前变更集」这种隐式状态，并发会话不会串；`reason` 让审查时不用回对话里翻 |
| 3 | **cc-bridge 不保存变更集状态**：改名、归类、出包、关闭都由使用方管；桥不开写接口 | 「出包」「需求生命周期」是使用方的概念；桥只记事实，开放性更好、工作量更小 |
| 4 | 变更集的**命名规则由项目定**，桥只做字符串清洗 | 爱尔 NC 项目约定「变更集名 = 补丁名去掉日期」，写在项目 CLAUDE.md，经 `list_allowed_roots` 带给模型 |
| 5 | `run_command` 引起的改动不记 | 只能按时间窗猜。使用方应以自己的版本控制状态为「改动全集」，变更日志只用来认领与解释 |

### 为什么不靠会话 id（2026-11-12 调研结论，供以后查）

- MCP 2026-07-28 版协议无状态，去掉了 `Mcp-Session-Id`；新增请求头只有 `Mcp-Method` / `Mcp-Name`，不带调用方标识。
- Claude Code 发给 HTTP MCP 的请求里没有会话 id。官方仓库的需求 anthropics/claude-code#54629、#76391 均因无人跟进被自动关闭，未实现；#76391 实测 `_meta` 为空、`traceparent` 头每请求一个新值。
- 能拿到会话 id 的途径（PreToolUse 钩子、stdio 转发进程读 `CLAUDE_CODE_SESSION_ID`、开启 OTel 追踪传播 `traceparent`）都要改客户端配置，且会话 ≠ 需求。

## 一、为什么不直接让别人读 audit.log

2026-11-11 实测本机 `audit.log`（10.7 MB / 9582 行），它是给 cc-bridge 自己看的，不适合当对外契约：

| 问题 | 影响 |
|---|---|
| 一条 = 一次工具调用；一次改多个文件（167 条）时 `backupPath`/`targetPath` 只有一个 | 其余文件的备份要去查 `cc-bridge.db` |
| 改了哪些文件藏在 `params`（请求参数全文的 JSON 字符串）里 | 使用方要按每个工具的参数形状各自解析 |
| 按保留期**原地重写变短** | 跟读方的偏移会失效 |
| 字段无版本号，还夹着耗时、token 估算等内部指标 | 没法承诺兼容 |

结论：audit.log 保持内部用途不动；另出一份**专门对外、按文件、带版本号**的变更日志。

## 二、能力定义

> cc-bridge 每改动一个文件，就在变更日志里记一条：改了哪个文件、怎么改的、改之前的备份在哪、改完是什么内容（哈希）、谁发起的、声称属于哪个需求、为什么改。
> 任何本机程序都可以只读地消费它。

### 2.1 变更日志文件

- 位置：`<数据目录>\journal\changes-YYYYMMDD.jsonl`（Windows 下即 `%APPDATA%\com.ccbridge.desktop\journal\`）。
- **只追加、按天切文件、整文件过期删除，绝不原地重写**。保留天数可配（默认 30 天）。需要长期保留的使用方自己边读边存（含备份内容），不依赖桥的保留期。
- 一行一条，UTF-8 JSON。cc-bridge 没运行时使用方仍能读历史。

单条格式（v1）：

```json
{
  "v": 1,
  "seq": 18342,
  "at": "2026-11-12T10:21:05.312+08:00",
  "op": "edit",
  "path": "C:\\work\\aier\\newar\\ic\\src\\private\\nc\\bs\\X.java",
  "from": null,
  "backup": "C:\\Users\\...\\.cc-bridge-backup\\X.java.20261112_102105_301.bak",
  "before": { "size": 10422, "sha256": "…" },
  "after":  { "size": 10517, "sha256": "…" },
  "call":   { "id": "c-7f3a…", "tool": "edit_files", "client": "claude-code", "source": "10.0.19.194" },
  "changeSet": "7691_平台耗材采购退库原仓库无货按WMS对照替换仓库",
  "reason": "原仓库无货时按 WMS 对照表取替换仓库，取不到则报错"
}
```

| 字段 | 含义 |
|---|---|
| `v` | 格式版本。只加字段不改版本；改语义才升 `v`，并保留旧版本一段时间 |
| `seq` | 单调递增序号（跨文件、跨重启不重复），使用方记住「读到哪」 |
| `op` | `create` / `write`（覆盖）/ `edit` / `delete` / `move` / `copy` / `mkdir` / `rmdir` |
| `path` / `from` | 规范化后的绝对路径（去掉 `\\?\` 前缀）；`from` 只有 move/copy 有 |
| `backup` | 本次改动前的备份；新建文件或备份关闭时为 null |
| `before` / `after` | 大小与 SHA-256。使用方把文件当前哈希和 `after.sha256` 比，就能确定「现在这份就是 AI 写的」还是「之后有人动过」；上一条的 `after` 与下一条的 `before` 不等，说明中间有桥以外的改动 |
| `call` | 哪次工具调用（同一次调用改多个文件共享同一个 `id`）、客户端类型（来自已有的 `client_kind` 识别）、来源 IP |
| `changeSet` | 调用方声称的需求名（已清洗，见 2.3）；未声明为 null。桥不维护 id、别名、状态 |
| `reason` | 调用方给的改动原因，最长 200 字，超长截断；未给为 null |

只记**确实改变了文件系统**的操作：写入失败、或改后与改前一致的不记（实现时去掉了原定的 `ok` 字段：失败记录对审查没有用，反而要使用方多过滤一道）。

### 2.2 模型侧接口（MCP）

| 改动 | 说明 |
|---|---|
| 写类工具加可选参数 `changeSet: string`、`reason: string` | `edit_files` / `write_files` / `move_files` / `copy_files` / `delete_files` / `remove_directory` / `notebook_edit` / `create_directory`，以及 `batch`（子操作继承外层的值，子操作自己传了以子操作为准）。两个参数作用于本次调用的全部文件。**v1 未做**：单个文件项上的 `reason` 覆盖；`prepare_upload` 上传（实际写入发生在之后的 HTTP 上传里，不在调用上下文中） |
| 写工具返回里**按需**回显一句 | 只在两种情况回显：① 该名字在保留期内第一次出现：「新变更集 X」；② 与已有名字只差一点（疑似敲错）：「新变更集 X，是不是「Y」？」。沿用已有名字、未传 `changeSet` 都不回显——省 token（见 2.5） |
| 新工具 `change_sets` | 只读，从变更日志里统计保留期内用过的变更集名：名字、文件数、最后改动时间。可按路径前缀过滤。让模型先查再沿用，避免长名字凭记忆重敲 |
| 服务说明（instructions）加一段 | 「项目规则约定了变更集的，写文件时传 `changeSet` 和一句 `reason`；先用 `change_sets` 查已有名字；拿不准属于哪个需求就问用户」。命名规则本身不写在这里 |

### 2.5 token 消耗控制（2026-11-12 确认）

变更日志写在本机磁盘，本身不进对话；额外消耗只来自工具定义、模型多传的参数和工具多回的文字。约束：

1. **回显按需**：见 2.2，只在新建或疑似敲错时回显。
2. **参数说明最短**：各写工具 schema 里 `changeSet` / `reason` 的 description 各一句短语（如「变更集名，见服务说明」「一句话改动原因」），详细用法只在 instructions 里写一次。
3. **原因按调用写**：一次调用改多个文件只写一句；instructions 建议不超过 30 字。
4. `change_sets` 返回紧凑文本（每行「名字 · 文件数 · 最后改动」），默认最多 20 条。

估算（未实测）：固定约 800 token / 会话（仅在加载这些工具时），每次写入约 40–60 token 输出；一个 30 次写入的需求合计约 1500–2000 token。实现后用实际 tools/list 大小核对。

### 2.3 名字清洗

去首尾空白；`/ \ : * ? " < > |` 一律换成 `_`；空名字视为未声明。大小写敏感，不做其他改写。
这条规则保证名字能直接当文件名用（与 NCForge 补丁名的清洗规则相同）。命名格式由项目规则约定，桥不校验。

### 2.4 使用方自己负责的事（写进规范文档）

- **改名 / 别名**：桥只记当时传来的名字。使用方改了需求名（如补清单号）后，模型可能仍用旧名字，使用方自己把旧名映射到新需求。
- **归类、出包、关闭**：使用方自己存。
- **长期保留**：需求可能拖几个月才上线，使用方应边读边把关心的条目和备份内容存到自己那里。
- **改动全集**：以自己的版本控制状态为准；变更日志缺命令引起的改动，也缺 cc-bridge 以外的改动。

## 四、不做 / 边界

- 不保存变更集状态；不开写接口；不知道什么是「补丁」「清单号」「出包」。
- 不加任何使用方专用字段；不为某个使用方过滤路径。
- 变更日志只记元信息与哈希，**不记文件内容**；内容在备份里，沿用现有备份的保留与清理。
- 本机 HTTP 接口（补读 / 实时推送 / 取备份）不做，等有不方便读文件的使用方再议。
- `run_command` 引起的改动不记。`prepare_upload` 上传 v1 不记。
- audit.log 不动。

- 不做按时间分段（原 `run` 字段，2026-11-12 去掉）：只用于展示，使用方按 `at` 自己算，间隔可在使用方里调。

## 六、默认关闭（2026-11-12 用户确认）

不做需求审查的用户不应受任何影响，所以 `journal_enabled` 默认关。关闭时 `tools/list` 与 instructions 和加这项能力之前完全一致（不列 `change_sets`、不注入参数、没有第 6 条），写入不记录。切换后客户端需重连才拿到新清单，设置页切换成功后提示。超期日志改为启动时与每天定时也清理，不再只靠写入时顺手清。

命名约定不由桥下发（不做约定目录，2026-11-12 用户确认）：模型只拿到通用规则，名字不规范由使用方自己改名 / 合并。
