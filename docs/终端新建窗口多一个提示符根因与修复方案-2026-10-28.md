# 终端新建窗口多一个提示符：根因与修复方案

> 报障（2026-10-28）：新建窗口后屏幕上出现两行 `lizuliang@code7:~$`，期望只有一行。
> 结论：**不是多了一个 prompt，是探针回显行被抹成了「提示符 + 一串空格」**——剥除器只抹命令
> 正文，不抹它前面的提示符前缀。这是 2026-10-13 把擦除策略从「整行擦」改成「等宽空格覆盖」
> 时引入的副作用，一直存在，只是被当成「连接后两个提示符」（10-20 修的末行问题）的另一个面。

## 一、屏幕上到底发生了什么

新建会话时注入合并探针，这一行**必然被回显**（ECHO 此刻还是开的，关回显的命令本身就是它）：

```
行1  lizuliang@code7:~$  stty -echo 2>/dev/null; printf '\033]1337;Shell=%s\007' "$0"
                          └────────────── 被剥除器抹成 62 个空格 ──────────────┘
```

回显发生在行规程层，**字节进 tty 的那一刻就上屏**；剥除器事后只能在 `term.write` 里改字节。
它的实现（`lib/terminalSttyDance.ts:278`）是：

```ts
out += vtInside ? "\r\x1b[2K" : " ".repeat(token.length);
```

即「命中时写等宽空格覆盖 token 所占的列」。**token 之前已经渲染出去的提示符前缀原封不动**：

```
行1  lizuliang@code7:~$                     ← 提示符还在，后面是 62 个空格（不可见）
行2  lizuliang@code7:~$                     ← 命令执行完 readline 打印的真提示符
```

两行长得一模一样。单测是这个事实的硬证据（`terminalSttyDance.test.ts:293`）：

```ts
expect(out).toBe(`$  ${" ".repeat(PROBE_ECHO_OFF_CMD.length)}\r\n`);   // 前缀 `$ ` 仍在
```

后续 kick 空回车、`printf '\r\033[2K'; stty echo` 收尾产生的提示符都被这个 62 字符 token 抹成了空格（`STRIP_TOKENS` 里三条命令都在），所以**不会再多出第三、第四行**——用户看到的正好两行。收尾命令 `ECHO_ON_CLEAN_CMD` 里那个 `\r\033[2K` 清的是**它自己所在行**，够不到上面这一行。

### 为什么是「每次新建都有」，不是偶发

`claimInjection` 保证**一个会话只注入一次**（`useTerminalOsc.ts:206`），新建窗口/标签 = 新会话 = 必然走一遍注入 ⇒ 必然留下这一行。偶尔没注意到，是因为有的主题/配色下 62 个空格与背景同色，扫一眼像空行。

## 二、为什么不能直接把 `" ".repeat(...)` 换成 `\r\x1b[2K`

10-13 实测过（`.workbuddy/memory/2026-10-13.md:98`）：无条件整行擦会让**本地 xterm 光标回到行首、
而远端认为光标还在 token 末尾**，两边列号从此错开——

- 远端后续发给同一行的增量（readline 退格重绘、`\x1b[K`）全部画歪；
- 按 ↑ 翻历史时提示符消失、残渣正文反而露出来。

所以空格覆盖不是随便选的，它是为「保持列同步」付的代价。**只有在 token 之后紧跟行尾时**，
列差才会被随后的换行归零、整行擦才是安全的。

## 三、方案 A（推荐）：区分「整行回显」与「行中 token」

在剥除器里对命中后的后续字节做一次判定：

| 命中后紧随 | 语义 | 处置 |
|---|---|---|
| `\r\n` / `\n`（中间无可见字符） | **整行回显**——这一行就是一条命令的回显 | 输出 `\r\x1b[2K`，**连提示符前缀一起擦掉** |
| 本 chunk 到此结束 | 未知 | **扣留**，等下一个 chunk 定夺（下一个字节必是换行或 prompt 的 `\r\n`） |
| 出现可见字符 | 行中 token（ConPTY 重绘把多行挤进一个 chunk） | 维持等宽空格覆盖（现状，保列同步） |

好处：

- 屏幕上「行1」变成真正的空行，提示符从 2 个降到 **1 个**；
- 扣留只发生在 token 之后、换行之前，被扣的内容本来就要抹掉 ⇒ **再晚也无感**，不引入可见延迟；
- 兜底不变：扣留超过阈值（如 64 字节 / 4 个 chunk）或 `flush()` 时，退回空格覆盖，绝不丢数据。

**残留的一行空行消不掉**：整行擦除后光标在行1 行首，远端 readline 随后输出的 `\r\n` 把光标推到行2
打印真提示符。要去掉这个空行只能「吞掉那个换行」，但那会让远端行号比本地多 1——见方案 B，
默认不做。

## 四、方案 B（可选，不推荐默认开）：连换行一起吞

整行擦除后再吞掉紧随的一个 `\r\n`/`\n`，提示符就直接打印在行1，屏幕**完全干净**（无空行无残渣）。

代价：远端认为光标在行 N、本地在行 N-1，两者恒定差一行。相对定位（换行、`\r` 行首重绘）不受影响，
但**绝对定位会歪**——全屏 TUI 用 `\x1b[row;colH` 定位时整体偏一行。CC 的 TUI 会整屏重绘（自愈），
普通 shell 不受影响，可是这个假设一旦不成立就是「界面莫名其妙错一行」这类最难查的 bug。
建议先上 A，真机确认空行碍眼再单独评估。

## 六、验证

1. 单测：`npx vitest run src/lib/terminalSttyDance.test.ts`；

## 七、风险

| 风险 | 评估 |
|---|---|
| 整行擦误伤同行真实内容 | 仅当 token 后紧跟换行才走整行擦；行中 token 仍走空格覆盖 |
| 扣留导致 prompt 延迟 | 扣留内容本就要抹，且下一字节必然紧随（换行/prompt），无感 |
| CJK 宽字符使列数算法出错 | 方案 A **不需要计算列号**（整行擦与列无关），天然规避 |
| 与 10-13 错位回归 | 整行擦只在「行尾」场景触发，列差被换行归零；单测与实际验证都覆盖该边界 |

## 八、实施记录（已落地，方案 A）

改动只有 `lib/terminalSttyDance.ts` + 单测，`useTerminalOsc.ts` 一行未动（它已 299 行贴线）。

实现形态：`createEchoStripper` 命中 token 后**不立刻出结论**，进入 `hitWait` 状态等紧随的字节——

| 到来 | 处置 |
|---|---|
| `\n` | `settleHit(true)` → 输出 `\r\x1b[2K` + 暂存的 `\r`，换行放行 |
| `\r` | 存进 `hitBuf` 继续等（`\n` 分属两个 chunk 时靠这一步） |
| 转义序列 | 存进 `hitBuf`（不占列，不影响判定） |
| 可见字符 | `settleHit(false)` → 空格覆盖（行中 token 的老路径），随后字节照常透传 |
| chunk 结束 | 什么都不输出，`hitBuf` 留到下一段 |
| 暂存 > 16 字节 | 立即按「行中 token」收尾，不让数据无限滞留 |
| `flush()` | 兜底走空格覆盖，绝不丢字节 |

**实施时纠正了一处认知**：一开始我以为「整行擦」意味着输出里不该出现提示符前缀，于是按字符串相等写测试——错了。前缀是**命中之前**就逐字符进了输出流，`\r\x1b[2K` 的作用是在**渲染层**把它擦掉。用户看到的是渲染结果，所以新增了一个 20 行的 `screenOf()` 极简渲染器，断言直接落在「屏幕上有几行、每行是什么」，例如：

```ts
const out = s.feed(`${p1} ${PROBE_ECHO_OFF_CMD}\r\n${p1}`);
expect(screenOf(out)).toEqual(["", "lizuliang@code7:~$"]);   // 1 个提示符 + 1 个空行
```
