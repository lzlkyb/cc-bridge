# 上下文消耗优化方案

> 日期：2026-10-22
> 前作：`docs/token_saving_tools_rfc.md`（24 工具面改造 + 文件直传，已落地）
> 定位：本文只回答一个问题——**直传之后，还能从哪省**。数字全部来自 `%APPDATA%\com.ccbridge.desktop\audit.log` 的真实调用记录，不是估算。
> 口径：本文按「不保证功能语义完全不变」的授权展开，每项都标明它改变了什么、没改变什么。

## 〇、一句话结论

**直传理论上解决了 25% 的历史流量（2.20MB），但目前还没有一次真实会话验证过它。** 剩下 6.75MB 里最大单项不是「工具写得啰嗦」，而是 **AI 为了对比同一批文件的 8 个版本，把 8 份全文逐个读进上下文**（1.53MB，占 `read_files` 的 60%）。这类消耗改任何默认值都省不掉，只能给它一个更好的工具。

## 一、实测基线

### 1.1 数据来源

`%APPDATA%\com.ccbridge.desktop\audit.log`，每条记录含 `tool` / `params` / `timestamp`，`resultBytes` 字段**只在一部分记录里存在**。`resultBytes` 由 `mcp/tools/mod.rs::result_text_bytes` 计算，**只数 text 块、图片块按 0 计**（注释已说明理由：base64 按字节算会让 Token 页虚高两个数量级）。

> 🔴 **两个分母，混一次就全错**（2026-10-22 二次复核，本文初稿就是这么错的）：
> 日志共 **3134 行**，其中**只有 1758 行带 `resultBytes`**（早期记录没落这个字段）。所以：
> - **8.95MB / 261 万 tokens 是这 1758 条之和**，时间跨度 10-10 09:39 → 10-22 12:39；
> - 若按全量行数算「调用次数」，得到的是 3134，不是 1758。
>
> **次数、字节、平均值必须出自同一个分母**。初稿把全量行数的次数（`read_files` 339 次）和带字段的字节（2.68MB）拼在同一行，算出 avg 7.9KB，真实值 15.3KB——整张表由此失真。本文所有表内数字统一取**带字段的 1758 条**。
>
> 单位：本文 **MB = MiB = 1048576 字节**，直接取脚本原样输出。初稿混用了十进制 MB（同一份字节写成 9.32MB），所以初稿的 9.32 与本文的 8.95 差 4%，**不是数据变了，是单位**。
>
> `resultBytes` 是「进入下一轮上下文的字符数」，不含工具 schema、不含系统 prompt。它衡量的是**我们这边可控的那部分**，正好是本文的战场。

### 1.2 复现脚本

```python
import json, os
from collections import defaultdict

p = os.path.expandvars(r'%APPDATA%\com.ccbridge.desktop\audit.log')
rows = [json.loads(l) for l in open(p, encoding='utf-8') if l.strip()]

# resultBytes 自 10-10 起才落字段：两个分母必须分开打印，否则会算出一个「四不像」的总数
withb = [d for d in rows if 'resultBytes' in d]
print(f'总行数 {len(rows):,}  带 resultBytes {len(withb):,}  缺失 {len(rows)-len(withb):,}')

g = defaultdict(list)
for d in withb:
    g[d.get('tool') or '<unknown>'].append(d.get('resultBytes') or 0)

tot = sum(sum(v) for v in g.values())
print(f'字节合计 {tot:,} = {tot/1048576:.2f} MiB  ≈ {tot/3.6:,.0f} tokens')
for t, v in sorted(g.items(), key=lambda kv: -sum(kv[1])):
    n = len(v) or 1                      # 防御除零
    print(f'{t:20} n={len(v):>5}  MiB={sum(v)/1048576:6.2f}  avg={sum(v)//n:>6}  max={max(v):>8}')

# 集中度：多少比例的调用吃掉多少字节
srt = sorted((d.get('resultBytes') or 0) for d in withb)[::-1]
print('top25 占比', f'{sum(srt[:25])/tot*100:.1f}%' if tot else 'n/a')
print('>32KB 次数', sum(1 for x in srt if x > 32768))
```

### 1.3 分布

**8.95MB ≈ 261 万 tokens**（3.6 字节/token 粗估；分母固定为上述 1758 条）。分布极度偏斜：

| 工具 | 次数 | 总量 | avg | max |
|---|---:|---:|---:|---:|
| `run_command` | 797 | 4.18 MB | 5.4 KB | 396 KB |
| `read_files` | 172 | 2.57 MB | 15.3 KB | 247 KB |
| `batch` | 38 | 0.72 MB | 19.5 KB | 185 KB |
| `write_files` | 211 | 0.61 MB | 3.0 KB | 33 KB |
| `search_files` | 93 | 0.57 MB | 6.2 KB | 133 KB |

三个关键读数：

1. **25 次调用（1.4%）吃掉 54% 的字节**；41 次 >32KB 占 **62%**。优化必须打尾部，不是打平均值。
2. `run_command` 占 **45% 的调用次数**（797/1758）但 avg 只有 5.4KB —— 说明 AI 在拿 shell 干文件活（`cd`/`ls`/`cat`/`grep`），每次都是一去一回。这是**提示层**问题，不是代码问题。
3. 固定成本可忽略：`tools/list` 24 个工具共 15.9KB ≈ 4.4k tokens，`instructions` 1319 字符 ≈ 366 tokens，合计占总消耗 **0.19%**。

## 二、已经拿到手的：25%（但未验证）

**口径必须收紧。** 按 `params` 里出现 `base64` / `.png` / `.jpg` / `.b64` / `screenshot` 粗筛，得 **69 次 / 2.35MB（26.3%）**，但里面混了四类**误命中**：

| 类别 | 为什么不算数 | 规模 |
|---|---|---:|
| `write_files` | base64 在**入参**里（AI 把内容编码后传进来），返回体只有 4.5KB/次 | 18 次 / 81 KB |
| `view_image` | params 含 `.png`，但返回的是图片块，`result_text_bytes` 按 0 计 | 7 次 / 1.5 KB |
| 截屏类 `run_command` | params 带 `screenshot`/`.png`，返回的是文本日志 | 11 次 / 39 KB |
| `batch`/`edit_files`/`read_files` | 参数里内嵌 `base64` 或 `.png` 字样，返回仍是文本 | 7 次 / 38 KB |

扣掉后，真正「base64 走 shell 回传」的是 **`run_command` 且 params 含 `base64`：26 次 / 2.20MB / 24.6%**。粗筛命中里 `run_command` 独占 2.28MB，其余四类全部加起来只有 0.11MB。

> 本文初稿写的是「85 次 3.09MB / 33.1%」，用今天的日志复现不出来：宽口径 26.3%、严口径 24.6%。现按最严的 **24.6%** 计——**宁可低估已得收益，也不拿高估的数字去撑后面的结论**。（初稿的 85 次/3.09MB 也是同一个分母混用的产物。）

时间线是决定性的：

- 全部 41 次 >32KB 的巨量返回，发生在 **10-21 16:01 之前**（最晚两条是 16:00:22 / 16:00:46）；
- `prepare_upload` / `prepare_download` 首次真实调用是 **10-21 22:48**。

**结论**：这 25% 在纸面上已被直传干掉，但**没有任何真实会话在直传上线后跑过完整流程**。它现在的状态是「理应如此」，不是「实测如此」。

所以：
- 不要把 25% 计入已得收益；
- 也不要在它上面再叠方案（先把真实使用跑起来）；
- 最该做的是**在 `instructions` 里明确禁止 base64 走 shell 传文件**——守住这 25%，比新增任何功能都值钱。

### 2.1 仓库里已经有过一次成功先例

`src-tauri/src/diff_utils.rs` 就是同一个问题的上一次解法：写/改文件后回传完整 diff，
对「整份替换」而言等于把模型刚写的内容第二次塞回上下文。它已经用 `DiffMode`
五档（`none`/`stat`/`hunks`/`full`/`auto`）+ 4KB 上限 + `auto` 按「目标是否已存在」分档解决了，
注释里把理由写得很清楚。

这说明本文的主张不需要论证可行性——**要做的是把这个先例从 2 个工具推广到其余工具**（§3.2），
以及把它用到「读两个文件比较」这个新场景上（§3.1）。

## 三、候选方向

按「收益 / 实施成本」排序。每项都标了**改变了什么**。

### 3.1 版本对比工具 —— 1.5 MB（最大单项）

**现象**：`read_files` 里最贵的 8 次调用合计 **1.53MB，占该工具 60%**，全部指向 `_patchcmp/flowbak/` 下 `k1..k4`、`s1`、`s2`、`c1`、`c2` 这批文件。它们是同一批文件的**不同版本快照**，AI 为了找差异把 8 份全文依次读进来自己算 diff。

这不是 AI 偷懒，是**我们没有更便宜的手段**——它能做的只有「全读进来比」，剩下的选择是让它猜。

**改法**（两个方案，选一）：

| 方案 | 接口 | 优点 | 缺点 |
|---|---|---|---|
| A | 新工具 `diff_files({a, b, mode: "unified"\|"stat"})` | 语义独立，schema 小（≈400B），可被 prompt 明确引导 | 多一个工具，AI 需要知道它存在 |
| B | `read_files` 加 `compareWith` 参数 | 不增工具数 | 参数语义别扭（一个读文件的工具做比较） |

推荐 **A**，而且它的实现成本比看上去低得多——**渲染层已经全部就位**：

- `similar = "3.1"` 早在 `src-tauri/Cargo.toml:120`，已用于 `edit_files`/`write_files` 的增删摘要；
- `src-tauri/src/diff_utils.rs` 已有 `DiffMode` 五档（`none`/`stat`/`hunks`/`full`/`auto`）、
  `line_stat()`、`unified_diff()`、`unified_diff_hunks()`，以及 hunks 档 **4KB 上限 + 按字符边界截断**
  （注释写明了理由：「一个 20MB 文件的整份替换展开成 `-`/`+` 两遍，比 base64 还贵」）。

所以 `diff_files` 要做的事只有三件：两个路径过 `resolve_safe_path_cached` + 扩展名/大小校验、
按文本读取（复用 `read_files` 的编码探测与二进制守卫）、调 `diff_utils::render`。
**不需要新写 diff 算法，也不需要新的截断策略。** 这也意味着返回格式与 `edit_files` 的
`diff` 字段完全一致，AI 已经在用同一套格式，学习成本为零。

**改变什么**：新增一个工具（+1 条 schema ≈ 400B）。**不改变**：其它工具行为、安全边界。
**收益**：这 8 次从 1.53MB 降到约 30KB 量级，即约 1.5MB。

### 3.2 pretty → compact —— 0.5 MB（几乎零代价）

**现象**：`mcp/tools/mod.rs:44` 的 `text_result` 用 `serde_json::to_string_pretty`。实测膨胀率（同一份返回，pretty 字节 ÷ compact 字节 − 1）：

| 工具 | 膨胀率 |
|---|---:|
| `list_directory` | **32.9%** |
| `search_files` | **21.0%** |
| `list_allowed_roots` | **36.8%** |

**覆盖面比想象中大**，两个统计（有重叠，不是两批地方）：

- `to_string_pretty` 共 **22 处，分布在 14 个工具文件 + `mod.rs`**（`notebook_edit` 7 处、`write_files` 2 处，其余各 1 处）；
- **17 个工具文件手写 `"content":` 壳**，其中一部分就是上面那些 pretty 调用的宿主（如 `list_directory.rs:68`、`edit_files.rs:150`），其余是 compact 或自拼结构。

只有 `read_files`、`batch`、`view_image` 的 info 块走了 compact。

也就是说 `mod.rs:36-46` 注释里记的「3 个私有同名函数 + 18 处内联，改一次要改 21 处」**还没真正收干净**——函数抽出来了，但调用点没全换过去，于是「换格式」需要改 14 个文件而不是 1 个。

**改法**：
1. 先把 17 个文件的内联壳统一改成调 `text_result` / `text_result_compact`（先统一，再谈格式——顺序不能反，否则格式要在 14 处各改一遍）；
2. 再默认改 compact，给 `text_result_pretty` 保留人读场景（如 `get_command_output` 的输出体）。

**改变什么**：返回 JSON 的缩进。AI 解析 JSON 不关心缩进。**不改变**：字段名、字段值、错误语义。
**代价**：人眼看原始返回费劲（调试时可用审计页或 `jq`）。

**注意**：审计日志存的是 `params` 与 `resultBytes`，不受格式影响；但 `resultBytes` 会**立即下降**，所以改完要重新取一次基线，否则新旧数据混在一起看不出效果。建议改动那一版在审计里能区分（可用版本号或标记）。

### 3.3 `run_command` 截断策略 —— 0.3 MB（更多是防爆）

**现象**：`mcp/tools/run_command.rs:59` 的 `default_max_output_bytes()` 返回 **1MB**，而 `:481` 的截断逻辑是 `take = (max_output_bytes - b.len()).min(n)` —— **截头部、保开头**。

对构建日志这是反的：错误在末尾，截头部等于留下满屏编译进度、丢掉唯一有用的那几行。

**改法**：
- 默认值 **1MB → 128KB**；
- 截断改为**保尾部**（保留最后 N 字节 + 前面加一行「已省略前 x 字节」），或保头尾各一半；
- `maxOutputBytes` 仍可显式放大到 1MB。

**改变什么**：超长输出默认只见尾部。**不改变**：正常长度输出、退出码、`truncated` 字段语义。
**风险**：若 AI 依赖「开头」定位（如看命令回显的第一行版本号），保尾部会丢。折中做法是保头 1/8 + 尾 7/8。

### 3.4 `batch` 摘要模式 —— 0.5 MB（需可选）

**现象**：`tools/batch.rs:169` 每个子结果都嵌完整返回（`{index, tool, ok, result}`），avg 19.5KB、max 185KB。

**改法**：加 `resultMode: "full" | "summary"`，默认 `full` 保持兼容。`summary` 只回 `{index, tool, ok, bytes}`，失败才带 `error`。

**代价**：AI 要看详情得再调一次。对「批量写」无所谓（本来就不看返回），对「批量读」等于白跑——所以**必须让它可选**，由 AI 自己按场景选。

### 3.5 `read_files` outline 模式 —— 0.4 MB（不伤功能）

**现象**：不传行范围就读全文，唯一上限是 `max_file_size_bytes`（默认 20MB）。

**不建议做硬截断**：默认 1500 行会让 AI 在没看完的情况下动手改代码，这是真风险（比多花 token 严重）。

**建议做 outline**：加 `outline: true` 返回符号列表（类 / 函数 / 关键字段 + 行号 + 总行数），AI 先看结构、再按 `startLine/endLine` 读需要的段。

**改变什么**：新增一个可选参数与返回形态。**不改变**：任何现有调用（不传 `outline` 就是现在的行为）。
**代价**：多一次往返。收益是省掉 80% 的盲读。

### 3.6 `search_files` 默认收紧 —— 0.2 MB

`tools/search_files.rs:83` 的 `default_max_results()` 返回 **100**，`context` 缺省回退到 2/2（`:140-141`）。`context: 12` 时单次可达 133KB。

**改法**：默认 `maxResults` 100 → 50，`context` 硬上限 5（超出报错而非静默截断，保持可预期）。

### 3.7 提示层引导 —— 零代码，收益最难估但最该做

三个数据支撑它：
- `run_command` 占 45% 的调用次数，avg 仅 5.4KB —— 拿 shell 干文件活；
- base64 走 shell 的 26 次调用全在直传之前 —— AI 没有更便宜的路就会选贵的；
- 25 次调用吃掉 54% —— 这些调用大多不是「必要的大」，是「不知道有别的办法」。

**改法**：`instructions` 加三条硬规则（放在现有 instructions 开头，因为顺序影响遵循度）：
1. 文件读写 / 查找 / 列目录**优先用专用工具**，不要用 shell 的 `cat`/`ls`/`grep`；
2. 大于约 500 行的文件，先用 `search_files` 定位再按行读；
3. **禁止**用 base64 走 `run_command` 传文件，改用 `prepare_upload` / `prepare_download`。

**代价**：instructions 变长（约 +200 字符 ≈ 55 tokens，相对 261 万可忽略）。

## 四、组合与收益

基数 = 8.95MB − 2.20MB（base64 走 shell，直传后应归零）= **6.75MB**。

| 组合 | 剩余 | 相对 8.95MB 总降幅 |
|---|---:|---:|
| 现状（直传已接住 2.20MB） | 6.75 MB | 25% |
| 3.1 + 3.2 + 3.3 + 3.6（−2.5） | 4.2 MB | 52% |
| 再加 3.4（−0.5） | 3.7 MB | 58% |
| 再加 3.5（−0.4） | 3.3 MB | **63%** |

口径说明：

- 表内数字**向下取到 0.1MB**（`6.75 − 2.5 = 4.25 → 4.2`），不是笔误；
- 每项收益（1.5 / 0.5 / 0.3 / 0.2 / 0.5 / 0.4）与 §三 各项标注一致，没有二次加成；
- 收益按「同一批历史调用在新实现下的字节数」重算，不是按「未来调用会变少」。若未来调用量增长，绝对字节仍会涨，降幅是比例；
- **如果那 2.20MB 并没有被直传真正接住**（AI 继续用 shell 传文件），把基数还回 8.95MB：全部落地后是 **5.6MB / 降 38%**。这就是为什么 §3.7 的禁令是整份方案里最值钱的一条。

## 五、明确不做

| 项 | 理由 |
|---|---|
| **工具描述瘦身** | 24 个共 15.9KB ≈ 4.4k tokens，占 0.19%；命中 prompt cache 后接近 0 |
| **instructions 压缩** | 1319 字符 ≈ 366 tokens，同上；且 3.7 还要往里加内容 |
| **会话内读取去重（缓存层）** | 重复读同一路径看着诱人，但扣掉 `_mcp_smoke`、`win.ini` 等测试噪声与跨会话重读后，真实会话内重复估 10–15%。为它引入会话状态（生命周期、失效、并发）不划算 |
| **`read_files` 硬截断** | 见 3.5，会诱发「没看完就改」 |
| **压缩返回值（gzip / 自定义编码）** | AI 客户端不负责解压；MCP 层无此约定 |

## 六、实施顺序（建议）

分两批，每批都能独立上线、独立验收：

**批 A（纯收益，无功能语义变化）**
1. 3.2 pretty → compact（先收敛 17 个文件的内联壳，再改默认档位——顺序反了要改 14 遍）
2. 3.3 `run_command` 默认 128KB + 保尾部
3. 3.6 `search_files` 默认收紧
4. 3.7 instructions 三条

预期：6.75 → 约 4.2MB（降 52%）。改动集中在 `mcp/tools/*`，风险最低。批 A 里 3.2 是唯一会动 14 个文件的项，建议单独一笔提交，便于回滚。

**批 B（新增能力）**
5. 3.1 `diff_files`
6. 3.4 `batch` summary 模式
7. 3.5 `read_files` outline

预期：再降到约 3.3MB（累计降 63%）。这批要动 schema（新增工具/参数），需同步 README 工具表与 `registry.rs`。

**两批都必须做的**：
- 改完重跑 24 工具真机冒烟（`--ignored` 的 over_wire 集 + 全量调用脚本），确认没有工具因格式变化而被客户端判为非法；
- 重取一次审计基线，与本文 §1.3 同口径对比，把实测降幅写回本文件。

## 七、验收口径

不看「感觉快了」，看三个可复现的数：

1. `audit.log` 的 `resultBytes` 总量，**只算带该字段的记录**（§1.2 脚本会分别打印两个分母），与 8.95MB 对比；
2. >32KB 的调用次数（当前 41 次）与 top25 占比（当前 54%）；
3. `read_files` 的 avg（当前 15.3KB）——它是「AI 是否学会先定位再读」的唯一代理指标。

⚠️ **对比时不要跨口径**：若新基线里带 `resultBytes` 的记录数变化很大，先看是「工具真的省了」还是「统计范围变了」。

## 八、风险清单

| 风险 | 触发条件 | 缓解 |
|---|---|---|
| compact 后 AI 解析异常 | 客户端对缩进敏感（理论上不该） | 批 A 先在一个工具上试，真机确认无回归再铺开 |
| `run_command` 保尾部丢开头 | AI 依赖首行（版本号 / banner） | 保头 1/8 + 尾 7/8，而非纯尾部 |
| `diff_files` 被滥用（读全仓差异） | 参数没有范围限制 | 强制两路径都在白名单内；`mode:"stat"` 优先返回计数 |
| instructions 变长反而降低遵循度 | 规则超过 5 条 | 只加 3 条，且放在开头 |
| 新旧 `resultBytes` 混算 | 改动前后同一天 | 改动版本记入审计，或改完当天重新取基线 |

## 九、落地时的五条硬约束

> 本机规则 `CLAUDE.md` §8.4 与此节同源。⚠️ `CLAUDE.md` 被 `.gitignore:28` 忽略、不进版本库，
> 所以**能随仓库分发的是这一节**。改动其中一处必须同步另一处。

无论本文哪些方向最终被采纳，以下五条对**以后每一次工具改动**都成立：

1. **先问「最坏一次返回多少字节」**，并给出上限（默认值 + 可调参数）。没有上限的返回值
   等于把成本外包给用户的上下文。反例：`run_command` 默认 1MB 且截**头部**，构建失败时
   留下满屏编译进度、丢掉末尾唯一的错误行。
2. **不要用 `to_string_pretty`**。新代码一律 `text_result_compact`，人读场景才用 pretty。
   改到时顺手把该文件手写的 `"content":` 壳收敛到 `mod.rs` 的两个函数。
3. **返回值要能被「先定位再读」**，不要靠硬截断。硬截断会让 AI 在没看完的情况下动手改代码，
   那比多花 token 严重。
4. **禁止引导 AI 用 base64 走 `run_command` 传文件**。文件进出必须走
   `prepare_upload` / `prepare_download`。**进度（2026-10-22，部分落地）**：`http.rs` 的
   `instructions` 已写明"字节不经过对话上下文，远优于 `write_files(base64)`"——但这是
   **正向推荐**，还没有「禁止」措辞；另两条（"专用工具优先，不用 shell 的 cat/ls/grep"、
   "大文件先 `search_files` 定位"）完全没做。
5. **统计审计日志必须同源分母**。`resultBytes` 只在部分记录里存在（当前 3134 行里 1758 行有），
   **次数、字节、平均值必须取自同一子集**；否则 avg 会算错一倍（`read_files` 真实 avg 15.3KB，
   混用分母算成 7.9KB）。宽窄口径各算一遍，报最严的那个——**这条是本文初稿翻车的直接原因**。
