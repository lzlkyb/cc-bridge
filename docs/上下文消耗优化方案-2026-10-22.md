## 〇、一句话结论

**直传理论上解决了 24% 的历史流量（2.20MB），但至今没有一次真实会话验证过它。** 剩下 6.85MB 里最贵的一块是 AI 为对比同一批文件的 8 个版本把 8 份全文逐个读进来（1.53MB，单一任务）；`run_command` 的 1MB 默认上限形同虚设，改成 32KB 在全量上能省 2.48MB，但其中 1.84MB 就是那批 base64 调用（与直传重叠），**真正新增的只有 0.64MB**——它的主要价值是正确性（失败日志的结尾不再丢），不是省字节。**批 A + 批 B 全部落地，预计从 9.05MB 降到约 3.8MB（降 57%，2026-10-23 逐项核实后由 64% 下调）；若直传没有真正接住那 2.20MB，则约 4.2MB（降 54%）——两者差得不多，正是因为 §3.3 与直传大部分重叠。⚠️ 57% 依赖条件项 3.1（1.5MB，单一任务样本的上限）；若 3.7 上线后数据显示无需 3.1，则为 5.3MB / 降 42%（§4）。**（初稿写的是「改一个默认值和给一个新工具就能拿走 4.6MB、占 75%」，把重叠部分算了两次，见 §4。）

另有一条**已实测的客户端硬门槛**（§2.2 第 5 条）：单次 MCP 结果的序列化文本超过约 **50,000 字符**，客户端会把整条结果**存成客户端本机的一个文件，对话里只给你前 2KB 预览 + 一条超限提示**。2026-10-23 在同一版本（2.1.303）上独立跑了两次，结论一致：**49,080B 文件 → 49,823 字符原样内联；52,116B 文件 → 模型只收到 2,373 字符**，而落盘文件 53,447B、尾部标记完整。🔴 **「文件完整」不等于「模型拿到了」**——要拿回全文得它自己再 Read 一次，而实测研究显示模型几乎不会回头读。所以取值依据不变：单次返回压进 50K 字符以内。

## 一、实测基线

### 1.1 数据来源

`%APPDATA%\com.ccbridge.desktop\audit.log`，每条记录含 `tool` / `params` / `timestamp`，`resultBytes` 字段**只在一部分记录里存在**。`resultBytes` 由 `mcp/tools/mod.rs::result_text_bytes` 计算，**只数 text 块、图片块按 0 计**（注释已说明理由：base64 按字节算会让 Token 页虚高两个数量级）。

> 🔴 **两个分母，混一次就全错**（2026-10-22 二次复核，本文初稿就是这么错的）：
> 日志共 **3092 行**，其中**只有 1801 行带 `resultBytes`**（早期记录没落这个字段）。所以：
> - **9.05MB / 264 万 tokens 是这 1801 条之和**，时间跨度 10-10 09:39 → 10-22 18:08；
> - 若按全量行数算「调用次数」，得到的是 3092，不是 1801。
>
> **次数、字节、平均值必须出自同一个分母**。初稿把全量行数的次数（`read_files` 339 次）和带字段的字节（2.68MB）拼在同一行，算出 avg 7.9KB，真实值 15.3KB——整张表由此失真。本文所有表内数字统一取**带字段的 1801 条**。
>
> 单位：本文 **MB = MiB = 1048576 字节**，直接取脚本原样输出。初稿混用了十进制 MB（同一份字节写成 9.32MB），所以初稿的 9.32 与本文的 9.05 差 4%，**不是数据变了，是单位**。
>
> `resultBytes` 是「进入下一轮上下文的文本的 **UTF-8 字节数**」（`mod.rs` 里是 `s.len()`，不是字符数；中文 1 字 = 3 字节），不含工具 schema、不含系统 prompt。注意客户端门槛（§2.2 第 5 条）是按**字符**量的，两者不能直接比。它衡量的是**我们这边可控的那部分**，正好是本文的战场。

### 1.2 冻结快照与复现脚本

⚠️ **日志会自己变短**：10-22 下午还是 3134 行，晚上变 3092 行（旧记录被裁掉），同一份脚本两次跑出的总量不同。所以先冻结：

```bash
cp "$APPDATA/com.ccbridge.desktop/audit.log" .workbuddy/tmp/audit-baseline-2026-10-22.jsonl
sha256sum .workbuddy/tmp/audit-baseline-2026-10-22.jsonl   # 0ae1781ce34d5c9ed9a9526e381237c57c64ee48d21d0aaf614288ce448d610d
```

**全文所有数字都出自这份 3092 行 / 1801 条 / 9.05MB 的快照**，改完也拿它对比，不跟活日志比。

```python
import json, sys
from collections import defaultdict

rows = [json.loads(l) for l in open(sys.argv[1], encoding='utf-8') if l.strip()]
withb = [d for d in rows if 'resultBytes' in d]          # 只有这些才带字节
tot = sum(d['resultBytes'] or 0 for d in withb)
M = lambda b: b / 1048576

print(f'行={len(rows)} 有字节={len(withb)} 总={M(tot):.2f}MiB ≈ {tot/3.6/1e4:.0f}万tokens')

g = defaultdict(list)
for d in withb:
    g[d['tool']].append(d['resultBytes'] or 0)
for t, v in sorted(g.items(), key=lambda kv: -sum(kv[1]))[:6]:
    print(f'{t:18} n={len(v):>4} sum={M(sum(v)):5.2f}MiB avg={sum(v)/len(v)/1024:5.1f}KB max={max(v)/1024:6.0f}KB')

srt = sorted((d['resultBytes'] or 0) for d in withb)[::-1]
print(f'top25 = {sum(srt[:25])/tot*100:.1f}%   >32KB n={sum(1 for x in srt if x > 32768)}')
```

**口径必须收紧。** 按 `params` 里出现 `base64` / `.png` / `.jpg` / `.b64` / `screenshot` 粗筛，得 **69 次 / 2.35MB（26.0%）**，但里面混了四类**误命中**：

> 本文初稿写的是「85 次 3.09MB / 33.1%」，用冻结快照复现不出来：宽口径 26.0%、严口径 24.3%。现按最严的 **24.3%** 计——**宁可低估已得收益，也不拿高估的数字去撑后面的结论**。

时间线是决定性的：

**结论**：这 24% 在纸面上已被直传干掉，但**没有任何真实会话在直传上线后跑过完整流程**。它现在的状态是「理应如此」，不是「实测如此」。

所以：
- 不要把 24% 计入已得收益；

## 三、候选方向

按「收益 / 实施成本」排序。每项都标了**改变了什么**。

### 3.1 版本对比工具 —— ≤ 1.5 MB（最大单项，但只有一个样本）

**现象**：`read_files` 里最贵的 8 次调用合计 **1.53MB，占该工具 60%**，全部指向 `_patchcmp/flowbak/` 下 `k1..k4`、`s1`、`s2`、`c1`、`c2` 这批文件。它们是同一批文件的**不同版本快照**，AI 为了找差异把 8 份全文依次读进来自己算 diff。

~~这不是 AI 偷懒，是我们没有更便宜的手段。~~ **（2026-10-23 更正）** 更便宜的手段其实已经有：AI 手里就有 `run_command`，
`git diff --no-index a b` 或 `diff a b` 一次就能拿到差异。它没这么做是**引导问题**：§3.7 的 instructions 加一句
「比较文件用 diff，不要全文读进来」就能覆盖。新工具的增量价值在于：结果自带 4KB 截断与编码探测（GBK 文件用
命令行 diff 会出乱码），且更容易被模型发现。

另外，**这 1.53MB 全部来自同一次任务**（`_patchcmp/flowbak` 下 8 个文件），只有一个样本。它能否代表常见场景未知，
下面的收益应视为**上限**。

**改法**（两个方案，选一）：

| 方案 | 接口 | 优点 | 缺点 |
|---|---|---|---|
| A | 新工具 `diff_files({a, b, mode: "unified"\|"stat"})` | 语义独立，schema 小（≈400B），可被 prompt 明确引导 | 多一个工具，AI 需要知道它存在 |
| B | `read_files` 加 `compareWith` 参数 | 不增工具数 | 参数语义别扭（一个读文件的工具做比较） |

**推荐 A**，理由不只是「语义干净」：Anthropic 的工具设计指引要求「参数名不能有歧义」（`user` → `user_id`），
并要求「两个工具可能服务同一请求时，描述里必须写清什么时候用哪个」。`compareWith` 会让 `read_files`
的描述必须同时解释「读」和「比」两种模式，正是这条指引要避免的。反过来，A 的
`mode: "unified"|"stat"` 恰好是官方推荐的 `response_format` 枚举模式。

实现成本比看上去低得多——**渲染层已经全部就位**：

- `similar = "3.1"` 早在 `src-tauri/Cargo.toml:120`，已用于 `edit_files`/`write_files` 的增删摘要；
- `src-tauri/src/diff_utils.rs` 已有 `DiffMode` 五档（`none`/`stat`/`hunks`/`full`/`auto`）、
  `line_stat()`、`unified_diff()`、`unified_diff_hunks()`，以及 hunks 档 **4KB 上限 + 按字符边界截断**。

所以 `diff_files` 要做的事只有三件：两个路径过 `resolve_safe_path_cached` + 扩展名/大小校验、
按文本读取（复用 `read_files` 的编码探测与二进制守卫）、调 `diff_utils::render`。
**不需要新写 diff 算法，也不需要新的截断策略。**

**改变什么**：新增一个工具（+1 条 schema ≈ 400B）。**不改变**：其它工具行为、安全边界。
**收益**：这 8 次从 1.53MB 降到约 30KB 量级，即约 1.5MB（单一任务样本，是上限；其中相当一部分靠 §3.7 一句引导也能拿到）。

**开工判断（2026-10-23）**：实现没有障碍，但**先不做**。等 3.7 的「比较文件用 diff」上线后观察一段：
若仍出现「同一批文件连续全文读」的模式，或 GBK 文件比较出乱码，再做。做的话工具数 24 → 25，
要同步 README 工具表、`registry.rs`、CLAUDE.md 规则 7 里的「现 24 个」。
**判据要可操作**（否则「观察一段」永远不会有结论）：按 §7 的方法取上线后的窗口，累计到 **≥200 次
`read_files`** 时看两个数——① >20KB 的全文读次数（冻结快照里是 17 次），② 单次 >20KB 全文读的最大字节。
① 明显回落 ⇒ 不做；① 不降或 ② 仍出现 MB 级读取 ⇒ 做。观察窗口与 §7 的验收窗口合并，不单独跑一次。

### 3.3 `run_command` 截断 —— 增量 0.64 MB（全量 2.5 MB；主要价值是正确性）【✅ 2026-10-23 批A 已落地，`output_clip.rs`】

**现象**：`mcp/tools/run_command.rs:59` 的 `default_max_output_bytes()` 返回 **1MB**，而 `:488` 的截断逻辑是 `take = (max_output_bytes - b.len()).min(n)` —— **保开头、丢结尾**。
🔴 而且这个上限是 **stdout 与 stderr 各自计算**的（`:545/547` 前台、`:693/695` 后台各起一个 reader，各持一份 `max_output_bytes`），
单次返回最坏是上限的 **2 倍**。

在冻结快照上实测各阈值的收益（833 次 `run_command`，合计 4.24MB）：

| 默认上限 | 超限次数 | 可省 | 占总字节 | 截后剩余 | 其中非 base64（真正新增） |
|---|---:|---:|---:|---:|---:|
| 1MB（现状） | **0** | 0 | 0% | 9.05 MB | — |
| 128KB | 11 | 1.27 MB | 14.0% | 7.78 MB | 2 次 / 0.34 MB |
| 90KB | 12 | 1.69 MB | 18.6% | 7.37 MB | 3 次 / 0.42 MB |
| 64KB | 13 | 2.01 MB | 22.3% | 7.04 MB | 3 次 / 0.50 MB |
| **32KB（推荐）** | **16** | **2.48 MB** | **27.4%** | **6.58 MB** | **5 次 / 0.64 MB** |

> 最后一列是 2026-10-23 复核补的：32KB 档 16 次超限里有 **11 次（1.84MB）就是 §2 的 base64 走 shell**。
> 在「直传已接住那 2.20MB」的前提下，§3.3 的增量只有 **0.64MB**；初稿拿 2.48MB 去叠加是重复计算。

三个读数很刺眼：

1. **1MB 这个默认值历史上一次都没触发过**——它既不省也不会防，只是把「最坏情况」留在那儿；
2. 🔴 **客户端门槛是「序列化结果 ≤ 约 50,000 字符」，超了整条落盘、对话里只剩前 2KB 预览 + 路径**
   （§2.2 第 5 条；2026-10-23 同版本两次实测：49,823 字符原样内联；52,116B 文件只收到 2,373 字符，
   落盘文件虽完整但模型当轮看不到，要它自己再 Read 一次）。
   `run_command` 的返回壳只有 `stdout`/`stderr`/`exitCode`/`*Truncated`/`timedOut`/`note`（`run_command.rs:660-678`），
   60KB stdout 序列化后 71.9KB，
   直接踩线。**所以默认上限必须按「序列化后」算，取 32KB**——32KB 指的就是序列化后的字节数，
   **不是「原文字节 + 估算转义膨胀」**（那是本文初稿的写法，已废止：两套口径并存会让实现在错误的
   那一步做裁剪）。64KB 序列化后必然 ≥64,000 字符，会稳定落进落盘档。
   🔴 **前提是 32KB 管的是 stdout+stderr 合计**。现在两路各算一份，只改默认值的话最坏是 32KB+32KB=64KB 原文，
   正好落进上面说的最坏档（cargo/mvn 这类构建两路都会大量输出）。另外带颜色的输出里每个 ESC 会转义成 6 字符的
   `\u001b`，膨胀可能超过 40%，所以最稳的是直接按最终序列化文本的长度裁；
   32KB 省得比 64KB 多（2.48MB vs 2.01MB）只是因为上限更低、多覆盖了 3 次 33–64KB 的调用；
3. 现行截断**保开头**，而 41 次 >32KB 的调用里绝大多数是构建/测试日志——**错误在末尾**，
   保开头等于留下满屏编译进度、丢掉唯一有用的那几行。这是 §2.2 第 2 条那个坑的同款。

**改法**：

- **把「保存上限」和「返回上限」分开**（2026-10-23 复核新增，见下条）：
  - **保存上限**：继续约 1MB，但从「保开头」改成「保头 + 保真尾」（边收边维护环形缓冲，不能像
    Claude Code 那样从「读回窗口」里切尾——那会把真正的结尾丢掉）；
  - **返回上限**：默认 **32KB，stdout+stderr 合计，按序列化后文本的 UTF-8 字节计**，只在组装返回时裁成
    **头 1/8 + 尾 7/8**；`maxOutputBytes` 可显式调整，但**封顶 45KB**（见下方设计定稿第 1、4 条）。
- 为什么必须分开：3.0.0 新增的后台命令工具全部建在这块缓冲上。`wait_command` 的 `untilPattern`、
  `include`/`exclude`/`tailLines` 和 `get_command_output` 的字节偏移，都在缓冲上工作。若把**缓冲本身**
  压到 32KB 环形：长构建中途出现的完成标记会被挤掉、`untilPattern` 永远等不到；内容在缓冲里移动后字节偏移
  也失去意义。分开后过滤与匹配照常扫完整保存的内容，只有进上下文的那一段受 32KB 约束。
  （顺带：现在 `tailLines` 在「保开头」的缓冲上取尾，输出超过 1MB 时给的是中段而非真尾——正是 §2.2 第 2 条那个坑，
  只是 1MB 很少触发；保存改成保真尾后一并解决。）
- 截断标记必须交代三件事：**这次给的是哪一段、整条输出多大、结尾是不是真的结尾**。

#### 3.3 设计定稿（2026-10-23）

开工核实时发现一条漏掉的路径：**`get_command_output` 没有任何默认返回上限**（`get_command_output.rs:60-65`
取 offset 之后的整段，只过一遍过滤），一次能把整块缓冲（最多 1MB）原样返回。历史上它 46 次调用最大
只有 1.5KB，不是现在的出血点；但保存改成「保真尾」后它就是一条没设防的路。`wait_command` 默认只给最后
40 行（`tailLines` 默认 40），基本安全，但传 `tailLines:0` 或 `include` 命中大量行时同样没有上限。
下面 **6 条**是定稿（前 4 条对应核实时列出的待定点，⑤⑥ 是后补的新增项）。

**① `maxOutputBytes` 管返回，不管保存**
- 保存上限固定每路约 **1MB**（头 1/8 + 滚动更新的尾 7/8，尾部始终是真尾），不对外开放。
- 返回上限就是 `maxOutputBytes`：默认 **32KB**，**封顶 45KB**（两者都指**序列化后的 UTF-8 字节**）。
  45,000 字节的 ASCII 恰好是 45,000 字符，仍在 50,000 门槛内；再大客户端会把整条落盘、只给路径
  （§2.2 第 5 条），多一轮往返反而更贵，所以超过的直接压到 45KB 并在返回里注明。
- 参数名不变以保兼容。CHANGELOG 写明含义变化：从「每路最多收多少字节」变为「整条返回最多多大」。

**② 偏移按整条输出的实际位置算**
- 每路保存缓冲记三个数：开头保留到哪、中间丢了多少、一共产生了多少。
- `get_command_output` 的偏移按真实输出位置计：落在头/尾保留区照常返回；落在被丢弃的中段时，返回
  「第 X–Y 字节已丢弃」的缺口标记，再从尾部保留区起点接着给。
- `stdoutTotalBytes` 改报真实总量，另加 `stdoutDroppedBytes`。调用方「上次读到哪、这次从哪接着读」的用法不变。
- 边界（写明不修）：`wait_command` 的 `untilPattern` 是轮询扫描缓冲的，只有两次轮询之间新产生的输出
  超过约 900KB，中途的完成标记才可能被挤掉。实际几乎碰不到，不值得为它把匹配挪进读取线程。

**③ 三个工具共用同一个裁剪函数**
- `run_command`、`get_command_output`、`wait_command` 都在组装返回时调它，顺序是**先过滤、再裁剪**。
- 预算分配：两路加起来放得下就全给；放不下就按各自大小分，但 **stderr 至少保底 1/4**（报错通常在 stderr）。
- 每一路保留开头 1/8 + 结尾 7/8，切点对齐到完整字符，不切断中文。
- 截断说明每路写明：总量、展示了哪两段、结尾是不是真结尾（命令还在跑就不是）。
- `get_command_output` 被裁剪时额外返回 `nextStdoutOffset` / `nextStderrOffset`，模型拿它就能接着往下读。
- `stdoutTruncated` 的含义统一为「本次返回的内容不完整」（无论是保存丢了还是返回裁了）。

**④ 按序列化后的 UTF-8 字节计量，不按字符**（核实时曾建议按字符，定稿改为字节）
- 客户端报错文案是「tokens」，真正的门槛很可能按 token 算。按字符算中文会吃亏：32K 个中文字符约 2–3 万 token，
  可能直接撞上 2.5 万 token 的上限。
- UTF-8 字节数恰好是好近似：英文 1 字节≈ 0.3 token，中文 3 字节≈ 1 token。32KB 换算下来英文约 3.2 万字符、
  中文约 1.1 万字符，两种都留有余量。
- 与审计的 `resultBytes` 同一单位，验收不用换算；按「序列化后」算，JSON 转义（含彩色输出的 `\u001b`）与两路合计一并解决。

**⑤ 前台命令被截断时，完整输出可分页取回**（新增，取代原 3.3-b）
- 截断后把本次命令的完整保存缓冲登记进后台命令注册表，返回里带 `handle`；模型可用现成的
  `get_command_output` 按偏移翻页，或用 `include: "error"` 在完整输出里查。
- 可行性已查：`state.rs` 的 `RunningCommand` 需要的进程句柄、两路缓冲、退出码，前台命令本来就有，
  登记时填好退出码即可。不用新存储、不用落盘——原 3.3-b 正是因「没有安全的落盘位置」才搁置的。
- 代价：这些条目按 `command_cleanup_secs`（默认 2 分钟）自动清掉，截断说明里写明「约 2 分钟内有效」；
  它们占后台 5 个名额里的位置，但名额满时现有逻辑会先清掉已结束的条目，不会挡住新的后台命令。

**⑥ 截断时把中段的关键行提到返回里**（新增，依据 §2.2 第 6 条）
- 模型几乎不会去翻第二页，所以 ⑤ 只是兜底，第一次返回本身必须尽量带上有用的内容。
- 裁剪时从被丢掉的中段里抽出匹配 `error|fail|panic|exception|warning`（大小写不敏感）的行，连同行号
  放进返回的「中段关键行」小节；占用该路预算的 1/4，头/尾按比例让出；关键行太多时取最靠近结尾的。
- 调用方已传 `include` 时不再做这一步（以调用方的过滤为准）。关键词表只用这一组简单词，不做打分组合——
  论文的结论就是简单关键词胜过复杂组合。

**测试覆盖**
- 中段关键行：中段含 `error:` 的行会出现在返回里且带行号、传了 `include` 时不重复抽取、总量仍不超上限；
- 保存缓冲：头/尾边界、偏移落在缺口里、超过 1MB 后结尾仍是真结尾；
- 裁剪函数：两路分预算、stderr 保底、不切断中文、彩色输出转义后仍不超上限；
- 端到端：前台命令输出 2MB 时最后一行和退出码都在、能凭 handle 翻页取回；后台命令输出超过 1MB 后
  `untilPattern` 仍能匹配到结尾标记。

**改变什么**：超长输出默认只见头尾各一段（完整输出可凭 handle 取回）；显式传入的 `maxOutputBytes` 含义变为整条返回上限且封顶 45KB；
`stdoutTotalBytes` 改报真实总量。**不改变**：正常长度输出、退出码、后台命令的过滤与匹配范围、偏移的用法。
**收益**：全量口径 2.48MB（27.4%），但在直传已接住 base64 的前提下**增量只有 0.64MB**。这一项的主要价值是
**正确性**（失败日志的结尾不再丢），其次是对直传的**兜底**（AI 万一又走 shell 传文件，也只会花 32KB）。
~~**可选加强（3.3-b，暂不做）**：超限时把完整输出落盘，回「路径 + 头尾预览」。~~ 已由上面第 ⑤ 条取代。

### 3.4 `batch` 返回上限 —— ≤0.26 MB（原「摘要模式」方案已被实测否决）

> 🔴 **2026-10-23 核实更正**：初稿设想的 `resultMode: summary`（只回 `{index, tool, ok, bytes}`）**没有用武之地**。冻结快照里 batch 共 38 次、0.723MiB，其中**纯写入的只有 1 次（4KB）**，其余 30 次都含读取——摘要模式会让「批量读」白跑。0.5MB 的估值无依据，删除。

**真问题**：`tools/batch.rs:169` 每个子结果都嵌完整返回，**整个 batch 没有任何返回上限**：6 次超过 32KB（合计 0.447MiB），2 次超过 78,060B（0.286MiB），最大一次 189,690B。

**改法**：给 batch 加**总返回上限**（默认 32KB，超限的子结果按 §3.3 规则头尾保留、标注被裁字节数，并给可凭 handle 取回的入口）。按 32KB 套用快照重算，batch 从 0.723 降到约 0.46MiB，**省 ≈0.26MiB**。

> ⚠️ **「共用同一个裁剪函数」要分两层，不能直接套**（2026-10-23 核）：§3.3 定稿 ③ 那个函数管的是
> **stdout/stderr 两路分预算**，而 batch 是 **N 个子结果**，语义套不上。全仓唯一的现成件是
> `diff_utils.rs:119` 的 `truncate_with_note()`——**私有、只保头部、按字符边界切**并附一句可执行的说明（diff 专用），
> 思路可借、语义不能直接用。所以要先抽出「按段裁剪任意文本」的公共原子，
> 再分别在「两路预算」和「N 个子结果预算」两层组装。抽分层的成本要算进 3.4，不能按「复用现成」估。

**代价**：超大批量读被裁，AI 需再按范围读一次（本来就该这么做）。

### 3.5 `read_files` outline 模式 —— ≈0.27 MB（与 3.1 重叠，不伤功能）

> 🔴 **2026-10-23 核实更正**：快照里 read_files 共 172 次，56 次带行范围、116 次读全文；全文读取里 >20KB 的 17 次共 1.91MiB，其中 8 次就是 flowbak 那批（1.531MiB，**已在 3.1 里算过**），其余 9 次 0.379MiB，outline 后约省 **0.27MiB（总量 3.0%）**，不是 0.4MB。与 3.1 联合计算为 1.71MiB（不是 1.5+0.27）。下文「省掉 80% 的盲读」**无任何数据依据，已删除**。

**现象**：不传行范围就读全文，唯一上限是 `max_file_size_bytes`（默认 20MB）。而客户端对单次 MCP 结果
超过约 50,000 字符会**把整条落盘、对话里只给前 2KB 预览 + 路径**（§2.2 第 5 条；2026-10-23 同版本两次实测：
49,823 字符原样内联；52,116B 文件只收到 2,373 字符）。落盘文件在客户端本机是完整的，但模型当轮看不到，
**要它自己再 Read 一次**——这就是「读全文」在一次调用里根本拿不到全部内容的实证。

**不建议做硬截断**：默认 1500 行会让 AI 在没看完的情况下动手改代码，这是真风险（比多花 token 严重）。

**建议做 outline**：加 `outline: true` 返回符号列表（类 / 函数 / 关键字段 + 行号 + 总行数），AI 先看结构、再按 `startLine/endLine` 读需要的段。

Claude Code 自己的 Read 工具就是这么做的：超 token 上限时给「第一页 + `PARTIAL view` 说明 + 怎么用
`offset`/`limit` 继续」，超大文件则**直接报错引导分页**。`read_files` 应对齐这个形状，而不是默默返回全文。

**改变什么**：新增一个可选参数与返回形态。**不改变**：任何现有调用（不传 `outline` 就是现在的行为）。
**代价**：多一次往返。

### 3.6 `search_files` 默认收紧 —— 0.2 MB【✅ 2026-10-23 批A 已落地】

`tools/search_files.rs` 的 `default_max_results()` 返回 **100**，`context` 缺省回退到 2/2（`handle()` 里
`before_context.or(context).unwrap_or(2)`）。`context: 12` 时单次可达 133KB。（初稿引的 `:83`、`:140-141` 行号已因
2026-10-23 的 `encoding` 参数改动而偏移，改为引函数名。）

**改法**：默认 `maxResults` 100 → 50，`context` 上限 5。
~~超出报错而非静默截断~~ **（2026-10-23 改）超出时压到 5，并在返回里注明「context 已从 12 压到 5」**。
报错会让模型多来回一轮重试（正是本文要省的往返）；压值加注明既不静默，也不浪费一轮。

### 3.7 提示层引导 —— 零代码，收益最难估但最该做【✅ 2026-10-23 批A 已落地，`instructions` 三条硬规则 + 4096 上限测试】

三个数据支撑它：
- `run_command` 占 46% 的调用次数，avg 仅 5.2KB —— 拿 shell 干文件活；
- §3.1 的 1.53MB 是本可以用 shell 的 `diff` 一次拿到却选择了全文读（复核补充）；
- base64 走 shell 的 26 次调用全在直传之前 —— AI 没有更便宜的路就会选贵的；
- 25 次调用吃掉 53% —— 这些调用大多不是「必要的大」，是「不知道有别的办法」。

**改法**：`instructions` 加三条硬规则（放在现有 instructions 开头，因为顺序影响遵循度）：
1. 文件读写 / 查找 / 列目录**优先用专用工具**，不要用 shell 的 `cat`/`ls`/`grep`；
2. 大于约 500 行的文件，先用 `search_files` 定位再按行读；比较两个文件用 diff，不要把两份全文都读进来；
3. **禁止**用 base64 走 `run_command` 传文件，改用 `prepare_upload` / `prepare_download`。

第 1 条可补半句：「命令输出大时先用 `include`/`tailLines` 或管道过滤再返回」——对应 Anthropic《Code execution with MCP》
的主张：数据先在执行环境里过滤，只把结果交给模型。

🔴 **长度约束（2026-10-23 依官方文档补）**：Claude Code 会把 server instructions 和预加载的工具描述在
**4,096 字符**处截断（经 tool search 延迟加载的工具描述是 16,384），模型只看得到截断前的部分。现在 instructions
约 1319 字符，加三条规则后必须仍在 4096 以内，最重要的规则放最前面。建议加一条单测卡住这个长度。

官方指引同样强调：**截断和报错文案本身就是引导手段**——要告诉 agent「怎么拿到剩下的」，
而不是给一个不带解释的截断。

### 3.8 给只读工具声明 `readOnlyHint` —— 不省 token，省延迟（2026-10-23 新增）【✅ 2026-10-23 批A 已落地，`registry.rs::annotations_for`】

**依据**：Claude Code 官方文档写明，`tools/list` 里标了 `annotations.readOnlyHint: true` 的工具，Claude Code
会与其他只读调用**并行执行**；标了 `idempotentHint: true` 的工具在连接中断时可以自动重试一次。

**现状**：cc-bridge 一个标注都没有（`registry.rs`、`http.rs` 里搜不到 `annotations`），所以 `read_files`、
`search_files`、`list_directory` 这些只读工具只能排队一个个跑。远程链路下每次往返都贵，并行的收益很直接。

**改法**：在工具注册处加 `annotations` 字段。⚠️ **不能用 `ToolSpec.is_write` 反推 `readOnlyHint`**——
`is_write` 是只读门禁的唯一真源，而 `stop_command`、`get_command_output`、`wait_command` 三个都注册为
`false`（`registry.rs:202-214`），直接映射会把「杀后台进程」也标成只读。只能按上面的显式清单下发。
- `readOnlyHint`：`read_files`、`list_directory`、`search_files`、`analyze_file`、`list_allowed_roots`、`view_image`、
  `get_command_output`、`mcp_list_servers`。`wait_command` 只读但会阻塞等待，是否标注待测。
- `idempotentHint`：只给重复执行结果不变的写工具，如 `create_directory`。`edit_files`、`run_command`、`move_files`
  这类重复执行会出错或产生副作用的**不能标**。
- `prepare_upload`/`prepare_download` 会签发一次性票据，不标。

**改变什么**：客户端可能并行发来多个只读调用。**不改变**：工具行为与返回。
**并发安全已确认**（2026-10-23，见 §十一 第 8 条）：`wait_command` / `get_command_output` 只加锁克隆缓冲区、
不改注册表；限流是 `DashMap`；路径锁是 `DashMap<PathBuf, Arc<Mutex<()>>>`。`batch` 已是顺序执行，不受影响。
⚠️ 但审计写盘是 `OnceLock<Mutex<AuditWriter>>` 的**全局串行段**（持锁期间写 `BufWriter` 并 flush，
`audit.rs:113-130`），并行只读调用会在这一个点上排队——**不竞态，但吞吐上限在这**；若实测显示并行收益被它吃掉，
再考虑改成 channel 异步落盘。
**仍待定的只有一项**：`wait_command` 只读但会阻塞等待，标 `readOnlyHint` 会不会让客户端发出互相等待的调用，
需上线实测（§十一 末尾第 ② 点）。

## 七、验收口径

不看「感觉快了」，看三个可复现的数。

> 🔴 **2026-10-23 更正**：初稿写「全部对冻结快照算」。但快照里存的是**改动前**的返回大小，用它验不出新代码的效果。
> 正确做法：① 新版装好后记下**上线时刻**；② 积累一段真实使用（建议至少与快照量级相当的带字节记录，或满一周）；
> ③ 再冻结一份新快照，**只取上线时刻之后的记录**，与旧快照按同一脚本、同一分母口径对比。
> 两份快照的调用次数不同，比较「总量」要换算成「每百次调用的字节」，否则使用量多少会盖过优化效果。
> 上线前可以先用旧快照做**离线模拟**（3.3/3.6 这类「按上限裁剪」的项可以直接算），但那只是估算，不算验收。

三个数：

1. `resultBytes` 总量（当前 9.05MB），**只算带该字段的记录**；
2. >32KB 的调用次数（当前 41 次）与 top25 占比（当前 53%）；
3. `read_files` 的 avg（当前 15.3KB）——「AI 是否学会先定位再读」的唯一代理指标。

⚠️ **对比时不要跨口径**：若新基线里带 `resultBytes` 的记录数变化很大，先看是「工具真省了」还是「统计范围变了」。

| 风险 | 触发条件 | 缓解 |
|---|---|---|
| 🔴 **客户端把 >50K 字符的 MCP 结果整条落盘、对话里只留路径**（已实测，§2.2 第 5 条） | 单次序列化结果 >50,000 字符 | 默认上限按序列化后算，压进 32KB（封顶 45KB）；绝不超过 50K |

| 🟠 **`get_command_output` 没有返回上限**（开工核实发现） | 保存改成保真尾后，一次取整块缓冲 | 与 `run_command` 共用同一裁剪函数（§3.3 定稿 ③） |
| 🟠 **中段丢弃后偏移失真** | 调用方按旧的字节偏移增量读 | 偏移按逻辑位置计，落入丢弃区间返回缺失标记（§3.3 定稿 ②） |
| 🟡 **显式传入的 `maxOutputBytes` 语义变化** | 调用方按「单路捕获字节」理解它 | CHANGELOG 与工具描述写明「整条返回上限、按序列化后 UTF-8 字节计、封顶 45KB」（§3.3 定稿 ①④） |
| 保尾部丢开头 | AI 依赖首行（版本号 / banner） | 保头 1/8 + 尾 7/8，而非纯尾部 |
| 「尾」不是真尾（Claude Code 踩过的坑） | 截断在缓冲区上做、而不是在完整输出上做 | 边收边维护环形缓冲；标记写明「结尾就是整条输出的结束」 |
| 32KB 切掉正在看的长日志中段 | 用户/agent 需要完整日志 | 截断时返回 handle，用 `get_command_output` 按偏移翻页或 `include` 检索完整输出（§3.3 定稿 ⑤；约 2 分钟内有效） |

| instructions 变长反而降低遵循度 | 规则超过 5 条 | 只加 3 条，且放在开头 |
| 新旧 `resultBytes` 混算 | 改动前后同一天 | 记下上线时刻，只统计该时刻之后的调用 |

## 九、落地时的五条硬约束

> 本机规则 `CLAUDE.md` §8.4 与此节同源。⚠️ `CLAUDE.md` 被 `.gitignore:28` 忽略、不进版本库，
> 所以**能随仓库分发的是这一节**。改动其中一处必须同步另一处。

无论本文哪些方向最终被采纳，以下五条对**以后每一次工具改动**都成立：

1. **先问「最坏一次返回多少字节」**，并给出上限（默认值 + 可调参数）。上限按**序列化后的结果文本**
   算，压在 **50,000 字符以内**（实测：约 50,000 是落盘线；超了模型只收到前 2KB 预览，
   文件虽在客户端本机完整，但要它自己再 Read 一次才看得到——不能算「内容不丢」）。
   实践取值 **32KB（序列化后的 UTF-8 字节）**，封顶 45KB——**不是「原文 32KB 再估算转义膨胀」**，
   两种口径并存会让实现在错误的那一步做裁剪。注意上限管的是**整条返回**：有多路输出（如 stdout/stderr）时合计，
   而且 `resultBytes` 是字节、客户端门槛是字符，口径要说清。
   反例（已修，2026-10-23 批A 落地）：`run_command` 曾默认 1MB 且截**头部**，历史 833 次里没有一次
   超过 1MB——既没防住任何事，也省不出一个字节。现已是「保存 1MB（头 1/8+真尾 7/8）与
   返回 32KB 分离」，见 `mcp/tools/output_clip.rs`。
2. **不要用 `to_string_pretty`**。新代码一律用 `text_result`（2026-10-23 批A 起默认就是
   compact）；pretty 仅限显式 `text_result_pretty` 人读场景与 `notebook_edit` 落盘。
   17 个工具文件手写的 `"content":` 壳已全部收敛到 `mod.rs`。
3. **返回值要能被「先定位再读」**，不要靠硬截断。硬截断会让 AI 在没看完的情况下动手改代码，
   那比多花 token 严重。
4. **禁止引导 AI 用 base64 走 `run_command` 传文件**。文件进出必须走
   `prepare_upload` / `prepare_download`。**进度（2026-10-23 批A 已落地）**：三条硬规则
   （专用工具优先、不用 shell 的 cat/ls/grep；大文件先定位再 `git diff --no-index` 比较；
   禁 base64 走 shell）已写进 `http.rs` 的 `instructions` 最前段，并有测试钉住 4096
   字符上限与规则片段（`instructions_under_client_limit`）。
5. **统计审计日志必须同源分母**。`resultBytes` 只在部分记录里存在（当前 3092 行里 1801 行有），
   **次数、字节、平均值必须取自同一子集**；否则 avg 会算错一倍（`read_files` 真实 avg 15.3KB，
   混用分母算成 7.9KB）。**且先冻结快照再算**——日志会被裁剪（同一天从 3134 行变 3092 行）。
