## 正文

先说清楚这是个**自己的项目**，4 个 star，介意推广的可以直接关页面了。发出来主要是想找人一起挑毛病。

### 我遇到的场景

Claude Code 我是跑在租的 Linux 上的——便宜、网络好、不用占自己机器的 CPU 和风扇。但代码在我本机 Windows 上，而且我想在 VS Code 里看着它改。

于是每次都是这套动作：

```bash
scp -r ./src vps:/work/proj/          # 传上去
ssh vps 'cd /work/proj && claude'     # 让 CC 改
scp -r vps:/work/proj/src ./src       # 再拉回来
```

三个文件还行，一个 React 项目就是几百兆、几千个文件，来回几次之后我已经不知道哪边是最新的了。试过 SSHFS，网络一抖挂载点就卡死，终端直接不响应，得去任务管理器杀进程。

后来我想明白一件事：**我真正要的不是更快的传输，而是让 CC 直接操作我本机的文件。** 而 MCP 本来就是干这个的——只是绝大多数 filesystem server 都装在「AI 旁边」，我要的是反过来：**装在文件旁边**。

### 做出来的东西

cc-bridge：一个 Tauri 2 桌面应用（Rust 后端，Windows 10/11 + macOS Apple Silicon），装在你**文件所在的那台机器**上。它在本地起一个 axum HTTP 服务，对外暴露 MCP 的 `/mcp`（Streamable HTTP）+ Bearer token；远端的 CC 用一条命令接进来：

```bash
claude mcp add --transport http cc-bridge http://<本机局域网IP>:7823/mcp \
  --header "Authorization: Bearer <token>"
```

之后在 CC 里说「读一下 `src/app.tsx`」「把这三处改掉」，工具调用落在**我本机**——代码一次都没上传到云上，VS Code 里立刻能看到改动。

24 个工具，常用的这些：

| 工具 | 干什么 |
|---|---|
| `read_files` | 批量读，带行范围、编码（GBK 自动识别）、换行风格 |
| `edit_files` | 唯一匹配的字符串替换，**按原编码回写**（GBK 文件改完还是 GBK） |
| `write_files` / `move_files` / `delete_files` | 写入 / 移动 / 删除，全部改前自动备份 |
| `search_files` | 文件名 glob + 内容正则，带软超时（超时返回部分结果并标注不完整） |
| `run_command` / `wait_command` | 在本机跑命令，默认关闭，要手动开关 |
| `view_image` | 把截图**当图片**返回给 AI，而不是十几万字符的 base64 |
| `prepare_upload` / `prepare_download` | 签发一次性 URL，让字节走 curl 而不走对话上下文 |

### 安全这块是重点（因为它在往外开一个能写文件的口子）

- **白名单 fail-closed**：根目录 + 扩展名 + 大小上限，每个工具调用都校验，白名单外直接拒。
- **审计日志**：append-only JSONL，每次写入/删除都记路径、行数、来源 IP。
- **改前自动备份 + 按组还原**：一次会话里改的 20 个文件可以整组回滚，不是逐个点。
- **只读模式**：给「只想让它看看」的场景，写入类工具全禁。
- **shell 默认关**：`run_command` 等同于授予远程任意代码执行，得你自己去「安全」页打开。
- 跨公网时用**内置自签 HTTPS**（一键生成，显示 SHA-256 指纹供你核对），不是裸 HTTP。

### 三条不太体面但真实的工程限制

1. **Windows / macOS only**，没有 Linux 版，也没有 Intel Mac 构建。跑 CC 的那台 Linux 不需要装任何东西。
2. **客户端对单次 MCP 请求大约 60 秒就断**（我实测 55s 全成功、65s 必失败）。所以 `run_command` 前台跑过 ~50 秒会自动转后台，返回 `backgrounded:true`，你再用 `wait_command` 去等——它超时**不杀进程**。
3. 别把端口裸暴露在公网。要么内网/VPN 直连，要么开内置 HTTPS 自签，要么自己挂反代 + Let's Encrypt。

### 同类里它大概是什么位置

- 官方 `server-filesystem`：装在 AI 那侧，只读写的沙箱，没有审计、没有备份、没有命令执行。
- SSHFS / scp / rsync：能用，但没有权限模型、没有审计，网络断了状态就崩。
- 那些把整个仓库同步到云端的方案：代码确实上去了——这恰好是我想避免的。

它不解决「AI 写代码好不好」这个问题，只是把**文件在哪**和**AI 在哪**解耦了。
