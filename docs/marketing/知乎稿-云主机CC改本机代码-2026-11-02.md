# 知乎稿：Claude Code 部署在云服务器上，怎么改我本机 Windows 的代码？

> 用途：**专栏文章**（首发），同时可裁成回答贴到这些问题的下面：
> - 「Claude Code 怎么操作本地文件？」
> - 「Claude Code 部署在服务器上，但代码在本地怎么办？」
> - 「有没有类似 SSHFS 但更稳的方案，让远程 AI 改本地代码？」
> 标题（选题已测过点击率的两种写法）：

## 先给结论

让云端 AI 改本地代码，能走的路只有三条，本质区别是**「谁迁就谁」**：

| 路线 | 做法 | 代价 |
|---|---|---|
| ① 搬文件 | `scp` / `rsync` 传到云上，改完再拉回来 | 每次都要传，几百兆的仓库来回几次就分不清哪边最新；断线重来 |
| ② 搬文件系统 | SSHFS / rclone mount，把远程目录挂成本地盘 | 网络一抖挂载点卡死，终端阻塞；权限模型几乎为零 |
| ③ 搬 AI 的手 | 把 MCP 服务器装在**文件所在的那台机器**上，AI 从外面连进来 | 需要一次安装 + 配白名单；换来的是代码不出本机 |

我最后用的是第 ③ 条，把它做成了一个桌面应用 **cc-bridge**（开源 MIT）。下面讲清楚它为什么能成立、具体怎么配、以及哪些地方会翻车——包括我自己踩出来的坑。

---

## 一、为什么「第③条」是成立的

MCP（Model Context Protocol）是 Anthropic 提的协议，Claude Code / Codex / 各类 AI 工具都能接 MCP server。绝大多数人装 MCP server 的思路是「装在 AI 跑的那台机器上」——因为习惯上 AI 就在本地。

但这个协议本身**没有任何要求说服务端必须和 AI 同机**。它就是个 HTTP 端点，加个 Bearer token 就能连。所以只要把服务端装在**文件所在的那台机器**上，云端 CC 一样能调它的工具，效果等于「AI 的手伸到了我本机」。

这也是我写这个项目时唯一的核心判断：

> 桥装在文件所在的那台机器上，AI 从对面接过来。

由此推出的两个方向，用的是同一个安装包：

- **模式 A**：CC 在云主机，文件在本机 → 云端 CC 改我本机代码（最常见的需求）
- **模式 B**：CC 在本机，文件在公司那台 Windows / 家里的 NAS → 本机 AI 整理远处机器

---

## 二、五步跑通（模式 A）

**第 1 步**：在**文件所在的本机**安装。Windows 是 4.5MB 的 `-setup.exe`，双击装完自动启动；macOS 是 `.dmg`/`.zip`（仅 Apple Silicon）。国内下载慢的话 README 里有 Gitee 镜像。

**第 2 步**：打开「安全」页 → 「浏览」把要开放的工作目录加进白名单。默认拒绝一切访问，这是故意的。

**第 3 步**：切到「连接」页，复制它给出的命令（token 已经填好在里面）：

```bash
claude mcp add --transport http cc-bridge http://192.168.1.100:7823/mcp \
  --header "Authorization: Bearer <token>"
```

**第 4 步**：把这条命令粘到**云主机**的终端里执行。`claude mcp list` 能看到 `cc-bridge: connected`。

**第 5 步**：回到 CC 里说「读一下 `src/app.tsx`，把这三处报警改掉」。改动落在本机，VS Code 里实时刷新。

要点：云端**不需要装任何东西**，也不需要开 SSH 反向隧道。它只认那个 HTTP 地址 + token。

---

## 三、比「能不能用」更要紧的三件事

### 1. 权限模型

所有工具调用都要过白名单：根目录（可多个）+ 扩展名 + 单文件大小上限，任何一条不满足直接拒，不做「尽力而为」。白名单本身不出现在任何工具返回值里以外的推断路径上，AI 只能通过 `list_allowed_roots` 知道自己的活动范围。

### 2. 可追溯 + 可回滚

- 每次写入 / 删除前**自动备份**，覆盖前备份旧内容，改错了可以按「一次会话」整组还原，而不是逐个文件点。
- **审计日志**是 append-only 的 JSONL，人眼可读：谁在什么时候读了哪个路径、改了 N 行、来源 IP 是什么。
- **只读模式**：写入/删除/命令执行全部禁用，适合「先让它看看」。

### 3. 命令执行是单独开关

`run_command` 等同于把远程任意代码执行权交出去，所以它**默认关闭**，得自己去「安全」页打开；打开后也只在你指定的壳层下执行（Windows 是 `cmd /C` 或 Git Bash，macOS 是 `sh`/`bash`）。

## 四、三个真实会翻车的地方（都是我踩的）

**① 客户端 60 秒就断。** 我实测同一条链路：55 秒内返回全成功，65 / 90 / 300 / 600 秒必失败。所以任何「挂在那儿等」的工具都必须在这条线前吐结果。`run_command` 的处理是：前台跑过约 50 秒自动转后台，返回 `backgrounded:true`，你再 `wait_command` 去等——而且**超时不杀进程**，`timedOut:true` + `running:true`，可以接着等。跑 `cargo build` 这种十几分钟的任务要按这个姿势来。

**② 一个大文件就能把上下文吃干。** 客户端对单条 MCP 结果有降级阈值：约 5 万字符原样给模型，再大就只剩 2KB 预览，更大直接报错。所以 `read_files` 在结果过大时**不返回正文**，而是返回「文件多少字节、多少行、建议怎么分段读」的指引——返回一段残文反而最坑，AI 会以为读完了。

**③ 中文 Windows 的编码。** GBK 项目用 UTF-8 去读就是满屏 `�`，写完还会把整个文件转码坏掉。现在的做法是读取时按行判断 UTF-8/GBK，`edit_files` 按**原编码回写**——GBK 文件改完还是 GBK。

## 五、它不适合谁

- **只在本机用 CC 的人**：你不需要它，官方 filesystem server 就够。
- **想要 Linux 版的人**：暂时没有，只有 Windows / macOS；跑 CC 的那台 Linux 什么都不用装。
- **想把端点直接挂公网的人**：不建议裸暴露。要么内网/VPN，要么用内置自签 HTTPS（一键生成、给出 SHA-256 指纹核对），要么自己挂反代 + Let's Encrypt。
- **指望它提升模型能力的人**：它只解决「文件在哪」和「AI 在哪」解耦，不改变模型本身好不好用。

---

## 六、一句话

**AI 在哪里跑不重要，文件始终待在它原来的地方。** 把 CC 放云上是为了算力和网络，不是为了把代码交出去；反过来，「公司规定代码不出内网、但想用云端大模型」这种更普遍的约束，靠的也是同一套东西。
