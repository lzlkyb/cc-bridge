## 一、核心结论：换的是 **IO 挂载点**，不是协议

现有直连：

```
spawn(claude) ──stdout──> pump(reader, sink)      ← NDJSON 行 → CcEvent
              <──stdin──  write_line(user / control_response)
```

托管：

```
读：ssh host 'tail -n +N -F <log>'  ──stdout──> pump(reader, sink)   ← 同一条 NDJSON 流
写：ssh host 'cat > <fifo>'         <──stdin──  write_line(...)      ← 同一条 user / control_response
                  └── worker(fd 9 <>) ──> claude ──> <log>
```

两点直接决定整批的风险边界：

1. **读通道的 stdout 就是原来那股 NDJSON 字节流** ⇒ `pump()` 一行不改；
2. **写通道的 stdin 就是原来那个管道** ⇒ `user_message_line` / `control_response_line` 一行不改。

所以 `proto.rs`、`lib/ccReducer.ts`、事件语义、审计归属（`active_session_id`）、
`ring`、前端五态判定**全部零改动**。这是选这条路的核心理由：风险被压进「IO 挂载」一层，
而不是散进协议层。

## 三、传输层抽象（唯一的结构性改动）

```rust
enum Transport {
    Direct(Run),        // 本机 / 未托管：一个 claude 子进程
    Hosted(HostedRun),  // 远端托管：两条 ssh + tmux 宿主
}
```

`CcSession` 的 8 个调用点逐个对照：

| 方法 | Direct（现状，不动） | Hosted（新） |
|---|---|---|
| `alive()` | 读线程活着（stdout 未 EOF） | 🔴 **`tmux has-session`**，不是「读线程活着」——见下 |
| `send_user` | 写 child.stdin | 写**写通道** ssh 的 stdin |
| `respond` | 同上 | 同上 |
| `interrupt` | 杀进程树 | `tmux kill-session -t <key>` |
| `kill` | 杀进程树 + 等读线程排干 | 同上（远端没有"读线程排干"，等读通道 EOF 即可） |
| `close_stdin` | 送 EOF，让 CLI 收尾退出 | 🔴 **无意义**：写通道关掉不影响 claude（这正是它能活下来的原因）。只用于释放本地句柄 |
| `shutdown(grace)` | 关 stdin → 等 → 强杀 | 🔴 **只拆两条 ssh，不杀 tmux**。app 退出恰恰是「进程该继续跑」的场景 |
| `stderr_tail` | 子进程 stderr 环形 | 空（远端 stderr 进了日志尾部，随 NDJSON 之外的行一起被 `pump` 当脏行跳过） |

### 🔴 `alive()` 语义分裂是本批最危险的一处

现在 `cc_cmds::cc_send` 的判断是：

```rust
if cc.is_running() && cc.send(&text).is_ok() { ...直接复用进程... }
// 否则往下走：新起一个 claude + --resume
```

`is_running()` 现在等于「读线程还活着」。托管时**读通道的 ssh 会随断网/超时死掉，而 claude 还活着**。
若沿用旧语义 ⇒ 判成「进程死了」⇒ 新起一个 claude 带 `--resume` ⇒ **两个 claude 同时写同一条会话的
`~/.claude/projects`**。这是会损坏会话历史的错，不是显示问题。

所以：`Transport::alive()` 对 `Hosted` 必须是 `tmux has-session` 的结论，
并且带 **TTL 缓存（建议 3s）**：每条消息都开一次 ssh 太重，而 3 秒的陈旧窗口不足以造成双进程
（`send` 本身会失败，失败了才走重建）。

## 四、幂等：按**行号**游标，不按字节

- 不用 `tail -c +N`（字节）：可能切在 UTF-8 多字节字符中间，也可能切在一行 JSON 中间；
- 用 `tail -n +N`（行）：协议单位就是行，与 `pump` 的 `read_until(b'\n')` 天然对齐。

游标 = **已消费行数** `seen_lines`。

重连时**故意重叠**重读：`tail -n +max(1, seen_lines - K + 1)`，`K = 32`。
按行号 `<= seen_lines` 丢弃，`> seen_lines` 才 `emit` 并推进游标。

### 🔴 为什么不能靠「判重」省掉重叠
`proto.rs` 里 CLI 事件**没有稳定 id**（查过：没有 `uuid` 字段），`ring` 的 `seq` 是我们本地铸的 ——
重放一行就是一条新 `seq`，用户会看到重复的一条消息。所以幂等只能自己用行号做。

### 落库时机
每消费 N 行（建议 64）或距上次落库 ≥500ms 才写一次库。**不要每行都写**：流式期间一秒钟几十上百行。

## 五、落库

`cc_sessions` 加**两列**（走 `ensure_column`，不用 `CREATE TABLE IF NOT EXISTS` 骗自己）：

| 列 | 类型 | 含义 |
|---|---|---|
| `hosted_key` | `TEXT` | tmux 会话名，`cc-<internal_id>-<started_at_ms>` |
| `hosted_lines` | `INTEGER NOT NULL DEFAULT 0` | 已消费行数（游标） |

**不存日志绝对路径**：它是 `$HOME/.cc-bridge/hosted/<key>.out`，而 `$HOME` 只有远端知道。
存一份本机算不出来的绝对路径等于存了个只能看不能用的东西。要用的时候按 key 在远端拼，
拼法在 `channel::hosted_attach` 里（`"$HOME/..."` 故意不 quote 死，让远端展开）。

会话名带 `started_at` 的理由：同一条内部 id 可能先后托管多次（第一次被 kill 了），
名字不带时间戳就会撞上一个已经死掉的名字，`has-session` 判出「活着」而其实是别人的。

## 六、生命周期差异（必须如实写进界面）

| 情境 | 直连（现在） | 托管 |
|---|---|---|
| 关掉 app | 进程被收，那一轮死 | **进程继续跑**，重开接回 |
| 关闭这条会话 | 杀进程 | `tmux kill-session`（不杀就是永久孤儿） |
| 点「中断」 | 杀进程树 | `tmux kill-session` 后重建（claude 的 stdin 是管道不是 TTY，Ctrl+C 只是写字节，没意义） |
| 网络断 | 那一轮死 | 进程活着，本机读通道断（`tail` 死）；恢复后重建读通道接回 |
| 远端重启 | — | 真的没了，`has-session` false ⇒ 标 `dead` |

🔴 **托管会话不能靠 EOF 收尾**：`close_stdin` 对它无效（那正是它能活下来的原因）。
所以「结束」只有一条路 —— `kill-session`。界面上「关闭会话」的语义因此与直连不同，要说清。

## 七、装配点

`cc_cmds::cc_send` 里现在这段：

```rust
let launch = match conn_id {
    None => { /* local_command */ }
    Some(id) => { /* remote_command：一条 ssh，exec claude */ }
};
cc.start(launch, sink)?;
```

改为：

```rust
let hosted = conn_id.is_some()
    && state.config.read().await.cc_hosted_sessions
    && hosted::tmux_available(state.inner(), &id).await;   // 探测结果按连接缓存

if hosted {
    cc.start_hosted(hosted::plan(...)?, sink)?;   // 内部：bootstrap → 开两条 ssh → 游标
} else {
    cc.start(launch, sink)?;                       // 原路径，一个字不改
}
```

`tmux_available` 用 `command -v tmux`，**按 connection_id 缓存**（一台机器一次就够）。
探测失败 ⇒ **静默回落直连**，不报错（fail-open 到旧行为，比「不让用」好）。

## 八、失败模式清单（写代码时逐条对照）

| # | 失败 | 现象 | 处理 |
|---|---|---|---|
| 1 | 写通道 ssh 静默死（NAT 超时） | 用户发消息报错 | 立即重建写通道 + 重试一次；仍失败才报错。**不许**因为写失败就判进程死 |
| 2 | 读通道 ssh 死（断网） | 事件流停，但进程活着 | 不重启 claude。重建 `tail`（从游标，含重叠） |
| 3 | tmux 会话没了 | 真死 | `dead`；下次发送走「新起 + `--resume`」原路径 |
| 4 | 日志被清 / rotate | 游标 > 现有行数 | 退化为从 1 重读，并如实提示「日志被截断，可能重复」 |
| 5 | 远端磁盘满 | claude 写不进日志 ⇒ **看着正常，其实每行都没到** | 我们这侧检测不到。只能靠：`turn_active` 超过阈值（建议 10 分钟无任何事件）就提示「可能卡住」 |
| 6 | 两条 ssh 同时断 | 全静默 | 恢复后按 #1 #2 分别重建 |

#5 是这条路唯一无法根治的失败模式，必须承认，不要假装能检测。

### S3 实施记录（2026-10-26）

改动只有两处，都是「换类型 + 改名字」，没有一行行为变更：

- `session.rs`：新增 `pub enum Transport { Direct(Run) }` + 5 个委托方法（`is_alive` /
  `send_user_images` / `respond` / `kill` / `shutdown`）。枚举上的注释写明了
  **`is_alive()` 语义按变体不同**（Hosted 必须是 `tmux has-session`），否则 S4 接线时
  很容易顺手沿用「读线程活着」那条判据。
- `manager.rs`：`live: StdMutex<Option<Run>>` → `Option<Transport>`，6 个调用点跟着改
  （`is_running` 的 `.map(Run::is_alive)` → `Transport::is_alive`、`start` 的存活判定
  与赋值、`send_user_images`、`respond`、`interrupt` 的 `Some(run) if run.is_alive()`）。

两处**没做**的决定：

- `stderr_tail` **不进** `Transport`：它对外没有暴露（`manager.rs` 一处都不调，只有 `Run`
  自己持有环形缓冲）。现在加进去就是 `dead_code`，`-D warnings` 会红。等 S4 真需要
  「Hosted 返回空 stderr」时再加，那时它才有调用点。
- `close_stdin` 同样不进：它只被 `Run::kill` / `Run::shutdown` 内部用。

🔴 **真机验证（方案的验收条件是「跑一轮对话」）尚未做**：要关闭用户正在用的安装版再重编译，

地方必须拿真实产出逐行比对，不能凭记忆写。**

## 十、明确不做

- **本机托管**：本机没 tmux，且本机进程本来就跟 app 同生共死，托管无从谈起；
- **attach TUI**：我们要 stdout 上的 NDJSON，attach 拿到的是屏幕；
- **后台轮询存活**：只在「发消息」与「切回会话」两个时机探，不设定时器（省 ssh）；
- **陈旧 tmux 会话的自动清理**：留一个手动入口（列出来 → 勾选 → kill），自动清理容易误杀别人正在跑的。
