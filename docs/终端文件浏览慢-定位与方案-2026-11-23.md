## 0. 结论速览

文件面板慢**不是某一个 bug，是三层叠加**：

1. **这台服务器每建立一条 SSH 连接要约 11 秒**（项目 2026-11-16 自己实测过，见 `docs/隧道启动认证耗时-11秒排查与修复-2026-11-16.md` §2.1/§2.3：TCP+KEX 只占 0.35 秒，剩下 ~10.6 秒在密码校验 / 会话建立）。而 **Windows OpenSSH 没有 ControlMaster，无法复用连接**——所以「新起一个 `ssh.exe`/`scp.exe` 进程」就等于「付 11 秒」。
2. **helper 常驻会话（唯一能省掉这 11 秒的机制）覆盖不全，且失效时代价是双倍的**：列目录/读写/建目录/删除走 helper，但 **scp 传输（下载/上传/用本机编辑器打开）永远新起进程，永远 11 秒**；helper 一旦坏掉，要先白等 `CMD_TIMEOUT = 15s` 再退回复古路径，于是 **15s + 11s ≈ 26 秒——正好落在用户报的 15–30 秒区间**。用户补充「**一直都慢**」（见 §1.5），这句按代码即可断定 **helper 从未成功驻留过**，所以这 26 秒不是偶发，而是每一次的固定成本。
3. **前端与交互在放大等待**：从终端路径点进面板会列两次目录；大目录没有虚拟化、选中判定是 O(n²)；任何一个传输进行中会把整个面板置为 busy，11 秒里连「点进另一个目录」都点不动。

**最值得先做的一件事**：让 helper 成为唯一路径（小文件下载也走它），并让它「永不静默死亡、丢了自己补建」。这一项能把绝大多数操作从 ~11 秒打到 1 秒以内，且完全在客户端、不碰服务器。

## 1. 第一性事实：一次登录 ≈ 11 秒

| 阶段 | 实测耗时 |
|---|---|
| TCP 建连 + 版本协商 + KEX | **0.35 s** |
| 密码认证 / 会话建立（PAM） | **~10.6 s** |
| 合计（`ssh <user>@<host> exit`） | **~11 s** |

来源：`docs/隧道启动认证耗时-11秒排查与修复-2026-11-16.md` §2.1（用 `ssh -vv` 逐行打时间戳测得）。已排除 UseDNS、GSSAPI、网络。待定位的是 PAM 哪一环（`pam_systemd`/`pam_motd`/NSS）。

### 1.5 补充事实（2026-11-23 21:40，用户口述 + 本机配置核对）

**用户原话：「一直都慢。」** 这不是「第一次慢、之后快」，而是**从第一次起每一次都慢**。

**这一句话本身就是判决性证据**，理由在代码里是确定的：`HelperSession` 一旦 `open()` 成功就常驻 `state.ssh_helpers`（`TTL = HELPER_IDLE_TTL = 1800 秒`），期间每次 `run_via_helper` 直接命中、零握手，命令本身是毫秒级。所以——

> **如果 helper 曾经成功驻留过，第二次操作必然 < 1 秒。用户说每一次都慢 ⇒ helper 从未成功驻留。**

**同时核对了本机配置，排除了两个此前的怀疑**：
- 连接是**内网机器** `10.0.19.194:22`，用户 `lizuliang`，`authType=password`，**`rememberPassword=true`** ⇒ helper 有资格拿到凭据，「没密码所以建不起来」被排除。
- `ssh_base_args`（`ssh_cmds.rs:527`）只有 `ServerAliveInterval=30` / `ServerAliveCountMax=3` / `StrictHostKeyChecking=accept-new` / `-p 22`，无可疑选项；本机 `Test-NetConnection 10.0.19.194 -Port 22` 成功 ⇒ 链路可达，排除配置错误。

**由此，「慢在哪」收敛成两个互斥的候选，且都能被一条命令分辨**（见 §4.1）：

| 候选 | 机制 | 预期耗时 |
|---|---|---|
| **C1：helper 建不起来** | PTY 登录失败（禁 `-tt` / `MaxSessions` 满 / rc 卡住 / 认证在 PTY 上更慢） | 每次 ≈ 11 s（负缓存期内立即失败，直接走一次性路径） |
| **C2：服务器上 `ls` 本身就慢** | helper **正常命中**，但 `gnu_ls_cmd` 要在服务器上跑十几秒，超过 `CMD_TIMEOUT = 15 s` ⇒ 判超时 → `drop_ssh_helper`（`ssh_cmds.rs:1188`）→ 退一次性路径再跑一遍（又 11 s 登录 + 又十几秒） | **每次 ≈ 15 s + 11 s ≈ 26 s** |

**C2 与此前所有修复都不冲突**，且解释力最强：11 秒修复报告（2026-11-16）修的是**隧道启动**，从来没测过 `ls` 本身；用户是内网 NC 开发环境，项目路径 `/home/lizuliang`，目录巨大或 home 在慢速存储上完全可能。**若 C2 成立，helper 是无辜的，真正该修的是列目录的数据量**（A3 从「可选优化」升级为「首要修复」）。

## 2. 逐操作耗时账（helper 正常 vs 失效）

`ssh_helper.rs` 的 helper 是每条连接一条常驻 `sh`，列目录/读写/mkdir/remove 都复用它（`run_via_helper`，`ssh_cmds.rs:1114`）。**scp 不走 helper。**

| 操作 | 后端命令 | 新起进程数（helper 正常） | （helper 失效/冷） |
|---|---|---|---|
| 打开面板（目录入口） | `ssh_sftp_list` | 0 | 1 ≈ 11 s |
| **打开面板（从终端点路径进入，initialPath 是文件）** | `ssh_sftp_list` ×**2** | 0 | 2 ≈ 22 s |
| 进目录 / 上一级 / 刷新 / 前进后退 | `ssh_sftp_list` | 0 | 1 ≈ 11 s |
| 双击文件打开编辑器 | `ssh_file_read` | 0 | 1 |
| Ctrl+S 保存 | `ssh_file_write` | 0 | 1 |
| 新建文件夹 | `ssh_sftp_mkdir` + 刷新 | 0 | 2 |
| 删除 N 项（串行） | `ssh_sftp_remove` ×N + 刷新 | 0 | N+1 |
| **下载单文件** | `ssh_sftp_get`（scp） | **1 ≈ 11 s** | 1 |
| **批量下载（同一目标目录 N 个）** | `ssh_sftp_get_many`（多源 scp 合并） | **1** | 1 |
| 批量下载（跨 M 个目录） | 同上，按目录分组 | **M** | M |
| **上传单文件 / 表单上传** | `ssh_sftp_put`（scp） | **1 ≈ 11 s** | 1 |
| 拖入 N 个文件（同目录） | `putMany`（多源 scp） | **1** | 1 |
| **用本机编辑器打开** | `remote_mtime`(helper) + scp | **1 ≈ 11 s** | 1+ |

**已核对的边界**：
- 拖拽上传不额外列目录（`useFileBrowserDrop.ts:55` 用手里 entries 判重名）✅
- `scp -s` 支持性探测是**本地进程、不建连、且全局缓存**（`ssh_cmds.rs:603`）✅ 不贡献耗时
- 批量传输的多源 scp 合并已在 2026-11-17 落地，N 个文件 = 1 次握手 ✅

## 3. 已定位缺陷清单（按严重度）

### P0-1　helper 输出缓冲 4 MB 上限会**静默吃掉结束哨兵** ⇒ 每次操作必跑满 15 秒

`ssh_helper.rs:44` `MAX_BUF = 4 MB`，reader 线程 `if s.len() < MAX_BUF { push }`（`:200-203`）。
而 `run()` 判完成只认「整行等于 `__CCB_E_<nonce>_<code>__`」（`scan_result`，`:76-96`）。

⇒ `ls -la` 输出超过 ~4 MB（**约 4–5 万个条目**，每行 60–100 字节）时，结束哨兵被缓冲上限挡掉，`scan_result` 永远返回 None，`run()` 白等满 `CMD_TIMEOUT = 15s`（`:31`）→ 返回 Err → `run_via_helper` 把 helper 拆掉（`ssh_cmds.rs:1187`）→ 调用方退一次性 ssh（再 11 秒）。

**净效果：该目录下每一次操作都是 15s + 11s ≈ 26 秒，且每次都把 helper 拆掉重建，周而复始。** 这是代码里**唯一能确定性产生「每次操作 15 秒起步」的机制**，与网络状况无关。【实测：代码路径；待真机复现确认条目量级】

同类风险：`ssh_file_read` 的 2 MB 上限文件 base64 后约 2.87 MB（含 PTY 的 ONLCR 膨胀），离 4 MB 只剩 ~1 MB 余量——文件再大一点或行数再多一点就会踩同一条线。

### P0-2　内联编辑器会把 256 KB–2 MB 的**远端文件静默截断**（数据丢失，非性能）

`ssh_file_cmds.rs:38` `PREVIEW_BYTES = 256 KB`，而 `read_script()`（`:152-181`）**恒定** `data=f.read(PREVIEW_BYTES)`，`truncated` 却只在 `st.st_size > MAX_EDIT_BYTES(2 MB)` 时为 true。

⇒ 一个 1 MB 的配置文件：打开后只拿到前 256 KB，`truncated=false`；
前端 `readOnly = !!meta.truncated`（`useRemoteFileEdit.ts:61`）、`canSave = !readOnly && ready`（`SshFileEditor.tsx:48`）⇒ **可编辑、可保存，保存后远端文件从 1 MB 变成 256 KB**。

文档写的意图是「≤2 MB 整份编辑，>2 MB 只读预览前 256 KB」（`docs/远程文件编辑-2026-11-17.md` §四），代码没实现前半句。无任何测试覆盖这个边界（`ssh_file_cmds.rs` 的测试只覆盖 `parse_read_output`）。

### P1-1　helper 预热与用户点击会**并发建两条 helper**

预热在 `ssh_connect` 末尾（`ssh_cmds.rs:2100-2141`）：等 `SSH_CONNECT_FAIL_GRACE = 5s` 就建 helper。但登录本身要 11 秒。

⇒ 用户在连接后 5–11 秒内点文件，`run_via_helper` 发现 map 里没有 key，**自己再建一条**；预热那条也在建。两条并发登录，`or_insert_with` 选一个赢家，输家被 drop（`ssh_cmds.rs:1165-1170`）。代价：多付一次 11 秒登录、多占一个服务器 session 名额；并发登录过多还可能撞上服务器 `MaxStartups`（默认 `10:30:60`）的随机丢包，丢一次就是一个 RTO 量级的额外延迟。

### P1-2　helper 丢了没有任何补建机制

`drop_ssh_helper` 的触发点：helper 跑坏（`:1188`/`:1256`）、断开终端（`:1772`）、改动/删除连接（`config_cmds.rs:944`、`:1668`）。丢掉之后**只有等用户下一次操作同步付 11 秒**，没有后台补建。用户「断开重连 → 点文件」必然慢一次。

### P1-3　从终端路径点进面板 = 两次列目录

`useSshFileInitialPath.ts:21-24`：initialPath 是文件时，先 `ls(file)`（**会成功**，`ls -la` 对文件也返回一行），靠 `isInitialFileListing`（`sshFilePaths.ts:10-12`，要求唯一条目且名字等于全路径）识别出来，再回退父目录列第二次。

⇒ 冷 helper 时开门就是 22 秒。而且这个识别依赖 `ls` 的输出形态，脆。

### P1-4　忙态把整个面板锁死

`SshFileBrowser.tsx:91-92`：`operationBusy = ops.busy || xfer.transfer || xfer.prompt || forms.download.busy`，`busy` 再 OR 上 loading/error；`openDir`/`openEditor`/`onNavigate` 全部 `if (!busy)` 才动（`:122-154`）。

⇒ 一次 11 秒的下载期间，用户连「点进另一个目录」都点不了，只能干等。慢操作期间不给任何并行探索的余地。

### P2-1　大目录前端渲染成本（与网络无关）

`SshFileRow.tsx:216-229`：`entries.map` 全量渲染，**无虚拟化**；每行 `selectedNames?.includes(e.name)`（`:221`）是 O(n) ⇒ 整表 O(n²)。几千行的目录，光渲染就要数秒，且每次刷新重演。`key={path}` 还会整表重挂 + 重播淡入动画（`:228`）。

### P2-2　失败路径的等待可以叠加到 45 秒

helper 坏（15s）→ 退一次性路径（`SSH_ONESHOT_TIMEOUT = 30s`，`ssh_cmds.rs:1031`）→ BSD 降级再跑一遍（又 30s）。`ssh_sftp_list` 的注释自己记着这个账（`:2328-2331`）。

## 5. 方案

### 方案对比（先选大方向）

| | 做法 | 收益 | 代价 / 风险 |
|---|---|---|---|
| **A（推荐）** | 客户端：让 helper 覆盖全部小文件操作 + 修生命周期 + 修前端 | 列目录/读写/mkdir/删除/小文件传输全部 ~11 s → <1 s；不碰服务器 | 要改 Rust + 前端；PTY 传 base64 有 4 MB 天花板（需配套限流） |
| **B** | 服务器侧治本：定位并修掉 11 秒 PAM（`pam_systemd`/`pam_motd`/NSS），或给账号换 ed25519 密钥 | **所有路径一次性受益**（终端、scp、隧道、转发） | 可能要 root；密码认证慢才有效，会话建立慢换密钥无效 |
| **C** | 换传输架构（内置 SFTP 客户端 / plink `-share` / WSL ssh mux） | 理论上最优 | B 方案已论证否决（ConPTY 二进制不安全、凭据落盘、回归面巨大），不做 |

**推荐 A + B 并行**：B 治本（若用户有服务器权限），A 把客户端能拿的收益先落袋。A 不依赖 B，B 落地后 A 的收益会变小但不会白做。

### A 的实施分期（每期可独立验收、独立回滚）

> **优先级按 §4.1 的判读结果二选一**：
> - **C2 成立**（服务器 `ls` 慢）：顺序改为 **A3 → A0 → A2 → A1 → A4**。A3 直接从「优化」变「首要修复」。
> - **C1 成立**（helper 建不起来）：顺序为 **A0 → A2 → A1 → A3 → A4**。
> - **两者都改**：A0 与 A3 互不冲突，可并行；A2 修 helper 生命周期，A1 扩 helper 覆盖面。
> **无论哪种，A0 与 P0-2（256 KB 截断）都先做**——A0 让故障可见，P0-2 是数据丢失、不该等排期。

**A0 · 先埋点再动手（半天，零风险）**
- `ssh_helper.rs` / `ssh_cmds.rs` 的关键路径加耗时埋点（helper 是否命中、建会话耗时、命令耗时、回退原因），经 Tauri IPC 暴露给面板一个「上次操作耗时」小徽标（`useSshFileListing` 已有 loading 态，挂上去即可）。
- 目的：把「我猜是 helper 没生效」变成「面板上写着 `helper 未命中 · 建会话 11.2 s · 列目录 0.3 s`」。这也是项目一贯的探针作风。
- 顺带把 P0-2（256 KB 截断）一起修掉——它是数据丢失，不该等排期。

**A1 · helper 覆盖小文件传输（收益最大）**
- 下载：文件 ≤ 2 MB 时改用 helper 跑 `base64` 拉取（读路径已有完整先例：`ssh_file_read` 就是 base64 + 哨兵），> 2 MB 才走 scp。
- 上传：`ssh_file_write` 已经走 helper，把「上传表单/拖入」的小文件也并过去（大文件仍 scp）。
- 「用本机编辑器打开」：≤ 2 MB 直接经 helper 落到本机临时副本，省掉 11 秒；大文件保持 scp。
- 预期：下载/上传小文件 11 s → <1 s。

**A2 · helper 生命周期加固**
- **建会话串行化**：每条连接一把「建会话中」锁（或 `OnceCell` 式占位），预热与用户点击不会并发建两条（修 P1-1）。
- **丢后自动补建**：helper 被拆后起一个后台补建任务，用户下次操作直接命中（修 P1-2）。
- **预热时机提前 + 去重**：连接一发起就预热（不必等 5 秒宽限期——宽限期是防 fail2ban 的，改成「宽限期内只登记、不登录」同样安全），并让 `ssh_connect` 与 `run_via_helper` 走同一个占位符。
- **快速失败**：helper 命令超时不要白等 15 s 才退——加「输出停止增长 N 秒 + 未见到开始哨兵」的早停判据，把最坏 45 s 压到 11 s 量级（修 P2-2）。

**A3 · 列目录本身瘦身（同时解 P0-1 与 P2-1）**
- 后端：`ls -la` 加行数上限（如 `head -n 5000`），超出时返回 `truncated: true` + 总条目数。**输出有界 ⇒ helper 的 4 MB 缓冲再也吃不到哨兵**（修 P0-1），前端也有「还有 N 项未显示」的诚实交代。
- 前端：表格虚拟化（或「显示前 500 行 + 加载更多」）；`selectedNames` 改 `Set`；`key={path}` 的重挂保留（换目录归位是对的）但去掉整表 FLIP 动画在 >200 行时的应用。
- 体量棘轮：`SshFileRow.tsx` / `SshFileBrowser.tsx` 都接近 300 行上限，虚拟化建议新开 `FileTable.tsx` 子组件，别往旧文件里堆（BASELINE 只许变小）。

**A4 · 交互层（不省钱，但把「等」变可忍）**
- 慢提示分阶段文案：现在 2.5 s 出现的是一句通用话（`SshFileBrowser.tsx:164-167`）。改成按阶段说人话 + 显示已等秒数：「正在建立会话（这台服务器登录约需 10 秒）… 已等 6 s」/「正在传输（不走常驻会话）…」。
- **传输期间不锁导航**：`operationBusy` 只锁「会互相踩的写操作」，列目录/进入目录保持可点（修 P1-4）。下载结果仍留在底部状态条，不打断浏览。
- 从终端路径进入：直接列父目录并在结果里定位该文件（一次往返），列不到再回退（修 P1-3）。

### D 的实施记录（2026-11-23 已落地）

**方案 D = 只把文件面板迁到内置 russh 长连接**（终端继续 PTY `ssh.exe` 不动，避开 xterm/resize/信号回归面）。选型依据见 `docs/同类软件文件传输架构调研-2026-11-23.md`：Tabby 的 SFTP 面板直接复用终端的 SSH 连接、Yazi 一条 `ChannelStream` + 请求 ID 多路复用，说明「内置协议栈 + 一条长连接」是同类软件的共识做法，ControlMaster 的限制从根本上不存在。

**新增两个模块**（`desktop/src-tauri/src/commands/`）：

| 文件 | 职责 |
|---|---|
| `ssh_russh_cmds.rs`（365 行） | 连接管理层：建连/认证/SFTP subsystem、负缓存、建连串行化、空闲 GC、keepalive |
| `ssh_russh_file.rs`（520 行） | 文件操作层：列目录 / 建目录 / 删除 / 取 mtime / 读 / 写 / 下载 / 上传 |

**已接线的 10 个命令**（一律「russh 优先，任何失败自动回退」到既有 helper / scp，旧代码一行未删）：

`ssh_sftp_list`、`ssh_sftp_mkdir`、`ssh_sftp_remove`、`ssh_sftp_get`、`ssh_sftp_put`、`ssh_file_read`、`ssh_file_write`、`ssh_file_open_external`、`ssh_file_upload_edited`。

**灰度策略能成立的两个前提**（缺一个就会比不接还慢）：

1. **负缓存** `RUSSH_BLOCK_TTL = 60s`：服务器禁 sftp 子系统 / 算法协商失败 / 没存密码时，`get_russh_session` 每次必败。若不加冷却，「先试 russh 再回退」会让**每一次操作都先白付一次最坏 40 秒的失败成本**才走旧路。
2. **建连串行化**：每条连接一把建连锁。没有它，面板刷新与拖拽上传会同时发现 map 里没有 key、各自建一条——白付一次 11 秒登录，还多占一个服务器 `MaxSessions` 名额，并发多了可能撞 sshd 的 `MaxStartups` 被随机丢包。这正是旧 helper 路径上已知的 P1-1，这里从第一版就避开。

**顺带修掉的缺陷**：P0-2（内联编辑器把 256KB–2MB 远端文件静默截断，数据丢失级）在 russh 与旧路径**双路径齐修**，并删掉诱饵常量 `PREVIEW_BYTES`——限量读与 `truncated` 判据分开定义就是在制造下一个错位。回归测试做过变异验证（把限量改回 256KB 后确实 FAILED）。

**已知边界（第一版明确不做，失败即回退，不静默）**：

1. **跳板机（ProxyJump）不支持**——russh 无内置 proxy，需要「先连跳板认证、再 `channel_open_direct_tcpip` 拿 stream、`connect_stream` 连目标」。用户当前连接是直连，故检测到跳板直接返回 Err。注意这个检查放在 `get_russh_session` 开头而不是留给建连失败：跳板连接永远走不通 russh，走失败分支会每 60 秒记一次负缓存并刷一行失败日志，变成周期性复发的假故障。
2. 🔴 **host key 校验语义弱于旧路径**。旧路径是 `StrictHostKeyChecking=accept-new`：未知 host key 自动接受，但 known_hosts 里已有记录而指纹**变了**时仍然拒绝（防中间人）。russh 这一版不做 known_hosts 比对，两种情况都放行，实际等同 `=no`。理由：russh 没有内置 known_hosts 解析，自己实现要处理 hashed 条目、`[host]:port` 形式、注释与 revoked 行，代价不小；而本工具面向内网开发机，且回退路径始终存在。**后续要收紧的正确做法**：在 `check_server_key` 里读 known_hosts 比对，比对不上返回 `Ok(false)`，让调用方回退到旧 `ssh.exe` 路径，由 OpenSSH 去拦——而不是在 russh 里自己造一遍校验。

**门禁**：`cargo fmt --check` / `clippy --all-targets --no-default-features -- -D warnings` / `cargo test --no-default-features` 全绿（1193 passed / 0 failed，lib 全量）。

**未验收**：真机确认 russh 路径把单次操作从 11–26s 打到 <1s（需 GUI 操作，用户本人在场）。判据已内建成可观测日志：建连成功打 `[SSH] russh 长连接已就绪（user@host:port）`，失败打 `[SSH] russh 建连失败（...），回退 helper 路径：<原因>`——没有这两行，「这次快」和「russh 从来没成过、一直在走旧路」从外表完全分不出来，而后者正是用户最初抱怨「一直都慢」的形态。

**代码审查中修掉的三个缺陷（2026-11-23 晚，均已加回归测试并做变异验证）**：

1. 🔴 **保存远端文件丢权限位**（属性丢失级）。russh 写路径只写内容不写权限，保存后权限变成 SFTP 默认值；旧路径远端 python 有 `os.chmod(tmp, st.st_mode & 0o7777)`，所以只有 russh 路径会丢：0755 的脚本保存后变 0644 跑不起来，0600 的私钥被放宽成 0644 是安全事故。修法：`set_metadata` 在 rename **之前**把权限写到临时文件（放 rename 之后会有一个「内容已是新的、权限还是旧的」窗口，且中途失败就留个错权限文件）。权限失败不阻断保存——内容丢了是数据丢失，权限错了是小事。
2. 🔴 **写临时文件名并发冲突**（数据丢失级）。临时名只含本机 pid，而旧路径临时名带的是远端 shell 的 pid、每次保存都新起 ssh 会话所以天然唯一——迁到长连接后才暴露：同一文件在两个标签页同时打开、先后点保存，两次写互相截断，最后 rename 出去的是半份内容且无任何报错。修法：进程内自增序号（`WRITE_SEQ`）进临时名，上传路径同理。
3. **`check_server_key` 的注释不实**（见上「已知边界 2」）。原注释写「已知指纹变更也不在此拦截（旧路径同样不拦）」——旧路径用 accept-new 是会拦的。注释说谎比没有注释更糟：后来人会以为两条路径一致而不去补。

## 6. 验收标准

1. `Measure-Command { ssh <user>@<host> exit }` 仍是 ~11 s 的前提下：
   - **C1 成立时**：列目录/进目录/刷新/双击读/保存/新建/删除，全程 < 1.5 s（helper 命中）。
   - **C2 成立时**：同一套操作 < 3 s，且面板明确提示「仅显示前 N 项，共 M 项」（A3 生效，`ls` 不再全量拉）。
2. **≤ 2 MB 的下载/上传/用本机编辑器打开 < 2 s**（A1 生效，不再新起 scp）。
3. 面板上的耗时徽标能直接读出每条操作的 `helper 命中/未命中` 与各阶段毫秒数（A0 生效）。
4. 5 万条目目录：列目录 < 3 s，界面不卡，且有「仅显示前 5000 项」提示（A3 生效）。
5. 一个 1 MB 的文件：打开可见全部内容，保存后远端大小不变（P0-2 修复，带回归测试）。
6. 下载进行中能继续点进其它目录（A4 生效）。
7. 门禁：`cargo fmt --check` / `clippy --all-targets --no-default-features -- -D warnings` / `cargo test --no-default-features` 全绿；前端四项（体量 / eslint / tsc / vitest）全绿；新增用例在实现回退时确实变红。

## 7. 红线与明确不做

- **不碰安全边界**：`ssh_enabled` 总闸、凭据只在登录一瞬存在、写回乐观锁、临时文件同目录 + 原子 rename，全部保持原样。helper 传 base64 不改变任何授权模型。
- **不做弹窗确认/审批门**（R17）；慢提示是状态说明，不是打断。
- **不重启「B 方案」（`ssh -s sftp` 长连接 + 手写 SFTP v3）**：已论证否决，见 `docs/B方案验证-2026-11-17.md`。
- **不在 Windows 上尝试 ControlMaster**：Win32-OpenSSH 不支持，写了必报 `getsockname failed`。
- **不用错误口令试探服务器**（会锁账号）；所有需要口令的测量由用户本人做。
- 不为了这次改动跳版本号；变更条目进 `CHANGELOG.md` 的 `[Unreleased]`。
