# 远端 MCP 接入的 token 消耗归因与优化规划

> 日期：2026-11-25
> 触发：用户反馈「用 cc-bridge 比直接用本地 Claude Code 消耗 token 多很多，是不是没做缓存」
> 定位：先回答「钱花在哪」，再给可执行的分级优化项。**本文只有规划，没有代码改动。**
> 前提拓扑：**Claude Code 跑在远端（云主机 / 另一台机器），通过 MCP（HTTP/SSE 或隧道）接入本机 cc-bridge 操作文件与命令**。不是「GUI 里本地起 claude」那条链路——那条链路的数字见 §2.4 备注。
> 相关前作：`docs/上下文消耗优化方案-2026-10-22.md`（工具面裁剪与 45,000 字符上限的由来）、`docs/中转多厂商适配-2026-11-25.md`（中转方言与 cache_control 处置）

---

## 〇、一句话结论

**缓存是好的（命中 92.7%～97.6%），不是我们没做缓存。** 贵在两处相乘：**每次请求要搬运 22.8 万 token 的上下文** × **每条用户消息平均 15 次请求**，一条消息就是约 340 万输入 token。MCP 的工具定义与 instructions（约 5k token）在命中缓存后只占 2%，可以彻底排除。

> **2026-11-25 补充**：§2.6 用本机会话日志做了「内置工具 vs cc-bridge」逐次对照（不看中转数据），结论修正为：缓存两边都 100% 沿用；cc-bridge 唯一显著更贵的是**改/写文件回显 diff（约 19 倍）**；`run_command` 反而比内置 Bash 省，P0-2 降级。修正后的优先级见 §2.6.4。

真正能动的三把刀，按收益排序：**① 让远端会话别顶到 25 万上下文还在跑；② 压工具返回值（`run_command` 默认 32KB 太宽）；③ 把纯礼貌性的往返砍掉（`push_notification` 每条任务一次、后台命令拆成两次调用）**。

## 二、实测结果

### 2.1 单次请求长什么样（数据源 A）

| 指标 | 实测值 |
|---|---|
| 请求数（当日） | 483 |
| `input` / `cacheWrite` / `cacheRead` / `output` | 1,948,154 / 6,140,085 / **102,123,378** / 310,499 |
| 缓存命中率 | **92.7%** |
| 平均每次请求上下文 | **228,181 token** |
| 平均每次输出 | **643 token** |
| 请求体大小 | 中位 **902KB**，最大 1,835KB |

读法：**每按一次回车、每跑一次工具，就要把 90 万字节的请求体再发一遍**，模型只回 643 个 token。输出/输入 = 0.28%，这是典型的「上下文搬运」型开销，不是「模型话多」。

### 2.2 乘数一：上下文基数（数据源 B）

工具结果一旦进上下文就永久占位，之后每一次请求都要重发。

| 工具 | 次数 | 合计字节 | 占比 | 平均/次 | 最大/次 |
|---|---|---|---|---|---|
| `run_command` | 5,734 | 8.92 MB | 40.0% | 1.55 KB | 213,721 B |
| `read_files` | 967 | 8.07 MB | 36.2% | **8.34 KB** | 157,510 字符* |
| `edit_files` | 865 | 1.92 MB | 8.6% | 2.22 KB | 20,119 B |
| `search_files` | 508 | 1.64 MB | 7.4% | 3.23 KB | 40,483 B |
| `wait_command` | 1,011 | 0.71 MB | 3.2% | 0.70 KB | 6,844 B |
| `list_directory` | 13 | 0.42 MB | 1.9% | 32.4 KB | 149,929 B |
| `write_files` | 756 | 0.33 MB | 1.5% | 0.43 KB | 7,136 B |
| `batch` | 13 | 0.16 MB | 0.7% | 12.6 KB | 33,189 B |
| `push_notification` | 522 | 8.4 KB | 0.0% | 16 B | 20 B |
| 合计 | **10,681** | **22.3 MB** | 100% | — | — |

\* `read_files` 现在超 `MAX_INLINE_CHARS = 45,000` 字符即拒（`docs/上下文消耗优化方案-2026-10-22.md` §3.5 已落地）；157,510 是落地前的历史记录，保留它正是为了说明「不设限时会变成什么样」。

22.3 MB ≈ **558 万 token** 的工具结果被写进了历史。远端拓扑下这批内容没有任何本地兜底（本地 CLI 的大输出会落盘，只给摘录），全部沉在上下文里，跟着每一次往返重发。

### 2.3 乘数二：往返次数（数据源 C）

| 指标 | 实测值 |
|---|---|
| API 请求 / 用户消息 | **15.18** |
| 工具调用 / 用户消息 | 7.33 |
| MCP 工具调用占比 | 86.9%（12,774 / 14,701） |

三个把往返数抬上去的具体来源：

1. **后台命令拆两次**：`run_command` 6,972 次 : `wait_command` 1,047 次。长命令走「发出去 + 等结果」两步，每次都是一趟完整上下文搬运。
2. **`push_notification` 737 次**：`registry.rs` 的描述与 `http.rs::build_instructions` 里都写了「完成任何任务后 **MUST** 调用」。这是一次纯礼貌往返，占全部请求的 2.4%；任务越短占比越高（3 次往返的任务 +33%）。
3. **`list_allowed_roots` 开场一次**：instructions 明确要求「连接后第一步调用」，返回里还会内联每个允许根目录的 `AGENTS.md` / `CLAUDE.md`（单文件上限 `PROJECT_RULES_INLINE_MAX_BYTES = 20KB`）。远端项目的规则文件若在 20KB 量级，这一趟就是 5k token 起步，而且与「CLI 自己已注入 CLAUDE.md」的情形重复。

反例：**`batch` 只有 85 次（JSONL）/ 13 次（audit）**。它是专门用来把 N 次往返合并成 1 次的工具，在「往返最贵」的远端拓扑下几乎没被用起来——说明 instructions 里那句「优先用 batch」没有约束力。

### 2.4 乘数三：MCP 固定块（≈2%，排除）

| 项 | 体量 |
|---|---|
| `tools/list`（全量 25 个工具的 desc + inputSchema） | 约 16–20 KB ≈ **4.5–5k token**（前作实测 24 工具 15.9KB/4.4k；本次在真实请求里量到 7 个核心 MCP 工具占 8.8KB） |
| `instructions`（`http.rs::build_instructions`） | 1.3–2 KB ≈ **400–600 token** |

命中缓存后只值约 500 token/请求，占 228k 的 **0.25%**。**工具描述瘦身 / instructions 压缩都不值得做**，理由与前作 §5 一致，此处再次确认。

> 备注（GUI 本地起 claude 那条链路）：同样是 92.7%～97.6% 命中，问题同构，只是基数小一些。本文的优化项对两条链路都成立。

### 2.5 已经排除的嫌疑人

| 假设 | 实测 | 结论 |
|---|---|---|
| 没做 prompt cache | A: 92.7%，C: 97.6% | ❌ 排除 |
| 每轮都在重写缓存前缀 | 每请求平均 `cacheWrite` 5,600 token | ❌ 排除 |
| 空闲 5 分钟打穿 TTL | 间隔 5–15 分钟的 268 次请求仍有 6,040 万 cacheRead（照常命中）；只有间隔 >1h 的 206 次请求发生整段重写（平均 15.8 万/次），贡献 19% 的 cacheWrite | ⚠️ 存在但量小（0.7% 的请求） |
| 结果超客户端落盘线（>49,823 字符 → 只给 2KB 预览） | 77 次 / 0.7%，其中 63 次是 `view_image` 的 base64（不计 token）；文本类仅 14 次 | ❌ 排除 |
| 工具调用大面积失败导致空转 | 386 / 14,697 = **2.6%** | ❌ 排除 |
| MCP 结果被 JSON 包装放大 | 客户端会解 envelope，正文原样 | ❌ 排除 |

### 2.6 内置工具 vs cc-bridge 逐次对照（2026-11-25 补测，不含中转数据）

**数据源 D**：Linux 端 Claude Code 全部主会话日志（`/home/claude-svc/.claude/projects/*/*.jsonl`，排除子代理），**70,300 次请求**，同模型、同批会话里两类工具混用。

**口径**：只取「本次请求恰好发出 1 个工具调用」的样本；该调用进上下文的 token = 下一次请求的总输入（input + cacheWrite + cacheRead）− 本次总输入 − 本次 output。这是上游**真实计费 token**，不是字节估算。剔除上下文 <5k（会话开头）与增量 <0 或 >6 万（compact / 断档）的样本。「前缀沿用」= 下一次请求的 cacheRead ≥ 本次总输入的 95%。

**局限**：两类工具来自不同任务，不是同任务 A/B；内置 Grep/Glob 样本不足，搜索类无对照。逐次比较的方向结论足够稳，绝对值不要外推。

#### 2.6.1 缓存：两边一样

| | 前缀沿用率 | 下一请求 cacheRead 占比 |
|---|---|---|
| 内置工具（Bash/Read/Edit/Write） | 100% | 97.6%～99.6% |
| cc-bridge（全部工具） | 99.8%～100% | 96.2%～99.8% |

MCP 工具结果**不会**打断缓存。「没做缓存」排除。

#### 2.6.2 每次调用进上下文的 token

| 工具 | 次数 | 结果字符 中位 / P90 / 均值 | 进上下文 token 中位 / P90 / 均值 |
|---|---|---|---|
| 内置 `Bash` | 5,925 | 696 / 4,956 / 1,894 | 435 / 2,698 / **1,065** |
| `run_command` | 11,487 | 501 / 3,388 / 1,401 | 311 / 1,940 / **819** |
| `wait_command` | 1,738 | 485 / 1,976 / 1,009 | 289 / 1,111 / 575 |
| 内置 `Read` | 516 | 800 / 16,104 / 4,955 | 2,754 / 10,133 / **3,863** |
| `read_files` | 5,576 | 3,821 / 15,136 / 6,340 | 2,027 / 7,975 / **3,401** |
| 内置 `Edit` | 445 | 133 / 196 / 141 | 89 / 117 / **99** |
| `edit_files` | 4,078 | 2,038 / 6,306 / 2,914 | 1,340 / 3,942 / **1,884** |
| 内置 `Write` | 304 | 188 / 209 / 171 | 102 / 135 / **106** |
| `write_files` | 1,722 | 246 / 4,805 / 1,909 | 472 / 5,403 / **1,987** |
| `search_files` | 5,934 | 1,972 / 11,838 / 4,506 | 1,071 / 6,282 / 2,440 |
| `batch` | 961 | 4,993 / 20,501 / 8,388 | 2,840 / 12,356 / 4,904 |
| `push_notification` | 1,683 | 20 / 60 / 30 | 16 / 51 / 34 |

读法：

- **命令、读文件：cc-bridge 不比内置贵，反而略省**（`read_files` 不带行号前缀；`run_command` 有过滤与裁剪）。
- **改/写文件：cc-bridge 约为内置的 19 倍。** 原因是 `diff_utils.rs` 的 `DiffMode::Auto` 对已存在文件落到 `Hunks`（单文件最多 `HUNKS_MAX_BYTES = 4096`），把改动以 unified diff 回显；内置 Edit/Write 只回一句「已更新」。改了什么，模型自己的 tool_use 入参里已经写过一遍，回显是**同一内容第二次进上下文**，之后每一轮都跟着重发。抽样里超过 5,000 字符的 `edit_files` 结果有 1,288 条。

#### 2.6.3 单独占一趟往返的调用

「本次请求只发了这一种工具」时，这趟请求本身就是一次整段上下文重读。

| 调用 | 单独成趟次数 | 当时平均上下文 | 占全部输入 token |
|---|---|---|---|
| `edit_files` | 4,223 | 28.7 万 | 7.46% |
| `wait_command` | 1,813 | 23.6 万 | 2.63% |
| `push_notification` | 1,686 | 24.3 万 | 2.51% |
| `write_files` | 1,775 | 26.3 万 | 2.88% |
| `ToolSearch`（加载延迟的 MCP 工具定义） | 1,273 | 14.1 万 | 1.11% |
| 对照：内置 `Edit` / `Write` | 504 / 319 | 26.4 万 / 25.6 万 | 0.82% / 0.50% |

改/写文件本身是必要往返（贵在回显，见 2.6.2）；`push_notification`、`wait_command`、`ToolSearch` 是 cc-bridge 链路**额外**多出的往返，合计约 6%。

全部 70,300 次请求的平均上下文为 **23.1 万 token**——内置与 cc-bridge 都在这个水平，**会话过长才是总量的第一驱动，与是否接 cc-bridge 无关**。

#### 2.6.4 修正后的优化优先级

| 序 | 项 | 改法 | 预估收益 |
|---|---|---|---|
| 1 | **改/写文件默认不回显 diff**（新增，原文无） | `DiffMode::Auto` 对已存在文件改落 `Stat`（只回「+8/-0 行，字节变化」），需要看 diff 时显式传 `diff:"hunks"`；同步改工具描述与守卫测试 | 每次改文件约 1,900 → 约 100 token，与内置持平 |
| 2 | **通知改走 Stop 钩子**（替代 P0-3 第 1 条） | 去掉 instructions / 工具描述里「每次任务后 MUST 调 push_notification」；由 Claude Code 的 Stop 钩子调 cc-bridge 通知接口，回合结束自动弹窗，0 token | 约 2.5% |
| 3 | 命令少等一趟（即 P0-3 第 2 条） | 前台命令服务端先等满约 50 秒再转后台；`wait_command` 支持一次等多个句柄 | 1%～2% |
| 4 | 上下文收口提示（即 P0-1） | 不变；对内置与 cc-bridge 同样有效，总量上收益最大 | 最大，但靠用户操作 |
| — | ~~P0-2 降 `run_command` 返回上限~~ | **降级为不做**：实测 `run_command` 均值 819 < 内置 Bash 1,065，长尾也不比 Bash 宽 | — |

**进度（2026-11-25）**：第 1～3 项已改完并过门禁（单测 1385 通过），另加一项「batch 提示改为点名顺序多步场景」；均在变更集「token优化」，未提交。第 3 项只改了提示文字，「wait_command 一次等多个句柄」未做（收益小）。

### 2.7 返回格式开销（对标内置工具的下一步）

目标：**不改变功能**的前提下，把 cc-bridge 单次调用的 token 压到与内置工具持平或更低。数据源同 §2.6（数据源 D），统计各工具返回里「格式本身」占了多少。

| 工具 | 调用次数 | 返回总字符 | 主要浪费 |
|---|---|---|---|
| `read_files` | 7,845 | 4,696 万 | 已是 raw 纯文本，基本无浪费 |
| `search_files` | 9,680 | 3,877 万 | 每条命中重复完整路径 + `"lineNumber"` / `"line"` 键 + `\n` 转义 |
| `run_command` | 16,854 | 2,134 万 | 只有 28%（4,727 次）传了 `format:"raw"`，其余走 JSON，换行与引号都要转义（转义序列约占 6%） |
| `batch` | 997 | 829 万 | 子结果 JSON 套 JSON，**转义序列占 20.9%** |
| `wait_command` | 2,248 | 214 万 | 每次带一段完整状态 JSON 和固定的长中文 note |

示例：一条搜索命中 `{"path":"D:/AItool/winapp/cc-bridge/desktop/src-tauri/src/diff_utils.rs","lineNumber":5,"line":"const HUNKS_MAX_BYTES: usize = 4096;\n"}` 约 140 字符，内容只有 38；内置 Grep 写法 `diff_utils.rs:5:const ...` 约 60 字符。

并行情况：含 cc-bridge 调用的 50,992 次请求里，9,264 次（18%）一次并行发了 ≥2 个 cc-bridge 调用——模型已会并行，batch 次数少不等于往返多。

#### 2.7.1 方案（按收益排序）

全部保留旧格式：传 `format:"json"` 仍拿到改造前的 JSON，功能不变。

| 序 | 项 | 改法 | 预估收益 |
|---|---|---|---|
| A | **搜索结果改 grep 风格纯文本** | `search_files` 默认按文件分组，路径只写一次，下面每行 `行号:内容`（上下文行用 `行号-内容`）；截断/省略说明放末尾一行 | 每条命中约减半；搜索是第二大来源 |
| B | **命令输出默认 raw** | `run_command` / `wait_command` 默认 `format:"raw"`；状态块只留一行（exitCode、是否仍在运行、被省略行数），输出不转义 | 命令类返回约 −10%～15% |
| C | **batch 子结果不再 JSON 套 JSON** | 每个子操作的 content 块原样作为独立文本块返回，前面加一行 `#序号 工具名 ok/失败` | batch 返回 −20% 以上 |
| D | **省掉默认值字段与固定提示** | `ok:true`、`UTF-8`、`LF`、`replacements:1`、`terminated:false`、`outputComplete:true` 等正常值不输出，异常时才出现；wait_command 超时 note 缩成一句 | 每次几十～百余字符，按调用次数累计 |
| E | ~~**list_allowed_roots 按需内联规则**~~ **已取消** | 实测 323 次调用，每次返回中位 657 字符、平均 1,453、最大 11,927；每会话只调一次，比每趟都重发的大头小两个数量级，不值得动 | — |
| ~~E-原方案~~ | **list_allowed_roots
| F | **减少工具延迟加载往返** | Claude Code 延迟加载 MCP 工具，每会话至少多 1 趟 ToolSearch（§2.6.3 实测约 1.1%）；评估精简工具描述、合并低频工具能否让核心工具不被延迟 | **先验证**客户端延迟加载的触发条件 |

**已不用再动**：读文件（已比内置 Read 省）、命令输出上限（与 Bash 持平）、工具描述长度（在缓存里）。

**实施建议**：A～D 都是返回格式改动、有 `format:"json"` 兜底，可一次做完一起过门禁；每项都要配「默认是新格式、传 json 逐字节等于旧格式」的守卫测试。注意审计口径：`result_text_bytes` / `result_wire_chars` 统计的是 text 块，格式变化后与旧日志不可直接对比，验收仍按 §2.6 的「下一请求上下文增量」口径。E 已取消，F 先验证，G 单独排期。

**进度（2026-11-25）**：A、B 已改完（搜索默认 grep 风格纯文本；run_command / wait_command 默认 raw，batch 内仍保持 json），D 只做了两处（改文件返回省掉替换 1 处 / UTF-8 / LF 三个默认值；wait_command 超时提示缩成一句），`ok:true` 因 batch 与测试依赖未动；门禁全过（单测 1387），未提交。**C 未做**：batch 返回是带预算层、占位替换、审计记账的整体，改成多文本块等于重写这一层；建议先用新版重新统计 batch 转义占比（原 20.9%），降到 10% 以下就不做。

#### 2.7.2 G 的方案

**现状**：界面里已经有上下文占用条（`ContextMeter.tsx`），上下文超过 80%（`CONTEXT_WARN_RATIO`）时只在鼠标悬停提示里写一句「可发送 /compact」。所以 G 不是从零做，而是补两件事：

1. **本地 GUI 会话**（数据来自 CLI 上报的 modelUsage）：把悬停提示升级成可见提示——上下文 ≥ 60% 在条上变色，≥ 75% 弹一句话并给「压缩」按钮（点击等于发送 /compact），提示里写明「压缩本身也要重读一遍整段上下文」。不自动触发。
2. **远端 Claude Code 接入（本文主要场景）**：界面看不到远端会话的上下文，这条链路目前没有任何提示。思路：服务端按 MCP 会话累计已经返回的工具结果字节数（上下文增量的下限），越过阈值时在返回里附一句话，提醒用户压缩或开新会话。每个阈值只提醒一次，避免提示本身反而在耗 token。**2026-11-27 已核实，结论：这条在现有协议下不可行**。现代协议（2026-07-28）没有协议级会话，没有 MCP 会话 id 可用；Claude Code 对 HTTP 服务器默认协商的正是这个版本。服务端能拿到的只有来源 IP + clientInfo（客户端级，不是对话级），同机并行的多个终端会话会被混在一起。建议删掉本条，只保留上面第 1 条（cc-bridge 内嵌 CC 会话的提示）。详见《MCP-Skills与Tasks适配评估》「遗留核实项结论」。仍未实证的：客户端是否在请求头里带了别的会话标识（探针已加请求头名称记录，下次真机可看）。阻塞阈值的取值题随之不再需要。

#### 2.7.3 MCP Skills / Tasks 对 token 的影响

详见 `docs/MCP-Skills与Tasks适配评估-2026-11-25.md` §八之二。结论：**Tasks 的收益更确定**（去掉 `wait_command` 轮询往返，约 2.6%，按 §2.6.3 的实测）；**Skills 直接省的很少**（说明文字命中缓存后只占约 0.25%），价值在把「怎么用才省 token」写透。错误地以为 Skills 能明显省上下文，会重踏§2.4 已排除的“工具描述瘦身”的坑。该评估中的版本号、规范编号尚未用官方资料核实。

## 三、为什么「远端 + cc-bridge」比「本地 Claude Code」贵

| 维度 | 本地 Claude Code | 远端 + cc-bridge | 差在哪 |
|---|---|---|---|
| 工具结果兜底 | Bash 大输出落盘只给摘录；Read 有 2,000 行 / 25k token 上限 + PARTIAL view | 上限更宽：`run_command` 默认 **32KB**（`DEFAULT_RETURN_LIMIT`），`read_files` 45,000 字符才拒 | 单次可多灌 4–8 倍 |
| 上下文收口 | 会话短、随手 `/clear`，撞墙前先 compact | 会话常驻，实测平均基数已到 **228k** 还在继续 | 基数被抬高一个量级 |
| 往返 | 同上，但每趟便宜（本地无网络往返） | 每趟都是完整上下文 + 隧道/网络往返，且被提示层主动加次数（后台+wait、通知） | 次数 ×1.2–1.3 |
| 工具面 | 只有内置工具 | 内置 + 25 个 MCP 工具并存（`Bash` 1,069 次 / `run_command` 6,972 次），远端拓扑下内置工具打在**错误的机器**上 | 固定块 +2%，误用往返若干 |
| 计费口径 | 官方直连：cache read 按 10% 计 | 走中转：**若上游把 cache read 按 input 计价，账单直接 ×10** | 数字级差异，见 §3.1 |

### 3.1 最可能被误读的一环：计费口径

官方直连 cache read 按 10% 计价，`cacheRead` 在账面上几乎不疼；不少中转/按量平台不支持缓存、或把 cache read 当普通 input 计，**同一份 1.02 亿 cacheRead，两种口径差 10 倍**。

我们的中转日志里 `cacheRead` / `cacheWrite` 是如实记录的（`relay/usage.rs`，§2.1 的数字就来自这里），**可以直接拿去和对账单核**。这是回答「为什么用户觉得多很多」的第一优先动作，不需要改一行代码。

## 四、优化项

分级：**P0 = 收益最大且改动可控；P1 = 收益明确但要动行为；P2 = 正确性/稳定性，收益小**。

### P0-1 远端会话上下文收口

- **现象**：A 显示平均基数 228k，说明会话顶到窗口边缘还在继续跑，每一次往返都在搬满窗口。
- **改法**：GUI 侧基于已有 `ccContextUsage` 的 `contextBar` 口径，在 60% / 75% 两档给提示；到 85% 提供「一键 compact」（向 CLI 发 `/compact` 走现有 `cc_send` 通道，不新增协议）。
- **收益**：这是唯一能直接压乘数一的项。基数从 228k 收到 ~120k，后续每一趟省一半。
- **改动面**：前端提示条 + 一个按钮；Rust 侧无需新命令（若 `/compact` 需要新会话语义，再评估）。
- **风险**：compact 本身是一次全上下文重写 + 摘要输出，**不能**做成自动触发（会变成"为了省钱多花一次 228k"）。只做提示 + 手动，且提示里写明「本次 compact 预计花费」。
- **验收**：A 日志里 `bytesIn` 中位数下降；同一任务的请求数不上升。

### P0-2 压工具返回值（`run_command` / `wait_command`）

- **现象**：`run_command` 占 40% 的结果字节，默认上限 32KB（`output_clip.rs::DEFAULT_RETURN_LIMIT`），模型不传 `limit` 就吃满。
- **改法**：默认降到 **8–16KB**；超限部分**落盘**（复用 `prepare_download` 的票据思路或直接在结果里给文件路径），只回「头 + 尾 + 中段命中关键词的行 + 落盘路径」。
- **收益**：按 audit 的分布，`run_command` 中位远小于上限，但长尾（单次 213KB）是真正的钱。降默认值几乎不影响正常调用，只砍长尾。
- **风险**：错误日志的结尾最有用，裁剪顺序必须是「先过滤、再裁剪」（`output_clip.rs` 已定），且必须给可执行的下一页指令，不能让模型"看不见又不知道去哪拿"。
- **验收**：`audit.log` 里 `run_command` 的 `resultBytes` P95 下降；失败排查场景不出现"AI 反复重跑同一条命令"。

### P0-3 砍掉礼貌性往返与错误拆包

- **现象**：`push_notification` 737 次纯通知往返；`run_command` : `wait_command` = 6,972 : 1,047 的两次调用；`batch` 只有 85 次。
- **改法**（都是文案层，改 `registry.rs` 描述 + `build_instructions`）：
  1. `push_notification` 从「MUST 每次任务后调用」改成「**仅当用户可能已离开窗口时**调用」，并把强制措辞只留给 CLI 类客户端里的"长任务"；
  2. 后台命令改成「一次调用走到底」的表述，明确「已知长任务用 background，随后**一次** `wait_command`；禁止 run → 立刻 wait → 再 wait 的链式轮询」；
  3. `batch` 从"建议"升级为「同一批文件的多步读写**必须**合并」。
- **收益**：粗估请求数 −8%～−12%（通知 2.4% + 拆包与重复等待的一部分）。
- **风险**：通知变少会削弱"远端跑完能提醒我"的核心体验——所以只在对**短任务**放宽，长任务保留强制。
- **验收**：C 口径下 `请求/用户消息` 下降；用户侧无"跑完了没人告诉我"的反馈。

### P1-1 关掉被 MCP 覆盖的内置工具（待验证）

- **现象**：远端拓扑下内置 `Bash` 跑在 **Claude Code 那台机器**上，与本机文件无关；C 里 1,069 次 `Bash` 有多少是误用需进一步查（工具结果失败率整体只有 2.6%，说明多数没报错，但可能"成功地在错误的机器上执行"）。
- **改法**：在接入文档里给出 `--disallowedTools Bash,Read,Write,Edit,Glob,Grep` 的推荐配置，或在 cc-bridge 提供的接入片段里默认带上。
- **收益**：工具块瘦约 7–10KB（≈2k token，缓存后接近 0）+ 减少误用往返。
- **风险**：`--disallowedTools` 的确切语义/是否影响 hooks 与权限需要实测；**不能**给本地 GUI 会话默认开（那里 Bash 是本机的，有正当用途）。
- **验收**：远端接入的会话里不再出现落在错误机器上的 `Bash` 调用。

### P2-1 把 `keyword_hint` 挪出工具描述（缓存稳定性）

- **现象**：`mcp/tools/mcp_proxy.rs::keyword_hint` 会把外挂 MCP server 的工具名清单（上限 `KEYWORD_BUDGET = 1200` 字符）拼进 `mcp_proxy` 的 `description`。清单一变（manifest 刷新、加/删 server），整个 `tools` 块就变，**228k 的前缀缓存整段作废**，按 1.25 倍重写。
- **改法**：清单改由 `mcp_list_servers` 的返回值承载，`description` 退回静态文案。
- **收益**：不是省日常 token，是消掉一次"整段重写"的隐患（发生一次 ≈ 28 万 token 的 cacheWrite）。
- **风险**：模型失去"一眼看到有哪些外挂工具"的线索，可能多调一次 `mcp_list_servers`——需要一次实测确认调用次数没有明显上升。
- **验收**：连续多轮会话里 `tools` 块的 shapeHash 稳定（可用 C 里的 `api-request-shape.shapeHash` 校验）。

### P2-2 诊断面板：把 340 万这个数摊开

- **改法**：在现有「上下文税」仪表（`cc_session/context_tax.rs`）上补两行：**本会话每消息请求数**、**cache read 占比**；并标注「本页面口径含 cache read，与终端状态行不可直接对比」。
- **为什么值**：现在用户报"多很多"但拿不出可比数字，我们只能靠日志反推。有面板之后，"多"能被拆成"基数大"还是"次数多"，也能直接回应用户。
- **风险**：口径写错会被当成新 bug（前作 §1.1 已经踩过一次分母混用）。文案必须写明公式。

## 五、明确不做

| 项 | 理由 |
|---|---|
| 工具描述瘦身 / instructions 压缩 | 合计约 5k token，命中缓存后占 0.25%（§2.4）。属于"看起来最像原因、实际最不值钱"的一类 |
| 会话内重复读去重 | 前作两次复算：剔噪后 2.3% 次数 / 0.10% 字节，结论不变 |
| 换返回格式（Markdown / CSV / TOON） | 官方明确没有一刀切，JSON 重复 key 换来的是可靠解析 |
| 自动 compact | 每次 compact 本身就是一次 228k 级重写，做成自动会让"省钱"变成"多花钱"（§P0-1 风险） |
| 对 MCP 结果做 gzip / 自定义编码 | 客户端不负责解压，MCP 层无此约定 |

## 六、实施顺序与提交切分

1. **先做零代码动作**：拿 A 的中转日志与用户的实际账单对一遍计费口径（§3.1）。如果对不上 10 倍差，本条就是这次反馈的全部答案，后面的改动按正常节奏排。
2. **P0-3（文案层）** — 改动只在 `mcp/tools/registry.rs` 的 desc 常量与 `mcp/http.rs::build_instructions`，一次提交，风险最低，能立刻验证往返次数是否下降。
3. **P0-2（返回上限）** — 动 `output_clip.rs` 的 `DEFAULT_RETURN_LIMIT` + 落盘/摘录路径，需要配"裁剪后仍能拿到下一页"的守卫测试。
4. **P0-1（上下文收口）** — 前端 + 提示，独立提交，可与 3 并行。
5. **P1-1 / P2-1 / P2-2** 各自独立提交，P1-1 先做 `--disallowedTools` 语义实测再定。

按仓库规矩：功能提交与版本元数据分开；`[Unreleased]` 由 `sync-version.mjs` 重建，不手补；Rust 改动必须重编译并过 `fmt --check` / `clippy -D warnings` / `test --no-default-features` 三道门禁。

## 七、验收方法（统一口径，别再各说各话）

同一任务跑两组，取 A 日志：

| 组 | 条件 |
|---|---|
| 对照 | 远端 Claude Code **不接** cc-bridge，用内置工具在本机目录跑（或直接从 C 里挑同规模会话） |
| 实验 | 远端 Claude Code 接 cc-bridge，同任务同模型 |

比四个数，**不比"总 token"**：

1. **请求数 / 用户消息**（乘数二）
2. **每次请求的平均上下文**（乘数一）
3. `cacheRead / (input + cacheWrite + cacheRead)`（确认没打穿缓存）
4. `cacheWrite` 是否出现 >50k 的尖峰（诊断 TTL 与缓存失效）
