# 批 4-1 上下文税仪表 —— 方案

日期 2026-10-25。目标：**在对话页直接回答「这一屏上下文被什么吃掉了」**，并在某次调用已经/即将被客户端整条降级时明确告警。

## 一、验收标准（修正后）

原计划写的是「逼近 32KB 上限时警告『整条将降级为 2KB 预览』」。调研后发现这个表述把两个不同的阈值混成了一个，落地前先拆开：

| 阈值 | 常量 | 谁在管 | 超了会怎样 |
|---|---|---|---|
| 45,000 wire 字符 | `mcp/tools/mod.rs::MAX_INLINE_CHARS` | **我们自己**（工具侧主动裁剪） | 工具自己截断，尾部丢失但结果完整到达模型 |
| 49,823 字符 | 客户端实测门槛（`docs/上下文消耗优化方案-2026-10-22.md`） | **客户端**（我们改不了） | 整条降级成 2KB 预览 ⇒ **模型当轮看不到内容、也不会回读** |

所以「32KB」其实是 `output_clip::DEFAULT_RETURN_LIMIT`，那是命令类工具（`run_command` / `get_command_output` / `wait_command`）自己的裁剪线，跟降级门槛不是一回事。

**修正后的验收标准**：
1. 对话页可见当前上下文的构成分解，按工具名分解到「次数 / 字节 / 估算 token」；
2. 单次调用 ≥ 45,000 wire 字符 ⇒ 标「已顶到裁剪线」（说明尾部被截断了）；
3. 单次调用 ≥ 49,823 字符 ⇒ 标「已被客户端降级成 2KB 预览」（这才是真事故：模型没看到）；
4. 分解之和与上下文总占用能对上，差额显式列出（不藏）。

## 二、口径：三层，不是一个数

```
当前上下文占用（= 余量条那个 used，与 2-1 同源）
├─ 工具结果（经桥）        ← audit.log 里带 ccSessionId 的条目，resultBytes / 4
│   ├─ read_files   5.2K  3 次
│   ├─ run_command  2.4K  5 次
│   └─ …
└─ 其他                    ← used − 工具结果
    系统提示 + 对话正文 + CC 内置工具 + 图片/附件
```

**为什么必须有「其他」这一档**：CC 自己的 Read/Bash/Grep 不走桥，系统提示与对话正文也不走桥。只报工具那一块会让用户以为「工具才吃了 8K，那 40K 是哪来的」。把差额显式摆出来，用户才知道「便宜不了是因为系统提示本身就很贵」。

**为什么不做「本轮」**：验收标准原文是「本轮」。但审计条目只有 `ccSessionId`、没有轮次号，要精确到轮次得给 `CcSession` 加 `turn_seq`（AtomicU64 + 递增 + `AuditEntry.ccTurn` + 旧日志兼容）。调研后判定**不需要**：

- 上下文占用 `used` 是 `modelUsage` 的**累计值**（2-1 已定，`inputTokens + outputTokens`）；
- 工具结果一旦进上下文就**一直占着**（不是每轮清零）；
- 两者都是累计口径，天然对齐。硬切「本轮」反而会让「本轮工具 2K、上下文 40K」这种没法解释的组合出现。

所以本面板叫**「上下文构成」**而不是「本轮消耗」。措辞上不出现「本轮」。

**与 2-6 的关系**：2-6 定死了「工具账 ≈ 对话账的子集，不能相加」。本面板正是把这个包含关系画出来 —— 不是新增一套账，是把已有的两个数放到同一张分解里。沿用同一份 `est_tokens = bytes / 4` 估算口径（`audit.rs::est_tokens`），Rust 侧复用同一个函数，不新造。

## 三、数据源

- 总量：`CcSession.modelUsage`（前端已有，`lib/ccContextUsage.ts::contextBar`）。
- 分解：`audit.log` 里 `ccSessionId == 当前会话 cliSessionId` 的条目。
  - 单条字节 = `result_bytes`（`http.rs` 在 dispatch 后按实际返回文本计，batch 子条目由 `batch.rs` 逐条落）；
  - 单条 token ≈ `est_tokens(result_bytes)`；
  - 入参字节 = `params.len()`（与 `read_usage_report` 同口径）。
- 🔴 **batch 容器只计次数、不计字节**（`is_batch_container`）：容器返回体裹着全部子结果，子条目已各自落过审计，外层再计一次会把同一次调用记两遍。这条在 `read_usage_report` 里已经踩过，新聚合必须复制该判据而不是重写一个。

## 四、查询

新增只读命令 `cc_context_tax(session_id)`：

```rust
pub struct ContextTax {
    pub session_id: String,
    pub calls: u64,
    /// 工具结果合计（字节，不含 batch 容器）。
    pub result_bytes: u64,
    /// 入参合计（字节）。
    pub params_bytes: u64,
    /// 按结果字节倒序、截前 12 名。
    pub tools: Vec<ContextTaxTool>,
    /// 超过降级门槛的条目（最多 20 条，用来告警），倒序。
    pub oversized: Vec<ContextTaxHit>,
}
```

- 复用 `AUDIT_CACHE`（与日志页、用量报表同一份解析缓存），**不新增全量扫描**；
- 过滤在内存里做（`cc_session_id` 不是 `AuditFilter` 的现有维度，且加索引要动日志格式，不值得）；
- 空 `session_id` ⇒ 直接返回空结构（新会话还没 `Init`，前端不要发请求）。

**性能**：对话页只在面板**打开时**查一次 + 每轮 `TurnEnd` 后若面板开着再刷。不做轮询 —— 审计是追加写，轮询会次次缓存未命中、反复重解析 `audit.log`（`read_recent_tail` 头注释专门记过这个坑）。

## 五、UI

**落点：会话条右端的上下文余量条本身变成按钮**。零新增占位 —— 这一行在 700px 窄窗下已经被挤爆过（cwd 都截成 `p...`），再加一个按钮必然挤压。用户看到 `40.2K/200K` 想知道「被什么吃掉了」，点它是最直觉的路径。

浮层（`absolute` + 不占布局，遵既有规矩）：

```
┌─────────────────────────────────────┐
│ 上下文构成           40.2K / 200K   │
│ ▓▓▓▓░░░░░░░░░░░░░░░░  20%          │
├─────────────────────────────────────┤
│ 工具结果（经桥）        8.1K   20%  │
│   read_files            5.2K   3 次 │
│   run_command           2.4K   5 次 │
│   search_files          0.5K   2 次 │
│ 其他                   32.1K   80%  │
├─────────────────────────────────────┤
│ ⚠ 1 次调用超过客户端门槛，已整条降级 │
│   成 2KB 预览（模型没看到内容）      │
│   read_files  D:/big.log    182KB   │
└─────────────────────────────────────┘
```

边界：
- 没窗口（`bar === null`）时，右端那串 token 数字同样可点，面板里不画比例条；
- `used === 0`（还没聊过 / 没收到 `result`）⇒ 面板只显示「还没有用量数据」；
- 工具账 > `used`（/compact 过：旧工具结果已被压掉，但审计还在）⇒ 「其他」显示 0 并提示「压缩前计入的 N 次调用已不在当前上下文里」；
- 没有任何经桥调用 ⇒ 明确写「这条会话没有经桥的工具调用（CC 内置工具不计入）」；
- 降级告警落在**余量条上的一个点**（`drop` 红 / `clip` 琥珀）+ tooltip 数字：原方案写的是「推到流里一条 notice」，实现时改了 —— 那条路要在 `CcPane` 再加一路常驻查询、把结果穿过 `SessionNotices`，改动面更大且与面板重复；警示点用的是同一份 query（同一 `sessionId` 的 key 共享，不会查两遍），效果一样：**面板不打开也能看见「这里有东西被吃掉了」**。

## 六、不改什么

- 不动 `audit.log` 格式、不加字段、不加索引（改格式会让存量日志解析出问题，收益不足）；
- 不动工具侧裁剪阈值（`MAX_INLINE_CHARS` 是防降级用的一层，与本面板是「防」与「报」的关系）；
- 不动 `read_usage_report`（设置页用量表的口径已定，本面板是另一个视角，两者共享聚合规则但不共享函数返回值）；
- 不给审计加轮次号（理由见 §二）。

## 七、落地顺序

1. Rust：`context_tax()` 聚合 + `cc_context_tax` 命令 + 单测（含 batch 容器、超阈、空会话、旧日志无 `resultBytes`）；
2. 前端：`lib/ccContextTax.ts`（分解 / 占比 / 阈值判定 / 文案，纯函数带单测）→ `hooks/useCcContextTax.ts`（懒加载 + 面板开时刷新）→ `ccgui/ContextTaxPanel.tsx`；
3. 接线：`SessionBar` 余量条改按钮（含 `bar === null` 分支）；降级告警走 `SessionNotices`；
4. 门禁：Rust 三项 + 前端四项 + `vite build`；真机核浮层不占布局、窄窗不挤压会话条。
