# 偶发白屏：取证与界面自恢复（2026-11-28）

## 一、问题

用户反馈：软件有很小机率变成白屏，界面上什么都没有，只能托盘右键退出再重新打开。

「很小机率」+「只能重启」这两个特征，指向的不是某一次点击出错，而是**渲染整体失效**：
要么 React 整棵树被卸载，要么 WebView2 的渲染进程已经不在了。这两种修法完全不同，
所以第一步不是猜，而是先让现场能被观察到。

## 二、排查发现的两个事实

### 1. release 版一条日志都不落盘

`main.rs` 用 `env_logger` 初始化，输出目标是 stderr。而 release 构建带
`windows_subsystem = "windows"`，没有控制台，stderr 在用户机器上等于丢进黑洞。
除中转服务（`relay/log.rs`）自己写了文件外，主程序没有任何持久化日志。

结论：这类反馈到手时**零信息**——不知道白屏前一秒后端在做什么，也不知道白屏时
后端是否还活着。

### 2. ErrorBoundary 的位置漏掉了 provider 层

原 `main.tsx`：

```
StrictMode → QueryClientProvider → UpdateProvider → App(ErrorBoundary → AppContent)
                                                      ↑ 只包到这里
```

`QueryClientProvider` / `UpdateProvider` / `ForceUpdateGate` 都在 ErrorBoundary **外面**。
这几个在渲染或 effect 里抛错时，React 会卸载整棵树，结果是**纯白屏**——
连「应用遇到错误」那个兜底页都出不来。这与用户描述的症状完全一致，是本次唯一
可以直接确认为缺陷的一条。

同时全项目没有 `window.onerror` / `unhandledrejection`：事件回调、定时器、
Promise 里抛出的异常，ErrorBoundary 一概看不到，release 下也没人接。

## 三、本次实现（0 + 1 + 2）

用户批准的范围是「证据 + 兜底 + 手动恢复」，**不做自动重载**（第 3 层）。

### 第 0 层：把证据留下来

| 改动 | 说明 |
|---|---|
| `src/logging.rs`（新） | 主程序日志落到 `<应用数据目录>/logs/app.log`，2MB 滚动、保留 2 份旧文件；调试构建下同时写 stderr |
| `logs/ui.log`（同模块） | 界面异常单独一份文件。主日志会被隧道重连、MCP 报错这类后台 `warn` 写入，高频时 2MB 很快被冲掉——界面证据不能被它们挤走 |
| `commands/ui_diag_cmds.rs`（新） | `report_ui_error` 命令，带 30 条/分钟限流（超出只计数，额度恢复后补一句「期间丢弃 N 条」）、字段截断 2000 字符、换行与控制字符压平（防日志错位与伪造） |
| `src/lib/uiErrorReport.ts`（新） | 前端 `window.onerror` / `unhandledrejection` 全局捕获 + 60 秒同签名去重；上报本身失败时**静默**，不给界面制造第二个问题 |

日志初始化放在 `main()` 第一行（要接住 setup 之前的 panic）。那时还没有 `AppHandle`，
目录按 Tauri 同一套平台规则自己推导；`setup` 里拿到真实 `app_data_dir()` 后调
`logging::confirm_dir` 复核，不一致会记一条 `warn`——拼错目录等于「写了但用户找不到」。

### 第 1 层：白屏变成可自助恢复的错误页

- `ErrorBoundary` 提到 provider 外层，包住整条链。
- `main.tsx` 里 `createRoot(...).render(...)` 外套 `try/catch`，失败时用**纯 DOM + 内联样式**
  写一个「界面没能正常加载 / 重新加载」的兜底页（不依赖 Tailwind，也不依赖任何组件——
  能走到这里说明渲染本身已经不成立）。
- `#root` 缺失时不再用 `!` 断言硬崩，而是上报一条「前端页面结构未正确加载」。
- `ErrorBoundary` 的 `componentDidCatch` 同步上报（含 `componentStack`）。

### 第 2 层：托盘里加「重新加载界面」

位置紧跟「打开面板」。它只重建 webview，后端（PTY / MCP / 隧道 / 中转）全程不动，
所以比「退出重开」轻得多：SSH 会话还活着、不会断，只是**终端画面会清空重绘**
（前端 xterm 实例重建，已有输出不回补）。这一点写在菜单文案里说不下，需要时告知用户。

两个细节：

- **先 `show_or_create_main_window` 再 reload**：它还负责复位「不可见」标记并发
  `app:visibility=true`。少了这一步，重载后的界面会以为自己仍在后台，轮询与动画全停，
  看着还是「死的」。
- **窗口已被销毁时只重建、不再 reload**：重建分支本身就是完整重载。
- 强制更新期间也保留该项。它不绕过遮罩（重载后 `ForceUpdateGate` 会重新盖上），
  但界面若白屏，用户连更新按钮都点不到——去掉这项等于把人锁死在白屏上。

## 四、下次白屏怎么取证

日志位置（Windows）：`%APPDATA%\com.ccbridge.desktop\logs\`

| 文件 | 看什么 |
|---|---|
| `ui.log` | 白屏前最后的界面异常。有 `ErrorBoundary` / `bootstrap` 记录 ⇒ 代码 bug，按栈修 |
| `app.log` | 白屏前后后端在做什么（隧道重连、MCP、更新） |

**关键判据**：

- `ui.log` 在对应时刻**有异常** ⇒ 前端代码路径出错，可直接定位到组件与调用栈。
- `ui.log` 在对应时刻**一片空白**、`app.log` 也正常 ⇒ 前端进程根本没机会执行
  （渲染进程崩溃 / 被系统回收 / WebView2 异常）。方向转向内存与 WebView2，
  这正是第 3 层（心跳 + 自动重载）要覆盖的那类。

这两份文件都不会超过 6MB，用户可以直接打包发过来。

## 六、明确没做

- **没有自动重载**（第 3 层：心跳 + Rust 侧检测 + `reload()` + 熔断）。它会不打招呼地
  刷新界面，丢输入框内容与滚动位置，用户暂未批准；等 `ui.log` 证明属于「渲染进程崩溃」
  那类再上，届时门控必须是「窗口可见且未最小化」，否则 WebView2 的后台节流会持续误判。
- **没有压内存**。若证据指向渲染进程崩溃，下一步应查常驻数天后的前端内存增长，
  而不是继续加兜底。
