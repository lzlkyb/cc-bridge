# SSH 钩子注入回显治理方案

> 问题：登录远端后，终端上会打出一段 400+ 字符的 `__ccb_p(){...}` 源码（以及探针一行），
> 用户会以为软件出 bug 了。本文分析根因、对照业界做法、给出方案与推荐。

## 一、根因

注入链路是「往一个活着的 shell 里打字」（`useTerminalOsc.ts`）：

```
t=900ms   发探针 PROBE_CMD\n   ──→ 远端 PTY（ECHO=on）──→ 回显一行
探针回执  发钩子 HOOK_CMD\n   ──→ 远端 PTY（ECHO=on）──→ 回显 400+ 字符 ← 用户看到的
+300ms    发 kick "\n"        ──→ 空回车，多一个空提示符行
```

PTY 的终端行规程（line discipline）默认 `ECHO` 开启，**凡是写进 stdin 的字节都会被回显到屏幕**——
这不是 bug，是 TTY 的本职。代码注释里也承认了这个已知代价（`useTerminalOsc.ts` 文件头
「已知代价」一节）：要彻底消除得改后端建连方式，当时选择了接受两行回显换零后端改动。

**为什么不能靠「掐准时机在提示符出现前发」**：回显发生在行规程层，比 shell 是否开始读还早——
字节一到就被回显，跟提示符出没出现无关。

**为什么不能用「藏进转义序列」的花招**（比如往载荷里塞 SGR 8 隐形属性）：
Linux 行规程默认 `ECHOCTL` 开，控制字符（含 ESC）回显时会被展开成 `^[` 两个可见字符，
转义序列根本活不到终端渲染那一步。readline 自己接管回显后同样显示 `^[`。此路不通。

## 二、业界对照

| 工具 | 做法 | 是否静默 |
|---|---|---|
| iTerm2 / WezTerm | 让用户手动往 rcfile 里贴集成脚本 | ✅ 但要手动装 |
| VS Code Remote | 直接改写远端 rcfile | ✅ 但写文件 |
| Warp SSH | 建连时 exec 一个包装命令 | ✅ 改了建连语义 |
| WindTerm「登录后命令」 | 会话设置里填命令，登录后模拟键入 | ❌ 同样可见 |
| Tabby | 本地 shell 用 exec 包装；SSH 场景键入 | SSH 下可见 |
| cc-bridge 现状 | 键入（探针 + 钩子两段） | ❌ 可见 |

结论：**没有魔法**。彻底静默只有两条正路——① 在 shell 启动前把钩子作为命令上下文带进去（exec 包装 / rcfile）；
② 打完字立刻把回显关掉（stty 舞步）。前者动后端，后者纯前端。

## 三、候选方案

### 方案 A：`stty -echo` 握手 + 前端残渣吞除（推荐 · 纯前端零 Rust）

时序重排（全部走现有 `ssh_input`，改动集中在 `useTerminalOsc.ts`）：

```
t=900ms   发 "stty -echo\n"            （唯一可见残渣：一行 10 字符）
t+250ms   发探针（ECHO 已关 → 静默）
探针回执  发钩子（静默）
+150ms    发 kick 空回车（静默，逼出第一条提示符 → 133;A 到达）
+250ms    发 "stty echo\n"             （静默恢复，舞步结束）
```

**安全网（四条退出路径全部恢复 ECHO，一条都不能少）**：

| 路径 | 动作 |
|---|---|
| 用户在窗口期敲键（typedRef） | 立即发 `stty echo` + 中止舞步 + 判 unsupported |
| 探针超时（非 bash/zsh） | `stty echo` → 走现有 giveUp 降级 |
| 钩子发出后 2s 没等到 133;A | `stty echo` → 降级 |
| 断开/卸载 | PTY 销毁，termios 随之失效，无需处理 |

**残渣吞除（把最后一行也抹掉）**：t0 起 temp 包一层 `term.write`，进入滚动匹配——
精确剥掉回显的 `stty -echo\r\n`（内容完全已知，只会出现一次）；收到 133;A 或 1.5s 超时后
恢复原样透传（fail-open：剥不掉也只是留一行 `stty -echo`，绝不丢用户数据）。

- 优点：零 Rust 改动（不触发 R10 重编译）；不写远端任何文件（守住产品承诺）；
  正常路径完全静默；每一步都有确定性恢复路径。
- 残余风险：echo-off 窗口约 0.6~1s，用户恰在此窗口敲键会短暂看不到自己敲的字
  （会话刚建立、用户盯着 banner 时概率极低；且敲键即刻触发恢复）。
- 工作量：约半天（时序状态机抽纯函数 + strip 匹配器 + 单测 + 手动实测）。

### 方案 B：Rust 侧 exec 包装（彻底静默 · 动后端）

建连时不裸开 shell，改 `request_exec`：

```
PROMPT_COMMAND='__ccb_p;...'  __ccb_p(){...};  exec bash -l     （bash）
precmd_functions+=(__ccb_p);  exec zsh -l                      （zsh，按 $SHELL 分支）
```

钩子作为命令上下文在 shell 启动前就位，字节根本不经过 readline/行规程 → 100% 静默，
还省掉探针/延时整个状态机。

- 代价：R10 重编译；按远端默认 shell 分支；ForceCommand / 受限 shell 服务器会挂；
  登录语义变化（profile 加载顺序、`$SHELL` 探测）；会话建立核心路径改动，回归面大。
- 定位：**P2**。若方案 A 上线后仍有场景不满意（如用户在 900ms 内狂敲键盘），再考虑。

### 方案 C：写远端 rcfile（一次性安装）

VS Code 同款。一次安装永久静默、与注入时机彻底解耦。
**明确排除**：违背产品承诺「只读取、不写任何文件、不动 .bashrc」（`HOOK_CMD` 设计取舍第 1 条），
且卸载/升级钩子版本要处理远端文件生命周期，复杂度不低。

### 方案 D：仅前端吞除（不动 stty）

要剥 400 字符载荷的回显，还得处理 readline 模式下 ESC→`^[` 变体、自动折行、与 MOTD 交错……
匹配器又长又脆。被方案 A 吸收（A 只需要剥一行 10 字符）。

## 四、推荐与实施清单

**推荐方案 A**，分两步交付：

1. **第一步（必做）**：stty 舞步时序重构——`useTerminalOsc.ts` 里把「探针 → 注入 → kick」
   改成上表时序；时序状态机抽成 `lib/` 纯函数便于单测；四条恢复路径写死。
2. **第二步（打磨）**：残渣吞除——write 包装 + 已知行精确匹配，测试覆盖
   「分片切割」「与 banner 交错」「完全缺席」三种分片形态。

验证：真实远端手测（bash + zsh 各一台）；断网中途断开、900ms 内狂敲键盘两个对抗场景；
单元测试跑 strip 匹配器与时序状态机；四项门禁照常。

## 五、不做的事

- ❌ 不写远端 rcfile（方案 C，违背产品承诺）
- ❌ 不用转义序列藏回显（ECHOCTL 下行不通，见第一节）
- ❌ 不做「检测到提示符再注入」——回显在行规程层，与时机无关，治不了本
