## 二、通道选择（不要改回 scp 读内容）

- **列目录只走 russh**（`ssh_sftp_list` → `russh_list_dir`，2026-11-24 起不挂任何降级，详见第十一节）；读一个小文件仍走 helper（常驻会话，零握手），再单独 scp 握手是白付一次 TCP + 认证。
- **读走 helper**：用 base64（PTY 会吃掉原始字节里的控制字符，base64 全是可打印 ASCII，天然抗 PTY）。
- **写有三条路径**（按优先级）：① russh 长连接 SFTP（无 PTY、无命令行，权限位/临时名唯一性都已修，见下）② helper 分块写（base64 ≤128 KB 时）：把 base64 拆成多条 ≤3600 字节的短行 `printf` 进 `.ccb-write-<序号>.part`，最后一条小命令做「校验长度 → base64 -d → 冲突检测 → chmod → `os.replace`」 ③ scp 上传 part + 同一个小 finalize（大 payload 或 helper 不可用时）。三条路径共用同一个 `finalize_script`，冲突锁 / chmod / 原子 rename / 失败清场语义完全一致。
- 为什么远端用 python3 而不是 `head -c | base64`：要同时拿到 size/mtime、按字节截断且不劈坏多字节字符（截断点的 UTF-8 判定在 Rust 侧 `encoding::decode_utf8_truncated`，russh 与 helper 旧路径共用同一个函数）。项目本就依赖远端 python3（stable_remote 整套）。
- helper 起不来（禁 shell / MaxSessions 满 / 无 `/bin/sh`）时 `remote_exec` 退回一次性 ssh，用 `printf '\n__CCB_RC_%d__\n' $?` 把退出码缀在输出末尾，从而和 helper 一样能区分「命令失败」与「ssh 本身失败」。

## 三、哨兵协议（前后端契约，改动必须同步）

读：`__CCB_F_META__{"size":N,"mtime":N,"truncated":bool}` / `__CCB_F_ERR__<msg>`
写：`__CCB_W_OK__{"mtime":N,"size":N}` / `__CCB_W_CONFLICT__<mtime>` / `__CCB_W_ERR__<msg>`

- 常量在 Rust 侧：`ERR_FILE_CONFLICT` / `ERR_FILE_BINARY`；前端 `useRemoteFileEdit.ts` 里有对应字面量。
- 🔴 **前端判类别必须用 `cleanErr(e).includes(marker)`，不能 `startsWith`**：错误被包成 `Error` 对象时 `String(e)` 会多一个 `Error: ` 前缀，`startsWith` 静默失效 ⇒ 冲突条不出现、用户只看到看不懂的 toast。有两条回归测试守着。
- `__CCB_F_ERR__` 的 `<msg>` 内容 2026-11-24 起会带归属诊断后缀（EACCES 时，见第十二节）；协议形状（前缀 + 行余部）不变，前端原样展示。

## 四、安全与数据边界

- 全部经 `ssh_enabled` 总闸；只经 Tauri IPC 给本机面板，**不注册为 MCP 工具**、不进审计、不向远程 Claude Code 暴露。
- 凭据明文仅在登录一瞬存在（`PendingCreds`）。
- 写回乐观锁：`expected_mtime != 0 && !force` 时比对远端 mtime，不符返回 `CCB_FILE_CONFLICT`。**不做二次确认弹窗**（R17）——冲突渲染成内联条，给「重新加载 / 仍然覆盖保存」两条出路，且不丢用户手上的修改。
- 临时文件落**同目录**（保证 rename 不跨文件系统）；失败分支清场，绝不把原文件写成半个。
- 本机临时副本：`%TEMP%\cc-bridge-edit\<连接id>\<文件名>`，按连接隔离，文件名剔 `/` `\` 防逃逸。
- 上限：内联编辑 2 MB（`MAX_EDIT_BYTES`，base64 后约 2.7 MB）；读取也以 2 MB 为限，超出部分截断并在 META 里标 `truncated:true`（读路径的截断点在 Rust 侧按 UTF-8 字符边界退让，`decode_utf8_truncated`：只原谅尾部被劈坏的多字节字符，中部非法字节仍判二进制）。二进制与超限都把「用本机编辑器打开」作为出路交回用户。

## 五、CodeMirror 集成的坑

- `value` 由 `updateListener` 单向流出；外部写入用单独 effect 先比 `view.state.doc.toString()` 再 dispatch，否则和用户正在敲的输入互相覆盖。
- `onChange` / `onSave` 必须存 ref：写进 extensions 会让每次渲染重建编辑器，丢光标与撤销栈。
- 主题用 `EditorView.theme(..., { dark })`，颜色取 `hsl(var(--*))`，跟着 `useThemeMode()`；语法高亮仍用 `defaultHighlightStyle`（深色下对比度略弱但可读，不值得为此引整套 one-dark）。
- 语言包按子路径导入 `@codemirror/legacy-modes/mode/*`，vite 只打包用到的 mode。`dockerfile` 的导出名是 `dockerFile`（驼峰）；该包自带类型，**不要写 `@ts-expect-error`**（会报 TS2578）。
- TerminalTab chunk 因 CodeMirror 涨到约 1.4 MB（gzip 479 KB），随路由懒加载，暂不做动态 import。

## 七、批量传输：多源 scp 合并（2026-11-17 追加）

单文件链路（列目录/读/写）早已零握手，唯独传输是「一个文件一次 scp 进程 = 一次完整
TCP+认证握手」。批量选 20 个文件就是 20 次。改用 scp 原生多源能力合并：

- **后端 `commands/ssh_batch_cmds.rs`**：`ssh_sftp_get_many` / `ssh_sftp_put_many`。
  按目标目录分组（下载按 local 父目录、上传按 remote 父目录——scp 多源只有一个
  target 目录，不同目录的条目不可能进同一次 scp），每组一次多源 scp。
  `-s`（SFTP 协议）优先，报「未知选项」才回退 legacy。
- **原子语义不丢**：下载先传到本地隐藏临时目录 `.ccb-batch-<传输id>/`，全部成功后
  逐个 rename 到正式名；上传先传到远端同名临时目录，成功后 `mv -f` 搬回，
  失败/取消 `rm -rf` 清场。取消/失败绝不碰用户原有的文件。
- **上传收尾走 helper**：`run_via_helper_blocking`（`ssh_cmds.rs`，async 热路径不动，
  两版逻辑逐行对应）；helper 不可用退回一次性 ssh。
- **覆盖一次问完**：下载由后端预检清单一次报 `CCB_TARGET_EXISTS`；上传沿用
  「同名一次问完 + skip」。批量下载的交互相应改为**一次目录选择 + 一次传输**
  （多源 scp 的 target 是单一目录，逐个另存为就失去合并意义）。
- 前端结构：传输态核心 `useTransferCore.ts`；批量编排 `batchTransfer.ts`（纯函数，
  core 作参数注入）。`useSshTransfer.ts` 303 → 126 行，移出体量 BASELINE。

B 方案（`ssh -s sftp` 长连接 + 手写 SFTP v3）已做可行性验证并**否决**，报告见
`docs/B方案验证-2026-11-17.md`：ConPTY 双向二进制不安全且无 raw 机制；askpass 虽成立
但密码要落盘；且 `run_scp` 早就在用 `scp -s`，B 的增量只剩「一条连接多次操作」，
而多源合并用零协议代码拿到了同一收益。

## 八、PTY 单行上限与三条写路径（2026-11-24 追加）

🔴 **PTY canonical 模式单行上限 4095 字节**（Linux termios：单行上限 4096 字符含结尾
换行，超出部分被内核静默丢弃；`stty -echo` 只关回显不关 canonical；helper 用 `-tt`
强制分配 PTY ⇒ 写进去的每一行都受此限）。

- **病灶**：旧 `write_script` 把整个 base64（最大 2.7 MB）作为**一行**写进 PTY ⇒ 约
  2.4 KB 起被内核截断 ⇒ 远端 sh 卡在半句话里等输入 ⇒ 15s helper 超时 + 一次性 ssh
  重握手（保存转圈约 26 秒）；payload >约 24KB 时一次性 ssh 的命令行还超 Windows
  32767 字符上限 ⇒ 保存直接失败。
- **修法**：`write_script_chunked` 按 `budget = 4095 - 96(哨兵) - 19(printf 骨架) -
  part 路径长度` 且 ≤3600 切片，逐行 `printf '%s' '<chunk>' >/>> part`；part 名
  `{path}.ccb-write-{next_write_seq()}.part`（序号全局递增，修掉「长驻会话 pid 恒定
  导致临时名碰撞」的隐性回归）。budget <1024（路径过长）直接放弃改走 scp。
- **`finalize_script`**（三条路径共用）：读 part → 长度校验 → `b64decode(validate=True)`
  → **写回 part**（🔴 曾丢失，见 §九）→ 冲突检测 → chmod（**包独立 try，失败 pass**：对齐
  russh/旧路径「权限位尽力而为」）→ `os.replace`（外层再包 try）→ replace 成功后 stat
  失败降级 `__CCB_W_OK__{"mtime":0,"size":0}`（不谎报失败）。每个错误分支都 `cleanup()` 清 part。
- **已知取舍**：helper 会话分块写到一半死掉会残留一个带唯一序号的 `.ccb-write-<序号>.part`
  （可手删，不会互相覆盖）；scp 路线无此缝隙（上传失败与 finalize 传输失败都补 `rm -f`）。
- 单测断言「每条物理行 ≤4095」「分块拼回逐字一致」「finalize 排在所有分块之后」；
  生成的远端 python 脚本用 `py_compile`、shell 用 `sh -n` 做过真语法校验。

## 九、软链写破坏修复 + 执行级语义测试（2026-11-24 追加）

### 9.1 病灶：保存软链文件会**替换掉链接本身**

`os.replace` / `mv` / SFTP `rename` 都**不跟随目标 symlink**。编辑软链文件时读的是目标
内容（open 跟随链接），但旧写路径把新内容 rename 到**链接路径**上——链接本身被换成普通
文件：真正的目标没改、链接静默消失、保存却显示成功。vim / nano / VS Code 的语义都是
「编辑软链 = 编辑其目标」。

- **russh 路线**：`russh_write_file` / `russh_upload` 在 tmp 计算**之前**先
  `resolve_rename_target`（lstat 判形态 → 是软链才 `canonicalize`；解析失败/不存在 ⇒
  **拒绝保存**，绝不回退「替换链接」）。tmp 必须与落点同目录（软链指向别的文件系统时
  rename 会 EXDEV），所以解析必须赶在 tmp 之前。
- **helper 分块 / scp 路线**：`finalize_script` 内插 `symlink_resolve_py` 片段
  （`os.path.islink` → `os.path.realpath` → 目标不存在则删 part + `__CCB_W_ERR__`
  拒绝）。片段**自包含**（自己删临时文件，不依赖调用方的 `cleanup()`：两个调用点的
  临时变量名不同，靠隐式契约迟早出一个只在错误路径触发的 NameError）。
- **C 路线回传的 scp 兜底**：原来是 `mv -f {tmp} {dst}`，同型 bug，改用同一片段。
- **不做修的两处**：① `ssh_sftp_put` 的 scp 回退用 SFTP open(O_TRUNC) 写路径，
  **跟随**软链，本就正确；② 批量上传（`ssh_batch_cmds`）的 `mv -f` 是显式覆盖 +
  二次确认的语义，判定为可接受取舍。

### 9.2 列表侧：软链目标类型与 `→ target` 展示

- readdir 是 lstat 语义：软链到目录也报 `is_dir=false`。russh 路径用**跟随软链的
  STAT**（`sftp.metadata`）补 `link_target_is_dir`，与 `read_link` 一并 `join_all`
  并发（约一个 RTT；不并发会在软链密集目录比旧路径 `ls -la` 还慢）。
- 前端 `SshFileRow`：`effectiveIsDir = isDir || (isSymlink && linkTargetIsDir)`——
  软链到目录可进入（readdir 本身跟随链接），软链到文件按普通文件走（单击选中、
  双击进编辑器）；行内展示 `→ {linkTarget}`。`SshFileEntry` 新增
  `linkTarget` / `linkTargetIsDir`（可选字段，旧 `ls` 路径不补 `linkTargetIsDir`，
  恒 false——分歧已文档化：那种环境下软链到目录点不进去，需从目标或其父目录进）。
- `parse_ls` 把 ` -> target` 后缀从 name 里拆出（旧路径零额外开销，目标就在输出行里）。

### 9.3 🔴 执行级语义测试逮到的第二个 bug（base64 写回丢失）

子串断言（`s.contains(...)`）证明不了「脚本跑起来是对的」。本次对生成的远端 python
做了**真执行**校验（临时目录建真软链、真跑 finalize 脚本），当即发现：
`data=base64.b64decode(...)` 之后**没有任何写回**，part 里躺着 base64 原文被直接
rename 成目标文件——用户存什么进去、读出来就是 base64 串。HEAD 旧脚本是
`f.write(data)` 后再 rename；part 化重构把这步丢了，而所有单测都是子串断言所以全绿。

- 修法：`finalize_script` 的 `if {is_b64}:` 块内，decode 成功后 `f.write(data)`
  写回 part（失败走 cleanup + `__CCB_W_ERR__`）；scp 路线（`is_b64=false`，part 里
  是原始字节）整段跳过。
- 回归断言：`decode_at < write_at < replace_at`（顺序），`if True:` / `if False:`
  （分支开关）。变异验证：删掉写回块 ⇒ `finalize_script_has_lock_atomic_replace_and_cleanup`
  变红；把解析片段退化成 `t={path}` ⇒ 三条软链测试全红。
- **教训**：生成的远端脚本属于「执行级语义」，`py_compile` + `sh -n` 只验语法；
  关键路径要么真跑（本地建软链即可复现绝大多数语义），要么明确记录「未执行验证」。

## 十、GBK 编码支持（2026-11-24 追加）

### 10.1 动机与范围

面板原来只认 UTF-8：GBK/GB18030 文件（国内服务器上极常见）打开即
`ERR_FILE_BINARY`，只能「用本机编辑器打开」。而 `encoding.rs` 的 GBK 探测 +
round-trip 守卫早就存在，只服务 MCP 本地工具——面板没接上。

本批只做内联编辑链路（`ssh_file_read` / `ssh_file_write` / russh 读写）。
**明确不做**：终端输出 GBK（`ssh_output` 另一套解码，另立批次）、MCP 本地工具
（已完备）、C 路线回传（本地编辑器自管编码、scp 原样回传字节，天然保真）、
UTF-16/BOM 显式支持（GBK 无 BOM；非 ASCII 的 UTF-16 被 `is_binary_content`
拦下，ASCII-only UTF-16 走 UTF-8 路线的既有行为不变）。

### 10.2 两个公共纯函数（`encoding.rs`，消除四份重复逻辑）

- `decode_panel_text(bytes) -> PanelText { text, encoding, crlf }`：
  **UTF-8 优先，GBK 兜底**。UTF-8 路线复用 `decode_utf8_truncated`（容忍尾部
  截断）；GBK 路线用流式 `Decoder` + `last=false`（尾部不完整序列被扣住），
  且**先过 `is_binary_content` 守卫**——GBK 几乎能无损解码任何双字节序列，
  不拦会把 PNG/EXE 当文本打开、保存后把乱码永久写回远端。UTF-8 路线不加
  守卫（合法 UTF-8 但含 NUL 的文件今天就能打开，本批不改这个语义）。
- `encode_panel_text(content, line_ending, label)`：`label_to_encoding`
  白名单校验 → 按原编码 + 原换行编码 → 面板版 round-trip 守卫。

### 10.3 四个踩过/避开的坑

1. 🔴 **探测顺序不能反**：多数 UTF-8 中文恰好也是合法 GBK。反序会把 UTF-8
   文件误标 GBK——虽无损（GBK 编回去字节一致）但状态栏对用户说谎，且探测
   规则一微调就会真损坏文件。`decode_panel_text_prefers_utf8_over_gbk` 守着。
2. 🔴 **GBK 流式解码的输出容量必须按 `max_utf8_buffer_length_without_replacement`
   预留**：GBK 双字节最多产出 3 字节 UTF-8，按 `bytes.len()` 预留会在解到约
   2/3 处静默返回 `OutputFull`、**丢掉剩余输入**——表现是「GBK 文件只解出
   前半段」而返回值又不是 Malformed，上层完全看不出。实际踩过：8 字节输入
   要 12 字节输出，第 3 个汉字起整段消失。
3. 🔴 **面板的 round-trip 守卫不能直接用 `encode_text` 的**：后者用
   `normalize_newlines` 比对（孤立 CR 也抹成 LF），而面板读路径**不**归一化
   孤立 CR。拿来主义会把「能打开却存不回去」的孤立 CR 文件误判成不可编码。
   面板版守卫只认 CRLF→LF，两处规则差异必须一直保持。
4. 🔴 **守卫比对必须用 `decode_without_bom_handling`**：面板把 BOM 当文本
   内容带着走，带嗅探的 `decode` 会剥掉 body 开头的 UTF-8 BOM，守卫于是永远
   对不上——带 BOM 的 UTF-8 文件会被误判「无法编码」而存不回去。

### 10.4 命令层与前端接线

- `RemoteFileContent` / `RusshReadResult` 加 `encoding` 字段（"utf-8"|"gbk"），
  两条读路径换用 `decode_panel_text`（重复解码收回一个函数）。
- `ssh_file_write` / `russh_write_file` 加 `encoding` 参数；**MAX_EDIT_BYTES
  检查移到编码之后**（GBK 编码后比 UTF-8 表示短，按 UTF-8 长度判会误杀）。
- 前端：meta 带 `encoding`，save 原样带回；`SshFileEditorStatus` 把写死的
  `<span>UTF-8</span>` 换成 encoding prop（未知标签原样显示，不吞成 UTF-8）。

## 十一、列目录去掉降级兜底（2026-11-24 追加）

### 11.1 病灶

用户实测：「正常情况下很快，遇到没有访问权限的文件夹就会进入兜底很慢」。
原 `ssh_sftp_list` 是三级链：

1. `russh_list_dir`（russh 长连接，零握手）
2. 常驻 helper `ls`（零握手，含 GNU→BSD 重跑）
3. 一次性 ssh `ls`（`spawn_capture_off_runtime`，**完整 TCP+认证握手，秒级**）

russh 一失败就**静默**下掉（调用方只看到一个 Err，回退不可观测）。
无权限目录命中第③级：换 `ls` 问同一台服务器还是被拒——sftp-server 与
shell 查同一套 Unix 权限，答案必然相同——第②③级纯属白付。

### 11.2 改法

- `ssh_sftp_list` 只调 `russh_list_dir`，失败即返回；helper / 一次性 ssh
  两级整条删除，`find_ssh` 前置检查也去掉（russh 内建 SSH 实现，不依赖
  系统 OpenSSH——没装 OpenSSH 的机器现在反而能列目录）。
- 连带删掉因此变成死代码的 `gnu_ls_cmd` / `bsd_ls_cmd` / `parse_ls`
  及其测试；`run_via_helper` / `spawn_capture_off_runtime` /
  `is_unknown_option_err` 仍有其它调用方（`remote_exec`、scp 协议降级、
  批量命令），保留。
- 源级回归 `list_dir_has_no_fallback_chain`：截取 `ssh_sftp_list` 函数体，
  断言不含任何降级调用、且仍走 `russh_list_dir`。needle 运行时拼接防
  `include_str!` 自匹配（`no_fallible_stat_after_rename` 同款教训）。
  变异验证：把 `run_via_helper` 塞回函数体 ⇒ FAILED，已亲眼见。

### 11.3 取舍与边界

- **读/写的 helper 兜底刻意保留**（`ssh_file_read` / 写回 / 回传）：
  那条链零握手不慢；且无权限文件的快速失败依赖它给出可读错误。
- 「initialPath 是文件则回退父目录」的前端逻辑
  （`useSshFileInitialPath`）对 **error 分支**本就成立——`ssh_sftp_list`
  返回 Err 即触发回退，不依赖兜底成功；russh 对文件路径 readdir 回
  Failure 时走的就是这条路。
- 已知代价（要改回来先读 `ssh_sftp_list` 的 doc 注释）：
  russh 建连失败后的 60s 负缓存期内列目录直接报错（原来靠 helper 成功）；
  sftp-server 异常的主机上列目录完全失效（原来能靠 `ls` 兜底）。

## 十二、读取失败带归属诊断（2026-11-24 追加）

### 12.1 病灶

用户报「文件编辑出错，读取失败：[Errno 13] Permission denied:
'/home/lizuliang/.claude/own-model.json'，我是有这个权限的」。SSH 实勘
（连上去跑 `id` / `getfacl` / python 直读）结论：文件属 `claude-svc`、
mode 0600，ACL 里**有**给 lizuliang 的授权项但被 `mask::---` 整个剥掉
（`os.stat` 成功——目录有 x；`open()` 被拒——文件读位不开放）。

排查中**唯一有用的信息（属主 / 权限位 / 当前 uid）远端 `os.stat` 一秒
就能给出**，却完全没进错误里，用户只看到一句 Errno 13，只能手工 SSH。
产品侧零服务器改动：服务器权限是用户自己的环境，不在产品方案里——
产品要保证的是「错误自己把原因说清楚」。

### 12.2 改法

- 新纯函数 `read_fail_detail_py(path_lit)`（`ssh_file_cmds.rs`）：插进
  `read_script_py` except 块的 python 片段，仅 EACCES（errno 13）时把
  归属信息拼进错误行（单行，前端原样展示）：

  ```text
  [Errno 13] Permission denied: '/path'（属主 claude-svc，权限 0600；你 lizuliang，不在属组 claude-svc，需属主或 root 放权）
  ```

- 三分支全部由事实推导，不猜：
  ① 文件归你但无可读位 → `chmod u+r`；
  ② 不在文件属组 → 需属主/root 放权（chmod/chown/setfacl）；
  ③ 在属组且组位有 r 却被拒 → POSIX ACL mask 或 SELinux 嫌疑
     （`getfacl` 查看）——正是上面那次事故的形状。
- 🔴 **只丰富 errno 13**：ENOENT/EISDIR 一类附属主信息只会误导
  （「打不开目录」的解不是放权）。
- 🔴 **失败免疫**：整段包在 try 里，任何一步失败（stat 也失败 / 平台
  没有 pwd 模块 / …）都退化成 `d=''`，错误行回到原来的裸文案；绝不
  exit、绝不 raise——诊断信息不许把原始错误搞丢。
- `read_script` 拆出 `read_script_py`（**不**过 shell_quote 的 python
  源）：执行级测试要拿它直接 `python3 -c` 跑，从包好的 shell 命令行
  里反解既脆弱又没必要。

### 12.3 验证

- 纯函数 1 条：片段形状（只丰富 EACCES / 三分支 / 两处 `d=''` 兜底 /
  不 exit 不 raise / **每行都有前导空格**——首行顶格会 SyntaxError，
  那会让整个脚本跑不起来，比不诊断更糟）+ 接线断言。
- 执行级 1 条（`#[cfg(unix)]`）：chmod 000 真跑 python3，断言错误行
  带出 `0000` 与「文件归你但无可读位」；可读文件必须照常出 META。
  Windows 门禁编译不进去，靠 CI（macOS）跑；没有 python3 / root 身份
  自动跳过。
- 本机补充（Windows python，`ast.parse` + 假 `os` 六场景）：语法通过；
  归你 / 不在属组 / 属组正常却被拒 / 属组无可读位 / 非 EACCES / stat
  失败——六个场景输出全部符合设计。
- **真机复验**（paramiko 连 10.0.19.194，脚本原样上传、sed 换路径）：
  ① 真实 own-model.json → 「属主 claude-svc，权限 0600；你 lizuliang，
  不在属组 claude-svc，需属主或 root 放权」（pwd/grp 真名解析）；
  ② 自建 chmod 000 → 「文件归你但无可读位，可 chmod u+r 后重试」；
  ③ 可读文件 → META + base64 正常；④ 不存在路径 → 裸错误、不丰富。
- 变异 3 个全部亲眼看到 FAILED：① 摘接线（detail 传空串）⇒ 接线断言
  红；② 删「不在属组」分支 ⇒ 分支断言红；③ 片段首行顶格 ⇒ 缩进断言红。
- 🔴 **教训**：接线断言第一版打在 `read_script`（过过 `shell_quote`）
  的产物上，而 `shell_quote` 把单引号转义成 `'\''`，needle 永远匹配
  不上——**变异验证前必须先确认「还原态的测试是绿的」**，否则变异
  「因错得对」看不出来。这次是全量门禁逮出来的（还原态跑全量才红）。

### 12.4 边界

- 只改**读**路径。写路径（`finalize_script` 的 6 个错误分支）与「用
  本机编辑器打开」的 scp 错误是同形状问题，另立批次。
  → 写路径已于同日补齐，见第十三节。
- 前端零改动：错误串从 `parse_read_output` 原样透到 `cleanErr`（只取
  末 6 行、无截断），全仓没有任何地方对读错误文案做精确匹配
  （`Permission denied` 的匹配全在隧道 / 认证域）。

## 十三、不可读预标 + 写路径诊断 + 诊断复制（2026-11-24 追加）

### 13.1 需求

同一台事故机第二天追问：「其它软件可以看，肯定是我们文件管理的问题，
**不要去改远端环境**」。零服务器改动是硬约束——产品要做的是让用户**在
双击之前**就知道哪些文件打不开，以及打开/保存失败时把原因说清楚。

三件事：

① 列目录带出 `uid/gid/mode`，面板把「你不可读」的条目提前标出来；
② 保存失败（写路径）给同款归属诊断；
③ 错误条加「复制诊断信息」——诊断文案越来越长，手选长文本是纯折磨。

### 13.2 后端

- `SshFileEntry`（`ssh_cmds.rs`）加 `uid/gid/mode: Option<u32>`；
  `attrs_to_entry`（`ssh_russh_file.rs`）从 SFTP attrs 填充，`mode` 复用
  既有的 `perm_bits`（剥掉 `S_IF*`，与 `setstat` 同一形状，前端不必再掩码）。
  `None` = 服务器没给 → 前端**放弃预判**，不猜。
- 新命令 `ssh_file_viewer`（`ssh_file_cmds.rs`）：一条
  `id -u; id -g; id -G`（`remote_exec`，helper 优先/一次性 ssh 兜底），
  `parse_viewer` **从末尾倒取三行**——helper 是长驻 PTY 会话，输出前面可能
  挂 motd 或上一条命令的残留；末尾三行恰好是 uid/gid/组列表，倒推比正推稳
  且不需要哨兵。`id -u`/`-G` 不带 `-r` 即**有效** uid 与有效组集，正是权限
  检查用的那份。注册进 `main.rs`（同一 `ssh_enabled` 闸、仅本机面板）。
- 写路径：新纯函数 `write_fail_detail_py(target_var)`（与
  `read_fail_detail_py` 同取向：只丰富 EACCES、失败免疫、不改控制流）。
  🔴 **stat 的是父目录**：`os.replace` 是 rename 语义，要的是**目标目录**
  可写 + 可进入，与目标文件自身 mode 无关——0444 的文件只要目录可写就能
  替换，而目录 0555 时文件 0666 也换不了。文案必须点明「目标目录」，否则
  用户会去 chmod 文件白费一轮。
- `finalize_script` 拆出 `finalize_script_py`（**不**过 shell_quote 的
  python 源），理由同读侧的 `read_script_py`：执行级测试要拿它直接跑。

### 13.3 前端

- `types.ts`：`SshFileEntry` 加 `uid/gid/mode`（`number | null`），新
  `RemoteViewer { uid, gid, groups }`。
- `utils.ts`：`canReadEntry(entry, viewer)` + `unreadEntryTitle`（纯函数，
  R11）。判定按 POSIX **按类**语义：命中属主类只看属主位，命中属组类只看
  属组位，**不回退**——一个归自己、权限 0004 的文件自己也读不了。
  取向是**宁可漏判不可误判**：缺 mode / 目录 / 软链 / 归属缺一半，一律
  不预标。误判（把能读的标成不能读）会把用户误导去要权限，代价远大于
  漏判（多点一次双击，读失败有归属诊断兜底）。
- `useSshFileViewer(connectionId)`：进面板拉一次；**失败静默置 null**
  （整表不预标）；切连接先清空再拉（避免 A 身份套到 B 的条目上）。
- `SshFileNameCell.tsx`（新文件）：锁图标（warning 色，**替换**文件图标）
  + 「你不可读」徽标 + 名字降弱色 + 完整 title。抽成独立文件的直接原因：
  `SshFileRow.tsx` 已贴 300 行体量门禁，而预标要在这一个单元格里加三处。
  🔴 名字保持可见、下载/删除/双击**一律不禁用**：删除看的是目录 w 位
  （可能成功），双击失败的读路径带同款诊断——预标只负责提前告知。
- `SshFileEditorNotice.tsx`：`errorKind` 区分读/存（顺手修掉一个既有缺陷：
  保存失败原先也显示「读取失败：」，而这段文案是要被用户复制去求助的，
  主体都说错）；保存失败追加「你的修改没有写入，编辑器里的内容还在」
  （先给定心丸再给诊断）；非二进制错误给「复制诊断信息」按钮，复制整段
  含前缀的原文，「已复制 ✓」就地反馈 1.9s（不 toast、不弹窗，R17）。
  剪贴板不可用（无权限/非安全上下文）退回 toast 提示，不静默失败。
