# 外挂 MCP 桥 · 让用户看得出“这东西是干什么的”

> 日期：2026-08-08
> 前提：外挂 MCP 桥第一步（v2.6.0）已落地，见 `mcp-bridge-step1-plan.md`

---

## 1. 问题

导入向导里，一个候选长这样：

```
☐ filesystem     npx -y @modelcontextprotocol/server-filesystem D:\
```

名字是用户（或别人）随手取的，命令是一串 npm 包名。**两者都不回答“它能干什么”**。
用户只能凭名字猜，猜完还得决定要不要把它交给远程。

同样的空白在导入之后依然存在：设置页的服务行、以及**启用前的风险确认框**，
都只有名字与命令。而启用才是真正交出执行权限的那一步。

## 2. 为什么一开始没有

不是漏做了一块 UI。想告诉用户“这是干什么的”，**唯一权威的来源是 server 自己**：
握手时的 `serverInfo`、`instructions`，以及 `tools/list` 里每个工具的描述。
这些 `Manifest` 里都存着，但 `capture()` **需要一条活连接**。

而导入向导走的 `mcp_bridge_scan` 是严格零进程的，这是当初刻意定的——
代码里原话：“而他只是想改个备份目录。启进程只能由 `mcp_bridge_probe` 显式触发。”
一打开设置页就把本机七八个 MCP server 全拉起来，代价与观感都不对。

**所以这是一条约束的直接后果，不是疏忽。** 任何方案都得正面回答它。

## 3. 已定的四个决策

| 决策 | 选定 | 备注 |
|---|---|---|
| 导入前能否启进程 | **能，但必须用户显式触发** | 扫描仍为零进程 |
| 该按钮要不要确认框 | **不要** | 行里已逐字展示完整命令 |
| 展示粒度 | **工具清单为主**，有 `instructions` 则堆在前面 | |
| 范围 | **导入向导 + 设置页** | 探测一次、两处复用 |

关于第二条，记下当时提出的异议以及它怎么被处理的：
该按钮会**真的执行那个程序**，而启用都要过风险确认框，于是出现了一条比启用**更短**的执行路径。
采纳不加确认框的前提是两个补偿（见 §4.6 / §4.7）：按钮文案直说是“运行”，且本次执行进审计。

## 4. 方案

### 4.1 取数据：扫描不变，只加一条显式路径

`mcp_bridge_scan` 一个字不改。新增命令 `mcp_bridge_inspect`：
起进程 → 握手 → `tools/list` → **立刻关掉**，不进连接池。
与现有「探测」按钮（`mcp_bridge_probe`）同款，是已验证过的路径。

### 4.2 存哪里：直接写 `mcp_manifest`，让导入后天然命中

键用候选的**最终**名字 + 指纹。用户导入后，设置页查这张表就已经有数据，
**不需要再探一次**——这是“两处都修”这个范围的主要收益。

孤儿行（探了没导入）是**惰性无害**的：`describe()` 只查配置里存在的 server。
且 `is_stale_for()` 会比指纹，所以日后出现同名但不同配置的 server 时不会误用旧数据。
清理挪到 `mcp_bridge_scan` 里顺手做：删掉「不在配置里且超过 N 天」的行。
零定时器，与 `sweep_idle` 同一个惰性思路。

### 4.3 展示：一套组件，四处复用

有 `instructions` 的先给（截断，可展开全文），然后工具清单：名字 + 一句话。
超过 8 个折叠成「…另 N 个」。数据直接复用 `manifest::compact_index`。

> `instructions` 是 MCP 的**可选**字段，很多 server 不提供；
> 而工具描述是必填项。所以以工具清单为主才能保证任何 server 都有东西可看。

### 4.4 四个落点

| 位置 | 现在 | 改后 |
|---|---|---|
| 导入向导候选行 | 名字 + 命令 + env 键名 | 加「运行一下」按钮与可折叠工具清单 |
| 设置页「探测」按钮 | 只更新工具数与状态 | 展开同一套工具清单 |
| 设置页服务行 | 名字 + 只有工具数的徽章 | 徽章可点开看具体清单 |
| **启用风险确认框** | 只列命令与参数 | **加上工具清单** |

第四处是最该改的：那是真正交出执行权限的一步。现有文案已经写了
「远程将获得这个 server 的**全部能力**」——却从不说那些能力具体是什么。

注：确认框里的清单只在**已探测过**时显示。没探测就不显示，
**不在这里顶起一个进程**：确认框弹出来时用户还没点“确认”。

### 4.5 失败原样透出

起不来 / 超时：直接给错误 + `stderr_tail`（已有机制），
不改写成“探测失败”这种没信息量的话。

### 4.6 按钮文案直说是执行

写「运行一下，看它有哪些工具」，**不写**「查看详情」。
后者会让用户以为只是展开一段已有文字。既然不加确认框，文案就是唯一的事前提示。

### 4.7 审计

`mcp_bridge_inspect` 进审计日志（名字 + 完整命令）。
不加确认框的情况下，**审计是唯一能回答“这个进程当时为什么被启动”的地方**，不能省。

## 5. 两条硬性规则的落点

**规则 7（`.tsx` ≤ 300 行）**：`ImportWizard.tsx` 现 166 行，加折叠区会超。
拆出 `CandidateRow.tsx`；工具清单抽成共用的 `ToolList.tsx`，上述四处 import 同一个。

**规则 8（性能）**：不新增任何常驻循环；每次 inspect = 一次进程起停，
与现有探测同量级；扫描路径完全不变，仍是零进程。
§8.1 的六条检查项不适用（本改动没有新增 `loop` / 周期任务 / 事件消费循环）。

## 6. 刻意不做（YAGNI）

- **不内置常见 server 词典**（filesystem / fetch / github …）。要维护，且一旦词典与
  实际安装的版本对不上号，给出的就是**看着可信的错误信息**。
- **不从命令名推断用途**。同上，而且推断错了比不说更坏。
- **不做“一键全部运行”**。那等于一键启动本机所有 MCP server，正是零进程约束要避免的。
- **不给 inspect 结果做 TTL 刷新**。指纹已经能判失效，再加一层时间维度是多余旋钮。

## 7. 未定 / 风险

- **孤儿 manifest 的 N 天取多少**尚未定。倾向 7 天；它只是垃圾回收，取值不敏感。
- **候选被改名时（`xxx-2`）的键**：写入时用改名后的名字。若用户先 inspect 后取消、
  下次扫描又改成了别的后缀，会多一条孤儿行。无害，由 §4.2 的清理兜底。
- **本特性不改变安全边界**，但确实新增了一条“未经确认框就执行程序”的路径，
  补偿是 §4.6 与 §4.7。这一点写在这里以便日后审视时能直接看到，而不是靠翻会话记录。
