## 一、结论摘要

**一句话定位：单会话的「读」与「信」在第一梯队，多会话的「管」与「可达」在第二梯队上沿。**

- 2026 年头部产品（Claude Code 桌面版 4 月重构、Cursor 2.0、Warp 2.0、Qoder Quest）竞争焦点已经从「对话好不好看」转到**「一次管几路、人怎么插手」**。我们的功能密度追到了这一代的 ~85%，但组织层（旁支对话、长会话规模、按项目分组）落后约一个代际。
- 我们有两处**超出所有对标产品**的能力，而且都不是靠堆功能得来的，而是这套架构天然长出来的：
  1. **审批即审计**（`ApprovalCard` + `ApprovalAuditPanel` + 自动放行规则 + 到期倒计时 + 整组还原）—— 头部产品普遍只有「允许/拒绝」，没有「这次批准改动了哪些文件、之后怎么整组退回去」。
  2. **上下文与成本可视化**（`ContextMeter` + `ContextTaxPanel` + `TurnFooter` 的同口径速度与四分类用量）—— 头部最多给「上下文用了百分之多少」，不给「谁在吃 token」。
- 落后最硬的三块，按「投入产出比」排序：**无障碍语义（几乎零成本、纯漏做）> 长会话规模（无分页无虚拟化）> 旁支对话（形态缺失）**。

### 分档判断

| 档位 | 含义 | 我们处在 |
|---|---|---|
| 第一梯队 | 做得比多数人好，且是可复用的方法论 | 审批链路、上下文成本、渲染分层、详略分档、会话内搜索 |
| 第二梯队上沿 | 该有的都有，缺的是组织与打磨 | 多会话、工具可见性、输入体验、键盘 |
| 明显落后 | 头部已标准化、我们还没有 | 旁支对话、长会话规模、无障碍语义、协作分享 |

## 四、我们确实做对了的（可当对外卖点）

1. **信任链闭环**。审批卡不是「允许/拒绝」二选一，而是带着 diff 行、影响文件、到期倒计时、可成规则的放行、以及事后的审计面板与整组还原。头部产品的审批是**一次性动作**，我们的审批是**一条可追溯的决策链**。这是「给公司内网跑编码代理」这个场景的核心竞争力。
2. **成本可解释**。速度口径剔除工具等待与首 token（否则一次跑三十个 Edit 会印成 13 tok/s）、`cache_read` 单列、`turnSpeed` 有上界防空分母、`afterId` 为空时把脚注挂到流尾。这套口径已经和 `cc-use`/`ccstatusline` 对齐，比大多数商业产品严谨。
3. **渲染分层的工程决定**。不分虚拟化而先做「事件合批 + 块级 memo」是对的：流式期间只有尾巴一块重建，改动面小、可回滚、有同构测试守着（`ccMarkdown.test.ts` 的分块叶子序列对齐）。这比先上虚拟化（滚动锚点、搜索定位、分叉遍历全都要重做）稳得多。
4. **索引与渲染同源**。「搜索说命中 2/5、界面上找得到」这条被当成硬约束写进了代码（`convSegments` 与 `ToolCard` 共用 `toolBodyText`，`reveal` 用派生值而不是 effect 里 `setOpen`）。这条纪律很多开源实现都没有。
5. **三档详略**（v/n/c）与 CC 桌面的 Verbose/Normal/Summary 同构，但我们把「档位只改默认展开态、不改内容是否存在」写成了红线，避免搜索与渲染分叉 —— 这比只做开关更深一层。

## 五、代差一：旁支对话（side chat）

**为什么它是 2026 的分水岭**：长任务跑到一半，人一定有「这个函数返回什么」「这包支持 ESM 吗」这类问题。只有两条老路 —— 打断主线（毁掉上下文），或者不问（丢掉自己的思路）。side chat 是第三条：**能读整条主线，但不写回**。CC 桌面把它绑到 `Ctrl+;` 和 `/btw`，官方明确「主会话学不到任何东西」。

**我们的现状**：`UserMessageBubble` 的「从此处分叉」是**新会话 + 前缀纯文本重放**，它解决的是「换条路走」，不是「顺口问一句」。用户为了问一句去开一条新会话，等于把主线丢了。

**为什么我们其实很容易做**：pane 基础设施、`cc_start` 的 resume、侧栏状态都已经在。旁支只是一条**标了只读语义的 pane**：
- 起会话时把当前主线已知的消息作为前缀（和分叉同一套 `paneForkSeed`）；
- 侧栏/会话条标「旁支」，不参与主会话的归档与标题重算；
- 关键约束：**旁支的消息绝不回流主线**（现在分叉是「原会话不动」，天然满足）。

成本主要不在协议，在**产品表达**（怎么让人一眼看出「这条不会影响主线」），以及要不要允许「把旁支的结论一键摘回主线」（这一步建议**不做**，一旦能回流就退化成普通会话，纪律就没了）。

## 六、代差二：长会话规模

`MessageList` 目前**全量渲染**（无 slice、无窗口化）。这与我们刚做完的「块级 memo」是两个不同的问题：
- 块级 memo 解决的是**单块重算**；
- 全量渲染的问题是**DOM 节点数与常驻内存随会话线性增长**，一次流式仍在整棵树上做 reconcile 的收尾。

一条 800 轮的会话，工具卡 + diff 行 + 高亮代码块是几万个节点。表现不会是「卡死」，而是**切会话时白屏一拍、滚动时掉帧、搜索高亮后回跳位置抖动**。

行业做法（通用 chat 最佳实践 + CC 桌面）是「**懒加载历史**：先给最近 N 条，往上滚再取」。我们是本地库，不需要网络，所以可以更简单：**渲染窗口 + 顶部「加载更早」**。

三个必须同时改对的点（否则会引入新缺陷）：
1. **搜索仍遍历全量**。`convIndex` 是文本索引，不能只索引窗口内 —— 否则「搜得到但屏幕上没有」的老坑会以新形态回来。命中窗口外的消息时，先扩窗口再滚动。
2. **滚动锚点**。加载更早必须保持视觉位置不跳（记录 `scrollHeight` 差）。
3. **分叉与导出遍历的是 `messages`**，不是渲染窗口 —— 这两处不能跟着窗口缩小。

## 七、代差三：无障碍语义（最便宜的短板）

取证：全仓 `aria-live` 只出现在复制按钮、审批详情、Clawd 状态、思考块、输入回执上；**转录区（`MessageList` / `ConversationStream`）没有 `role="log"`、没有 `aria-live`、没有独立的 status 播报区**。

按 2026 年的通行做法，一个 agent 对话界面至少有四件事：

| 要求 | 我们 | 说明 |
|---|---|---|
| 转录区 `role="log"` + `aria-live="polite"` | ❌ | 读屏用户无法知道「有新消息来了」 |
| **不逐 token 播报**，只在「一段完成」时播报摘要 | ❌（因为整块没有） | 直接给 `aria-live` 而不做节流，会让读屏连续念几百次 |
| 独立 status 区播报「正在执行 Read」「等待批准」「已完成」 | ❌ | 这是把「卡住了」的反馈扩到非视觉通道，和我们刚做的 `StreamHud` 是同一件事的两面 |
| 审批卡把「动作 + 目标 + 是否可逆」放进可访问名 | 部分 | 已有到期倒计时与规则说明，但 `aria-live="polite"` 用在详情区，语义上应是 `role="alert"` 或按严重度分级 |

成本极低（一个 `useAnnouncer` + 三个挂点），收益是**从「不可用」到「可用」**，而且顺手解决「视觉之外没有活性信号」这件事。

## 九、明确不该学的

1. **可拖拽任意 pane 布局**。CC 桌面这一代最亮的功能，但我们已否决（批 B），且理由仍然成立：容器查询只能挂 `TabsContent`、浮层一律不占布局、终端 `fit` 一旦被 pane 尺寸牵动就会触发远端 TUI 重排。**不做**。
2. **8 路并行 + 影子虚拟文件系统**。Cursor 靠 SVFS 才敢让多个 agent 同时写一个仓库。我们的多 pane **共享同一个 cwd**，直接抄等于让两个进程互相覆盖文件。要碰这条线，前置条件只能是「每 pane 一个 git worktree」（见 P1-5），而那是另一件事。
3. **factories-as-code / 团队 Drive**。Warp 把它做成了平台，我们的定位是「本机 + 一个远端」的桥，加上去只会稀释。
4. **「自动推荐下一步并一键起后台会话」**。CC 桌面有，但它和我们的「人在环审批」哲学直接冲突，而且用户没批准就烧钱。
5. **虚拟化滚动**（作为第一步）。在 300 行门禁与滚动锚点/搜索定位/分叉遍历三处耦合下，先分页比先虚拟化安全一个量级。

## 十一、一句话给决策

**不要把力气花在「再抄一个头部功能」上。** 我们真正的位置是「给 CLI 编码代理做一层可信的图形外壳」，而 2026 年头部产品在「可信」这件事上普遍比我们薄。P0 那五项（无障碍语义、流式光标、中断态、助手动作区、长会话窗口化）是补及格线，加起来不到两周；P1 的旁支对话是把形态拉到当代；剩下的都是加分项，不做也不掉队。

真正的风险在别处：**多 pane 共享 cwd**。这是我们和 Cursor/Warp 的结构性差异，也是唯一一个「功能越用越顺、事故越攒越大」的地方。它不在本报告的 GUI 范畴里，但值得单独立项。
