## 一、P0 · OSC 52 剪贴板：**现在这条功能是坏的**

### 证据链

**① Claude Code 的复制就是发 OSC 52**（`claude.exe` 内实测字符串）：

```js
// 复制入口，按 mux 类型分支
t(`clipboard: setClipboard mux=${s??"none"} ssh=${n} native=${i} predicted=${lye()} emit=${f} bytes=${e.length}`)
if (s === "tmux")   { let m = `${R0}]52;c;${r}${Vz}`; return m + xI(m) }   // tmux → DCS passthrough 包一层
if (s === "screen") { /* 分片 */ }
return t_(em.CLIPBOARD, "c", r)                                          // 默认：直接发 OSC 52
```

注意它**自己会识别 SSH 与多路复用器**（`ssh=` / `mux=` 已在日志串里），说明这是它跨终端复制的主路径。

**② cc-bridge 没注册 OSC 52**（`desktop/src/hooks/useTerminalOsc.ts:132/143/158`、`hooks/useTerminalProtocol.ts:128`）：

已注册的 OSC 只有 `7`（cwd）、`9`（通知）、`133`（语义提示符）、`1337`（Shell/Git）、`7501`（程序状态）。**没有 52。**

**③ xterm.js 6 也不兜底**：`@xterm/xterm/lib/xterm.mjs` 内 `grep -c 'osc52\|52;c;'` = **0 命中**，核心不实现 OSC 52（需要 `@xterm/addon-clipboard` 或自建 handler）。

**④ 它不会「因为你可能不支持」就不发**（这条最关键，先验证过才敢下结论）。完整决策函数：

```js
async function bk(e){
  let r = base64(e), n = C() /*是否 SSH*/, o = O() /*平台*/, i = false;
  if (!n) { if (o==="linux" && …) await x().probe(); i = St(e) }   // i = 本地有 xclip/wl-copy 等
  let s = HYt() /*mux: tmux|screen|null*/, u = v() /*终端类型*/,
      d = s===null && i && (o==="linux"||o==="wsl") && … && !ALACRITTY_WINDOW_ID && !KITTY_WINDOW_ID && !WEZTERM_PANE,
      f = d ? "none(vte)" : s==="tmux" ? "raw+dcs" : s==="screen" ? "dcs" : "raw";
  log(`clipboard: setClipboard mux=${s??"none"} ssh=${n} native=${i} predicted=${lye()} emit=${f} …`);
  if (d) return "";                        // ← 唯一「什么都不发」的分支
  if (s === "tmux")   { … return DCS 包装的 OSC 52 }
  if (s === "screen") { … }
  return t_(em.CLIPBOARD, "c", r);         // ← 默认：无条件发 OSC 52
}
```

三点结论：
1. **`predicted=` 只进日志，不进任何分支** —— 它不参与决策，所以「预测终端不支持」不会阻止它发。
2. **唯一不发（`d`）的分支要求 `i === true`，而 `i` 只在非 SSH 时才可能为真**（本地 `xclip`/`wl-copy` 探测）→ **SSH 场景下 `d` 恒为 false**，OSC 52 是必然路径。
3. `native` 通道同样只对非 SSH 生效。**远端没有第二条路可走。**

→ 所以不是「可能收不到」，是 **SSH 下必定收不到**。

### 后果（这才是关键的连锁）

TUI 全屏态下**鼠标被应用捕获**（`?1000h`/`?1006h`）→ xterm 的原生拖选失效 → 用户唯一的复制路径就是「应用自己发 OSC 52」。此时：**Claude Code 界面显示「已复制 ✓」，而系统剪贴板一个字都没变。** 用户以为复制成功了，去粘贴却发现是旧内容 —— 这类「静默失败」比报错更伤。

社区已有人写下了完全相同的诊断（wmux 项目源码注释）：

> 全屏 TUI 应用（Claude Code、vim、tmux、neovim…）接管鼠标，拖拽不再产生 xterm 原生选区。用户复制时这些应用无法直接碰系统剪贴板，于是发 OSC 52 请求**终端**代劳。**xterm.js 默认禁用 OSC 52**，所以没有显式 handler 时请求被静默丢弃：应用显示 "copied"，系统剪贴板从未改变。

### 修法（业界统一策略：只开写半边）

| 请求形态 | 含义 | 我们的处理 |
|---|---|---|
| `52;c;<base64>` | 写剪贴板 | ✅ 允许（base64 → UTF-8 → 剪贴板） |
| `52;c;?` | 读剪贴板 | ❌ 拒绝（**这是唯一的泄露面**：远端进程可静默窃取你刚复制的密码/token） |
| `52;c;`（空 payload） | 清空剪贴板 | ❌ 拒绝（不该让应用静默抹掉） |
| 超大 payload（> 1MB base64） | DoS 面 | ❌ 解码前拒绝（别在主线程解几 MB） |

业界默认值（terminfo.dev 实测矩阵）：

| 策略 | 终端 |
|---|---|
| 写允许 / 读禁止（**默认**） | Ghostty、Kitty、Warp、Terminal.app |
| 写读都允许 | iTerm2、VS Code、Cursor（iTerm2/Kitty 新版支持 `read-*-ask`，读时弹确认） |
| 完全关闭 | Otty（opt-in） |

→ 结论：**写半边是行业共识，不是我们擅自放宽。** 且 `51`/`52` 的读半边拒绝要显式写进注释（防将来有人"顺手补全"）。

⚠️ 还有一个必须处理的细节：**handler 必须对「被拒绝的请求」也 `return true`**，否则序列会继续落进其它 handler / 被渲染成乱码。

## 二、Claude Code 只探测 6 项终端能力（我们已答 1 项）

`claude.exe` 里 `.answer(...)` 的**全集**只有 6 个：

```js
function d(){ return {
  extendedKeys:      T(a.terminal, bg),
  synchronizedOutput:_(),
  kittyKeyboard:     E(a.terminal, bg),
  kittyGraphics:     b({ terminal, bgWorker:bg, multiplexed:Boolean(TMUX)||Boolean(STY), forced:CLAUDE_CODE_FORCE_TERMINAL_IMAGES }),
  mousePixels:       y({ terminal, bgWorker:bg, multiplexed:Boolean(TMUX)||Boolean(STY) }),
  programStatus:     g({ bgWorker:bg, tabWritesDisabled:CLAUDE_CODE_DISABLE_TERMINAL_TITLE })
}}
```

| 能力 | 探测方式 | 我们的现状 | 结论 |
|---|---|---|---|
| `programStatus` | OSC 7501 探测应答 | ✅ **已答**（`useTerminalProtocol.ts:131`） | 完成 |
| `synchronizedOutput` | **DECRQM**：`answer(name, status===1\|\|2\|\|3, "probe: DECRPM 2026 status=…")` | ✅ **xterm 6 自动通过** —— 它有 DECRQM 应答（`registerCsiHandler({prefix:"?",intermediates:"$",final:"p"})`）且真的实现了 DEC 2026（`_syncOutputHandler` + `decPrivateModes.synchronizedOutput`） | 无需改动 |
| `mousePixels` | DECRQM 1016 | ✅ xterm 支持 `1016` → `SGR_PIXELS` 编码（用真实像素坐标） | 无需改动（但 Claude Code 还要求 `cellPixels` 已知才会启用，见下） |
| `kittyKeyboard` | 终端名预测 + 探测 | ❌ xterm 6 不实现 kitty 键盘协议 | **保持不答**（见下） |
| `extendedKeys` | 终端名预测 | ❌ 同上（modifyOtherKeys 也未实现） | **保持不答** |
| `kittyGraphics` | 图形查询 | ❌ 只支持 iTerm2 协议（需 `addon-image`），不支持 kitty 图形 | 不答 |

**为什么 kittyKeyboard / extendedKeys 必须保持"不支持"**（这是红线，不是保守）：

1. xterm.js 6.0 实测既不支持 kitty 键盘协议也不支持 modifyOtherKeys（bundle 与源码均 0 命中）。
2. 假报「支持」会让 Claude Code 推 extended-keys 模式，触发 **#38766**：Esc / Ctrl+C 被静默吞掉（2.1.83/84 的系统性事故，2.1.85 才靠恢复白名单修好）。
3. `kittyKeyboard` 的**默认预测值是 `true`**（`var s={extendedKeys:!1, synchronizedOutput:!1, kittyKeyboard:!0, …}`），说明它本来倾向乐观 —— 我们唯一能做对的事就是**别冒充白名单里的终端名**（`["iTerm.app","kitty","WezTerm","ghostty","tmux","windows-terminal","WarpTerminal"]`），让 xterm 如实回「未识别」。

**顺带两条实现约束（已满足，但要留着）**：
- 我们的 CSI handler 是 `{prefix:"?", final:"h"|"l"}`，DECRQM 是 `{prefix:"?", intermediates:"$", final:"p"}` —— **final 不同，不会互相截胡**。但 `return false` 回退 built-in 必须保留（否则 `?1000h`/`?1049h` 全坏）。
- `mousePixels` 的真实启用条件是 `finePointerHolds>0 && altScreenActive && altScreenMouseTracking==="full" && now("mousePixels") && cellPixels !== undefined` —— **还依赖终端把字符格子的像素尺寸告诉它**（`MR().cellPixels`）。xterm 是否回应这条查询（推断是 `CSI 16 t` / `CSI 14 t` 类）**未验证**，若没回，1016 也不会启用。这条只影响「TUI 内点击精度」，价值低，先不深挖。

## 三、P1 · 会话环境注入（零文件改动、随会话生灭）

我们**自己 spawn 远端 shell**，这是别的终端拿不到的位置优势：可以在会话环境里导出变量。逐条：

| 变量 | 作用 | 证据 |
|---|---|---|
| **`COLORFGBG`** | 修 `theme: auto` 的**语法高亮半残**：`auto` 走异步 OSC 11 时，高亮那一层拿不到结果 → 代码块白底白字（#56848）。`COLORFGBG` 是同步可见的（首帧前就有值）。SSH 过来默认**不存在** | issue #56848 |
| **`CLAUDE_CODE_SCROLL_SPEED`** | **直接决定滚轮每格滚多少行**：`…let i=SCROLL_SPEED; if(!i)return base; let p=parseFloat(i); return p<=0?base:Math.min(p,20)` | 源码实证 |
| `CLAUDE_CODE_BS_AS_CTRL_BACKSPACE` | 治 Windows 上「每按一次 Backspace 删掉一个词」（终端发的 `^H` 被读成删词键）；反向亦可 | 官方文档 |
| `CLAUDE_CODE_DISABLE_NOTIFICATION_PRESENCE_CHECK` | Claude Code 自己也有「用户在场就不通知」的判定。我们已在 cc-bridge 侧做了同样的静默（`visible && document.hasFocus()`）→ **两层判定叠加会漏通知**。要么让远端不做这层判定，要么我们这层放宽 | 源码实证 |
| `CLAUDE_CODE_NO_FLICKER` / `FORCE_SYNC_OUTPUT` | 治闪烁。⚠️ `NO_FLICKER` 会切到**全屏渲染器** —— 正是滚轮问题最重的形态；`FORCE_SYNC_OUTPUT` 在非 tmux 下强制 DEC 2026。**取舍需你拍板，不建议默认注入** | 源码实证 |
| `CLAUDE_CODE_DISABLE_MOUSE` / `_CLICKS` / `DISABLE_VIRTUAL_SCROLL` | 一刀切除鼠标捕获 / 点击 / 虚拟滚动。能根治滚轮被吃，但会丢掉 TUI 内点击 → **只适合做「故障救急开关」** | 源码实证 |
| `CLAUDE_CODE_DISABLE_TERMINAL_TITLE` | 会连带关掉 `programStatus`（`tabWritesDisabled` 进了它的判定式）→ **别顺手设** | 源码实证 |

### tmux 三行配置：可以在会话内搞定，不必改用户 `.tmux.conf`

官方文档：tmux 内默认坏两件事 —— **Shift+Enter 变成提交**，**桌面通知与进度条到不了外层终端**。修法是三行：

```tmux
set -g allow-passthrough on
set -s extended-keys on
set -as terminal-features 'xterm*:extkeys'
```

`tmux set` 作用于**运行中的 server**，不需要改用户的配置文件 —— 也就是说我们可以像现有的 stty dance 一样，**检测到 `$TMUX` 就把这三条注入进去**（`tmux set -g …`），用户零操作。

⚠️ 两个必须交代的副作用：
1. 这些是**全局**设置，会影响该用户在同一台机器上的**其它 tmux 会话**；
2. `allow-passthrough on` 的含义是「允许转义序列穿透到外层终端」——文档明确提醒**共享/远程主机上要知情后再开**（穿透意味着远端能写你的终端标题、剪贴板等）。

**额外发现：`allow-passthrough` 同时是「复制」的依赖，不只是通知。** Claude Code 在 tmux 内走 `mux="tmux"` 分支，会把 OSC 52 包进 **DCS passthrough**（`return m + xI(m)`）—— tmux 不开 passthrough 就会把这层吞掉，于是**复制也一起坏**（与第一节的 OSC 52 缺陷叠加：一个在 tmux 侧丢，一个在我们侧丢）。

→ 建议做成**设置里的可选开关（默认关）+ 首次检测到时一次性提示**，而不是静默全局改。

## 四、P1 · 交互侧（差异化机会）

对标 2026 年的「agent 工作区」新品类（Herdr / cmux / ShellBoard / Okena / Wortel / Vertical Tabs / Graftty），业界共识是三件事：**① agent 跑得住（会话持久）② 看得出谁卡住 ③ 输出可组织**。我们已经用 OSC 7501 拿下 ②，剩下：

| 功能 | 说明 | 依据 | 成本 |
|---|---|---|---|
| **命令块（command blocks）** | 每条命令 + 它的输出成为**一个可折叠、可复制、可导出的单元**。Warp 的核心卖点；我们**数据已经在手**（OSC 133 A/B/C/D 注入钩子 + `terminalCommandNav` 已在算耗时） | Warp blocks；VS Code shell integration | 中（前端，需 marker + 分组 UI） |
| **跨标签 / 跨会话输出搜索** | 现有搜索只在本标签 buffer 内。ShellBoard 的差异点是「全局搜索输出」 | ShellBoard | 中 |
| **会话导出 / scrollback 恢复** | `@xterm/addon-serialize` 能把 buffer 序列化成 VT 序列或 HTML → 导出为可读文件；断线重连时可完整还原屏幕 | ShellBoard / Okena；xterm 6 `#5436` 给序列化加了 range | 中 |
| **广播输入到多标签** | 一条命令同时发给多个会话（对标 WezTerm pane broadcast / ShellBoard） | WezTerm | 小 |
| **端口转发图形化** | 我们**完全没有**（`grep` 全空）；Termius / Wireline 把它当标配 | Termius / Wireline | 中（Rust 侧要开 forward 通道） |
| 内联图片（iTerm2 协议） | `@xterm/addon-image`；WezTerm/Ghostty 支持 Kitty/Sixel/iTerm2 三协议 | xterm addon | 中（**体积预算压力**，安装包 ≤20MB 红线） |
| `addon-ligatures` / `addon-unicode-graphemes` | 连字（Nerd Font 图标）+ 字素簇聚类（emoji/组合字符宽度更对） | xterm 6 官方 addon | 小 |
| agent 注意力环 / 标签强化 | cmux 的「notification rings for processes needing attention」——我们有 BEL 角标 + AgentSeg，但缺一个**显眼的"需要你"视觉** | cmux | 小 |

**明确暂缓**：广播/AI 汇总式的「Fleet 批量执行」（Wireline 式：选一组主机 → 一句话 → 并发跑 → AI 汇总成表）。价值真实但属于**产品级新模块**，不是终端能力补齐。

## 五、明确不做（附理由）

| 不做 | 理由 |
|---|---|
| OSC 52 **读**（`52;c;?`） | 唯一的泄露面。行业默认禁止；开启等于让远端进程静默读取你剪贴板里的密码/token |
| 冒充 `TERM_PROGRAM=iTerm.app` / `WezTerm` / `ghostty` 骗能力 | 这些在 extended-keys 白名单里 → 触发 #38766（Esc/Ctrl+C 被吞）。**已列入红线** |
| kitty 键盘协议 / modifyOtherKeys | xterm.js 6 不实现；自实现属深水区，且 Claude Code 不依赖（有 Ctrl+J 兜底） |
| OSC 8 超链接 | xterm 5.0 起核心原生解析，无需我们做。⚠️ 但**别**给不可信来源的链接做美化（OSC 8 可伪造显示文本指向别的 URL） |
| OSC 104 / OSC 4 调色板查询 | `claude.exe` 里确实有 `]104;255` 和 `]4?`，但用途是内部重置/查询，**不实现不影响功能**（xterm 已有调色板管理），价值极低 |
| 前端自建剪贴板读权限弹窗 | 复杂度换不来价值 —— 读半边直接拒绝即可，用户有 Ctrl+Shift+C 本地复制 |
