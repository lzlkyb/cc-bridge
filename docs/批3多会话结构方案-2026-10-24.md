共享同一套地基，本方案覆盖 3-1 与 3-2 的结构面；3-3 依赖 3-1 落地后的 resume 点管理，单独一期。

## 一、现状：单例化只有两个点

| 位置 | 现状 | 多实例化难度 |
|---|---|---|
| `state.rs:179` | `pub cc: crate::cc_session::CcSession` | 改字段类型 + 初始化 |
| `cc_cmds.rs` 9 个命令 | 全部经 `state.cc`，**无 sessionId 参数** | 每个命令加参数（破坏性） |

**已经是多实例结构的**（这是本方案成立的前提，白捡的地基）：

- `manager.rs:594` `CcSession { shared: Arc<Shared>, live: StdMutex<Option<Run>> }` —— 一个实例就是一条完整会话链（进程 + 事件流水 + resume id + 待批单 + 落盘行号），没有任何全局单例状态。
- `store.rs:85` `cc_sessions` 表按行存，`save(conn, row_id, snap)` 已支持「更新自己那一行」，`prune(KEEP=100)` 已按条数淘汰。
- `usage.rs` 账按 `session_id` 主键，天然多会话。
- `ring.rs` 每 `Shared` 一条流水，序号互不干扰。

**真正的缺口只有两个**：

1. **事件出口没有会话标识**：`manager.rs:42` `CC_EVENT = "cc-event"`，载荷 `CcEventPayload { seq, event }`（`manager.rs:51`）。多条会话同时推事件，前端无法分流。
2. **MCP 审计归属假设只有一条会话**：`manager.rs:626` `CcSession::active_session_id()` 是单体方法。

## 二、五个设计决策

### D1 内部会话 id：单调递增的 `u64`，不用 `resume_id` 做 key

`resume_id` 是 CLI 在 `system/init` 里给的（`manager.rs:12` 文档：启动前拿不到，由事件回填）。
侧栏要在**启动前**就显示条目、可切换、可恢复，所以必须有一个启动前就存在的稳定 id。

- 分配：`CcSessions::next_id: AtomicU64`，从 1 起。
- 序列化：`sessionId: u64`（数字比字符串省事，且内部使用不外泄）。
- 一条会话的完整身份 = `(sessionId, resume_id)`：前者是我们的句柄，后者是 CLI 的续接线。

**调研背书**：MCP 2026-07-28 移除协议层 session 后，官方推荐应用层 mint 显式 handle 由调用方回传
（"state visible to the model rather than hidden away"）；OpenHands 的 conversation_id 同为服务端
mint、客户端拿它做全部后续操作。内部 id + 显式传递与协议演进方向一致。

### D2 事件分流：`CcEventPayload` 加 `sessionId`

```rust
pub struct CcEventPayload {
    pub session_id: u64,   // 新增
    pub seq: u64,
    pub event: CcEvent,
}
```

- 方向是 Rust → 前端，**加字段不破坏任何老前端**（TS 类型同步加即可）。
- `seq` 保持每会话独立（ring 本就是每 `Shared` 一个），跨会话不要求序号可比。
- 前端 `useCcEventStream` 从「全局 dispatch」改为「按 sessionId 找到对应会话再 dispatch」。
- **seq 兼作重放游标**（调研补入）：MCP SSE 用 per-stream event id + `Last-Event-ID` 做断线补拉，
  且规范 MUST NOT 跨流重放。我们的 ring 本就是 per-Shared 一条——前端重连时带 last seq
  向 Rust 补拉该会话 ring 内事件即可，语义天然对齐。

### D3 命令签名：全部显式带 `sessionId`

不采用「活动会话 + 切换命令」的隐式方案。理由：并发场景下（两条会话同时在跑），隐式当前会话会让「点发送却发到另一条」这类错误无法从代码上看出来；显式 id 让每次调用的目标在调用点就写死。

**调研背书（三层同构）**：OpenHands V1 API 每个端点带 conversation_id；Cline SDK 的 client 先
register/attach session 再交互，hub 只按会话 fan out；MCP 2025-06-18 起 `Mcp-Session-Id` 要求
客户端在所有后续请求里携带。Cline 老架构的「实例栈 + getCurrentCline()」隐式形态已被新 SDK
弃用——它依赖严格调用嵌套，天然排斥并发。

| 命令 | 现在 | 改后 |
|---|---|---|
| `cc_start` | 往当前会话发首条 | `cc_new_session()` 建壳返回 id；`cc_start(sessionId, req)` 给这条起进程 |
| `cc_send` / `cc_respond` / `cc_interrupt` / `cc_snapshot` / `cc_reset` / `cc_restore` | 无 id | 第一个参数 `sessionId: u64` |
| `cc_probe` / `cc_polish` | 不属于某条会话 | **不动** |

`cc_new_session()` 只建壳不启动：侧栏点「+」立刻出现条目（带「未开始」态），
比「发第一句话时才创建」更符合侧栏形态，也顺带解决「新建的空会话要不要落盘」——
空壳不落盘（`persist_shared` 已有 `events.is_empty()` 早退，`manager.rs:302`）。

### D4 退出与持久化：遍历而非单体

`main.rs:1149` 退出路径现在调 `st.cc.persist(&conn)` + `st.cc.shutdown(600ms)`。
改为 `CcSessions::persist_all(&conn)` / `shutdown_all(grace)`，内部遍历 map。
顺序不变：先同步落盘（异步线程会被进程退出强杀），再给宽限期杀进程。

### D5 MCP 审计归属：从「那条」变成「只有一条在跑才归」

`active_session_id()` → `CcSessions::active_session_ids() -> Vec<String>`：

- **只有一条会话有活跃轮次** ⇒ 返回它。工具调用记到它头上（现行为，覆盖 90% 场景）。
- **多条同时在跑** ⇒ 返回空，不归属。方向必须是「宁可漏、不可错」——现有口径
  （`manager.rs:622`）的延伸，张冠李戴比漏记更难排查。
- 残余毫秒级误差不变（`send()` 先置位再写 stdin）。

**远期**（3-2 会话不死落地后）：给每条会话的 claude 传独立的 `--mcp-config`，
在 MCP 请求头里带 session 标识，即可精确归属。本期不做——它会把改动手续从
「加个 header」扩大到「每条会话管一份临时配置文件」，而收益只在「同时跑两条以上」
才出现。

## 五、风险

1. 🔴 **3-1a 是破坏性变更，前后端必须同一个 commit**。中间态（Rust 加了参数、前端还没改）
   会在第一次调用时直接报错。不能拆两个 commit。
2. **体量门禁**：`CcGuiTab` 298 行已贴红线，先拆再长（见上）。
3. **`cc_restore` 语义要重新定义**：现在它是「恢复上一条」；多会话下变成「把这条历史
   装进侧栏某一行」。装进去之后它和「新建的空壳」是同一个东西，两条路径要合并。
4. **进程数不设硬上限**（2026-10-25 按调研改）。业界：Cline Cloud 硬限 10 是云 sandbox
   成本约束；CC workflow guideline（medium<10 / Pro<5）明文 "advice rather than a hard cap"；
   本地类产品（CC Desktop / Cline 本地扩展）无文档化上限。真实约束是 CC 服务端的 usage
   线性增长与 rate limit 全局共享——产品层拦不住也不该拦。本地侧只做资源可见性
   （侧栏显示会话数与进程状态），不拒绝新建。已知代价入档：每条会话的 SessionStart
   钩子会各自跑一遍，开十条就是十遍。
5. 🔴 **同目录多会话不是安全边界**（调研新发现，OpenHands 原话 "A separate conversation is not
   a security boundary when it shares a sandbox"）。多条 CC 会话默认共享同一远端工作目录，
   一条会话的 `rm -rf` 会伤及全部。CC 的解法是 git worktree 隔离，但我们连接的远端项目
   未必是 git 仓库——本期不强行隔离，3-1b 侧栏对「同目录并发」给明确警告。

## 六、0-4 探针（3-2 前置，2026-10-25 已验证）

要回答的问题：**关窗 / SSH 断线后，远端的 claude 能不能继续跑，重连后能不能接回。**

- 本机 Windows 侧现在就能「不随窗口退出」，但 `main.rs:1149` 的退出路径**主动杀**——
  所以本机场景的问题是策略问题（要不要杀），不是能力问题。
- 远端场景是真问题：SSH 一断，claude 跟着死。tmux 是标准答案（Anthropic Remote Control
  文档原话：断线保活 "start it inside tmux or screen"）。
- **setsid 分支降级为兜底证据**（调研修正）：nohup/setsid 对交互式 TUI 只能证明「进程不死」，
  不能证明「交互可恢复」——社区明确记载 "Running nohup claude creates a process you can't
  reattach to"。可恢复性只有 tmux 能给。
- **CC 原生 `--bg` + supervisor 路线作废**（2026-10-25 实测）：远端定制版 claude 禁用一切
  非交互模式（`--print`/`--bg`/`--cloud`，报错原文「仅限 claude-svc」），该路线在目标环境
  不可用。我们管理层走交互 TUI + stream-json stdin/stdout，**天然合规不受影响**。
  情报：远端是企业托管部署（Claude Team / managed settings / 日预算 $80 / 已接 2 个 MCP），
  非交互任务归专用服务账号 claude-svc——将来做无人值守批量的对接点是它。
**实测结论**（2026-10-25，远端 10.0.19.194，全程记录见 `CC对话协议探针报告-2026-10-24.md` 文末）：

- ✅ tmux 主路径成立：60s 计数任务跨 SSH 断开跑完（日志 62 行完整跨过断开时刻）；补验的
  alive 循环与**交互式 claude TUI** 重连后 `capture-pane` 原样可读——attach 恢复交互态成立，
  xterm 侧重连时 `tmux attach` 拿全量重绘即可恢复画面。
- ✅ setsid 兜底成立：日志 60 行完整跨断开（SID 精确判据因 `pgrep -f` 匹配过宽打折，脚本待修）。
- 探针脚本两处待修：B 分支 pgrep 匹配面；A 分支任务必须不自行退出（否则验不到 attach 抓屏）。
