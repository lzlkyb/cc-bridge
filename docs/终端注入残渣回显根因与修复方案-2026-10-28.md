# 终端「自己输入 echo」根因与修复方案

> 2026-10-28。用户报障：SSH 终端偶尔会自己往屏幕/输入行打出 `echo` 一类文本，新建会话时尤其明显。
> 本文只做诊断与方案，**未改动任何代码**。

## 一、结论先说

不是「终端自己打字」，是**注入的 shell 钩子在被关掉回显之前就到达了远端 PTY**，被行规程 ECHO 原样回显到屏幕。
用户看到的 `echo` 来自两处注入原文：`stty -echo` / `stty echo`，以及 649 字符的钩子体（其中含 `PROMPT_COMMAND=...`）。

三条缺陷叠加，按严重性排序：

| 编号 | 缺陷 | 触发条件 | 用户可见后果 |
| --- | --- | --- | --- |
| A | 注入时序靠**固定延时猜**，与远端 shell 是否就绪无因果关系 | 远端 ready > 900ms（新建会话几乎必然） | 649 字符钩子明文整屏露出（折行 7~9 行），strip 无法匹配 |
| B | `claimInjection` 失败分支**不挂剥除器**，而 cleanup 已把上一个 `end()` 掉 | 注入开关切换 / closed 变化导致 effect 重跑 | 本会话之后整场失去剥除器，ConPTY 整屏重绘时残渣「又自己输入一遍」 |
| C | cleanup 兜底 `stty echo` 在 `stripHandle.end()` **之后**才被回显 | 断开 / 卸载 / 换会话 | `stty echo` 残渣无人擦 |

A 是主因；B、C 是「好不容易偶尔出现了还记得住」的第二、第三条通道。

## 二、证据链

### 2.1 t0 一定早于远端就绪

- `src-tauri/src/commands/ssh_cmds.rs:1300-1313`：`ssh_connect` 在 `spawn_command` 成功后**立刻**返回 `session_id`（后面才是 TCP 握手 / 认证 / 远端 shell 启动）。
- `src/hooks/useTerminalOsc.ts:234`：`at(DANCE.PROBE_DELAY, ...)`，`terminalSttyDance.ts:67` 里 `PROBE_DELAY: 900`。
- 即：**进程 spawn 后约 900ms 就开始往远端打字**。远端要跑完 TCP + 认证 + `/etc/profile` + `/etc/bash.bashrc` + MOTD，常见 1~3s，跨洋/慢 MOTD 更久。900ms 赢不了。

### 2.2 回显发生在字节进 tty 的那一刻，不是 shell 执行的那一刻

这是 POSIX tty 的既定行为，也是本 bug 的关键：

- 字节到达远端 PTY → 行规程（line discipline）按当时 `ECHO` 状态决定是否回显 → 之后才进输入队列等 shell 读取。
- 因此 `stty -echo` 只能保护**它执行之后**到达的字节。它执行之前到达的字节全是明文回显。
- shell 未 ready 时，`stty -echo` 只是躺在 tty 队列里；此时 `ECHO` 仍是登录初态的 on。

⇒ **900ms 发出的三条命令（stty -echo / 探针 / 钩子）全部在 ECHO=on 时到达 ⇒ 全部被回显。**

### 2.3 strip 只能吞短 token，吞不了折行的钩子

- `useTerminalOsc.ts:211`：token 表 = `[ECHO_OFF_CMD, PROBE_CMD, ECHO_ON_CLEAN_CMD, ECHO_ON_CMD]`，即 `stty -echo`(11) / 探针(≈40) / 两条收尾命令。
- `terminalStatusbar.ts:413` 的 `hookCmd()` 实测 **649 字符**（含 `envInjectCmd` 前缀）。PTY 按列宽折行，100 列 → 7 行，80 列 → 9 行。
- `terminalSttyDance.ts:197` 的 `createEchoStripper` 是**单行匹配**（遇到 token 外的字符即失配归还），跨行的 token 无法命中。
- 历史决策也印证过：`2026-10-13` 记录「HOOK_CMD 超 450 字符会被远端行规程折行，加 token 也匹配不上，不值得加」。

⇒ 钩子回显后**没有任何机制能擦掉它**，整片留在屏幕上。

### 2.4 为什么是「偶尔」

900ms 与远端就绪是一场赛跑：

- 局域网 / 已复用连接 / profile 很轻的机器：900ms 内 ready → `stty -echo` 先执行 → 后续静默 → 看不到。
- 跨洋 / 慢 MOTD / 首次认证 / 机器负载高：ready 晚于 900ms → 整轮明文。

「新建会话时尤其明显」正是因为它永远是新链路（没有复用、没有缓存）。

### 2.5 B 缺陷（剥除器丢失）的证据

```ts
// useTerminalOsc.ts:199-202
if (!claimInjection(sessionId)) {
  setState("ready");
  return;              // ← 直接返回，attachEchoStripWhenReady 根本没跑
}
// useTerminalOsc.ts:295
stripHandle?.end();    // ← 上一个 effect 的 cleanup 已经把剥除器撤掉了
```

effect 的依赖是 `[sessionId, enabled, closed, reset, termRef]`。`enabled`（设置里切「远端路径/分支探测」）、`closed`（断开）都会让它重跑；重跑时 cleanup 先 `end()` 旧剥除器，新 effect 又因 claim 失败提前 return ⇒ **整场会话再没有剥除器**。
此后 ConPTY 任何整屏重绘（resize / 字号 / TUI 进出）都会把缓冲区里的残渣原样重发，屏幕上「又自己输入一遍」（这正是 2026-10-13 常驻化要解决的问题，被这个分支绕过了）。

### 2.6 C 缺陷（兜底 restore 的残渣）

```ts
// useTerminalOsc.ts:289-295
if (echoOffRef.current) {
  echoOffRef.current = false;
  void invoke("ssh_input", {...});   // 异步：命令还在路上
}
stripHandle?.end();                   // 同步：剥除器已经撤了
```

`invoke` 是异步的，`end()` 是同帧同步的 ⇒ 这条 `stty echo` 的回显（若 ECHO 实际未关闭）无人擦。

## 三、修复方案

核心思路一句话：**把「什么时候可以安全说话」从时间猜测换成回执证明 —— 长命令（钩子）必须等「ECHO 已关」的回执到达之后才发。**

### P0-1 合并探针：一条命令同时拿到「ECHO 已关」+「shell 是谁」

新增常量（`terminalSttyDance.ts`）：

```ts
// 关回显 + 报 shell 名，一条命令一个回执。
// 该行自身必然被回显（ECHO 在它执行前仍是 on），故必须进 token 表。
export const PROBE_ECHO_OFF_CMD =
  ` stty -echo 2>/dev/null; printf '\\033]1337;Shell=%s\\007' "$0"`;
```

时序改造（`useTerminalOsc.ts`）：

```
t0 = 900ms（保留：还要躲密码提示自动填充，不能更早）
  └─ send(PROBE_ECHO_OFF_CMD)
        ↑ 短命令（≈62 字符），即便被回显也在 strip 覆盖范围内
        ↑ 若 shell 未 ready，它排队等 ready 后执行

收到 OSC 1337;Shell=xxx      ← 这一个回执同时证明：shell 已 ready 且 ECHO 已关
  ├─ !isSupportedShell → 立即 restore（ECHO 已关，必须恢复），判 unsupported
  ├─ tuiOnScreen 复查 → abort + restore
  └─ send(hookCmd())        ← 649 字符长命令，此刻 ECHO 确定已关，不再回显
        └─ kick → restore(true)
```

- 删除 `ECHO_GAP`（250ms 固定余量不再需要）。
- `PROBE_TIMEOUT` 由 1200 → 8000ms（允许命令在远端队列里等 ready）。
- 超时仍发 `ECHO_ON_CMD`（有 token 能吞），不能让用户键盘变哑。

**为什么这样就够**：`stty -echo` 与钩子的先后关系不再由本地定时器决定，而由**远端自己执行完并发回执**决定。排队多久都无所谓 —— 长命令永远排在 `stty -echo` 之后。

### P0-2 token 表更新 + 折行安全阀

- token 表改为 `[PROBE_ECHO_OFF_CMD, ECHO_OFF_CMD, ECHO_ON_CLEAN_CMD, ECHO_ON_CMD]`（长 token 排前，与现有注释一致）。
- **折行安全阀**：token 只有在「整个 token 落在同一行」时才可能命中。注入前校验
  `term.cols >= PROBE_ECHO_OFF_CMD.length + 4`，不满足就**放弃注入**（判 unsupported，屏幕上什么都不留）。
  默认 100 列、62 字符 token 有充足余量；用户把窗口缩到 60 列以下则不注入，属于可接受降级。

### P0-3 剥除器与注入生命周期解耦（修 B）

把剥除器从「注入 effect」里提出来，单独一个 effect：

```ts
useEffect(() => {
  const h = attachEchoStripWhenReady(termRef, STRIP_TOKENS);
  return () => h.end();
}, [termRef]);          // 只依赖 termRef（稳定），随终端实例生死
```

- 注入 effect 里的 `attachEchoStripWhenReady` / `stripHandle.end()` 全部删掉。
- 于是 `claimInjection` 失败分支提前 return 也无所谓 —— 剥除器不在那条路径上。
- 顺序红利：本 effect 声明在注入 effect **之前**，React 逆序 cleanup ⇒ 卸载时注入 effect 先发兜底 `stty echo`、剥除器后撤，正好修掉 C。

### P0-4（可选）cleanup 兜底加一拍

即使有 P0-3 的顺序保证，仍建议兜底 restore 之后 `setTimeout(() => h.end(), 300)` 再撤，给回显留往返时间。P0-3 做对了这条可以不做，二者选一。

### P0-5 解析器扩展

`terminalStatusbar.ts:309` 的 `parseOsc1337` 目前只认 `Shell=` / `Git=` / `Cmd=`。合用既有 `Shell=` 通道即可，**无需新增 key**（这是合并探针比新增 `EO=` 更省的原因）。

### Phase 2（可选，提升 t0 精度，有风险）

用「首次远端输出 + 输出空闲 ≥300ms」替代固定 900ms，把注入提前到真正就绪时。**不建议本轮做**：
密码阶段也会有输出，若在密码提示后立刻注入，字节会被当成密码喂给 ssh ⇒ 认证失败。要做得先在前端复刻 Rust 侧 `prompt_tail` 的密码提示识别（`ssh_cmds.rs` 的 `strip_ansi` + 尾部判据），成本与风险都不低，收益只是「少等几百毫秒」。

## 四、测试与验证

### 单测（必补）

1. `terminalSttyDance.test.ts`
   - `PROBE_ECHO_OFF_CMD` 含 `stty -echo` 且以 `printf` 回执收尾；
   - stripper 能吞掉**带前导空格**的整行 `PROBE_ECHO_OFF_CMD`；
   - 折行后的同一命令**不被吞**（显式锁住「为什么必须有 cols 安全阀」）。
2. 状态机不变量（本次最重要的一条）
   - 未收到 `Shell=` 回执时，**任何路径都不得进入 `hookSent`**（把「hook 只在回执后发」钉成 reducer 级断言）。
3. 剥除器生命周期
   - `attachEchoStrip` 在 effect 重跑（模拟 claim 失败）后仍生效 —— 用 hook 层测试或抽成纯函数断言。

### 复现构造（想自己确认根因就地验证）

用 `ssh -o ProxyCommand="sleep 3"` 的跳板把远端就绪推迟 3 秒，新建标签 —— 现状下几乎必现 649 字符明文。修后应完全不出现。

## 五、风险与取舍

| 项 | 说明 |
| --- | --- |
| 注入变慢 | 正常链路无变化（回执 RTT 通常 <100ms，比现在固定的 250ms 余量更快）；慢链路最多等 8s，超时即降级 |
| 窄窗口不注入 | cols < 66 时放弃注入（状态栏退化为只显示本地可算的信息）。比露出命令原文好 |
| 非 POSIX shell | 第一条命令就会在 fish/csh 下报错（`stty` 不存在时 stderr 被 `2>/dev/null` 吃掉）。探针回执拿不到 ⇒ 8s 后降级 + `stty echo` 兜底。与现状同风险，不新增 |
| 兜底仍发 `stty echo` | ECHO 状态未知时宁可多发一条（有 token 能吞），也不能让用户键盘变哑 |
| 钩子回显的极端残留 | 若远端某 rc 脚本在 ready 之后又把 termios reset 成 echo on，钩子仍会回显。概率极低（rc 都在 ready 前跑完），不在本轮处理 |

## 六、临时规避（改完之前的用户侧开关）

设置 → 终端 → 历史与集成 → **「远端路径/分支探测」关掉**：立刻不再有任何注入，残渣消失。
代价：状态栏的远端 cwd / git 分支 / 上一条命令退出码与耗时失效（本地可算的部分仍显示）。

## 八、实施记录（2026-10-28 已落地）

门禁：体量 0 / `tsc --noEmit` 0 / `eslint .` 0 / `vitest run` **1448 passed (139 files)** / `vite build` 通过。
单测：`terminalSttyDance.test.ts` 33 → **40 条**（合并探针 5 条 + 剥除器生命周期 2 条，另有一条状态机不变量并入既有断言）。

实际落地与上面方案的差异（三处，都是实施时想清楚后的改进）：

1. **剥除器不是「独立 effect 挂一次」，而是「幂等 + 不提供 end」**
   （`attachEchoStripWhenReady` 改为返回 `{ cancel }`，用挂 `globalThis` 的 `WeakSet` 去重）。
   原因：方案里说的「effect 声明顺序 = cleanup 顺序」不足以解决问题 —— React 的 cleanup 是**正序**执行，
   且 `invoke` 是异步的，兜底 `stty echo` 的回显到达时，同 tick 执行的 `end()` 早把包装撤了。
   只有让剥除器**活到终端实例销毁**，这条兜底命令的回显才一定有人擦。
2. **剥除表抽成 `STRIP_TOKENS` 常量**（从 hook 移到 `terminalSttyDance.ts`），单一真源 + 可直接单测顺序；
   同时**移除单条 `ECHO_OFF_CMD`**——它已是 `PROBE_ECHO_OFF_CMD` 的前缀，留着反而会在折行时只吞半截。
3. **折行安全阀复用 `abortDance()`**（此时 `echoOffRef` 还是 false，不会多发 `stty echo`），
   比单开一条 `unsupported` 分支少两行——`useTerminalOsc.ts` 最终 **299 行**，贴线未超。

还有一处实施中确认的**行为变化**：`PROBE_TIMEOUT` 1200 → 8000ms。等待期间用户一敲键就走 `onData`
立即 abort + 恢复 ECHO，所以「键盘哑 8 秒」不会发生。
