# 自动更新流程测试指南（2026-10-18）

> 目标：把「检查 → 提示 → 下载 → 进度 → 安装 → 重启」这条链路按**四层**分别验证。
> 绝大多数缺陷在第 1、2 层就能暴露；第 3 层专门验「装完重启能不能起来」这类**发了才知道、且升不回去**的风险。
> 配套工具：`desktop/scripts/fake-update-server.mjs`（本地假更新源，仅 dev 可用）。

---

## 0. 一句话选路

| 你想验什么 | 用哪层 | 耗时 | 风险 |
|---|---|---|---|
| UI 七个状态、进度读数、错误文案、多源回退 | **Layer 1**（dev + 假源） | 10 分钟 | 零（签名是假的 ⇒ 永远不会装） |
| 真签名 + 真端点 + NSIS 真装 + 版本号真变 | **Layer 2**（装旧版 → 升级） | 20 分钟 | 会覆盖已装应用，可装回 |
| 「装完能不能重启」「配置/数据是否幸存」 | **Layer 3**（本地全真，两次 build） | 30 分钟 | 中（改 tauri.conf，测完必须还原） |

**建议**：至少跑 Layer 1 全表 + Layer 2 一次。Layer 3 只在改动过安装/重启相关代码时跑。

## 1. 链路断面（哪一段由什么决定）

| # | 环节 | 代码位置 | 由什么决定 | 本地可控？ |
|---|---|---|---|---|
| 1 | 版本比较 | 插件 `check()` | manifest `version` **vs 编译进 exe 的** `tauri.conf.json` version | ✅ manifest 可任意伪造 |
| 2 | 选源 | `commands/update.rs:113` `candidate_endpoint_groups` | `CCBRIDGE_UPDATE_ENDPOINT` > Gitee（硬编码 `lzul/cc-bridge`）> `tauri.conf` 的 ghproxy/GitHub | ✅ env 覆盖 |
| 3 | https 强制 | 插件 `config.rs:149` `validate_endpoints` | **release 必 https**；debug 仅打 WARNING | ⚠️ 见 §2.1 |
| 4 | 重试退避 | `update.rs:45` `retry_with_backoff` | 每个源：检查最多 3 次（1s、2s 退避），下载安装最多 3 次 | ✅ 用不可达源诱发 |
| 5 | 下载 | 插件 `download_and_install` | 二进制 URL 在 manifest 里是**单值**，没有二进制级兜底 | ✅ 本地服务 |
| 6 | 验签 | 插件 `verify_signature(pubkey)` | pubkey **编译进 exe**，私钥只在 CI secret | ⚠️ 见 §2.2 |
| 7 | 安装 | Windows NSIS `/P /R /UPDATE /ARGS` | **安装器自己杀进程 + 重启** | 需真 build |
| 8 | 前端状态机 | `contexts/UpdateContext.tsx` | 7 个 `update:*` 事件 + 3 个 localStorage 键 | ✅ dev 可测 |

> 🔴 **事件顺序有个坑（测试时会看到，属已知）**：插件在 `download()` 里是
> `on_download_finish()` **先**回调、`verify_signature()` **后**校验（`updater.rs:710-712`）。
> 所以**签名失败时前端会先闪一下「就绪」并开始 8 秒倒计时，几十毫秒后才变错误**。
> 这不是我们代码的问题，是插件 API 顺序决定的；看到别当成新 bug。

## 2. 三条硬约束（不先弄清会白跑）

### 2.1 release 构建拒绝 http 更新源

`tauri-plugin-updater` 的 `validate_endpoints`：非 `https` 时，**debug 只警告、release 直接报错**
（`InsecureTransportProtocol`）。所以：

- `npm run dev`（debug）→ 可以指向 `http://127.0.0.1:8899/updater.json`，**Layer 1 靠这条**。
- 已安装的 release 版 → 只能用 https。想在本地 release 上走 http，要在
  `tauri.conf.json` 的 `plugins.updater` 里临时加 `"dangerousInsecureTransportProtocol": true`
  （**会被编译进二进制，改完必须重新 build**，测完删掉）。
- 自签证书没用：插件默认 `rustls-tls` 且没启用 `native-roots`，把证书塞进 Windows 受信任根也不认。
  CI 里 mac 的自动更新 E2E 就是因此改用「临时 GitHub prerelease」当 https 源（`.github/scripts/mac-updater-e2e.sh`）。

### 2.2 本机没有 cc-bridge 的签名私钥

已核：

| 来源 | 公钥指纹（前 8 字节） |
|---|---|
| `tauri.conf.json` 内置 pubkey | `5A AF 18 51 21 FB DA ED` |
| 本机 `~/.tauri/filck-v2.key.pub` | `BF A3 AC F9 92 16 85 EE` |

→ **不是一对**（那是 PastePanda 的密钥）。所以本地拿现成密钥签出来的包，验签必失败
（报 `The signature was created with a different key than the one provided`，且**只写日志**）。

要在本地跑完整安装，只有两条路：
1. **Layer 2**：装官方旧版本，让应用用**生产签名**自己升上来（不需要私钥）。
2. **Layer 3**：`npx tauri signer generate` 造一次性密钥对，**在 build 之前**把配对公钥写进
   `tauri.conf.json`（pubkey 编译进 exe，事后改无效）。

### 2.3 Windows 上「8 秒自动重启倒计时」基本看不到

默认 `installMode = Passive` → 安装器参数 `/P /R /UPDATE /ARGS`。NSIS 模板在更新模式下会
**taskkill 掉正在运行的 app**，装完自己用 `/ARGS` 重启。因为 `update:ready` 在 `install()` 之前就发出，
所以实际顺序是：`就绪` → 倒计时刚开始 → 安装器杀进程 → 新版自己起来。

结论：
- Windows 上**倒计时/「重启」按钮基本没有展示窗口**，这是安装器语义决定的，**不是 bug**。
- 倒计时真正起作用的是 macOS（那边安装只是替换 `.app`，不会自动重启，必须应用自己 `relaunch`）。
- Windows 上顺带要验一件事：**进程被 taskkill 时配置/审计有没有被写坏**（见 Layer 3 用例 C5）。

### 2.4 其它已核事实

- **当前 Gitee 首选源是 404**（实测：`https://gitee.com/lzul/cc-bridge/raw/releases/latest/updater-gitee.json`
  → `Repository or file not found`；该仓库只有 `main` 分支，没有 CI 应该创建的 `releases` 分支）。
  后果：**每次检查都会先在 Gitee 上白跑 3 次（含 1s+2s 退避）再回退到 ghproxy**。
  测试时看到 3 条「检查更新失败（第 x/2 次）」警告属预期，但这是一条待修项。
- **日志只到 stderr**（`main.rs:364` `env_logger::init()`，没有文件 target）。所以测更新
  **必须从终端启动 exe 并重定向**，否则什么都看不到：
  ```bash
  RUST_LOG=info,tauri_plugin_updater=trace \
    "D:/soft/cc-bridge/cc-bridge-desktop.exe" > /tmp/app-upd.log 2>&1 &
  tail -f /tmp/app-upd.log
  ```
- **更新链路目前零自动化测试**：`commands/update.rs` 无 `mod tests`，`UpdateContext.tsx` 无 vitest。
  这是「防回归」的缺口，见 §6。
- **dev 与已安装版共用同一份 WebView 数据目录**（`%LOCALAPPDATA%\com.ccbridge.desktop`），
  所以 localStorage 是共享的。反复测试前先清：
  ```js
  // dev 窗口里 Ctrl+Shift+I → Console
  localStorage.removeItem("ccbridge_last_update_check");   // 24h 节流
  localStorage.removeItem("ccbridge_dismissed_update_version"); // 「稍后」抑制
  ```

## 3. Layer 1：dev + 本地假源（10 分钟，零风险）

### 3.1 起假源

```bash
cd /d/AItool/winapp/cc-bridge

# 默认：版本 99.9.9 / 20MB / 限速 2MB/s —— 适合看进度与读数
node desktop/scripts/fake-update-server.mjs
```

它会打印要复制的 env 行。常用变体：

```bash
node desktop/scripts/fake-update-server.mjs --version 2.9.1      # 测「已是最新」
node desktop/scripts/fake-update-server.mjs --mode stall          # 传到 30% 卡 4 秒
node desktop/scripts/fake-update-server.mjs --mode noclen         # 不给 Content-Length
node desktop/scripts/fake-update-server.mjs --mode 404            # 元数据 404
node desktop/scripts/fake-update-server.mjs --mode badjson        # 坏 JSON
node desktop/scripts/fake-update-server.mjs --size-mb 2 --rate-kbps 0   # 测失败路径（快）
```

### 3.2 起应用

```bash
cd /d/AItool/winapp/cc-bridge/desktop
export CCBRIDGE_UPDATE_ENDPOINT=http://127.0.0.1:8899/updater.json
export RUST_LOG=info,tauri_plugin_updater=trace
npm run dev
```

> ⚠️ 跑 dev 前先关掉已安装版（`single-instance` 会抢锁，dev 秒退）。

### 3.3 用例表

| # | 操作 | 预期 | 失败说明什么 |
|---|---|---|---|
| L1 | 清 localStorage → 重启应用 | 启动自检 → 状态条走「检查中」→ 出现可更新徽章 `更新 v99.9.9` | 事件在监听注册前丢了（UpdateContext 的启动竞态回归） |
| L2 | 点徽章 | 弹更新说明框，显示 `v当前 → v99.9.9`、CHANGELOG 正文 | `update:available` 的 payload 字段缺失 |
| L3 | 点「下载并更新」 | 状态转下载中；**2px 顶栏进度线**出现；顶栏中段出现 `12.4 / 20.0 MB  ↓ 2.0 MB/s  剩 4s` | `total`/`bytesPerSec` 没进 state，或读数框没挂上 |
| L4 | 拖窄窗口到 ≤900px | 剩余时间消失，其余保留 | 窄窗退化断点错 |
| L5 | 继续拖到 ≤740px | 整条读数隐藏，进度线仍在 | 同 L4 |
| L6 | 用 `--mode stall` 重跑 | 传输静默 >1.5s 后读数转灰、显示「等待响应…」 | 心跳判定 `STALL_MS` 回归 |
| L7 | 用 `--mode noclen` 重跑 | 无百分比，进度条走**不确定态**（扫动），读数只显示「已下载 X MB」 | `totalBytes=null` 分支回归 |
| L8 | 默认模式跑完 | 下载完 → **先闪「就绪」** → 立刻转错误「更新失败，请重试」 | 见 §1 的已知顺序坑；若**停在就绪不动**才是 bug（说明错误事件没发） |
| L9 | 看终端日志 | `下载安装失败（第 1/3 次），1 秒后重试` ×2，最后一条 `全部更新源均失败` | 重试/回退逻辑回归 |
| L10 | `--version 2.9.1` + 手动点「设置 → 关于 → 检查更新」 | 版本 pill 显示「已是最新」4 秒后回 idle；**手动**检查弹「已是最新」提示框 | `manualCheck` 区分回归（自动检查不该弹框） |
| L11 | L10 后**重启应用**（不手动点） | 不弹框，只在版本号处提示 | 同上 |
| L12 | 出现更新时点「稍后」 | 弹框关闭，本版本不再弹；重启应用仍不弹 | `ccbridge_dismissed_update_version` 未写入 |
| L13 | 连点两次徽章 / 连点两次「下载并更新」 | 只有一次下载；日志 `更新任务已在进行，忽略重复触发` | Rust `SingleFlight` 或前端 `downloadingRef` 回归 |
| L14 | `CCBRIDGE_UPDATE_ENDPOINT` 设成 `http://127.0.0.1:1/x.json,http://127.0.0.1:8899/updater.json` | 先对第 1 个源重试 3 次（约 3s），再第 2 个源**成功** | 多源顺序回退回归（`candidate_endpoint_groups`） |
| L15 | 不设 env（走真实源） | 日志先 3 条 Gitee 失败 → 再由 ghproxy 拿到 2.9.1 | 若非如此，说明真实源顺序/回退变了 |

> ⚠️ 测失败路径（L8/L9）用 **`--size-mb 2 --rate-kbps 0`**：因为失败会**重下 3 次**，
> 20MB@2MB/s 要等 30 秒以上。

## 4. Layer 2：真实发布链路（20 分钟，最接近用户）

思路：把自己降级到**已发布的旧版本**，再让应用按真实链路升到最新。全程用生产签名、真实
Gitee/ghproxy/GitHub 端点、真实 NSIS，不需要任何私钥。

```bash
# 0) 先关掉正在运行的应用
# 1) 下 v2.9.0 的安装包（实测存在：cc-bridge_2.9.0_x64-setup.exe，6.8MB）
mkdir -p /d/tmp/rel2090 && cd /d/tmp/rel2090
"/c/Program Files/GitHub CLI/gh.exe" release download v2.9.0 \
  --repo lzlkyb/cc-bridge --pattern "cc-bridge_2.9.0_x64-setup.exe"

# 2) 安装（覆盖当前 2.9.1；currentUser 安装，不需要 UAC）
./cc-bridge_2.9.0_x64-setup.exe

# 3) 从终端启动，保住日志
RUST_LOG=info,tauri_plugin_updater=trace \
  "D:/soft/cc-bridge/cc-bridge-desktop.exe" > /tmp/app-upd.log 2>&1 &
tail -f /tmp/app-upd.log
```

| # | 检查点 | 预期 / 证据 |
|---|---|---|
| L2-1 | 顶栏/侧栏版本号 | `v2.9.0`（证明降级成功） |
| L2-2 | 等待启动自检或手动「设置 → 关于 → 检查更新」 | 3 条 Gitee 检查失败（预期，见 §2.4）→ 然后出现 `更新 v2.9.1` |
| L2-3 | 更新说明弹框 | 正文是 v2.9.1 的 `### 更新摘要`，不是乱码/空 |
| L2-4 | 点「下载并更新」 | 进度真实前进；速度为数 MB/s 量级；总大小 ≈ 安装包体积 |
| L2-5 | 下载完成瞬间 | 应用窗口**自己关闭**（安装器 passive 进度条），约 10–30 秒后**新版自己打开** |
| L2-6 | 重开后的版本号 | `v2.9.1`；`(Get-Item "D:\soft\cc-bridge\cc-bridge-desktop.exe").VersionInfo.FileVersion` 也是 `2.9.1`（**硬证据：文件真被替换**） |
| L2-7 | 配置幸存 | 更新前改一个设置（比如改端口/切换主题），更新后仍在 |
| L2-8 | 数据幸存 | SSH 连接列表、审计记录、备份目录都在（`%LOCALAPPDATA%\com.ccbridge.desktop` 未被清） |

> 🔴 判据要点：**「进程还活着」不能证明替换发生**（新旧都能启动）。必须比 `FileVersion` 或
> 比 exe 的 `LastWriteTime` —— 这正是 CI 的 mac 脚本用「标记文件」而不是「/health 200」的原因。

**回滚**：再装一遍 v2.9.1 即可（`gh release download v2.9.1 --pattern "cc-bridge_2.9.1_x64-setup.exe"`）。

## 5. Layer 3：本地全真（可选，30 分钟）

只在改了「安装 / 重启 / 更新源解析」相关代码时做。目标：**用自己造的更新包，把 ready →
安装 → 重启 → 新版本起来**这段完整跑通，能反复跑且不污染线上。

> 为什么值得：Windows 上没有等价于 `.github/scripts/mac-updater-e2e.sh` 的脚本，
> 「更新后起不来」在 Windows 上同样是**发了才知道、且升不回去**的风险。

### 5.1 造一次性密钥对

```bash
cd /d/AItool/winapp/cc-bridge/desktop
mkdir -p /d/tmp/updtest
npx tauri signer generate -w /d/tmp/updtest/smoke.key -p "" --ci
cat /d/tmp/updtest/smoke.key.pub      # 这份内容本身就是 base64，不要再编一次
```

### 5.2 改 `tauri.conf.json`（**只改工作区，不提交**）

两处：

```jsonc
{
  "plugins": {
    "updater": {
      // 1) 换成刚生成的 pubkey（整段 base64 字符串）
      "pubkey": "<smoke.key.pub 的内容>",
      // 2) 允许 http 源（release 默认拒绝，见 §2.1）
      "dangerousInsecureTransportProtocol": true
    }
  }
}
```

### 5.3 第一次 build（当前版本 2.9.1）→ 装上

```bash
cd /d/AItool/winapp/cc-bridge/desktop
export TAURI_SIGNING_PRIVATE_KEY="$(cat /d/tmp/updtest/smoke.key)"
export TAURI_SIGNING_PRIVATE_KEY_PASSWORD=""
npx tauri build 2>&1 | tail -20
# 产物：src-tauri/target/release/bundle/nsis/*.exe  与同名 .exe.sig
```

装它（会覆盖现有 2.9.1）。装完先启动一次，确认能跑、版本号是 `2.9.1`。

### 5.4 第二次 build（版本改成 99.9.9）

版本号真源是 **`Cargo.toml`**（`tauri.conf.json` 由 `sync-version.mjs` 从它同步，别手改）：

```bash
cd /d/AItool/winapp/cc-bridge/desktop
# 1) 只改 src-tauri/Cargo.toml 里 [package] version = "99.9.9"
# 2) 同步到 tauri.conf.json + package.json（npm run build 会自动跑，这里显式跑一次）
node scripts/sync-version.mjs
# 3) 依赖全在缓存里，只有本 crate 重编，增量很快
export TAURI_SIGNING_PRIVATE_KEY="$(cat /d/tmp/updtest/smoke.key)"
export TAURI_SIGNING_PRIVATE_KEY_PASSWORD=""
npx tauri build 2>&1 | tail -20
```

记下产物路径与新 `.exe.sig` 内容。

### 5.5 起「真签名」的本地源

`fake-update-server.mjs` 支持替换签名与产物，但要指向**真实 exe 文件**，用一层薄包装即可：

```bash
# 把产物放到一个目录，用 python 起静态服务（自带 Content-Length，进度能算）
mkdir -p /d/tmp/updsrc && cd /d/tmp/updsrc
cp "/d/AItool/winapp/cc-bridge/desktop/src-tauri/target/release/bundle/nsis/"cc-bridge_99.9.9_x64-setup.exe .
SIG=$(cat cc-bridge_99.9.9_x64-setup.exe.sig)
cat > updater.json <<JSON
{
  "version": "99.9.9",
  "notes": "本地全真测试",
  "platforms": {
    "windows-x86_64": {
      "signature": "$SIG",
      "url": "http://127.0.0.1:8899/cc-bridge_99.9.9_x64-setup.exe"
    }
  }
}
JSON
python -m http.server 8899 --bind 127.0.0.1
```

### 5.6 跑

```bash
RUST_LOG=info,tauri_plugin_updater=trace \
CCBRIDGE_UPDATE_ENDPOINT=http://127.0.0.1:8899/updater.json \
  "D:/soft/cc-bridge/cc-bridge-desktop.exe" > /tmp/app-upd.log 2>&1 &
```

| # | 检查点 | 预期 / 证据 |
|---|---|---|
| C1 | 检查更新 | 出现 `更新 v99.9.9` |
| C2 | 下载并更新 | 进度走完 → `update:ready` |
| C3 | 安装 | 窗口关闭 → NSIS 进度条 → 自动重启 |
| C4 | **硬证据** | `(Get-Item "...\cc-bridge-desktop.exe").VersionInfo.FileVersion` = `99.9.9` |
| C5 | 崩溃安全 | 更新前故意在界面上改一个设置、生成一条审计；更新后仍在（进程被 taskkill，验证写盘不是「先清后写」） |
| C6 | 二次更新 | 再指回 2.9.1 的 manifest（version 写 100.0.0 也行）能再升一次，不卡在首次状态 |

### 5.7 🔴 收尾（必做，否则仓库带毒）

```bash
cd /d/AItool/winapp/cc-bridge
git checkout -- desktop/src-tauri/Cargo.toml desktop/src-tauri/tauri.conf.json desktop/package.json
git status --short | grep -E "Cargo.toml|tauri.conf.json|package.json"   # 必须为空
# 把本机装回官方版本
cd /d/tmp && "/c/Program Files/GitHub CLI/gh.exe" release download v2.9.1 \
  --repo lzlkyb/cc-bridge --pattern "cc-bridge_2.9.1_x64-setup.exe"
./cc-bridge_2.9.1_x64-setup.exe
rm -rf /d/tmp/updtest /d/tmp/updsrc
```

> ⚠️ 这次改了**三个**文件：`Cargo.toml`（版本真源）、`tauri.conf.json`（pubkey + version +
> `dangerousInsecureTransportProtocol`）、`package.json`（同步过来的 version）。三个都要
> `git checkout` 回来。

## 6. 缺口：这条链路目前没有自动化测试

现状：`commands/update.rs` 零单测；`contexts/UpdateContext.tsx` 零 vitest。
这次修的 `SingleFlight`、`totalBytes` 读数、8 秒倒计时、`restarting` 复位，全靠人工点。

1. **`UpdateContext` 状态机单测**（vitest，mock `listen`/`invoke`）——把 7 个事件按顺序推给

## 8. 实测战果：假签名暴露真 P1 bug（2026-10-18 已修复）

Layer 1–3 用假源实测时，`--mode` 默认（假签名）路径抓到一个真 bug，链条如下：

**现象**：点「下载并更新」→ 20MB 下载到 100% → 验签失败（`Invalid encoding in minisign data`）
→ **app 在 +9.2s 被自行 relaunch**，但更新根本没装上。日志时间线：05:06:37 验签失败 →
05:06:46 app 重启，正好一个 `AUTO_RESTART_DELAY_SECS`。

**根因**（三层对齐后定位）：

1. 插件 `updater.rs:709-713`：`on_download_finish()` 回调在 `verify_signature()` **之前**触发；
2. 我们在 `commands/update.rs` 里用这个回调 emit `update:ready`；
3. 前端 `UpdateContext.tsx` 收到 ready → `status="ready"` → 自动重启倒计时 9.2s 到点 relaunch。

生产影响：只要发布了一个签名不匹配/损坏的包，用户点一次下载就会被无故重启，
且重启后版本没变、可再次触发。

**修复**（`commands/update.rs`）：`on_download_finish` 回调改空操作；
`update:ready` 移到 `download_and_install(...)` 成功返回之后才 emit。
Windows NSIS 成功路径走不到 emit（`install_inner` 以 `process::exit(0)` 收尾，
重启由安装器负责），macOS/Linux 走到 emit、前端倒计时才有意义——语义恰好各自正确。

**修复后实测**（同假源重跑）：下载 → 验签失败 ×2（`retry_with_backoff(2)`）→
发 `update:error` → toast「更新失败，请重试」+ 徽章红色「⚠ 重试」；
**PID 全程不变**（13:19:31 启动的进程活过了整条失败路径），无 relaunch、日志无 `update:ready`。

**连带发现**：

- dev 链路（vite/tauri dev）退出后 app 若还活着，前端懒加载会报
  `Failed to fetch dynamically imported module: .../RcOverlay.tsx`——不是代码回归，
  是 dev 服务器掉了，重启 dev 即可。
- 应用启动时假源不可用 → 三轮退避全失败 → 徽章不出现；假源恢复后需等下一轮定时检查
  或手动触发（设置页「关于」组的检查按钮）。
- `tauri.conf.json` 加 `--remote-debugging-port=9222` 到 `additionalBrowserArgs`
  会导致 WebView2 创建失败（0x8007139F），两种参数组合都试过——**别用这条路做 UI 取证**，
  用 `desktop-window-screenshot` + `updtest/win.py`（SetForegroundWindow + 截图 + 点击）替代。
