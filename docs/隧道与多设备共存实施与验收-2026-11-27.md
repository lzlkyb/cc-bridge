# 隧道与多设备共存实施与验收（同一账号、两台电脑、同一台服务器）

## 结论先说

用户场景：**同一台服务器、同一个 SSH 账号，两台电脑各跑一个桥，接到同一个项目（或全局）**。

改之前**跑不起来**：后上线的那台会撞在同一个反向隧道端口上，停连并只能人工点「重新接入」；项目级还被直接拒绝。现在四条缺口都补上了，并且**全部以「多设备接入模式」开关为门控**——关闭多设备的连接继续使用原账本和原端口候选。

## 四条缺口

1. **端口账本按账号、不按设备。** 账本在服务器账号 home 下（`~/.cc-bridge/tunnel-port`），两台机器读同一本账、认领同一个号。历史提交 `f8de291` 只覆盖了「不同账号各自一本账」的情况，同账号多设备仍共用。
2. **恢复路径不重分配。** 自动恢复（`op.access.is_none()`）只试 `saved.port`，撞号即「服务器拒绝监听」并停连；用户看到的只是「请在接入页点「重新接入」」。两台电脑轮流开机是常态，每次都要人点一下，等于这个功能没做完。
3. **项目级被拒。** `validate_setup` 直接拒绝「多设备 + 项目级」，前端也把开关藏在 `scope === "user"` 后面。
4. **旧条目被沿用。** 服务器上残留 legacy `cc-bridge` 条目时，多设备连接会把它当成本机条目继续改写，两台机器互相覆盖。

## 改动

### 端口账本按设备分文件

- `tunnel_ledger(multi, device_id)`：多设备时路径为 `tunnel-port-<尾号>`，否则仍是原来的 `tunnel-port`。
- `ledger_device()` 清洗尾号：只留 ASCII 字母数字与 `-_`，限长 32，空值退成固定串 `device`——它会进文件名，不能留路径分隔符之类的东西。
- `configure.py` / `reallocate.py` 写账本时统一带上 `multi` 与 `deviceId`，保证「写的账」和「读的账」是同一本。
- `inspect` 的 `tunnelPort` 在多设备下取本机账本的值；`describe` 在多设备下不再把 legacy `cc-bridge` 当成本机条目（本机条目名是 `cc-bridge-<尾号>`）。

### 撞号后自动换号重接

- 监管线程判到「服务器拒绝监听」且这条连接是多设备（见下节门控）时：先把状态写成人能看懂的提示（"正在自动换号重接"），再 spawn `recover_multi_port`，**不再**把「请点重新接入」丢给用户。
- `recover_multi_port` → `heal_multi_port`：重读服务器接入（`multi = true`，读本机那本账）→ 只挑本机条目（先认上次写过的 target id，其次认「名字 = `cc-bridge-<尾号>` 且令牌匹配」）→ 走一次 `configure`。
- `configure` 的候选端口在多设备路径下优先本机账本里的号；那个号若被占，本地一轮候选之后走服务器重分配（`reallocate_script(multi, deviceId)`，写回同一本账），不会在同一个号上来回撞。
- 自愈全程只改本机自己的条目，不碰另一台电脑的。

### 项目级放开

- `validate_setup` 去掉「多设备必须全局」的限制：条目名已经按设备区分了，项目级 `.mcp.json` 里同样能并存两条。
- 前端「更多设置」在两种范围下都渲染多设备开关；说明文案按范围切换（全局 `~/.claude.json` / 项目 `.mcp.json`）。

## 不回归的边界

用户要求是「**没启用多设备就按现在的代码走**」，逐条对齐：

| 位置 | 未开多设备时 |
|---|---|
| `tunnel_ledger` | 返回原路径 `tunnel-port`，与从前一致 |
| `describe` / inspect | `known` 判据等价于原逻辑；`tunnelPort` 取原账本 |
| `configure` / `reallocate` payload | `multi: false`，条目名仍是 `cc-bridge` |
| 监管线程自愈 | 门控 `enabled && multi_device` 为假，不触发，照旧提示用户 |
| `validate_setup` | `multi` 参数不再参与判断——原来也只拒了「多设备 + 项目级」，其它组合行为不变 |
| 前端 | 开关可见性只在项目级新增；已开多设备的用户文案随范围变化 |

额外两条硬约束：

- 自愈前检查 `stable_operations` 里这条连接是否正在配置；正在配置（`active`）就放弃，避免两个写者抢同一台服务器。
- 监管线程拿不到配置读锁时会显示重试提示。后台查完远端后会再次核对失败的隧道实例和已保存的接入，避免覆盖用户刚做的变更。

## 验证

- Python 夹具覆盖多设备独立账本、离线设备的端口保留、端口重分配、旧条目归属，以及过期检查结果无法覆盖或迁移另一台设备的条目。
- Rust 测试覆盖自动重接的准入、接入变更后的快照校验、保持当前选中的接入，以及远端脚本的 Windows 命令行长度预算。
- 前端交互测试覆盖项目级开关、重新检查时停用提交，以及提交新检查取得的端口和配置。

## 对抗审查（第二轮自审，2026-11-27）

按「怎么让它出错」重过一遍，找到 4 处真问题并已修，另有 3 条确认为不成立或可接受。

### 已修

1. **自愈会把用户刚点的「断开」悄悄撤销。** `heal_multi_port` 先读一次服务器接入（往返数秒），
   再拿着这份快照去重配。这期间用户点「断开」并写完 `enabled=false`，自愈照样把连接拉起来，
   `configure` 还会把 `enabled` 写回 true。修法：拿到启停锁后**复核一次**配置里的这条连接是否
   仍是 `enabled && multi_device`（与 `stable_connect_stop` 用同一把锁排队，窗口才真正关掉）。
2. **识别不到本机条目时会白跑一趟。** 归属筛选用的是路径严格相等，`/work` 与 `/work/`
   会被当成两个项目 → 找不到 target → 交给 `configure.py`，而它在「同名条目已存在又没有
   target」时直接 `CCB_TARGET_REQUIRED`。修法：路径比较先去掉尾斜杠。
3. **认错条目等于替另一台电脑改配置。** `configure.py` 的写入名取 `selected['name']`，
   所以自愈认到谁的条目就会写谁。原实现只按「上次记录的 target id」认，没有核对名字与范围。
   修法：抽成 `adopts_entry()`，要求范围一致且名字是本机尾号（或老固定名 + 令牌是本机），
   并加单测 `heal_only_adopts_its_own_entry_in_the_saved_scope`，做过变异验证（判据恒真 → FAILED）。
4. **自愈退出时留下一句不会发生的承诺。** 监管线程先写「正在自动换号重接」，而自愈可能因为
   用户刚断开、正在配置、读不到服务器、或前置条件变化而退出，那句提示就成了空话。
   修法：新增 `announce()`，只在隧道仍处于错误态时改写为「自动换号没成功，请点重新接入」；
   换号成功则改成「已自动换到 N 重接，若在别处复制过地址请重新复制」。

顺带补了两条前置条件：自愈前要求 `ssh_enabled && !remote_tls_enabled && transport == http &&
mcp_running`，与用户手动「重新接入」的准入一致，避免后台写出一条连不上的条目。

### 确认不成立 / 可接受

- **「关掉多设备后 `describe` 判据变了」——不成立。** 逐字对比 HEAD：原判据是
  `name in ('cc-bridge', 'cc-bridge-' + deviceId)`，新代码在 `multi` 为假时等价。
- **「密码型连接自愈不了」——与现状一致。** `SshLink::from_config` 只从配置取服务器信息，
  运行期密码不落盘（`supervise` 退出即清零），自动恢复同样拿不到，属于既有边界。
- **「两台机器同名尾号会互踢」——复制配置才会发生。** `device_id` 是「这一份安装」的身份，
  导入配置时会被本机值覆盖；只有手工整份拷贝配置才可能撞名，UI 上能看到尾号可诊断。

## 已知边界
- **自愈链路本身没有集成测试**：它需要真实的 `AppHandle`、真实 ssh 服务器与两台设备。能测的部分已抽成纯函数（`auto_reconnects_on_port_conflict`）并加了变异验证；`heal_multi_port` 的编排部分靠代码路径审查，未做端到端跑测。
- 已分配端口在设备离线时继续保留。两台设备同时首次接入仍可能竞争，遇到端口冲突会尝试换号一次。
- 多设备 + 项目级：条目写在服务器项目目录的 `.mcp.json`，范围迁移会在写入前重新核对所选条目的归属。
- 未在用户服务器上执行真实的两机并发接入；本轮验收基于夹具、单测与代码审查。
