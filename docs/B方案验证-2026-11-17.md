# B 方案（SFTP 长连接）验证报告

> 2026-11-17。A+C（helper 读写 + CodeMirror 编辑器）已落地后，对预留的 B 方案做可行性验证。
> 结论先行：**B 的「借 helper 会话讲协议」形态已实测判死；「管道 + 免交互认证」形态技术成立但 ROI 低于一条更轻的替代路线。**

## 一、B 方案定义与要验证的问题

B 方案 = 用 SFTP 协议取代「一次性 scp 进程」，让一次连接承载多次文件操作。它有两条实现形态，验证问题各不相同：

| 形态 | 设想 | 必须验证的问题 |
|---|---|---|
| **B2** | 在已认证的 helper 会话里 `exec sftp-server`，复用登录 | ConPTY 通道能否承载二进制协议帧 |
| **B1** | Rust spawn `ssh -s sftp` 新进程，管道讲 SFTP v3 | 密码认证如何免交互；收益是否值得 |

## 二、验证矩阵

| # | 验证项 | 方法 | 结果 |
|---|---|---|---|
| 1 | ConPTY 输出方向能否透传二进制 | portable-pty 探针：slave 写 256 字节，master 收 | ❌ **不通** |
| 2 | ConPTY 输入方向能否透传二进制 | master 写 256 字节，slave read | ❌ **不通** |
| 3 | Windows 上能否把 PTY 设成 raw 救场 | slave 执行 `stty raw` | ❌ **机制不存在** |
| 4 | 管道模式下密码认证能否免交互 | `SSH_ASKPASS` + `SSH_ASKPASS_REQUIRE=force` | ✅ **成立** |
| 5 | 远端是否具备 sftp-server | banner 探测 + 发行版默认组件推断 | ⚠️ **间接成立，未直连** |

## 三、关键实测数据

### 3.1 ConPTY 二进制不安全（B2 判死）

探针：`src-tauri/examples/pty_binary_probe.rs`（portable-pty 0.8.1 + ConPTY + 本机 python）。

- **输出方向**：slave 写 `00..ff` 256 字节，master 收到 598 字节。前 18 字节全部变形错位（`00->07`、`01->1b`、`02->1c`…）——ConPTY 把控制字节解释成 ANSI 转义序列/回显记法。SFTP 帧头是 4 字节小整数长度字段，正落在这片变形区，**帧长不可信，协议无法解析**。
- **输入方向**：master 写 `00..ff`，slave 回显显示 `0x00–0x09` 彻底消失、控制字符被终端层消费、`0x0A` 提前断行（canonical 模式按行提交，后续字节滞留缓冲）。
- **raw 救场**：探针原设计用 `stty raw -echo` 绕过，实测 `'stty' 不是内部或外部命令`——**Windows 没有 stty/termios**，slave 侧（Windows 程序）根本没有设置 raw 的机制；ConPTY 主机的转换层也不受 slave 控制。前两场景里的 `stty raw` 全部静默失败，S2 输出反而被解释成 `ESC[2J`（清屏）——「raw 能救」这个假设连前提都不存在。

这与 helper 的文本哨兵设计互证：哨兵全是可打印 ASCII，正是为了待在 ConPTY 的安全区。

### 3.2 askpass 免交互成立（B1 认证有解）

```
SSH_ASKPASS=<bat> SSH_ASKPASS_REQUIRE=force ssh -o PreferredAuthentications=password ...
debug1: read_passphrase: requested to askpass
lizuliang@10.0.19.194: Permission denied (publickey,password).
```

`read_passphrase: requested to askpass` 证明 ssh.exe 在无 TTY 的管道模式下确实执行了 askpass 程序（喂假密码后认证失败，符合预期）。OpenSSH 10.3p1（本机）支持该机制。

### 3.3 远端环境

- banner：`OpenSSH_8.9p1 Ubuntu-3ubuntu0.18`。Ubuntu 的 openssh-server 默认启用 `Subsystem sftp /usr/lib/openssh/sftp-server`，存在概率极高，但**未直连验证**。
- TCP RTT：5.2 / 13.5 / 18.6 ms（内网 10.0.19.194，三次）。

### 3.4 一个容易被忽略的现状：scp 已经在跑 SFTP 协议

`run_scp` 先探测 `scp_supports_sftp_protocol`，本机 scp 10.3p1 usage 选项簇含 `s`（`[-346ABCOpqRrsTv]`），通过即传 `-s`——**现有 scp 传输跑的就是 SFTP 协议**，只是每次新起进程、新连接。B1 相对现状的增量只剩「一条连接多次操作」。

## 四、结论与建议

### 4.1 B2 判死，不再投入

ConPTY 双向二进制不安全且无 raw 机制，「在 helper 会话里切 sftp-server」没有可行性。

### 4.2 B1 技术成立但 ROI 不划算

| 维度 | B1（手写 SFTP v3 over stdio） |
|---|---|
| 收益 | 批量 N 个文件省 N−1 次握手。单次握手 ≈ 冷启 75ms + RTT + KEX + 认证；内网约 100–200ms，VPN/跳板下秒级 |
| 成本 | SFTP v3 客户端约 700 行（帧编解码 + 状态机 + READ/WRITE 分块窗口）+ 全套测试；传输取消/进度机制要从 `spawn_capture` 的 monitor-kill 模式重写；askpass 凭据传递需具名管道 + 辅助 exe |
| 风险 | askpass 若用临时脚本 = **密码明文落盘**，违反「凭据仅在内存」纪律；stdio 全双工存在潜在写死锁；远端 sftp-server 版本差异（SFTP v3/v4/v5/v6）要兼容 |

### 4.3 建议改走「scp 多源合并」

`scp -s host:/a host:/b host:/c localdir/` 是 scp 原生多源能力，**一次进程传 N 个文件**，收益与 B1 相同（省 N−1 次握手），而：

- 零新协议代码，`run_scp` 已是 `-s` 模式；
- 复用现有 `spawn_capture` 取消/进度/错误体系；
- 无凭据落盘新面。

代价：批量进度粒度从「每文件一个 transfer_id」变粗；多源远端路径的引号处理可复用 `shell_quote` 经验。预估 100–200 行改动。

当前批量下载循环在 `useSshFileSelection.ts:61`（`downloadSelected` 逐个 `await onDownload`），合并点清晰。

## 五、未验证项（需一次真机密码）

1. 远端 sftp-server 实际存在与版本（现只有 banner + 发行版推断）；
2. SFTP v3 over 管道往返耗时、大文件分块稳定性——仅在选择 B1 实施前才需要；
3. 若改走多源合并：多源 scp 在 `-s` 模式下对含空格/特殊字符路径的行为。
