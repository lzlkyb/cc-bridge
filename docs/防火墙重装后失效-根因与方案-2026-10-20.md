# 防火墙重装后失效：根因与方案（2026-10-20）

## 一、现象

用户反馈两件事同时成立：

1. **重装软件后必须再点一次「一键修复规则」**，否则远程连不上。
2. **连接页却显示「防火墙已放行」**（服务链路图第三个圆点绿色）。

两个现象看似矛盾，实际来自**两个互不通信的判定源**：一个把废规则当放行（假绿），另一个正确地判未放行（告警块）。用户看到的绿色来自前者。

## 二、实测取证

### 2.1 安装后的可执行文件名是 `cc-bridge-desktop.exe`

```
D:\soft\cc-bridge>  cc-bridge-desktop.exe   uninstall.exe
```

依据：`Cargo.toml` 的 package 名是 `cc-bridge-desktop`，`tauri.conf.json` 未设 `mainBinaryName`，
Tauri 取首个 bin target 名作为主二进制名（NSIS 模板里对应 `${MAINBINARYNAME}`）。

### 2.2 安装器写规则时却用了 `cc-bridge.exe`

`desktop/src-tauri/installer-hooks.nsh:23`

```nsis
nsExec::ExecToLog 'netsh ... add rule name="cc-bridge (7823/TCP)" ... program="$INSTDIR\cc-bridge.exe"'
```

→ 安装/升级后落地的规则 `program=` 指向一个**不存在的文件**。Windows 会接受这条规则（netsh 返回 0），
但没有任何进程能匹配它，等于没放行。

本机 `netsh advfirewall firewall show rule name=all dir=in verbose` 实测：

```
Rule Name: cc-bridge (7823/TCP)   Program: D:\soft\cc-bridge\cc-bridge-desktop.exe   ← 应用内一键修复写的（正确）
Rule Name: cc-bridge             Program: ...\target\debug\cc-bridge-desktop.exe    ← 安全弹窗/开发版遗留，LocalPort=Any
```

正确那条的 program 是应用内 `current_exe()` 写进去的，不是安装器写的。这直接证明：
**安装器写的规则从来没有正确过，用户每次靠「一键修复」补救。**

### 2.3 安装器的「先删后加」会覆盖掉用户已修好的规则

`installer-hooks.nsh:19-23`：`delete rule name="cc-bridge (7823/TCP)"` → `add ... program="...\cc-bridge.exe"`。

- 覆盖升级（updater）：用户上次一键修复写入的正确规则**同名**，被 delete 掉，再被错误规则替换。
- 卸载重装：`NSIS_HOOK_PREUNINSTALL`（第 34 行）先删掉正确规则；若 POSTINSTALL 因未提权（currentUser 模式）失败，
  则一条规则都不剩。

两条路径结果一样：重装后规则失效，必须再点一次。

### 2.4 「已放行」是粗粒度 netsh 判定的假绿

两个判定源：

| 展示位置 | 数据来源 | 判据 |
|---|---|---|
| 连接页服务链路图（`serviceChain.ts:183-190`） | `status.firewallPortOpen` | `firewall.rs:160-212` 的 `parse_inbound_allow` |
| 连接页告警块 / 设置页卡片 | `get_firewall_diagnosis` 缓存 | `firewall_diag.rs::analyze`（看 program / profiles / enabled / block） |

粗粒度解析只看四个字段：方向=入站、操作=允许、协议 TCP、本地端口 == 7823。
**不看 `Program`、不看 `Profiles`、不看 `Enabled`**：

```rust
// firewall.rs:203-209
let dir_ok = direction.contains("入站") || ...;
let act_ok = action.contains("允许") || ...;
let proto_ok = proto.is_empty() || proto.to_uppercase().contains("TCP");
let port_ok = localport == port || localport.split(',').any(|p| p.trim() == port);
```

于是「名字对、端口对、程序路径是废的」这条规则被算作已放行 → 链路图绿 → 用户看到「防火墙已放行」。

同一份事实到了 `analyze` 里：`allow_rules` 要求 `program_matches` 为真（`firewall_diag.rs:721-725`），
废规则进 `stale_rules` → `port_open=false` → 告警块红「未放行端口 + 残留废规则」。

**两个 UI 自己打架，而绿色的那个是错的。**

### 2.5 首屏还会额外取一次粗粒度结果

`commands/status.rs:273-291`：`cache.checked_at.is_none()` 时直接调 `query_firewall_state`（粗粒度），
不用结构化诊断。启动瞬间结构化诊断（PowerShell 冷启动 + netsh 全量枚举约 1–4s）还没跑完，
所以首屏必然是粗粒度结论。若本机 PowerShell 诊断不可用（组策略 / 安全软件拦截），
`query_full` 会永久回退到粗粒度（`firewall.rs:86-89`），假绿就一直存在。

### 2.6 附带问题（不阻塞连通，但脏）

- 安装器端口写死 7823（`installer-hooks.nsh:21-23`）。用户改过端口后重装，装出来的是错端口的规则，
  真正端口的规则仍缺失；且安装器只会删 7823 的同名规则，其他端口规则永久残留。
- `build_repair_script` 只删 `name=当前端口规则` 和 legacy `cc-bridge`，**不清理旧端口规则**
  （`firewall_diag.rs:211-232`）→ 改端口后残留。
- 安装器按名字删 `cc-bridge`，会连带删掉 Windows 安全警报弹窗建的 TCP+UDP 成对规则（本机那两条）。

## 三、方案

### 方案 A（推荐，最小改动）：修安装器 + 不再覆盖用户规则

1. **`installer-hooks.nsh:23`**：`program="$INSTDIR\cc-bridge.exe"` → `program="$INSTDIR\${MAINBINARYNAME}.exe"`。
   `${MAINBINARYNAME}` 由 Tauri 模板顶部 `!define` 提供，值是 `cc-bridge-desktop`。
2. **POSTINSTALL 改成「缺才写」**，不无条件 delete+add：
   ```
   nsExec::ExecToStack 'netsh advfirewall firewall show rule name="cc-bridge (7823/TCP)"'
   Pop $0   ; 退出码：0 = 规则存在
   ${If} $0 != 0
     ... add rule ...（带 ${MAINBINARYNAME}）
   ${EndIf}
   ```
   这样自动更新不会破坏用户已修好的规则；首次安装且提权成功时则一次到位。
3. **PREUNINSTALL 只在真卸载时清理**（保持现状即可，注意它会在卸载重装路径里删规则——若接受
   "重装后点一次修复"，可保留；若要求"重装后零操作"，见方案 A4）。
4. （可选）把「是否重装后需要点一次」的选择权交给用户：安装器结束时用 DetailPrint 提示
   「若首次启动提示未放行，点一次一键修复即可」——现状已有类似提示，保留。

### A 的前置事实：安装器可能根本没写进去

`installer-hooks.nsh:6-9` 自己写明：Tauri 默认 `installMode = currentUser`，安装器**不提权**，
`netsh add rule` 会因权限不足失败；钩子里 `Pop $0` 后只是 DetailPrint 一行提示，不中止安装。

所以「重装后必须点一次」有两种成因，A1（修路径）只解决第一种：

| 成因 | 修法 |
|---|---|
| 安装器提权成功，但写的是 `cc-bridge.exe` 废规则 | A1 + A2 |
| 安装器没提权，规则压根没写（旧规则又已被 PREUNINSTALL 删掉） | 只能靠：① 方案 B（规则不绑路径 + 卸载不删，重装后旧规则仍然有效）；② 改 perMachine（否决）；③ 接受「点一次」 |

这一点必须在选方案前拍板：**要「重装后零操作」且安装器不提权，只有方案 B 能同时满足。**

### 方案 C（必做）：统一真相源，堵掉假绿

1. **`commands/status.rs:273-291`**：首屏不要自己跑粗查询，直接调 `crate::firewall::refresh_cache(&state, port).await`
   （它内部走 `query_full`），读同一份 `cache.port_open`。一处判定、两条展示。
2. **`firewall::query_full` 的 netsh 兜底改为 fail-closed**：兜底路径拿不到 program/profiles/enabled，
   就**不给 `port_open` 结论**（`port_open=None` + `source="netsh"`），前端已有「无法检测」态；
   或者在 `parse_inbound_allow` 里补齐三重校验（program 相等、profiles 覆盖活动配置、enabled=Yes）——
   但 netsh 非 verbose 输出没有 Program 字段，所以**建议直接返回 unknown**，别猜。
3. **前端单一来源**：`serviceChain.ts` 的 `firewallPortOpen` 改由 `get_firewall_diagnosis` 提供
   （或在 `status` 里让该字段直接取 `diagnosis.port_open`），删掉「粗粒度布尔」这条链。
4. **补测试**：
   - 废规则（端口/协议/方向全对、program 指向别的路径）不得被判 `port_open=true`。
   - 粗粒度兜底路径对「有规则但无法校验 program」返回 `None` 而非 `true`。
   - status 首屏与诊断面板对同一事实给出同一结论（可用 `analyze` 单测锁死，避免真跑 netsh）。

### 方案 B（🔴 已否决，2026-10-20 决定不做）：规则不绑程序路径

把入站规则改成 `program=any`（只锁 `localport=<port>` + `profile=any`）：

- 优点：重装、覆盖升级、换安装目录、改程序名**都不需要重建规则**；安装器写错路径的问题自然消失。
- 缺点：任何监听该端口的进程都被入站放行（现在是指定 exe）。缓解因素：端口固定、服务有 token 鉴权、
  仅入站 TCP。对「装完即用、永不点修复」的体验收益很大。
- 不建议做成双规则（精确 + 兜底），维护成本高、语义混乱。

### 推荐组合

**A1 + A2 + C1 + C2 + C3 立刻做**（纯修复，无体验/安全降级，装完即用）；
**B 单独拍板**，若要彻底消灭「重装后再点一次」，B 是唯一能覆盖「安装器根本没提权」场景的解法。

## 五、验收用例

1. **干净卸载 → 提权安装 → 首次启动**：连接页链路图与设置页卡片都显示「已放行 7823/TCP」，无需点修复。
2. **覆盖升级（updater）**：升级前后规则 `program=` 不变且指向真实 exe；不出现「未放行」。
3. **手工把规则 program 改成不存在的路径** → 两处都显示未放行 + 残留废规则；点一键修复后恢复。
4. **模拟 PowerShell 诊断不可用**（临时改名 `Get-NetFirewallProfile` 不可行时可直接改代码返回 None）：
   显示「无法检测」，绝不显示「已放行」。
5. **仅覆盖 Public、当前网络 Private**：两处都判未放行（结构化侧已有单测）。
6. **改端口 7823 → 8080 后重装**：不出现 7823 的废规则残留（或残留但不影响 8080 判定）。

## 六、不做的事

- 不改成 perMachine 安装（会让静默自动更新也要 UAC，代价大于收益）。
- 不在应用启动时自动弹 UAC 静默修复（R17：不做二次确认门；UAC 必须用户主动触发）。
- 不动 `build_repair_script` 的「先删后建」幂等结构（它是对的，问题在安装器那份脚本）。
- **不把规则改成 `program=any`（方案 B 已否决，2026-10-20）**：规则继续绑定本程序路径，
  保持「只放行 cc-bridge 自身」的语义。代价是 currentUser 非提权安装下，装完 / 重装后仍需
  点一次「一键修复」——这是明确接受的取舍，不是遗留缺陷。若日后又想去掉这一次点击，
  正确路径是重新评估安全边界，而不是顺手改 `program`。

### 方案 B 的处理（同日决定：不改）

方案 B 已起草（`build_repair_script` / `manual_command` 改为 `program=any`、安装器 PREUNINSTALL 不删规则），
**在落笔阶段被否决并已全部回退**，`git diff` 里不含任何 B 痕迹（可用
`grep -rn "program=any" desktop/src-tauri/src` 复核，应为空）。

否决理由（比方案阶段的评估更强）：B 的收益是「重装免点一次」，代价是**把入站放行的范围从
单个 exe 扩大到该端口的任意进程**，并且必须靠「卸载不删规则」来兜底 —— 即用户卸载后
机器上仍留着一条放行规则。两者叠加，等于用长期的安全面换取一次点击，不划算。

接受的结果：currentUser 非提权安装下，装完 / 重装后仍需点一次「一键修复」（一次 UAC）。
A 已保证这一次点击**真的有效**（规则 program 指向真实 exe），C 已保证点了之前界面说的是真话。

### 与方案的两处偏差（都有理由）
1. **A2 没有改成「规则存在就跳过」**：安装器读不出规则里的 `program` 是否对得上（解析 netsh 文本太脆），
   「存在就跳过」会让上一版写错的废规则永久留存，反而把需要修复的用户钉死在坏状态。
   改为「先删同名再加」的幂等重建 —— 路径正确后，对已修好的规则是无损重建。
2. **C3 没有改前端取数路径**：C1 之后 `status.firewallPortOpen` 与 `diagnosis.portOpen` 是同一份
   `firewall_cache.port_open`，天然同源，不需要再改 `serviceChain` 的数据来源。
   真正需要补的是「null 到底是检测中还是查不了」，所以新增 `checkedSecondsAgo` 字段并在链路图分档。
