# 发版提速：并行构建 + 发布独立成 job（2026-11-28）

## 一、改之前到底慢在哪（真实数据，不是估算）

取 v3.4.1 成功那次 run（`46057472698`）的计时：

| job | 起点 | 终点 | 时长 |
|---|---|---|---|
| Build macOS app (arm64) | 19:33:13 | 19:54:06 | **20 分 53 秒** |
| Build Windows exe + installer | 19:54:08 | 20:22:19 | **28 分 11 秒** |
| **合计（推 tag → Release 公开）** | 19:33:13 | 20:22:19 | **49 分 6 秒** |

Windows 那个 28 分 11 秒里，**构建其实只占 21 分 48 秒**（到 upload-artifact 结束），
后面 6 分 15 秒是发布动作：

- 确认签名 1s（缓存热）
- 安装版冒烟 37s
- Release 公开 36s
- Gitee 附件上传 30s
- **清单发布 3 分 53 秒**（clone releases 分支 → push → 四段验证）
- rust-cache 回写 38s

两件事叠加才慢：

1. **两个平台串行**。`build-windows` 有 `needs: [build-macos]`，因为 `updater.json`
   只能有一份，而它需要 mac 的安装包条目才能写出双平台清单。于是 mac 跑完 21 分钟，
   Windows 才开始，Windows 又跑 28 分钟。
2. **发布动作挂在 Windows job 尾巴上**，白占了串行时间。

v3.4.0 那次更慢（60 分 51 秒），Windows 单 job 就 37 分 57 秒 —— 冷缓存下波动很大，
下面的收益按 v3.4.1 这个较快的基线算。

## 二、改成了什么样

```
tag push
   ├── build-macos ────┐  （只交付产物）
   ├── build-windows ──┤  （只交付产物）
   └───────────────────┴──> publish  （清单 / Release / Gitee）
```

- `build-windows` 去掉 `needs: [build-macos]`，两个构建 job **完全并行**；
  同时去掉 `contents: write`（它不再碰 Release，按最小权限只读）。
- 新增 `publish` job（`needs: [build-macos, build-windows]`，`windows-latest`），
  承接原来挂在 Windows job 尾巴上的七件事：生成清单、验签、安装版冒烟、
  建 Release / 上传 / 公开、Gitee 附件、清单推 releases 分支。
- `concurrency: ccbridge-publish-stable` 从 build-windows 移到 publish ——
  现在「不能并发」的是发布，不是构建。
- 跨 job 传 **json 片段**的机制整个删掉（`updater-macos.json` / `updater-macos-gitee.json`
  / `UPDATER_MERGE_INTO`）。publish 把两个平台的产物摆回 `bundle/nsis/` 与 `bundle/macos/`
  之后跑一次脚本，双平台条目一次写出。片段机制当初存在的唯一理由就是「两个平台分属
  不同 job、各自只看得到自己」——那个前提现在没了。

### 为什么发布必须是单独一个 job，而不能留在任一端

`updater.json` 只能有一份。两个平台各自生成并 attach 会**静默互相覆盖**：后跑的
盖掉先跑的平台条目，那个平台的用户从此检测不到更新，**且不报错**。所以谁都不能在
「另一个平台的产物还没到」的时候就写清单。串行能保证这点（所以以前是串行），
而抽成 publish 也能保证（它 `needs` 两个 job），且不牺牲并行。

## 三、本地 push 的那 6 分钟（C）

发版要推两次：`git push origin main`，然后 `git push origin vX.Y.Z`。两次都触发
pre-push 钩子，每次都跑一遍全量门禁 —— 而第二次推的是**同一个提交**。

现在钩子顶部会读 git 传进来的 ref 列表，判定：

> 只推 tag，**且**每个 tag 指向的提交已在 `refs/remotes/origin/main` 的历史里

成立就跳过 `[6] cargo clippy` 与 `[7] cargo test`（约 5~6 分钟），其余六项照跑
（前端五项 + `cargo fmt`，合计约 1 分钟）。`cargo fmt` 留着是因为它不到 1 秒。

为什么不加检查就跳过：tag 可以指向任何提交，包括开发分支上没走过门禁的。
「已在 origin/main 历史里」这个条件把范围限制在「就是某个 main 提交」，而 main
push 刚刚才在同一台机器上把全部门禁跑过一遍。

**回退行为（默认就是安全的）**：

| 情况 | 结果 |
|---|---|
| `git push origin main` | 全量（有非 tag ref） |
| `git push origin main --tags` | 全量（同上） |
| 只用 tag 名推、tag 指向 main 提交 | 跳过 Rust 两项 |
| tag 指向未合并提交（开发分支打 tag） | 全量 |
| 本地从没 fetch 过 main | 全量（找不到 `refs/remotes/origin/main`） |
| 空 stdin / 删除 tag | 全量 / 只跑前端（删除没有内容要验） |

CI 侧不依赖这个优化：tag 发版时两个构建 job 内部都有 `cargo test --release` 全量。

## 四、验证记录

改动只碰 `.github/workflows/build.yml`、`.githooks/pre-push`、`CLAUDE.md`，没有动源码。

**1. workflow 结构**（js-yaml 解析 + 断言）

```
jobs: up-to-date, frontend, python-remote, test, check-macos, smoke-macos,
      build-macos, build-windows, publish
build-windows: needs=undefined（并行）  permissions=继承顶层 read
publish: needs=["build-macos","build-windows"]  permissions={contents: write}
publish steps=15，顺序：checkout → download(两 artifact merge) → 摆回 bundle →
        node/rust/sccache 清空/rust-cache → 抽取说明 → 生成 updater.json →
        copy 清单进 dist-out → 验签测试 → 安装版冒烟 → Release → Gitee
```

静态反向检查：build-windows 里已无 `gh release` / `GITEE_TOKEN` / 上传清单；
publish 里已无 `mac-artifact` / `TAURI_KEY_FILE` / `updater-macos` 片段。

**2. 清单脚本**（隔离目录，假产物，不碰真实 target）

摆入 `nsis/cc-bridge_3.4.1_x64-setup.exe(.sig)` 与 `macos/cc-bridge.app.tar.gz(.sig)`，
跑两次脚本：

| 变体 | 平台 key | URL |
|---|---|---|
| GitHub | windows-x86_64, darwin-aarch64 | `https://gh-proxy.com/https://github.com/.../download/v3.4.1/<file>` |
| Gitee | windows-x86_64, darwin-aarch64 | `https://gitee.com/<repo>/releases/download/v3.4.1/<file>` |

`notes` 透传了 `UPDATER_NOTES` 并带上 `cc-bridge-release-history:` 元数据，
签名非空校验生效。

**3. 钩子判定**（把判定段抽出来，喂真实 git 对象）

```
1 tag 指向 origin/main 提交      → 跳过 Rust（SKIP=1）
2 tag 指向孤立提交(commit-tree)   → 全量（SKIP=0）
3 main + tag 同推                → 全量（SKIP=0）
4 空 stdin                       → 全量（SKIP=0）
5 只推分支                       → 全量（SKIP=0）
6 ref 名含 $                     → 正确解析，未发生变量展开（SKIP=1）
```

第 6 项对应一个真实修过的缺陷：原先用 `<<EOF` here-doc 喂内容，here-doc 会对内容
再做一次参数展开，ref 名里合法出现的 `$` 会被当成变量而变形。改成先落临时文件
（`trap` 清理）再重定向读。

## 五、收益

第一轮（A+C）落地后，第二轮又做了四件事（见 §七、§八），两轮叠加的账：

| 口径 | 改前（v3.4.1 实测） | 第一轮 A+C | 第二轮之后 |
|---|---|---|---|
| mac 构建 job | 20:53 | 20:53 | 3~8 分（命中缓存）/ 13 分（冷） |
| Windows 构建 job | 28:11 | 21:48 | 4~9 分（命中）/ 17 分（冷） |
| 验证（frontend/test/check-macos） | 塞在 build 里串行 | 同左 | 最长 12 分，**与 build 并行** |
| publish（Release 公开） | 含在 Windows 内 6:22 | 约 2.5 分 | 约 2.5 分 |
| Gitee 镜像 | 阻塞 4 分钟 | 阻塞 4 分钟 | **并行，不阻塞** |
| **用户能下载到新版** | **约 23 分** | 约 24.5 分 | **约 17 分（冷）/ 12 分（热）** |
| **CI 总时长** | **49:06** | 约 30 分 | **约 19~20 分（冷）/ 14 分（热）** |
| 本地 tag push 等待 | 约 6 分钟 | 约 1 分钟 | 约 1 分钟 |

⚠️ 注意第一轮那一列「用户能下载」反而晚了 1.5 分钟：发布动作搬到独立 job 后要多一次
artifact 下载。它换来的是总时长从 49 降到 30 分钟。第二轮把这个代价也补掉了。

publish 的 2.5 分钟是按改前各步骤实测估的：checkout/下载 ~15s、node+rust 工具链 ~50s、
rust-cache 恢复 ~40s、抽取说明+生成清单 ~10s、验签测试（缓存热）~30s、安装版冒烟 37s、
Release 公开 36s。原「Gitee 附件 30s + 清单发布 3:53」已移到 gitee-mirror，不再算在这里。

## 六、回滚

单文件可回滚：`git revert` 这一个 commit 即恢复串行结构（`build-windows` 的
`needs: [build-macos]` + 尾部发布步骤 + 片段机制）。钩子部分同理，把判定段删掉
就是把 `SKIP_RUST_TESTS` 恒定当 0。

风险点集中在「publish 拿到的 dist-out 内容是否完整」：它由两个 artifact 合并而来，
下载后第一步就是 `Get-ChildItem` 打印文件清单，缺文件会在 `Copy-Item` 那步以
`-ErrorAction Stop` 直接红，不会带着残缺产物往下走。

## 七、第二轮：和 cc-switch 的差距到底在哪

cc-switch 最近一次发版（v4.0.44，run 46025629354）**5 个平台、20 分 52 秒**；
我们 2 个平台、49 分 21 秒。差距不在平台数量。

它的 job 时间线（UTC）：

| job | 起 | 止 | 时长 |
|---|---|---|---|
| Check in-app what's new | 15:31:16 | 15:31:34 | **18 秒** |
| release (windows-2022) | 15:31:43 | 15:44:09 | 12:26 |
| release (windows-11-arm) | 15:31:44 | 15:46:47 | 15:03 |
| release (ubuntu-22.04) | 15:31:45 | 15:43:03 | 11:18 |
| release (ubuntu-22.04-arm) | 15:31:46 | 15:42:19 | 10:33 |
| Build macOS binary ×2 | 15:31:46 | 15:47:15 | 15:29 |
| Bundle macOS release | 15:48:48 | 15:51:38 | 2:50 |
| Publish GitHub Release | 15:51:41 | 15:52:04 | **23 秒** |

三条可复制的做法：

1. **前置快检 18 秒**。摘要没写就立刻红，不白烧 20 分钟编译。
2. **各平台完全并行，发布单点收口**。publish 只跑在 ubuntu 上做下载+生成清单+建 Release。
3. **release 里根本不跑测试**（只有摘要那一条单测）。它敢这么做是因为 tag 只承载
   打包职责，代码早已在 main 上验过。

第 3 条我们**不能照搬**：我们的 tag 提交带着版本号改动（`chg: 发版 x.y.z`），
且仓库没有 main 分支保护兜底。直接跳过等于把正确性赌在"人不会推错"上。

我们改成了等价但安全的形式：**验证与构建全部并行，发布前用 `needs` 卡住**。
墙钟时间与"不跑测试"接近，但一条断言都没少。

## 八、第二轮具体改了什么

### 8.1 验证不再给发版让路（P0）

此前 `frontend` / `test` / `check-macos` 三个 job 的 `if` 是「非 tag 才跑」，
tag 时分别由 `build-windows` 内的 `npm run check`（2:13）和两个 build job 内的
`cargo test --release`（12:04 / 12:19）补上。结果是这三块**全部压在关键路径上**。

现在三个 job 在 tag 时也启动，与两个 build 并行；`publish` 的 `needs` 加上它们。
build job 里的重复检查与测试全部删除。

顺带修掉一个真实缺口：**tag 构建此前从未跑过 clippy**。`check-macos` 被跳过，
而 `cargo test` 不覆盖 `-D warnings` 这条线——发版产物只经过测试，没经过 lint。

### 8.2 缓存预热（P1）

实测确认此前缓存命中率为 0，原因有两层：

- GitHub 的缓存作用域是「当前 ref + 默认分支」，**不同 tag 之间互不可见**
  （官方文档：cannot restore caches created for different tag names）。
  仓库里 100 条缓存全部挂在 `refs/heads/refs/tags/v3.4.1` 这一个永不復用的作用域下。
- `build-macos` / `build-windows` 只在 tag 时运行，main 上从来没有它们的缓存。

改法：新增 `warm-release`（`push` + `refs/heads/main` 时跑，Windows/macOS 各一个
matrix），执行与 tauri build 相同形态的 `cargo build --release`（**不带**
`--no-default-features`，因为 default = notifications 而测试用的是关掉它）；
三个 job 的 rust-cache 统一 `shared-key: ccbridge-release`。

**版本号变更会不会打穿缓存 key？** 不会。rust-cache 默认
`add-rust-environment-hash-key: true`，会把 Cargo.toml/Cargo.lock 纳入 hash，但它
（源码 `src/config.ts`）把 Cargo.toml 的 `package.version` 归一化为 `0.0.0`，
并且 Cargo.lock 只取带 `source`/`checksum` 的包（workspace 自身被排除）。
所以 `chg: 发版 x.y.z` 这种提交不会让 key 变化。

**降级路径**：若某次 tag 读不到 main 的缓存（比如超过 7 天没发版、rustc 版本漂移），
build 只是回到冷启动的 17 分钟，功能与正确性不受影响。

### 8.3 Gitee 镜像移出关键路径（P1）

Release 在 publish 里公开后，用户已经能检查并下载新版；后面的
「生成 updater-gitee.json → 上传 Gitee 附件 → 推清单分支 + 四段验证」还要约 4 分钟
（实测 20:17:41 → 20:21:34 是 3:53）。

拆成 `gitee-mirror` job（`needs: publish`，重新下载一次产物，约 1 分钟开销），
失败只影响国内通道，不再拖累 GitHub 发布。需要 `contents: write`——清单仍推到
GitHub 的 releases 分支再由 Gitee 镜像拉取，不能直接建在 Gitee（镜像会剪掉上游
不存在的分支）。

### 8.4 前置快检（P2）

`preflight` job，仅 tag，约 20 秒，三条断言：版本号三处一致且等于 tag、
tag 提交在 `origin/main` 历史内、CHANGELOG 有该版本段。
`build-macos` / `build-windows` / `publish` 都 `needs` 它。

注意这里**不能**给 `publish` 写 `always()`：job 级 `if` 一旦出现函数调用就不再
隐含 `success()`，依赖失败时发布照跑，等于把未验证的产物发出去。

## 九、本轮验证记录

- YAML 解析 + 结构断言：三个验证 job 无 `if` 门槛、两个 build job 无
  `cargo test` / `npm run check`、publish 无任何 Gitee 动作、gitee-mirror 承接三步、
  `shared-key` 对应关系正确、preflight 仅 tag、warm-release 仅 main、publish 无 `always()`、
  清空 `RUSTC_WRAPPER` 在 rust-cache 之前（否则 env hash 进 key，与 build 对不上）。
- 版本一致性断言做变异验证：`GITHUB_REF_NAME=v3.4.1` → exit 0；
  `v9.9.9` → exit 1 并打印三处不一致（证明断言真的在拦，不是摆设）。
- tag 归属断言双向验证：`GITHUB_SHA=origin/main` → 通过；
  本地未推送的 HEAD → 失败并给出可操作提示。
- `check-release-notes --stage=latest` 通过。

### 9.1 复查时抓到的一个真 bug（A 方案遗留）

`publish` 里的「确认两端安装包、清单和策略的签名」是 Rust 集成测试
（`--test release_artifacts`），要真的编译一遍 lib 与测试目标。它的 rust-cache
注释写着"key 与 build-windows 相同"——**实际上没设 `shared-key`**，rust-cache
默认拿 job 名当 key，生成的是 `v0-rust-publish-…`，命中不了任何缓存。

在 A 方案里这步还留在 Windows job 内（同 runner、产物现成），所以只花 1 秒，
看不出问题。一旦 publish 拆成独立 job，它就要冷编 release 版 lib + 测试，
10 分钟以上，而且正好压在关键路径尾部——足以把前面所有优化吃掉。

修法：`publish` 显式 `shared-key: ccbridge-release-nodefault`（它跑的是
`--no-default-features`，与 build 的默认 features 不是同一套产物），
并让 `warm-release` 多一个 Windows 的 `--no-default-features --tests` 预热条目。

### 9.2 还没验证的

tag 的 run 是否真的命中 main 的缓存、命中后 Windows 构建的实际耗时。
未命中的表现是耗时回到 17 分钟，功能与正确性不受影响（降级路径见 §8.2）。

## 十、本轮回滚

四块互相独立，可以单独回退：

| 改动 | 回退方式 |
|---|---|
| 验证 job 并行 | 三个 job 加回 `if` 门槛，build job 恢复 `cargo test` / `npm run check`，publish 的 `needs` 去掉三者 |
| 缓存预热 | 删 `warm-release` job 与三处 `shared-key`（其余不变，回到冷启动） |
| Gitee 旁路 | 把 gitee-mirror 的三步搬回 publish 末尾，删该 job |
| 前置快检 | 删 `preflight` job 与三处 `needs` |
