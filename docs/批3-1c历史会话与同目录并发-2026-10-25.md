# 批 3-1c：库里的历史会话回侧栏 + 同目录并发提示

日期：2026-10-25　　前置：批 3-1a（多会话容器）/ 3-1b（pane + 侧栏）已落地

## 一、要解决的两个问题

1. **重启后侧栏是空的。** 3-1b 之后侧栏列的是「这个窗口里开着哪几条」（前端列表），
   一关 app 就只剩一条自动恢复的会话，其余全在 `cc_sessions` 表里躺着，只有
   会话条的「历史」按钮（那是 CLI 转录，另一套账）才摸得到。
2. **同目录并发没有任何提示。** 两个 pane 指向同一台机器的同一个目录时，两个
   CC 进程会改同一批文件，互相覆盖对方刚写的改动 —— 界面上看不出任何异常。

## 二、决策

### D1　侧栏历史区的数据源是 `cc_sessions`，不是 CLI 转录

两套账分工保持不变，只是各给一个入口：

| 入口 | 数据源 | 打开语义 | 覆盖范围 |
|---|---|---|---|
| **侧栏「历史」区**（新） | 我们自己的 `cc_sessions` | **新开一条 pane**，不动当前 | 只在对话页里聊过的 |
| 会话条「历史」按钮（既有） | `~/.claude/projects/*.jsonl` | **接管当前 pane** | 全部，含终端页手敲 claude 产生的 |

理由：能摆回侧栏的前提是「有标题、有轮数、有目标、有目录」——那是 `cc_sessions`
已经算好并落盘的（`title` / `message_count` / `connection_id` / `cwd`）。CLI 转录
要现场扫描 60 个文件 24MB 才能得到同样信息，不适合挂在侧栏每次进页都跑。
反过来，转录能打开「从没在对话页聊过的」会话，那是侧栏做不到的，所以两个入口都留。

### D2　打开历史 = 新开一条 pane，不接管当前

3-1b 之后「当前 pane」是个有身份的实体（内部 id、进程、待批单）。用历史内容顶掉它
等于把用户正在看的东西抽走。新开一条才符合侧栏的心智：**列表里点一条，就是又多开
了一条**，关掉它还回到原来那条。

### D3　只有「进页面的第一条」自动恢复上次，`+` 出来的一律空白

3-1b 有一个隐性缺陷：每个新 pane 挂载都走 `cc_restore`（取 `latest`），所以
`+` 新建的第二条会**重复载入上一条的内容**（两份同样的事件、两个 reducer 各跑一遍）。
3-1c 把它改成显式三态：

```ts
type CcRestoreReq = { kind: "none" } | { kind: "latest" } | { kind: "row"; rowId: number };
```

- 进页面造的第一条 pane → `latest`（保持「重启接着上次」）；
- `+` / Ctrl+N 造的 → `none`；
- 侧栏历史点开 → `{ kind: "row", rowId }`。

`none` 时**根本不调** `cc_restore`，不是调了再丢掉返回值 —— 后者会白白把几 MB
`events_json` 从库里读出来再扔。

### D4　同目录并发的判据与文案

判据：**同目标（`connectionId` 相同）+ 同目录（`cwd` 相同）+ 对方状态是
run/ask/wait 之一**。空 cwd 也参与比较（两条都不填目录 ⇒ 都落到 CLI 的默认目录，
是同一个目录，同样会打架）；但正因为「对方必须真在跑」才算，新建的空白 pane
不会误报。

文案只说**会发生什么**，不说「建议你不要这样做」：

> 同一目录下「<另一条标题>」正在运行 —— 两个进程会改同一批文件，可能互相覆盖。

不做：不阻止发送、不自动排队。理由与 R17 一致（不做审批门），而且「我就是要
两个都跑」是完全正当的用法（一个改前端一个改后端，目录相同但文件不重叠）。

`cwd` 要进侧栏元信息（`CcPaneMeta.cwd`），冲突判定放在宿主 `CcGuiTab` ——
只有它同时看得到所有 pane。

### D5　历史区对账必须用**两套 id**（真机验证时抓到的竞态）

最初只用 CC 的 session id（`view.sessionId`）判「这条已经打开了」。真机一下就露：
`cc_restore` 返回后，前端要等 **`Init` 事件**才拿到 session id，而那之间隔着一次
进程启动 —— 几百毫秒里那条**仍待在历史区，还能再点一次**，于是开出重复的 pane。

改成两个判据并集，各自覆盖对方的盲区：

| 判据 | 什么时候有 | 盲区 |
|---|---|---|
| `rowId`（库里的行号） | `cc_restore` 一返回就有，`openStored` 造的 entry 干脆自带 | 盘上还没落过盘的新会话没有 |
| `cliSessionId`（CC 的 session id） | `Init` 事件之后 | 恢复完成的头几百毫秒没有 |

`filterStored(rows, { rowIds, cliIds })`，两者命中任一即滤掉。为此 `CcPaneMeta`
加 `rowId`，`useCcPaneList.report` 的字段判重也要跟着加一项。

而且还要堵第三个口子：**恢复完成前两套 id 都还没有**，那条会话在历史区里
照样可点。所以 `CcPaneMeta` 再加一个 `restoring`（`!session.ready`），宿主
`CcGuiTab` 见任一 pane 在恢复就整体不摆历史区 —— 宁可晚半拍出现，也不要
让用户点出重复的一条。

**不做的方案**：给历史行加「点击后 300ms 内禁用」。那是猜时间，慢机器上仍能点穿，
而且把「为什么点了没反应」变成了新的困惑。

⚠️ 另有一个同源缺口，一并修掉：库里的流水有体积上限，超限时**从头丢到一条用户
消息为止**，那时第一条 `system/init` 早被裁掉 ⇒ 恢复出来的会话没有 `sessionId`。
`cc_restore` 因此在返回前补一条 `with_leading_init`（已有则原样），否则历史区
永远滤不掉这条。

## 三、落地清单

### Rust

| 文件 | 改动 |
|---|---|
| `cc_session/store.rs` | 新增 `Summary`（不含 `events_json`）+ `list(conn, limit)` + `by_row_id(conn, row_id)` |
| `commands/cc_cmds.rs` | `cc_restore` 加 `row_id: Option<i64>`；`CcRestore` 加 `row_id`；新增 `cc_list_stored`；`with_leading_init` 补首条 `Init` |

⚠️ `list` 必须**不读 `events_json`**：那是每行几十到几百 KB 的正文，列表只要摘要。
`SELECT` 里不出现那一列就够，不需要额外索引。

### 门禁

- Rust：`cargo fmt --check` / `clippy --all-targets --no-default-features -- -D warnings` /
  `test --no-default-features`（**必须补 PATH**，见 `MEMORY.md` 十三）。
- 前端：`check-component-size` → `eslint` → `tsc --noEmit` → `vitest`。
- 真机核：重启后侧栏出现历史区、点历史新开一条、两个同目录 pane 都发消息出横幅。

### 体量预算

`CcPane` 的 useState + useEffect 现在顶在 8（门禁上限），本次**不加状态**：
`restore` 用 `useRef` 固化首帧值（props 在 pane 生命周期内不变），横幅是纯 props。
`SessionSidebar` 已经接近 300 行，历史区**必须**单独成 `SessionHistoryList.tsx`。

## 四、真机核验（2026-10-25）

环境：Windows 11 / DPI 1.25 / 默认 1280×840 窗。

| 项 | 结果 |
|---|---|
| 重启后侧栏出现「历史 N 条」区，行是「标题 / 本机 · N 轮 · X 小时前」 | ✅ |
| 已打开的那条**不再**出现在历史区（两套 id 对账生效） | ✅ |
| `+` / Ctrl+N 出来的 pane 是空白新会话，不再重复载入上一条 | ✅ |
| 点历史行 → 新开一条载入该行，历史区随即消失，原 pane 不动 | ✅ |
| 有 pane 在恢复时历史区不摆（`restoring` 门控） | ✅ |
| 页脚「N 个在跑 · 共 M 个」随 pane 数变化 | ✅ |

⚠️ 本机 WebView2 窗口**不接受注入的鼠标事件**（`mouse_event` / `SendInput` /
绝对坐标三种都试过，键盘 `keybd_event` 有效）。所以「点历史行」这一条是用
临时 effect 自动调 `openStored(historyView[0].rowId)` 验的 —— 顺带把
「验证代码必须和产品用同一个值」这条教训写进了过程记录：第一版验证用的是
**未过门控**的 `historyRows`，于是它自己开出了重复的一条，看起来像产品 bug。
