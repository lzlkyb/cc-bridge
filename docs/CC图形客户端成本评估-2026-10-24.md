# CC 图形客户端 · 成本评估

> 评估日期 2026-10-24。本文是 RFC 的「成本评估」章节，可整体并入。
> 关联：`design/CC图形客户端设计稿-2026-10-24.html`（形态）、`docs/ClaudeCode客户端开源项目调研-2026-10-24.md`（路线）、`docs/desktop-cc-gui源码分析-2026-10-24.md`（可移植设计）。
> **标注约定**：`【实测】` = 本机量出来的；`【估算】` = 按模型推算，附推算依据。

## 〇、结论先行

| 维度 | 结论 | 是否构成约束 |
|---|---|---|
| **安装包体积** | 4.48 MB → **4.7 / 4.9 / 5.5 MB**（三档），红线 20 MB | ❌ 不构成约束，余量极大 |
| **内存** | 当前稳态 **442 MB**（主进程 16.7 MB + WebView2 378.5 MB），GUI 预计 **+20~70 MB** | ⚠️ 需要虚拟化设计，否则失控 |
| **代码量** | 约 **8000 行前端 + 2000 行 Rust**，等于现有前端（19253 行）的 40% | ✅ **真正的成本** |
| **维护** | CC 每加一个斜杠命令都要跟 | ✅ 长期负债 |

**一句话**：先决定「做不做」时，别被体积绊住 —— 体积是最不痛的一维。真正要权衡的是 1 万行代码和长期跟版。

## 一、体积

### 1.1 基线【实测】

| 项 | 实测值 | 来源 |
|---|---|---|
| 安装包（Windows NSIS） | **4.48 MB** | README 记录的 v2.4.0 实测值 |
| 主 exe（release，`strip` + `lto=thin` + `opt-level=s`） | 14 MB | `docs/benchmark-vs-native-claude-code.md` |
| 前端 dist 原始 | 3.05 MB | 本机 `dist/` 实测 |
| 前端 dist brotli | **1.06 MB** | 同上（q11） |
| ├ JS | 1343 KB → **331 KB br** | 同上 |
| └ 字体（FiraCode + JetBrainsMono） | 1396 KB → **552 KB br** | 同上，**占 dist 的 52%** |
| 最大单特性 chunk（`TerminalTab`） | 336 KB → **77 KB br** | 同上，作为「一个大特性」的体积标尺 |
| 前端源码 | 338 文件 / 19253 行（非测试） | 同上 |

⚠️ **口径待统一**：`Cargo.toml` 的 `[profile.release]` 注释写着「基准 12.03MB，预算 20MB」，与 README 的 4.48MB 差 7.5 MB。可能是 msi 与 NSIS 之别，也可能是旧基线。结论不受影响（两种口径下余量都很大），但要盯预算就得先统一。建议以 CI 产物为唯一真源。

### 1.2 三档预估【估算】

| 档位 | 内容 | 前端增量 | Rust 增量 | 安装包 | 合计 |
|---|---|---|---|---|---|
| **A · 最小可行** | 只读事件流；工具卡纯文本 + 自绘样式；diff 自己写 Myers；无 markdown / 高亮库 | +100 KB br | +0.3 MB exe | **4.70 MB** | **+0.2 MB** |
| **B · 实用** | 加 markdown 渲染、语法高亮、真 diff、检查器侧栏 | +200 KB br | +0.45 MB exe | **4.90 MB** | **+0.4 MB** |
| **C · 完整** | 再加 WebSocket（`--sdk-url`）、多会话并发 | +250 KB br | +1.8 MB exe | **5.50 MB** | **+1.0 MB** |

### 1.3 换算模型

两段式，因为两类内容的压缩率完全不同：

```
安装包增量 ≈ (exe 机器码增量 ÷ 3.1)  +  (前端资源 br 增量 × 1.0)
```

- **除以 3.1**：LZMA 对机器码约 3.1 倍——这正是当前 14 MB exe 变成 4.48 MB 安装包的比例。
- **乘以 1.0**：Tauri 嵌入的前端资源已是 brotli 数据，NSIS 的 LZMA 压不动了，基本原样传递。

### 1.4 前端增量的构成

前端现有依赖极简，**没有任何 markdown 渲染器、语法高亮库、diff 库或图标库**（图标全是内联 SVG）。所以增量是「新代码 + 三四个小库」：

| 项 | brotli | 备注 |
|---|---|---|
| 新增组件代码 | 100~160 KB | 按 `TerminalTab`（77 KB br）的 1.3~2 倍估；含消息流、工具卡、审批卡、检查器 |
| `marked` + `dompurify` | ~20 KB | CC 输出是重度 markdown（代码块 / 列表 / 表格），必须有；且**必须过 DOMPurify**，否则是 XSS 面 |
| `highlight.js` 常用子集 | ~40 KB | 只引 8~10 种语言；全量版 ~120 KB，不要 |
| diff | 0 KB | 自己写 Myers（约 60 行），别引库——顺带解决 `desktop-cc-gui` 那个误差 13.7 倍的坑 |
| 图标 | 0 KB | 沿用内联 SVG 惯例，**不要引图标库** |
| 字体 | **0 KB** | 复用现有 FiraCode / JetBrainsMono，聊天界面同样够用 |

### 1.5 为什么增量这么小（三条结构性原因）

1. **不打包 claude**。远端零安装——连的是服务器上本来能用的 CLI，一个字节都不进安装包。同期 Electron 类 CC 客户端动辄 100~150 MB，差距全在这里。
2. **没有 Electron**。复用系统 WebView2，前端资源就是那 1 MB。
3. **Rust 侧基础设施全在**。`axum` / `tokio` / `serde_json` / `rustls` 都已链接，协议解析与 HTTP 服务几乎白捡。

### 1.6 两个必须警惕的依赖

有先例：`docs/cc-bridge-mcp-bridge-plan.md:48` 记着「`transport-child-process` 增量约 **1.5~2 MB**」——**一个依赖就能吃掉整个预算的量级**。

| 依赖 | 代价 | 建议 |
|---|---|---|
| `claude-codes` crate | 类型现成，但可能拖入 `reqwest`，**+1 MB 起** | **不引**。手写 serde 结构体约 300 行，零依赖。`desktop-cc-gui` 也是手写的 |
| `axum` 的 `ws` feature | `tokio-tungstenite`，**+1 MB 起** | **延后**。`--sdk-url` 本身就是最不稳定的一条路（纯逆向、随时可能失效），只在核心链路跑通后作为可选增强 |

## 二、内存

这是比体积更需要提前想清楚的一维，因为**当前口径的表述会被 GUI 放大成问题**。

### 2.1 当前基线【实测】

测量条件：2026-10-24 09:43，安装版 `cc-bridge-desktop.exe` 已连续运行 **661 分钟**，无活跃会话子进程（除 WebView2 自身），系统内 6 个 `msedgewebview2.exe` **全部归属 cc-bridge**。

| 进程 | 角色 | 工作集 | 私有字节 |
|---|---|---|---|
| `cc-bridge-desktop.exe` | Rust 主进程 | 64.0 MB | **16.7 MB** |
| `msedgewebview2` | browser | 65.8 MB | 71.7 MB |
| `msedgewebview2` | **gpu-process** | **150.4 MB** | 189.8 MB |
| `msedgewebview2` | renderer | 91.9 MB | 84.7 MB |
| `msedgewebview2` | utility ×2 | 59.9 MB | 20.9 MB |
| `msedgewebview2` | crashpad | 10.5 MB | 3.0 MB |
| **合计** | | **442.4 MB** | |

**两个必须知道的事实：**

1. **「启动内存 < 20 MB」指的是主进程私有内存**（实测 16.7 MB，吻合）。`lib/platform.ts:158` 的注释也写明是主进程口径、mac 约 22 MB。但 `platform.ts:181` 的标签写的是「运行时内存」，用户会读成整机占用——**实际是 442 MB，差 22 倍**。加 GUI 后这个数字会更显眼，建议尽早把标签改成「主进程内存」或直接换成真实总占用。
2. **gpu-process 150 MB 是最大单项**，很可能是 `@xterm/addon-webgl` 的 WebGL 上下文。`renderer` 的 91.9 MB 里才是 JS 堆 + DOM —— **GUI 的增量只加在 renderer 上**，主进程基本不动。

⚠️ 该数据是**长时运行后的稳态**（11 小时）。冷启动会更低，但无法在不打断正在跑的会话的前提下复测（见 §五）。

### 2.2 GUI 的内存增量【估算】

增量集中在 renderer 的 JS 堆 + DOM，三块：

| 来源 | 估算 | 依据 |
|---|---|---|
| **消息 store**（真正的风险点） | **8~64 MB** | 见下 |
| 虚拟列表 DOM | 5~15 MB | 只渲染可视区 + overscan，与消息总数无关 |
| markdown / 高亮缓存 | 5~20 MB | 渲染结果缓存与语法树 |

**消息 store 是唯一会失控的地方**，算一下：

```
1000 条消息 × 平均 4 KB 文本 = 4 MB 字符串 → JS 内部 UTF-16 翻倍 = 8 MB
1000 条消息 × 上限 32 KB     = 32 MB        → 翻倍              = 64 MB
```

⇒ **GUI 总增量约 +20~70 MB，在 442 MB 基线上是 +5%~16%。** 可以接受，但前提是两条设计约束：

1. **必须虚拟化列表**。不虚拟化时，几百条消息的 DOM 节点本身就能吃掉几百 MB，这是 Electron/WebView 类应用最常见的翻车方式。
2. **消息 store 必须复用已有的 32 KB 返回上限规则**（`docs/上下文消耗优化方案-2026-10-22.md` §九，同源五条）。这条规则当初是为省 token 立的，**在这里顺带成了内存防线**——把单条结果硬顶在 32 KB，1000 条会话的最坏情况就从 64 MB 封顶，不会随会话长度线性爆炸。

### 2.3 一条外溢结论

`platform.ts:180-184` 另有两处数字已过期，建议顺手一起修（不在本评估范围内，仅提示）：

- 「3.4 MB 安装包」→ 实测 4.48 MB（CHANGELOG 里改过 README，但这里漏了）
- 「17 个 MCP 工具」→ 实为 **24 个**（`mcp/tools/registry.rs` 实测 `register_tool!` 调用数）

## 三、代码量与维护

### 3.1 代码量【估算】

| 部分 | 行数 | 对照 |
|---|---|---|
| 前端（方案 B） | 8000 行 | 现有前端 19253 行的 40%；`desktop-cc-gui` 的 `features/chat` 是 38587 行（但覆盖 11 个引擎） |
| Rust（方案 B） | 2000 行 | `desktop-cc-gui` 的 `engine/` 共 7566 行 / 11 引擎，CC 单引擎约 1500~2000 行 |
| 合计 | **约 1 万行** | 不含测试。按项目惯例，测试会再添 30~50% |

### 3.2 维护成本【判断】

- **协议跟版**：无官方文档，字段随版本漂移。对策是启动时探测 + 兼容层，`desktop-cc-gui` 的做法是版本号紧跟 CLI。
- **斜杠命令跟版**：TUI 里免费的东西 GUI 要一件件补，且 CC 每加一个新命令都要跟。这是长尾，也是最容易被低估的部分。
- **与项目定位的张力**：cc-bridge 正在从「CC 专用」转「通用 MCP 桥」。做深 CC GUI 会把重心拉回去，而且**只有 CC 有这套协议**（Codex / Gemini 各不相同）。

## 四、决策建议

**体积不构成约束**——最坏情况（方案 C）也只占掉 20 MB 红线的四分之一。不要用它当决策依据。

真正该拿来决策的三个数字：

1. **约 1 万行代码**（不含测试）→ 相当于现有前端的 40%
2. **内存 +20~70 MB**，且**必须先做虚拟化 + 32 KB 截断**，否则失控
3. **长期跟版**：协议 + 斜杠命令双线

若决定推进，建议顺序：

```
方案 A（验通道，最小体积）→ 探针实测审批链路 → 方案 B（可用）→ 方案 C 视需要
```

先做 A 的价值不只是省体积：**它用最少的代码把「SSH 管道 + 事件流 + 卡片渲染」全链路跑通**，这一步的结论决定了 B 和 C 还有没有必要做。

## 五、未实测项（诚实标注）

| 项 | 为什么没测 | 怎么补 |
|---|---|---|
| **冷启动空载内存** | 需要重启安装版，会打断正在跑的会话（已运行 11 小时） | 在用户空闲时重启后立即测量，脚本见下 |
| **真长会话内存** | GUI 尚不存在，无可测对象 | 方案 A 出原型后用 DevTools Memory 面板抓 heap snapshot |
| **bundle 实际落包增量** | 未新增代码，无法实测 | 方案 A 落地后对比 CI 产物的安装包体积，用真实值替换 §1.2 的估算 |

**复测脚本**（PowerShell，归属 WebView2 子进程后求和）：

```powershell
$procs = Get-CimInstance Win32_Process -Filter "Name='cc-bridge-desktop.exe' OR Name='msedgewebview2.exe'" |
         Select-Object ProcessId, ParentProcessId, Name
$main = $procs | Where-Object { $_.Name -eq 'cc-bridge-desktop.exe' }
$ids = New-Object System.Collections.Generic.HashSet[int]
foreach ($m in $main) { [void]$ids.Add([int]$m.ProcessId) }
$changed = $true
while ($changed) {
  $changed = $false
  foreach ($p in $procs) {
    if ($ids.Contains([int]$p.ParentProcessId) -and -not $ids.Contains([int]$p.ProcessId)) {
      [void]$ids.Add([int]$p.ProcessId); $changed = $true
    }
  }
}
$sum = 0
foreach ($id in $ids) {
  $gp = Get-Process -Id $id -ErrorAction SilentlyContinue
  if ($gp) { $sum += $gp.WorkingSet64 }
}
"总工作集: {0:N1} MB" -f ($sum / 1MB)
```

⚠️ 必须按父进程链归属——本机同时运行着其他 WebView2 宿主，不归属会把他人的进程算进来。
