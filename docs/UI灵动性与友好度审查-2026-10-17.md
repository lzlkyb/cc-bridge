## 0. 一句话结论

这个应用的「动效骨架」已经相当好（toast/Modal/FLIP/countup/reduced-motion 全有兜底），
真正的差距不在「不够炫」，而在两类**基本功**：
① **抖动**——一大半动态数字没有 tabular-nums/锁宽，轮询一跳就横跳；
② **出现/消失硬切**——顶栏、侧栏、状态栏上的元素仍是「条件渲染」，出现即推挤邻居，
和更新徽章改造前是同一种病。另有一处**失败静默**反模式（开机自启 revert 无提示）。

---

## 1. 审查透镜（更新徽章改造沉淀的 8 条原则）

1. **布局稳定优先**：元素出现/消失/变宽不许推挤邻居（槽位模型、min-width、零占位）。
2. **空白区优先于遮挡**：找既存空位，别硬盖。
3. **反馈连续性**：状态切换淡入淡出（320ms 档），不硬切。
4. **数字不抖**：`tabular-nums` / 定宽段 / 0 显示「—」而非隐藏。
5. **真状态可感知**：卡死要有信号（心跳判定），别让「慢」看起来像「死」。
6. **文案匹配真语义**：错误文案说什么就是什么（重启失败 ≠ 更新失败）。
7. **失败路径必须有反馈且可恢复**：静默 revert 是反模式。
8. **克制**：工具行为，克制比热闹重要。

## 2. 已达标面（这些不用动，也是修别的点时要复用的原语）

- **进出场**：toast 200ms 进场 + 3.5s 倒计时条 + error 抖动；Modal 180/140ms 统一缩放淡入。
- **列表**：`useAutoAnimateRM` FLIP 已用在 RecentActivity / LogTab（新行平滑下移）。
- **数字入场**：`useCountUp`（700–900ms easeOut，reduced/隐藏窗口直出终值）。
- **保存反馈**：`useSettingSave` 行内「已保存」1.5s + 失败 toast；`SavedHint` 带 0.22s 淡入。
- **复制反馈**：`useCopyFeedback` 收敛 6 套为 1 套（成功内联回滚，失败才 toast）。
- **reduced-motion**：全局 CSS 兜底 + `useAutoAnimateRM`/`useCountUp`/Modal 各有 JS 分支。
- **参考实现**：`UpdateReadout` 的 tabular-nums + 定宽 68px + 「—」三件套；`update-slot` 槽位模型。

## 6. 落地建议（三批 + 明确不做）

- **批 1 · 防抖统一（P0 抖动 #1-11）**：全部是 className/CSS 级改动（tabular-nums、min-width、`--`→「—」），
  零布局结构变化、不触发任何 fit。**建议先出一张小设计稿核对锁宽值**（锁宽数字要 CDP 实测回填），
  然后一批提交。
- **批 2 · 出现/消失过渡（#12-16）**：SecurityBadgeGroup 槽位化是重点（与更新徽章同款修法、同款收益）；
  按 R4 先出 HTML 设计稿（含真窗口控件结构核字形带）再动手。
- **批 3 · 反馈补齐（#17-20）**：AppGroup 失败 toast（复用 useToast）、TerminalGroup 接 useSettingSave、
  Menu/CommandPalette 进出场复用 Modal 模式。改动小、风险低。
- **明确不做**（克制红线）：常驻动效/呼吸灯泛滥；给日志行加花哨入场；为 #14/#15 上复杂 overlay
  （收益低、踩 fit 红线风险高）；不加任何新依赖。

> 各批都落在体量棘轮扫描范围内，改动以 CSS/小改为主，预计不触碰 300 行/8 hooks 上限；
> 批 2 的 SecurityBadgeGroup 若加槽位逻辑需盯一眼（现 45 行左右，余量充足）。
