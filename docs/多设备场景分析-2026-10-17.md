# 多设备场景分析：同账号双机接入的设计缺陷与改进方案

> 日期：2026-10-17 ｜ 类型：架构分析 + 实施记录 + 完整规划（P0–P3 全收口）
> 场景：用户在两台电脑（下称 A/B）都装了 CC Bridge，远端服务器上的同一个 AI 工具
> （如 Claude Code，user 级 `~/.claude.json`）接入本应用的服务端。
> 状态总览见 §9 路线图；P2 详细方案见 §7（可直接开工）；P3 定位见 §8。

## 0. 一句话结论

问题不在某个 bug，而在三个**结构性成因**：① 客户端侧存在「单值全局资源」但写者有两个；
② 数据账本全是「本地事实」却被当成「全局事实」使用；③ 系统里**没有设备身份**，
导致冲突既无法协商、也无法展示、更无法归因。治标方案都绕不开先补 ③。

## 1. 架构事实核对（2026-10-17 代码实测）

| 事实 | 位置 | 多设备含义 |
|---|---|---|
| 接入配置是单值：sed 替换 `~/.claude.json` 里的唯一 URL | `lib/utils.ts buildIpSedCommand` | A/B 生成的命令**互相覆盖** |
| 令牌全局单值，`regenerate_token` 无作用域 | `commands/config_cmds.rs:601` | B 重新生成 ⇒ A 的 sed/连接全部作废 |
| 无任何设备身份字段 | `config.rs` 无 device/hostname 概念 | 无法展示「另一台机器在用」，无法归因 |
| 审计/用量/AI 改动时间线全在本地 SQLite | `state.db` | 各自为政，跨机不可见 |
| 备份按本机路径生成 | `backup.rs` | 若做云同步会互覆盖 |
| tmux 桥接注入**全局**设置（per-user） | TerminalGroup 明示 ⚠️ | 两台都开会互踩 |
| 路径锁/白名单 per-machine | `move_files.rs` 双路径字典序锁 | 跨机无锁 |
| 桌面通知 `notify_desktop` 只发给已连的那个端 | MCP 工具 | 只有一台收得到 |

## 2. 问题清单（六类，按用户感知排序）

### A. 接入互踢（用户说的「登录互踢」的真身）
- **现象**：在 B 上完成接入（或点「复制命令」修复），A 的远程连接立刻变「远程不可达」；
  反过来亦然。表现为「两台机器互相踢」。
- **成因**：`~/.claude.json`（user 级）是**单值全局资源**，sed 命令把唯一 URL 换成执行者
  自己的 IP:Port。后写者赢，先写者失联——这不是登录系统，但冲突模型与互踢完全同构。
- **连带**：修复链路也互斥。A 触发「IP 已变化」修复（选中 IP + 落盘 last_selected_ip），
  B 侧的 last_selected_ip 基线不变 ⇒ B 的变更判定错乱（在自己机器上看到与事实不符的
  「地址已失效/已恢复」）。

### B. 令牌与证书作用域（误伤面比想象大）
- `regenerate_token` 一刀切：所有已写入远端配置的旧 token 同时失效。双机场景下，
  一台上的安全操作直接废掉另一台的接入，且对方只看到 401/不可达，**不知道原因**。
- 自签 TLS 证书按本机生成：远端若刚信任了 A 的证书，切到 B 后又要重新信任一遍
  （若两台都开 HTTPS）。

### C. 账本割裂与同步冲突（「数据同步混乱」的真身）
- 审计日志、Token 用量、「近期 AI 改动」时间线都是**本机账本**：AI 经 B 的桥做的操作，
  在 A 的界面里不存在。用户以为什么都能看到，实际只看到本地一半。
- 若用「导出/云盘」合并：两台同时写同一份文件 = 后写覆盖先写；审计是 append-only
  语义，覆盖即**丢数据**——这比看不到更糟。
- 备份文件若进入共享目录，同名冲突同理。

### D. 会话与远端环境互扰
- SSH 会话本身**天然隔离**（独立 pty），两个终端页互不影响——这块没有问题。
- 但 tmux 桥接是**全局设置**（对运行中的 tmux server 生效）：A 开、B 不开，B 的
  交互预期就会变；两台同时注入重复设置。远端探测钩子注入同理，重复注入靠幂等兜底。
- 两台机器同时经桥对**同一远端项目**执行文件操作：本机路径锁拦不住跨机竞态，
  极端情况下 A/B 同时 move/rename 同一文件。

### E. 通知的重复与丢失
- **丢失向**：AI 只连一个端 ⇒ 通知/任务完成只到一台；另一台连「发生了」都不知道。
- **重复向**：若用户为求两台都能用而配置两个 server 条目且同时启用 ⇒ 同一事件的
  通知双发。
- **断线窗口**：SSE/HTTP 轮询的重连间隙里的事件，当前协议没有补发/游标机制 ⇒ 丢。

### F. 策略漂移与安全盲区
- 白名单、允许目录、安全策略都是本机配置：同一用户两台机器策略不一致时，
  「同一句命令在 A 被拦、在 B 放行」，事后审计对不上。
- 安全提示（SecurityBadge）只反映本机视角。

## 3. 方案（四层，从止血到架构）

> **🔴 兼容性契约（2026-10-17 用户拍板，优先级高于以下一切细节）**：
> 多设备相关能力全部走「多设备模式」开关（默认关）。**开关关闭时，产品行为与今天逐字一致**——
> 接入命令保持现有 sed 形态（连注释都不多一个字）、冲突文案维持两分支、确认弹窗维持现有文案、
> 不出现任何「本机身份」UI。device_id 允许在后台静默生成（无界面变化），但**一切 UI 呈现与
> 命令形态变化都以开关开启为前提**。老用户升级后感知为零。
> 另：**不做云同步**（从 P2 划入「明确不做」）——账本策略只保留「本地账本 + 导出聚合」。

### 第一层：设备身份与可观测（前置件，其他一切的地基）
- 启动时生成 `device_id`（机器名 + 短随机），持久化进 config；连接页展示
  「本机身份：DESKTOP-A（id 尾号 3f2c）」。
- 远端探测链路顺带上报「当前接入方指纹」（谁最后写入的 sed 就带谁的 id——sed 命令
  的注释里捎带 device_id 即可，远端文件里就有据可查）。
- 冲突文案升级：`remoteReachable=false` 时区分「网络问题」与「接入方可能已变成
  另一台设备」（探测到 401/指向别处时给针对性提示）。
- **代价小、收益大**：冲突从「玄学断连」变成「看得到是谁接走的」。

### 第二层：接入配置多写者治理（治 A/B 两类）
- **多 server 条目指引**：Claude Code 支持配置多个 MCP server 条目。连接页新增
  「多设备模式」：为每台机器生成**独立条目名**的 sed（`cc-bridge-a` / `cc-bridge-b`），
  两台共存于远端配置，用户在 AI 侧按需切换——把「互踢」变成「并存 + 显式切换」。
- `regenerate_token` 加影响面确认（「将使所有已接入设备失效，包括可能的另一台机器」）；
  远期可做 per-device token（每台机器独立令牌，重置只影响自己）。
- TLS：证书指纹在连接页展示，双机都开 HTTPS 时提示「远端需分别信任」。

### 第三层：账本策略（治 C/E 两类）
- **默认姿态：本地账本 + 显式聚合**（不做云同步）。审计/用量继续本地记账（append-only 不可被
  远端覆盖），聚合靠导出 CSV（用量已支持）按「设备名」列合并——导出时带上
  device_id 列，合并才有主键。
- 通知双发问题：多 server 条目下由用户选择「通知跟谁走」——单选哪台接收通知
  （连接页一个开关），或远端只启用一台的条目。

### 第四层：架构演进（与既定「通用双向 MCP 桥」身份转变合流）
- 引入**服务端协调点**（rendezvous/中继，RFC `mcp_2026_07_28_adaption_rfc` 的方向）：
  设备注册、per-device 令牌、审计聚合到服务端、AI 侧只认服务端不认具体桌面——
  多设备从「互斥资源争用」变成「多端同源」。
- 配置写入从「各端生成 sed」演进为「服务端代写 + 版本号」，消除多写者。
- 跨机文件操作若要支持，需远端文件锁服务（远期，当前明确**不支持**并写进文档）。

## 5. 明确不做 / 风险声明

- **不支持**两台机器同时对同一远端项目做文件写操作（路径锁不跨机）——文档写明，
  不做跨机锁。
- **不做云同步**（2026-10-17 用户拍板）：不引入任何云端协调/同步组件，跨设备一致性
  只靠「导出 + 显式合并」与用户手动操作。
- 不做审计日志的「双向合并」（append-only 语义下合并 = 冲突黑洞），只做单向上报/导出。
- tmux 全局设置互踩暂不改（低频 + 影响面清晰，界面上已有 ⚠️ 文案）。

## 6. 实施记录（2026-10-17）

### 6.0 批1/批2 摘要（P0 + P1 命令生成器）

按兼容性契约全量落地（opt-in 默认关，关闭 = 逐字现状；详细改动清单见 `.workbuddy/memory/2026-10-17.md`）：

- **device_id**（4 位小写 hex）首启静默生成落盘（`main.rs`），`multi_device_mode` 开关字段默认 false。
- 连接页 `MultiDeviceCard`：开关行常显；开启后出现「本机身份：{机器名} #尾号」。关闭时组件不渲染身份区（契约）。
- 接入/更新命令换形：`network::ip_sed_for` → `ip_update_command(IpUpdateTarget)`，多设备 + claude-code 走条目级 `claude mcp remove/add cc-bridge-<尾号>`（幂等、固定 user 级），否则原 sed 逐字不变。五个入口同源：向导 / IP 横幅 / 全局横幅 / 托盘两项 / 命令面板。
- 冲突文案三分支 + 令牌确认文案升级（CommandPalette `act-token` 与 TokenManager 两处，受开关门控）。
- 实现偏差（诚实记录）：第三分支当时按「多设备 + 探针不通」启发式触发（批3-1 已升级为 401 证据判定）；WorkBuddy/Codex 条目化留批3（已完成，见下）。

### 6.1 批3 记录

按用户「开工」落地。范围 = 401 证据链（第三分支精确判定）+ WorkBuddy/Codex 条目化。
兼容性契约不变：多设备模式关闭时，横幅渲染条件、命令形态、片段条目名逐字与旧版一致。

**批3-1 令牌失效证据链（第三分支从启发式升级为有证据判定）**
- `BanRegistry::recent_failure_ips(within)`：封禁记账本就带 `last_fail` 时间戳、认证成功即清除
  →「窗口内仍有失败记录」天然等价「问题仍在」，零新增状态。窗口对齐 `remote_ban_window_min`。
- `get_status` 暴露 `authFailureSources`（近期 401 失败来源数）。
- 全局横幅渲染条件扩一项 `multiDeviceMode && authFailureSources > 0`：令牌失效时服务可达、
  TCP 探针是绿的，不扩条件永远弹不出来。开启多设备时出现精确分支「远程 AI 工具鉴权失败」
  （区别于 TCP 失败的「可能是另一台设备完成接入」启发式分支）。
- 已知局限（诚实记录）：外网扫描器打 401 也会计入（来源无法与远端 AI 工具区分）；
  封禁关闭（127.0.0.1 绑定）时不记账 → 证据恒空，自动退回启发式文案。

**批3-2 WorkBuddy/Codex 条目化**
- 接入片段（手动粘贴的 JSON/TOML）条目名带尾号：`build_connect_command`（Rust，托盘/get_status）
  与 `buildClientSnippet`（前端，向导 ManualSteps）双端同步，`deviceId` 非空才生效。
- IP 修复：Codex/WorkBuddy 升级为**条目锚定 scoped sed**（`build_scoped_sed_command` /
  `buildIpSedCommand` 多设备分支，逐字对齐）——Codex 用 TOML 段头行锚点（规范保证），
  WorkBuddy 用 JSON 条目键 → `"Authorization"` 行锚点（依赖规范序列化顺序）。
  范围失配 = sed 无匹配 = 不改任何东西（良性失败），不会像全局替换那样改坏相邻条目。
- **不用 Codex CLI 的原因**（调研结论，三来源核对 `--help`）：`codex mcp add` 的令牌只能走
  `--bearer-token-env-var` 环境变量名（令牌须进 shell profile），破坏「重跑命令即更新令牌」
  的既有语义，且该 flag 要求较新版本。
- **WorkBuddy CLI 不出命令的原因**：第三方逆向文档称 `codebuddy mcp` CLI 写
  `~/.codebuddy/mcp.json`，与 cc-bridge 既有目标 `~/.workbuddy/mcp.json` 品牌路径分歧，
  验证前出命令有写错文件风险——保持手动片段 + scoped sed。
- 附带修复（双端不一致）：多设备开启但 device_id 缺失时，批2 的 Rust 返空串、前端回退 sed；
  批3 统一为回退 sed（对本机永远是正确的单设备命令，比空串有用）。

**门禁**：前端四项全绿（vitest 684，+6）；Rust fmt/clippy 绿，cargo test 398 过
（run_command spawn 族 1 条全量并行偶发，单跑必过=已知）。

## 7. P2 详细方案：per-device token（方案就绪，可直接开工）

> 目标：多设备模式下每台设备可持有**独立令牌**，重置某台的令牌只断那一台，
> 不再出现「B 上点一下重新生成 ⇒ A 的远程连接全灭」。兼容性契约不变：
> 开关关闭时鉴权路径、UI、导出行为与今天逐字一致。

### 7.1 现状核对（2026-10-17 代码实测）

| 事实 | 位置 | P2 含义 |
|---|---|---|
| 鉴权是单值常量时间比较 | `security/auth.rs verify_token` | 需新增「多候选集合」校验原语 |
| http 中间件读 `config.token` 单值 | `mcp/http.rs:244-283` | 校验点换 `verify_any`，ban/限流逻辑零改动 |
| SSE 两处独立校验 | `mcp/sse.rs:65,155` | 同上，两处都要换 |
| `regenerate_token` 只重置主令牌 | `config_cmds.rs:611` | 语义保留 =「重置主令牌」；新增「重置设备令牌」 |
| 配置导出脱敏只清 `token` | `config_cmds.rs:630-634`（M1 不变量） | 🔴 `device_tokens` 必须同款脱敏，否则导出泄密 |
| 接入命令 token 参数已参数化 | `build_multi_device_command(token, ...)` | 命令链路只需换 token 来源 |

### 7.2 配置结构（config.rs）

```rust
/// 每设备独立令牌（P2）。仅多设备模式消费；键为 device_id（不含机器名）。
/// 落盘为独立键 `device_tokens`（JSON 数组，保序展示）；主 token 语义不变。
pub device_tokens: Vec<DeviceToken>,   // { device_id: String, token: String }
```

- 解析/落盘沿用现有 `parse_or_warn` / `save_config_field` 逐键模式（新增一键）。
- 导入兼容：老配置缺键 → 空集合（与「开关关闭」同态，天然零风险）。
- 🔴 `export_config_json` 脱敏面扩为 `token` + `device_tokens`（同 M1 注释口径，单测锁定）。

### 7.3 鉴权原语（auth.rs）

```rust
/// 多候选校验：主 token 或任一设备令牌命中即放行。
/// 逐项调用 verify_token（每项恒定时间）；集合小且「第几项命中」不构成
/// 有意义的侧信道（命中即成功响应，无逐项时序差可观测面）。
/// fail-closed 语义不变：集合与主 token 全空 → 一律拒绝。
pub fn verify_any(provided: &str, main: &str, devices: &[DeviceToken]) -> bool
```

- 三个调用点（http 中间件 + sse 两处）换用 `verify_any`；`inc_auth_denies` /
  `record_failure` / `record_success` 与限流不动。
- 开关关闭时集合恒空 → `verify_any` 退化为 `verify_token(provided, main)`，逐字等价（契约）。

### 7.4 令牌管理 UI（MultiDeviceCard 扩展，无新组件）

- 「设备令牌」小节（仅开关开启渲染）：列表显示各设备 `#尾号` + 生成时间，**不回显完整 token**（生成时一次性展示 + 复制按钮，同现有令牌页口径）。
- 「为另一台设备发令牌」：生成 `DeviceToken` → 直接输出该设备的条目级接入命令（复用批2/批3 生成器，token 参数换成新设备令牌）。
- 单设备「重置」：只重置该条目（确认文案：「仅 {机器名} #尾号 需要重新执行接入命令，其他设备不受影响」）。
- 主令牌 `regenerate_token` 文案在多设备模式下补一句「已单独发令牌的设备不受影响」（受开关门控，关闭时逐字现状）。

### 7.5 语义与边界

- 本机接入默认仍用主 token（零迁移成本）；本机也可以换发独立令牌（可选）。
- 关闭多设备模式开关：设备令牌**立即全部失效**（鉴权集合清空）——UI 提示一句，
  这是「关闭 = 回到单设备现状」的自然推论。
- 删除设备令牌 ≠ 封禁 IP（401 证据链不受影响，批3-1 的窗口语义照旧）。

### 7.6 测试与门禁清单

- Rust：`verify_any` 六例（主命中 / 设备命中 / 全不中 / 空集合 / 主空+集合非空 fail-closed / 长度侧信道不变量沿用）；
  导出脱敏断言扩 `device_tokens`；config 解析老配置缺键。
- 前端：MultiDeviceCard 渲染门控（关闭时 DOM 无设备令牌节）；文案门控两处。
- 预估改动面：后端 4 文件（config / auth / config_cmds / http+sse）+ 前端 2 文件，一个批次。

## 8. P3 定位收口：服务端协调点/中继

- **定位**：架构级终态，本体是「桥的自建服务端形态」——与身份转变 RFC
  （`proposals/mcp_2026_07_28_adaption_rfc.md` Phase 1，含 SSE 补 token）合流推进，
  不在本规划内排期，也不预留半成品接口（避免两头维护）。
- **触发条件**（满足其一再启动）：真实出现 >2 台设备、移动端接入、或团队共享同一桥的需求。
- **纯本地形态的终态** = P0 + P1 + 批3 + P2：互踢已治（条目并存）、断因可判
  （401 证据链）、令牌误伤已消除（per-device token）。P3 解决的是剩下的
  「账本聚合、通知补发、配置代写」这类需要协调点的问题——它们在两台机器场景下
  靠「导出聚合 + 用户手动」已可接受（§5 已声明不做云同步）。
