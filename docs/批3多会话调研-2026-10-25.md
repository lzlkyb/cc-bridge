# 批 3 多会话管理业界调研（2026-10-25）

用户对结构方案三个拍板点的回应是「去看看别人怎么做的」「先做好再测试」「别人不限制我们就不限制」。
本报告回答「别人怎么做」，作为回修 `批3多会话结构方案-2026-10-24.md` 的依据。
调研对象：**Cline（SDK + 本地扩展 + Cloud）、OpenHands、Claude Code 官方（best practices / Desktop app / agent view）、MCP 协议规范本身**——选它们是因为都真实实现了「多会话管理」且架构公开可查。

## 一、命令 API：显式带 sessionId 是业界一致做法

三个独立技术栈全部收敛到同一形态，**没有一家用「隐式当前会话」作为多会话的承载**：

| 产品 | 形态 | 证据 |
|---|---|---|
| OpenHands | REST 端点**每个都带 conversation_id** | `POST /api/v1/app-conversations/{conversation_id}/send-message`、`GET /api/v1/conversation/{conversation_id}/events/search` |
| Cline SDK | client 先 `client.register` 广告能力，再 **create or attach to a session**，之后所有交互都挂在会话上；hub 把事件 fan out 给所有 attach 该会话的 client | hub-spoke 架构文档 |
| MCP 协议（2025-06-18 起） | `Mcp-Session-Id` 由 initialize 分配，**客户端 MUST 在后续所有请求头里带它**；没带而服务端要求则 400 | Transports 规范原文 |

Cline 老架构（VS Code 扩展）确实有过「隐式当前」形态——`ClineProvider` 维护 Cline 实例**栈**，`getCurrentCline()` 取栈顶——但那套是为「父任务派生子任务、子任务完成还回父任务」设计的，**新 SDK 已明确弃用该形态转向 hub-spoke 显式会话**。栈式管理的 `finishSubTask(lastMessage)` 恢复父任务这套语义，恰恰说明了隐式当前在并发下的脆弱：它依赖严格的调用嵌套，天然排斥「两条会话同时跑」。

**结论：方案 D3（命令全部显式带 `sessionId`）不仅成立，而且是与协议层同构的选择。**

## 二、会话标识：内部 mint + 显式传递，MCP 正在往这个方向演进

- **OpenHands**：conversation_id 由服务端 mint（异步启动任务轮询到 READY 才拿得到），客户端拿着它做一切后续操作。
- **Cline**：session 记录由 hub 建，`sessions.db` SQLite 索引 + `[session-id].json` 权威快照，session 生命周期**独立于任何 client**（client 断了会话继续跑，另一个 client 可 mid-flight 接入同一事件流）。
- **MCP 2026-07-28（已 ratified）**：移除 initialize/initialized handshake 与 `Mcp-Session-Id`，协议变 stateless；应用要跨调用带状态时，官方推荐 **explicit handle 模式**——工具铸造一个 handle（basket_id / browser_id），模型在后续调用里当普通参数传回去。官方原话：这让 **"state visible to the model rather than hidden away"**。

这与我们批 9 的 MCP 协议升级 RFC 直接相关（`proposals/mcp_2026_07_28_adaption_rfc.md`）：协议层不再管会话，会话归属应用层显式管理。**方案 D1（内部单调 `u64`，启动前就存在、显式传递）与协议演进方向完全一致**，且比 resume_id 更早可用（resume_id 要等 `system/init`）。

## 三、并发上限：别人分两类，本地类不限制

| 产品 | 上限 | 性质 |
|---|---|---|
| Cline Cloud | **最多 10 条并行** | 硬限。但那是「每会话一个云 sandbox」的成本约束，不是本地场景 |
| CC workflow guideline | medium <10 / Pro <5 | **"advice rather than a hard cap"**，/config 可改可删 |
| CC agent view / Desktop app | 无文档化上限 | 约束是用量与限流：**"Rate limits still apply across all sessions"**、usage 随会话数线性翻倍 |
| Cline 本地扩展 | 无文档化上限 | task 栈结构本身不设限 |
| 社区经验（tmux 跑 CC） | 「three or four on one laptop is comfortable」 | 经验值，非产品限制 |

按用户规则「别人不限制我们就不限制」：**不设硬上限**。真实约束本来就不在我们这边——

1. **usage 线性增长 + rate limit 全局共享**是 CC 服务端的事，产品层拦不住也不该拦（拦了反而挡住「跑一夜批量」的正当用法）；
2. 本地资源（N 个 claude 进程各几十 MB）做**可见性**（侧栏显示会话数/进程状态），不做拒绝新建；
3. 已知代价记录在案：每条会话的 **SessionStart 钩子会各自跑一遍**，开十条就是十遍。

原方案 §五风险 4 的「建议 5、超出拒绝新建」据此删除，改写为上述口径。

## 四、会话驻留（3-2 的前置问题）：tmux 是标准答案，CC 自带 --bg 是观察项

**断线驻留的三条路，社区与官方文档高度一致：**

- **tmux（标准答案）**：`tmux new -s <name> claude` → Ctrl-b d detach → 断 SSH → 重连 `tmux attach -t <name>`，会话原样恢复。Anthropic Remote Control 文档原话："To keep a session running on a remote machine after you disconnect from SSH, start it inside tmux or screen."
- **nohup/setsid（对交互式 TUI 无效）**：明确记载 "Running nohup claude creates a process you can't reattach to"——TUI 需要真终端做渲染与按键捕获。**这直接影响 0-4 探针 B 分支的定位：setsid 只能证明「进程不死」，不能证明「交互可恢复」；可恢复性只有 tmux 能给。** B 分支降级为兜底证据，A 分支（tmux）才是主路径。
- **CC 原生 background session（`claude --bg`，2026-10 为 research preview）**：per-user **supervisor 进程**托管会话（预 warmed worker），`claude agents` 管理、`claude attach` 拉进终端、`claude logs` 看输出、`claude respawn` 带会话记录重启、`claude agents --json` 机器可读状态（working / blocked / done + waitingFor）。**能力上正是我们 3-2 想要的**，但两条保留意见：① agent view 还是 research preview，稳定性未经验证；② `claude attach` 是「拉进当前终端」语义，与我们的常驻 SSH PTY 模型可能冲突（同一 bg 会话被两个终端 attach 的行为文档未明）。**结论：主路径仍 tmux，--bg 列为远期备选，0-4 探针不加 --bg 分支。**

**0-4 探针需要补一项**：tmux attach 之后的**屏幕重绘完整性**——我们的 GUI 是 xterm.js，重连后靠 tmux 全量重绘恢复画面，这与「日志继续增长」是两个不同的验证点。

## 五、事件分流与断线重放：我们的 D2 与事件流架构同构

- **OpenHands**：所有交互走类型化事件流（MessageEvent / ActionEvent / ObservationEvent / CondensationEvent / SystemPromptEvent / FinishAction），事件日志是唯一事实来源，可重放、可审计，**CLI / web GUI / cloud 三个前端是同一事件流的不同视图**（"can't quietly drift apart"）。
- **Cline hub**：spoke 产事件 → hub 中继给所有 attach 的 client，client 可随意进出不打断执行。
- **MCP SSE**：event id 按流分配做**断线重放游标**，客户端带 `Last-Event-ID` 重连补拉；规范明确 **MUST NOT 跨流重放**。

对我们 D2 的加强：`CcEventPayload` 加 `sessionId` 之外，**每会话的 `seq` 应当作重放游标用**——前端断线重连时带 last seq 向 Rust 补拉该会话 ring 里的事件（我们的 ring 本就是 per-Shared 一条，语义天然对齐）。这一条原方案没写，补入。

## 六、新发现的风险（原方案未覆盖）

1. 🔴 **同目录多会话不是安全边界**。OpenHands 原话："A separate conversation is not a security boundary when it shares a sandbox with another conversation." 我们多条 CC 会话默认共享同一远端工作目录，一条 `rm -rf` 会伤到所有会话。CC 的解法是 **git worktree 隔离**（Desktop app 与 `--bg` 都在编辑前把会话移入 `.claude/worktrees/`；`bgIsolation: none` 可关）。我们连接的远端项目未必是 git 仓库，worktree 不是默认选项——**列为已知风险 + 3-1b 侧栏给「隔离警告」提示**，不强行做隔离。
2. **会话生命周期边界要照抄 CC 的口径**：会话抗睡眠不抗关机（关机时进行中的显示 failed）；空闲约一小时进程被停、会话留盘可恢复；48 小时未见显示 stopped；pin 可保活。我们的 `persist_all`/`shutdown_all` 语义与这套对齐即可，不需要发明。
3. **分叉（3-3）CC 已有原语**：`/fork` 把当前对话复制成新后台会话、原会话继续；`claude --resume <id>` 是「续写同一会话」（两个进程续同一 id 会冲突，不是分叉）。我们的「分叉」按钮底层应走 fork 语义而非 resume。
4. **编辑重发（3-3）的业界参照**：CC 用 checkpoint/rewind（双 Esc 或 `/rewind`，可只恢复对话 / 只恢复代码 / 两者），且 checkpoint 不捕获 Bash 改动的文件（"not a replacement for git"）。我们「从该消息截断重跑」更直接，但要在 UI 上诚实标注：截断点之后由会话自己产生的文件改动不会回滚。
