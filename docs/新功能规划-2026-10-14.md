# cc-bridge 新功能规划（2026-10-14）

> 定位基线：`proposals/bidirectional_bridge_rfc.md`（2026-10-12 拍板）——**一个桌面端，正反双向；装在文件那端，AI 从任意一端连进来。**
> 本文只谈「下一步还能做什么」。所有现状判断都基于**当日真实源码/文档核查**，标注 `file:line`，不做凭记忆推测。

---

## 0. 两条前提

**前提 1 · 产品原则（2026-10-14 拍板）**

> 🔴 **不做任何「弹窗让用户点确认」的功能。** 用户不会点；真弹了也是无脑点通过 —— 零安全增益，纯摩擦。

安全因此**不建立在事前拦问上**，而建立在四件已经就位或可以补完的事上：

| 机制 | 现状 |
|---|---|
| 路径 / 扩展名白名单（`canonicalize` 防逃逸、空名单 fail-closed） | ✅ 已有 |
| 写 / 删 / 覆盖前**自动备份** | ✅ 已有 |
| 全量**审计日志**（含量化耗时） | ✅ 已有 |
| 高危工具的**一次性总开关**（`run_command` 默认关、`shell_enabled` 默认关） | ✅ 已有 —— 这是「配置一次」而非「每次打断」 |
| **事后可还原**（逐个文件已可还原 + 看 diff） | ⚠️ 只做到单文件，见 §2 A |
| **自动熔断**（异常写速自动暂停，不问用户） | ❌ 缺，见 §2 A3 |

**前提 2 · 能力面已不缺工具数量**

20 个 MCP 工具 + 外挂 MCP 桥 + 双向 A/B + 审计 / 备份 / 回滚 + HTTPS 自签。**再堆工具是低 ROI。**

**结论**：真正还空着的是三块，且都**不需要用户介入**：

| # | 方向 | 一句话 |
|---|---|---|
| **①** | **自动可逆** | 不说"要不要做"，只说"做了也能撤" |
| **②** | **协议面与网关能力** | 从"工具集合"升级成"MCP 一等公民"，纯模型侧体验 |
| **③** | **零介入运维与生态** | 桥的存在感归零：连得上、能自检、文案不挑客户端 |

## 2. 功能候选清单

### A. 自动可逆 —— 把"敢放手"建立在**事后可撤销**上

| 编号 | 功能 | 说明 | 成本 | 风险 |
|---|---|---|---|---|
| **A1** | **会话级快照 / 一键全撤** | 把一次 AI 会话（或指定时间窗）内所有写操作归为一组：列出「这一轮改了哪些文件 + 每个文件的 diff」→ **整组回滚**。全程无弹窗，用户只在"要撤"时主动进审计页操作 | 中 | 先决条件是「审计条目 ↔ 备份文件」的可靠关联（`rollback_and_diff_rfc.md` 已规划）；整组回滚要处理"中途有文件被用户手改过"的冲突 |
| **A2** | **改动摘要（自动生成，不是确认）** | 每轮会话结束自动在审计页生成一条摘要：「本轮 N 个文件、+X/−Y 行、耗时」——**只告知，不询问**。托盘可选提示，默认静默 | 低-中 | 复用 `diff_utils.rs`；纯展示 |
| **A3** | **写操作自动熔断** | 滑动窗口检测异常写速（如 1 分钟 > N 次写 / 单轮 > M 个文件被删），超阈值**自动暂停并告警**（托盘 + 审计记 `blocked_by_breaker`），而不是问用户。复用 401 封禁已有的滑动窗口计数思路 | 低-中 | ❗ `batch` 单次调用天然会对多文件连写，阈值必须按**子操作**而非按调用计数，否则会误伤正常批量重构 |

> 🔴 **A1 是前提 1 的直接兑现**：产品 tagline 已承诺「白名单、全审计、**误操作可还原**」（`README.md` 首屏 / RFC 叙事），而现状只做到一半——单文件还原要人在审计日志里**一条条翻**。不靠弹窗，靠"随时能整组撤"。

### B. 协议面与网关能力 —— 纯模型侧，零人工

| 编号 | 功能 | 说明 | 成本 | 风险 |
|---|---|---|---|---|
| **B1** | **外挂桥扁平化（step2）** | 让模型直接看到 `mcp__<server>__<tool>`，而不是"先猜哪个 server 有这个能力，再 `mcp_proxy` 代理"——省**一次往返 + 一轮推理**。方案已给：启动时从持久化 manifest 把工具名 `Box::leak` 成 `&'static str`，所有外挂工具**共用一个 fn 指针**，从 name 自解 server/tool 查全局单例 | 中 | 要动 `ToolSpec` / `WRITE_SET`（只读模式的安全门），须一次改透四处的引用 |
| **B2** | **Session-Id / 协议头补齐** | 回传 `Mcp-Session-Id`、读 `MCP-Protocol-Version` / `Mcp-Method` 头 | **低** | 低。属 `mcp_2026_07_28_adaption_rfc.md` 那条线，顺手项 |
| **B3** | **SSE 真流式 → 进度与日志通知** | 先修 SSE 为真流式（`sse.rs:8-9` 自述非真），再补 `notifications/progress`（后台 `run_command`、大目录递归、批量写）与 `notifications/message` | 中 | SSE 是前置依赖，不能跳过；进度条能否渲染取决于客户端 |
| **B4** | **Resources：把白名单暴露为 MCP 资源** | `resources/list` / `resources/read` / `resources/list_changed`。客户端可浏览、@ 引用白名单内文件，文件变更主动通知 | 中-高 | **客户端差异大**：Claude Code 对 resources 的呈现能力有限 → **先写小样验证 ROI 再全量做** |
| **B5** | **工具面裁剪（per-token / per-client）** | 配置决定对某个主体暴露哪一子集工具（如给弱客户端只暴露只读集）。配置型，运行时不弹窗 | 低-中 | 与 A 组无关；`WRITE_SET` 的语义要跟着主体走 |
| **B6** | 外挂桥支持 HTTP / SSE 型 server | 配置已预留 `transport` 字段，补齐即可接远端 MCP server | 中 | 低 |

## 4. 反向清单（明确不做，附理由）

| 不做 | 理由 |
|---|---|
| 🔴 **任何"弹窗让用户确认"的功能** —— 写操作审批门、高危动作二次确认、dry-run 确认卡片 | **产品原则（2026-10-14 拍板）**：用户不会点，点了也是无脑通过 → 零安全增益，纯摩擦。安全改由「白名单 + 自动备份 + 全审计 + 事后整组还原 + 自动熔断」承担，全部**无需任何用户介入** |
| **改动预览（dry-run）作为独立工具** | 其价值原本全在"审批卡片上显示 diff"，审批方案撤下后失去落点。改动明细改由 **A1/A2 在审计页事后呈现** |
| **Sampling**（桥反向借客户端的模型跑 LLM 调用） | 客户端支持度极低 + 隐私边界复杂（等于把本机文件喂给任意客户端的模型） |
| **自动安装外挂 MCP server** | `mcp-bridge-step1-plan.md §S6` 已划界：各 server 安装方式不同（cargo/npm/pip/curl binary），桥管不过来，**只检测 + 提示** |
| **把 SSH 终端做成 MCP 工具** | 与 `run_command` 高度重叠，且会让"给人用的交互面"和 AI 抢同一个 PTY |
| **完整版端口转发**（ControlMaster 动态加规则） | 要改会话启动参数 + 管 master socket 生命周期 + Windows 上 ControlPath 的 unix socket 路径长度限制。先做零 Rust 的「转发规则簿」D-lite，用出真实需求再评估 |
| **Linux 版 / headless 服务模式 / macOS Intel** | `bidirectional_bridge_rfc.md` 已明确：桥只有桌面端一种形态（Windows x64 + macOS Apple Silicon）；headless 路线已废弃 |
| **Prompts（预置提示词）** | 客户端支持不一，价值存疑 |

## 5. 建议执行顺序

```
第一批（可逆性闭环 + 模型侧体感，两条独立线，可并行）
  A1 会话级快照 / 一键全撤   ← 先决条件：审计↔备份关联（rollback_and_diff_rfc.md 已写好）
  B1 外挂桥扁平化           ← 让模型直接看到 mcp__<server>__<tool>

第二批（低成本的"身份与体感"补齐，都是零用户介入）
  D1 文案通用化   ·  B2 Session-Id / 协议头   ·  D5 接入自检   ·  A2 改动摘要

第三批（运维与自动安全）
  C1 空闲关停 + manifest 刷新   ·  A3 写操作自动熔断（阈值按子操作计数）
```

**旁路顺手项**（可插入任一批次）：`D1`（纯文案，最低）、`B2`（低）。

## 6. 待拍板

1. **第一批做 A1（会话级全撤）还是 B1（外挂桥扁平化）？** 两条独立的线，也可以并行。
2. **`A3` 自动熔断做不做？** 好处是"不问用户也能兜底"，代价是阈值需要按 `batch` 的子操作计数，否则会误伤正常批量重构。建议**先只做"单轮删除文件数"这一条**（最危险且最容易计数）。
3. **`B4` Resources 要不要先做小样？** 建议：只做 `resources/list` + `read`，在 Claude Code 与 WorkBuddy 上各验一次"用户到底能不能用上"，再决定全量。
4. **`D6` 多桥管理台** 是否确认继续不排期？（RFC 原定"待 P1/P2 落地后的真实需求"）
