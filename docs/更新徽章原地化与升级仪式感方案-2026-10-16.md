## 0. 一句话结论

侧栏底部的更新徽章在 `updateStatus !== "idle"` 时是「foot 里的一整行」，只要开始检查更新就会**插入一行**，
把 foot 从 1 行变 2 行、导航区压扁 25.9px。把非 idle 的整行徽章也收进**设置行右端那个固定宽度槽位**
（七态原位变形）即可彻底消除位移；下载期再补「窗口顶部通栏进度线」与「**顶栏中段网速读数**」，
重启期补「重启过渡层」——升级就有了应有的分量。
（网速读数最初设计成 28px 通栏浮层，同日二次改造移入**顶栏中段的空白拖拽区**，见 §11。）

## 1. 现状与根因

### 1.1 代码位置

`desktop/src/components/layout/SideNav.tsx:149-181`

```tsx
<div className="app-side-foot">
  {(settingsMode || updateStatus !== "idle") && <UpdateBadge currentVersion={status?.version} />}
  {!settingsMode && (
    <div className="app-side-settings-row">
      <button …>设置</button>
      {updateStatus === "idle" && <IdleVersionPill currentVersion={status?.version} />}
    </div>
  )}
</div>
```

`desktop/src/index.css:1897`

```css
.app-side-foot { display: flex; flex-direction: column; gap: 6px; padding: 8px; }
.app-side-foot .header-badge { justify-content: center; }   /* 整行居中 */
```

### 1.2 为什么会「多出一行」

foot 是 **column + gap 6**，nav 是 `flex: 1 1 auto`。所以：

- `updateStatus !== "idle"` 时，`<UpdateBadge>` 作为**新的 flex 子项**插到 foot 顶部 ⇒ 多一行。
- foot 高度从 53.8px 涨到 79.7px ⇒ nav 可用高度从 194.2px 被压到 168.3px。
- 因为 foot 贴底，视觉上是 **foot 顶边上移 25.9px**（设计稿 §1 的红虚线就是这个位置）。

实测（设计稿 §1，1:1 复刻 200px 侧栏）：

| 状态 | foot 高 | nav 可用 | 相对 idle |
|---|---|---|---|
| idle | 53.8px | 194.2px | — |
| available | 79.7px | 168.3px | **+25.9px / −25.9px** |
| downloading | 79.7px | 168.3px | 同上 |

### 1.3 连带问题

1. **对齐不一致**：插入的整行徽章是**居中**的，而设置行是**左对齐**的 —— 两个部件重心不齐。
2. **信息密度失衡**：`下载中 42% · 3.2 MB/s` 这种长文案在 200px 侧栏里被强行拉成一个全宽色块，
   视觉权重远高于它实际的重要性。
3. **一旦开始就回不去**：从 `checking` 起 foot 就一直是两行（`uptodate` 要等 4 秒才回 idle），
   这段时间里用户的侧栏是「变形」状态。

## 2. 方案 A：原地状态机（必做）

### 2.1 做法

把徽章从「foot 的独立一行」降级为「设置行右端的一个槽位」，**七种状态在同一个槽位里原地变形**。

```tsx
// SideNav.tsx —— foot 改造后
<div className="app-side-foot">
  {!settingsMode && (
    <div className="app-side-settings-row">
      <button …>设置</button>
      <UpdateSlot currentVersion={status?.version} />
    </div>
  )}
  {/* 设置目录模式下设置行不存在，槽位单占一行（该行常驻，idle 也显示版本号，高度恒定） */}
  {settingsMode && <UpdateSlot currentVersion={status?.version} row />}
</div>
```

```css
/* 槽位：锁死宽度 → 七态零位移 */
.update-slot { flex-shrink: 0; min-width: 66px; display: inline-flex;
  justify-content: center; align-items: center; }
.update-slot .header-badge { padding: 2px 8px; font-size: 10.5px; }
```

`UpdateBadge.tsx` 的 7 个 `if (status === …)` 分支**全部保留**，只做两件事：
① 每个分支的返回包进同一个 `<span className="update-slot">`；② 文案压到 2–3 字。

### 2.2 七态文案表

| status | 槽位内容 | 图标 | 底色 | 动效 |
|---|---|---|---|---|
| idle | `v0.1.5` | — | 版本渐变 | hover 微抬升（现状） |
| checking | `检查中` | spinner 10px | 版本渐变 | 旋转 |
| available | `更新` | arrowUp 10px | 蓝渐变 | **呼吸环 2.1s** |
| downloading | `42%` | 进度环 12px | 版本渐变 | 环按百分比推进 |
| ready | `重启` | check 10px | 绿渐变 | **呼吸环 2.1s** |
| uptodate | `最新` | check 10px | 版本渐变 | 4 秒后自动回 idle（现状） |
| error | `重试` | alertTriangle 10px | 红渐变 | — |

**完整信息不丢，只是移进 `title`**：

- available → `发现新版本 v0.1.6，点击查看更新详情`
- downloading → `正在下载更新… 42% · 3.2 MB/s · 已下载 12.4 MB`
- ready → `更新已安装，点击重启`
- uptodate → `已是最新版本` ／ error → `更新检查失败，点击重试`

### 2.3 宽度预算（200px 侧栏，实测）

| 项 | 宽 | 说明 |
|---|---|---|
| `.app-side` | 200px | 固定 |
| foot 内容区 | 184px | 200 − padding 8×2 |
| gap | 6px | `.app-side-settings-row` |
| **槽位** | **66px** | `min-width` |
| 设置按钮 | **112px** | `flex: 1` 吃剩余；内容左对齐，槽位变化时不动 |

七态自然宽实测：`idle 42.3 / checking 62.5 / available 52 / downloading 53.7 / ready 52 / uptodate 52 / error 52`。

- **66px 的由来**：最长态是 `checking`（spinner + 「检查中」三字）= **62.5px**，取 66 留 3.5px 容差，
  防止用户机器上的字体度量差异把最长态顶破。
- 若把文案压成两字（「检查」）可收到 56px，但牺牲表意，**不值得为 10px 这么做**。
- 槽位锁宽后，`available`（52px）到 `checking`（62.5px）的 10px 差异不会被看见 —— 这正是目的。

### 2.4 已知取舍（需要你确认）

**「更新」不显示版本号**。锁宽 66px 放不下 `更新 v0.1.6`（需 ~85px）。
版本信息在**点击后的弹框**里（`UpdateNotesDialog` 已有 `v0.1.5 → v0.1.6` 的醒目对比）+ `title` 里。
如果你更看重「不点开就知道升到哪版」，可选**不锁宽**：槽位自然宽（42–71px），
代价是设置按钮宽度跟着伸缩（视觉上是 pill 向左生长，不是位移）。**我推荐锁宽。**

### 2.5 涉及文件

| 文件 | 改动 |
|---|---|
| `components/layout/UpdateBadge.tsx` | 7 个分支包进槽位；文案压缩；`IdleVersionPill` 并入后删除 |
| `components/layout/SideNav.tsx` | 删掉「整行徽章」与「条件渲染 pill」两处，改为常驻槽位 |
| `src/index.css` | `.app-side-foot .header-badge{justify-content:center}` 改挂到独立行场景；新增 `.update-slot` |

**净变化约 −20 行**（删掉 `IdleVersionPill` 与条件分支，新增 CSS 约 10 行）。

## 3. 方案 B：窗口顶部通栏进度线（推荐）

### 3.1 为什么需要它

侧栏槽位只有 66px，装不下「还剩多久 / 多快」。而**下载是需要被感知时长的事件** ——
现在除了侧栏那个 42% 就在没有别的地方能看到。进度线解决的是这个，不是布局问题。

### 3.2 做法

```tsx
// components/update/UpdateProgressLine.tsx（新增，最终 45 行 —— 多出的部分是 320ms 淡出状态机）
export function UpdateProgressLine() {
  const { status, progress, progressIndeterminate } = useUpdate();
  if (status !== "downloading") return null;
  return (
    <div
      className={`update-progress-line${progressIndeterminate ? " indeterminate" : ""}`}
      style={progressIndeterminate ? undefined : { transform: `scaleX(${progress / 100})` }}
      aria-hidden="true"
    />
  );
}
```

```css
.update-progress-line {
  position: fixed; left: 0; right: 0; top: var(--titlebar-h, 32px);
  height: 2px; z-index: 60; pointer-events: none;
  transform: scaleX(0); transform-origin: left center;
  background: linear-gradient(90deg, #4F46E5, #7C3AED, #3B82F6);
  box-shadow: 0 0 8px rgba(79, 70, 229, .45);
  transition: transform .2s linear;
}
.update-progress-line.indeterminate {
  transform: none; width: 34%;
  animation: updline 1.15s cubic-bezier(.4, 0, .2, 1) infinite;
}
@keyframes updline { 0% { left: 0 } 100% { left: 100% } }
@media (prefers-reduced-motion: reduce) {
  .update-progress-line.indeterminate { animation: none; width: 100%; opacity: .6 }
}
```

挂在 `App.tsx` 里 `UpdateProvider` 的子树上 —— 实际做法是直接渲染在 `UpdateContextProvider`
自己的返回尾部（与 `UpdateNotesDialog` 同级），这样挂载点与数据源同文件，不必再回 `App.tsx` 改一次。

### 3.3 🔴 硬约束

- **必须 `position: fixed` + `pointer-events: none`**，用 `transform: scaleX()` 而不是 `width`。
- 一旦改成占位元素（例如给 `app-main` 加 `border-top` 再动画），内容区高度会变化 1–2px ⇒
  终端面板触发一次 `fit` ⇒ **远端 TUI 重排**。本项目已经因为「1–2px 高度抖动」踩过坑，不能重蹈。
- 顶部位置取标题栏高度（`top: var(--titlebar-h)`）；若拿不到变量，退化为「侧栏顶部」，不要盖住拖拽区。

## 4. 方案 B+：网速读数（推荐）

> 🔴 **实施后的形态与本节原案不同**：这里论证的是「一条窗口级状态条」，但实测证明任何
> ≥18px 的贴顶浮层都会切掉顶栏控件字形（§11）。**最终落点是「顶栏中段内嵌」**，
> 零遮挡零占位。本节保留作为选型过程的记录，「窗口级 / 通栏」这两处描述视为**已作废**。
> 六项读数的内部结构、数字不抖规则、`totalBytes` 数据缺口这三部分**不受影响，仍然有效**。

### 4.1 为什么必须补它

进度线回答「走了多远」，回答不了「走多快」。而下载时用户真正想知道的是**还要多久**——那必须先有速度才算得出来。
侧栏槽位（66px）放得下 `42%`，放不下 `3.2 MB/s`；`title` 悬浮提示里的速率要悬停才看得见，等于没有。
所以下载期需要一条**窗口级状态条**：进度 · 网速 · 已下载/总量 · 剩余时间同屏。

### 4.2 🔴 一个必须先补的数据缺口

| 字段 | 现状 | 位置 |
|---|---|---|
| `bytesPerSec` | ✅ 已有 | `contexts/UpdateContext.tsx:253` 的 `update:progress` 事件携带（后端 ~250ms 窗口重算） |
| `downloadedBytes` | ✅ 已有 | 同一事件 `setDownloadedBytes`（`:255`） |
| **`totalBytes`** | ❌ **缺** | `total` 只在回调里换算成百分比，**没有存进 state**（二次改造后已在 `:258` 补上） |

不补这一步，就显示不了「8.6 / 20.4 MB」和「剩余 4 秒」。改动约 3 行：

```tsx
const [totalBytes, setTotalBytes] = useState<number | null>(null);
// update:progress 回调里：setTotalBytes(total);   // total 为 null ⇒ 不确定态
// update:downloading 回调里重置：setTotalBytes(null);
```

并把 `totalBytes` 加进 `UpdateState` 接口与 Provider 的 value。

### 4.3 形态比较（设计稿 §4 有 1:1 渲染）

| 形态 | 内容 | 结论 |
|---|---|---|
| 1 · 尖端读数 | 网速胶囊跟在进度线生长端 | 未采用：只有速度，没有剩余时间 |
| 2 · 顶部通栏状态条 | 28px 浮层横贯窗口顶部 | 🔴 **已退役**（同日二次改造）：与顶栏控件字形带冲突，详见 §11 |
| 3 · 底部状态条 | 同上，贴窗口底 | 未采用：底部是终端输入行进区 + 侧栏设置行，遮挡代价更高 |
| **4 · 顶栏中段内嵌** | 同样六项读数（环/百分比/轨道/网速/已下载·总量/剩余），铺在顶栏中间的空白拖拽区 | ✅ **现行实现**：零遮挡、零布局影响。窄窗退化见 §4.4 |

形态 2 / 3 / 4 共用同一套内部结构（`.ur-*`），只差一个容器；形态 4 没有浮层容器。

### 4.4 解剖与数字规则（实测值）

**窗口内实测**（复用产品 `index.css` + 真实顶栏结构，CDP 探针量取）：

- 读数的**最小完整宽 349px** = 环 12 + 状态 60 + 轨道 ≥34 + 速率 68 + 已下载/剩余 139 + 4×gap 36。
- 顶栏中段可用宽 = `W − 侧栏(200/56) − 左组 108 − 右组 270 − 内边距与间距 46`：
  1280 下 **618**、1080 下 562、900 下 382、741 下 223。
- 顶栏高度在**所有窗宽下都是 52px** —— 读数出现/消失不改变任何盒（这是它能替换浮层的前提）。

**数字不抖的三条硬规则**：

1. **`font-variant-numeric: tabular-nums`** —— 等宽数字，`1` 与 `8` 同宽。
2. **速率段定宽 `min-width: 68px`** —— 实测最短态 `—` 与最长态 `↓ 999.9 MB/s` **都是 68px**
   （`formatBytes` 单位封顶 GB 且 ≥10 取整，13 字符已是上界）。不定宽的话，
   `—` → `↓ 3.2 MB/s` 会把右侧「已下载 / 剩余」整体右推约 56px。**68 是量出来的，不是拍脑袋。**
3. **`bytesPerSec === 0` 时显示 `—` 而非隐藏** —— 下载刚开始的第一个窗口还没算完（源码注释已说明）；
   隐藏会让右侧读数先左移再弹回。

其余状态映射：`total == null` → 切不确定态（百分比改「下载中」、轨道循环扫光、隐藏剩余时间，
复用已有 `progressIndeterminate`）；进度事件静默 > 1.5s（`STALL_MS`）→ 速率转 `--muted` + 文案「等待响应…」，
避免用户盯着冻结的读数以为卡死。

**窄窗退化（两条断点，都是量出来的）**：

| 窗宽 | 中段可用 | 行为 |
|---|---|---|
| ≥ 901 | ≥ 383 | 六项全显（轨道是唯一可压缩段，先被压到下限 34px） |
| 741–900 | 223–382 | 丢「已下载/剩余」，余 环+百分比+轨道+网速（最小 201px） |
| < 741 | < 223 | 整块收起 —— 靠侧栏槽位的百分比 + 顶部进度线兜底 |

断点取 900 而非临界值 870：`ur-rest` 的文本随数字位数浮动（至多再宽 ~26px），卡在临界值上会切掉末尾半个字。
**绝不靠 flex 换行**：换行会把读数撑成两行、顶破恒定 52px 的顶栏。

### 4.5 🔴 硬约束与代价（二次改造后）

- **零布局影响是第一条**：读数是顶栏中段那块空白 `flex-1` 区里的**普通内容**，不是浮层。
  它既不占新高度（顶栏恒定 52px），也不覆盖任何控件 —— 属于「比让位更好的第三种解法」。
- **`pointer-events: none` 仍必须**：中段是窗口拖拽区，读数不穿透的话拖到数字上窗口不动。
- **牺牲了两处可见性**（这是它唯一的代价，且都有兜底）：
  ① 窗口 < 741px 时无位可放 ⇒ 只剩侧栏槽位百分比 + 进度线；
  ② 全屏终端态（`fixed inset-0 z-50` 盖住顶栏）下读不到明细 ⇒ 只剩 2px 进度线。
- 早先「半透明 + 毛玻璃 + 宁可遮挡」那套（90% / `blur(12px)`）随形态 2 一起退役：
  它论证的是「遮挡可以接受」，而二次改造证明**有不遮挡的解法**。

### 4.6 涉及文件（二次改造后的实际落点）

| 文件 | 改动 |
|---|---|
| `contexts/UpdateContext.tsx` | 新增 `totalBytes` state（约 3 行）+ 接口与 value 各 1 行 |
| `components/update/UpdateReadout.tsx` | **新增**，**117 行**；六项读数 + 心跳判定 |
| `src/index.css` | `.upd-readout` / `.ur-*` 样式约 25 行 + 两条窄窗断点 |
| `components/layout/Header.tsx` | 中段那段 `flex-1` 拖拽区由自闭合改为容器，内嵌 `<UpdateReadout />` |

**与方案 B（进度线）的关系**：原方案建议两者合并成一个 `UpdateProgressBar`，用
`variant="line" | "bar"` 决定渲染 2px 线还是 28px 条。二次改造后**容器彻底不同**（一个是
`fixed` 全窗口浮层、一个是顶栏内的普通内容），继续合并只会让一个文件同时承担两套定位，
故拆为 `UpdateProgressLine.tsx`（45 行，自带 320ms 淡出）+ `UpdateReadout.tsx`（117 行）；
两者共享 `useUpdate()`，各自独立挂载（线挂 `UpdateContextProvider` 尾部，读数挂 `Header`）。

## 5. 方案 C：重启过渡层（推荐）

### 4.1 为什么

现在点「重启」：界面闪一下没了 → 1–3 秒空白 → 应用重新出现。
用户**无法区分「正在升级」和「崩了」**。把这段空白用一个 1.1 秒的过渡层包住，升级就成了一件被看见的事。

### 4.2 做法

```tsx
// contexts/UpdateContext.tsx
const [restarting, setRestarting] = useState(false);

const restart = useCallback(async () => {
  if (restarting) return;
  setRestarting(true);
  // 让过渡层播完再重启 —— 这段等待本身是"仪式感"的载体
  await new Promise((r) => setTimeout(r, 1100));
  try {
    await relaunch();
  } catch (e) {
    console.error("[Update] 重启失败:", e);
    setRestarting(false);            // 🔴 必须复位
    setError(String(e));
    setStatus("error");
  }
}, [restarting]);
```

`RestartOverlay` 与 `UpdateNotesDialog` 一样挂在 Provider 内部（应用级）。
内容：渐变圆角 logo + 「正在应用更新」+ `v0.1.5 → v0.1.6` + 2px 扫光条 + 「应用将自动重启，请稍候」。
入场：250ms 淡入 + 图标 `scale .94 → 1`；`prefers-reduced-motion` 下扫光改静态。

### 4.3 🔴 唯一的真实风险

**失败路径必须复位。** `relaunch()` 的 catch 里若忘了 `setRestarting(false)`，
过渡层会永久盖住界面，用户只能杀进程 —— 比现在「闪一下」更糟。
这也是本方案唯一需要在验收时专门测一条的原因。

## 6. 方案 D：升级后首启欢迎（可选）

### 与方案的三处偏差（均为实施中发现的更优解）

1. **进度线与状态条并存，不是二选一**：线 `top:0`（2px）、条 `top:2px`（28px）。
   线的独特价值是**折叠态下依然可见**（窗口级元素），条负责明细；两者同位置叠加时
   线会成为条的高光顶边，不重复。
   ⚠️ **二次改造后此条的「叠加」部分作废**：28px 条已退役，线不再与它叠放，
   而是回到贴顶独占（`top: 0`，2px）。「线与明细并存」这个结论本身仍成立 ——
   明细搬进顶栏中段后，两者的分工关系不变（线管远观/折叠态，读数管明细）。
2. **欢迎条改右上角卡片，不是通栏条**：通栏会遮侧栏品牌区 36px 达 9 秒，收益却只是
   一条一次性通知。卡片 `fixed top:60px right:12px`，不遮侧栏、不遮顶栏窗口控件。
   （初版写的是 `top:10px` —— 那会整块盖住顶栏最右端的窗口控件，见下方复查。）
3. **新增「等待响应」判定**（方案 §4.4 表格里原写「连续 3 个窗口 < 1KB/s」）：
   改为**心跳**实现 —— 进度事件 ~250ms 一跳，静默 > 1.5s 即转灰显示「等待响应…」。
   真卡死时进度事件不再来，只有定时器能给出信号，按速率的阈值判断反而判不出来
   （速率恒定在低位时不会重新触发依赖）。

### 实现细节上值得记下的两点

- **槽位 `min-height: 22px`**：版本号还没拿到时槽位也要在，否则设置按钮会横跳。
- **available / ready 的呼吸光圈走 `::after` 伪元素**：`.header-badge` 自身已承载立体阴影
  与 hover 阴影变化，直接对 `box-shadow` 做 keyframes 会把它们覆盖掉。
- 新增的 4 个 infinite 动画（两条扫光、呼吸圈、过渡层扫光）已补进
  `:root[data-app-hidden]` 的 `animation-play-state: paused` 列表 —— 这份列表是
  「窗口收进托盘时别白烧 CPU」的唯一防线，容易漏。

### 复查修复（同日，`9ea43ac` 之后）

复审全量改动后发现三处问题，已修：

1. 🔴 **欢迎卡片 `top:10px` 整块盖住窗口控件**（真实缺陷）。顶栏 52px，窗口控件
   （最小化/最大化/关闭，3×`w-8` = 100px + `gap-2px`）钉在最右端、左右留白 12px；
   卡片宽约 330px、高约 38px、`top:10px right:12px` ⇒ 与控件区 [右-112, 右-12] ×
   [10, 42] **完全重叠**，且它自身那枚 `uw-close`（22px）正好落在系统关闭按钮上。
   症状：升级后 9 秒内点「关闭窗口」会把提示卡点掉，窗口纹丝不动。
   修法：`top: 60px`（顶栏 52px 下沿 + 8px 余量），只遮挡内容区右上角的页签工具栏，
   不再碰系统窗口框架；卡片自带关闭按钮，遮挡可被用户一秒解除。
   ⚠️ 这是静态稿抓不到的坑 —— 稿里没有窗口控件，必须拿真窗口结构核。
2. 🔴 **重启失败把 `status` 打成 `error`，丢掉「重启」入口**（回归）。旧实现
   （`9ea43ac^`）失败只 `console.error`，徽章仍停在「重启」可再点；新实现
   `setStatus("error")` 之后徽章变成「重试」，而那个分支触发的是 `check_update`
   —— 用户被迫重走「检查 → 下载」一整轮，而更新其实早已下载安装完成。
   修法：失败时**保留 `status = "ready"`**，失败反馈改由 `UpdateBadge` 监听
   `restarting` 回落 + `error` 弹 toast（三条同时成立才可能是 relaunch 抛错）。
3. **`restart()` 的重入防护用了 state 而非 ref**：state 在同一帧内恒为旧值，双击 /
   连按 Enter 会拿到两次 `restarting === false` ⇒ 两次 `relaunch()`（双杀进程）。
   本文件对下载早已用 `downloadingRef` 这个套路，改成 `restartingRef` 保持一致。
   （概率低：过渡层 1.1s 内就铺满全屏、会吃掉第二击；但代价仅 3 行。）

顺带确认不是问题的两处：

- `update-slot` 锁宽 66px 后最长态是 `downloading` 的「下载中」（环 12 + gap 5 +
  3×10.5 CJK + padding 16 = 64.5px），仍在 66px 内；窄窗口媒体查询其实用不上
  （最小窗宽 560 下固定段 424px 也放得下），属保守兜底，保留。
- `:root[data-app-hidden]` 那串逐个列举的暂停列表对新增动画是**冗余**的
  （`[data-app-hidden] *` 已 `animation-play-state: paused !important`），但无害。

### 仍需实机确认（门禁覆盖不到）

> 二次改造后原第 1 条（状态条毛玻璃观感）已失效 —— 毛玻璃与状态条一起退役了。

1. **顶栏中段读数在真实 WebView2 下的宽度**。CDP 探针是在 Edge 里量的（复刻页 `link` 了产品
   `index.css`，token 与类名都是真的），但**字体度量可能与 WebView2 有差**，而「最小完整宽

## 11. 二次改造：网速读数搬进顶栏中段（同日，`9ea43ac` 之后的审查）

### 11.1 怎么发现的

复审判 §4 的「28px 通栏状态条」时，用 CDP 复刻真窗口量了状态条与顶栏每个控件**内层墨迹盒**
的重叠。结论比预期严重：

- 顶栏 `.app-topbar` 高 **52px**、控件垂直居中 ⇒ 图标按钮（36px）占 y=8–44、
  窗口控件与 sm 按钮（32px）占 y=10–42，**所有字形与文字都落在 y=18–34** 这条「字形带」里。
- 28px 贴顶条下沿 **y=30** ⇒ 与字形带重叠 12px，压掉 **8 个控件字形**（含最小化/最大化/关闭）
  的 **78%**。

⚠️ 这条在静态设计稿里看不出来：稿里没有窗口控件，只有内容区。**必须拿真窗口结构核。**

### 11.2 定夺过程

摆出三种形态给用户选（各带实测代价）：

| 形态 | 结论 |
|---|---|
| ① 28px 贴顶通栏条 | 现状。压掉 8 个控件字形 78%，含窗口关闭按钮 ⇒ 不可接受 |
| ② 16px 贴顶通栏条 | 推演的最薄可行值：墨迹恰好不重叠，但按钮**底色**仍被切一刀，且 16px 放不下六项读数 |
| ③ **顶栏中段内嵌** | ✅ 选中。顶栏中段本来就有一块空白 `flex-1` 拖拽区，读数作为**普通内容**住进去 |

选 ③ 的关键认知：这**不是「要不要忍遮挡」的二选一，而是存在第三种解法** —— 那块空白
本来就存在，读数既不让位（不改任何盒高）也不遮挡（不覆盖任何控件）。

### 11.4 实测数字

- **读数最小完整宽 349px** = 环 12 + 状态 60 + 轨道 ≥34 + 速率 68 + 已下载·剩余 139 + 4×gap 36。
- **顶栏中段可用宽** = `W − 侧栏(200/56) − 左组 108 − 右组 270 − 内边距与间距 46`：
  1280 → **618**、1080 → 562、900 → **382**、741 → **223**。
- **顶栏高度在所有测试窗宽下恒为 52px** —— 这是它能替换浮层的前提：读数出现/消失不动任何盒
  ⇒ 不触发终端 `fit`（见 §3.3 那条 1–2px 红线）。
- **两条窄窗断点**：`≤900px` 隐藏「剩余时间」（中段 382，留 30px 余量）；
  `≤740px` 整条读数 `display: none`（中段 222 时轨道仍有 55px+，但已放不下六项）。

### 11.5 踩过的三个坑（都是取证方法本身的坑）

1. **复刻页的分组容器漏了 `items-center`** ⇒ 组内 svg/span 顶对齐，量出的墨迹位置整体偏 8px，
   差点误判「16px 方案仍压 2.5px」。补齐后重测：图标墨迹 y=17.5–33.5 ⇒ 真实报错源是**复刻缺陷**，
   不是产品。
2. **CDP 量到了 transition 途中的宽度**：`.app-side` 有 160ms 的 `width` 过渡，探针设完
   56px 立刻量，读到的是 200px，整轮扫描数字全偏 144px。修法：探针改 async IIFE，
   `await 400ms` 后再量；且必须连 `data-collapsed` 属性一起设，否则品牌文案会撑宽 grid 的 auto 列
   （实测又多 144px）。
3. **SVG 元素的 `className` 是 `SVGAnimatedString`**（没有 `.split`），探针直接抛异常 ⇒ 无输出。
