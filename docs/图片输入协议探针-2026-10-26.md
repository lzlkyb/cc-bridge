# 图片输入协议探针（批 C，2026-10-26）

> 结论先说：**通了**。`stream-json` 输入的 user message 可以带图片，CLI 会把 image block **原样转发**给 API，base64 字节级不变。cc-bridge 不需要动协议层，只要把 `content` 从「一个 text 块」扩成「块数组」。

## 一、结论表

| 探针项 | 结果 | 证据 |
|---|---|---|
| `source.type: "base64"` | ✅ 原样转发 | 输入 `data` 长度 512，转发的 `data` 长度也是 512，前缀 `iVBORw0KGgoAAAANSUhEUgAAASwAAABkCAIAAACz` 一致 |
| `source.type: "url"` | ✅ 也原样转发 | `source.type=url`，`media_type` 与 `data` 均为空（CLI 不下载、不改写） |
| `media_type` 声明错误 | ⚠️ CLI 按**文件头嗅探**纠正 | 传 `image/bmp` 但数据是 PNG ⇒ 转发出去的 `media_type` 变成 `image/png`，数据未变 |
| image 块放在 text **之后** | ✅ 顺序无关 | 两种情况都正常转发 |
| 需要额外启动旗标吗 | ❌ 不需要 | `--print --input-format stream-json --output-format stream-json --verbose` 即可，与现有 `PROTOCOL_ARGS` 完全一致 |
| 真 API 端到端 | ⚠️ **未验证** | 用户配置的中转站 `agentrouter.org` 返回 503，详见 §五 |

## 二、可以直接抄的形状

stdin 里写一行（现有 `cc_session/session.rs::user_message_line` 只需把 `content` 改成块数组）：

```json
{
  "type": "user",
  "message": {
    "role": "user",
    "content": [
      { "type": "image",
        "source": { "type": "base64", "media_type": "image/png", "data": "<base64，不带 data: 前缀>" } },
      { "type": "text", "text": "这图里是什么" }
    ]
  }
}
```

URL 形态（远端会话免传 base64 时用）：

```json
{ "type": "image", "source": { "type": "url", "url": "https://…/a.png" } }
```

🔴 `data` 是**裸 base64**，不要带 `data:image/png;base64,` 前缀 —— 带了 CLI 不会剥，会当垃圾转发。

## 三、CLI 自己做的两件事（都会影响我们的实现）

### 1. 图片落盘 + 追加文本引用

转发给 API 的 `content` 末尾，CLI 自己加了一条：

```
[Image: source: C:\Users\19145\AppData\Local\Temp\claude\D--AItool-winapp-cc-bridge--workbuddy-tmp\c35fad69-…\image.png]
```

含义：**CLI 把 base64 解成文件写到自己的临时目录**，再在 content 里补一条路径引用。带来的影响：

- 每次带图的消息都会在 `%TEMP%\claude\…` 留一份副本（远端是远端的 `/tmp/claude/…`）。我们不负责清理，但**别在审计里把这个路径当成用户文件路径**记。
- 模型因此同时拥有「图像本体」和「源文件路径」两份信息 —— 后者可能让它去用 Read 工具重读，属于 CLI 自身行为，我们不管。

### 2. media_type 嗅探纠正

声明的 `media_type` 与实际文件头不符时，CLI 以**文件头**为准改写后再发。所以：

- 前端不必为「类型识别」写一套 magic number 嗅探（CLI 兜了）；
- 但**大小限制不能指望 CLI**（见下）。

## 四、限制（前端必须自己把关）

CLI 二进制里有一组与图片相关的错误文案，说明限制在 **API 侧**：

- 尺寸：`the image is more than <N> pixels wide or tall … send a copy scaled to at most <K> pixels on its longer side`
- 格式白名单：`it accepts PNG, JPEG, GIF and WebP`
- 体积：`the file is larger than the server's upload size limit`
- 解码成本：`Image is too costly to decode`

按 Anthropic 公开限制，实现时采用：**单图 ≤ 5 MB、单边 ≤ 8000 px、格式限 PNG/JPEG/GIF/WebP**。前端在粘贴/选择文件时先拦，超限给明确提示（缩放或换格式），不要让它跑到 API 才 400。

## 五、为什么没跑真 API（方法学，下次别再踩）

第一次按常规打真链路，被环境挡在门外，**不是协议问题**：

1. `~/.claude/settings.json` 的 `env` 把 `ANTHROPIC_BASE_URL` 指到 `https://agentrouter.org`。
2. 该域名**直连 TCP 不通**（curl 15s 超时，`http=000`）；走本机 7897 代理可达（`/` 返回 200）。
3. 但带 `HTTPS_PROXY` 时 CLI 的错误是 `error: "unknown"` —— 因为 **Node/Bun 默认不读 `HTTPS_PROXY`**，需要 `NODE_USE_ENV_PROXY=1`。加上之后错误变成 `server_error 503`，证明代理链路通了、**堵在中转站**（中转站故障，与本项目无关）。
4. 逆向对照也失效：喂非法 content block（`source.type: "bogus_source"`、`type: "video"`）CLI 同样不报错，因为失败点在更后面的 API 层 —— 「不报错」本身无法证明它解析了。

🔴 **另一个必须记住的坑**：`settings.json` 的 `env` **优先级高于进程环境变量**。直接 `ANTHROPIC_BASE_URL=http://127.0.0.1:8899 claude …` 完全无效（实测三次请求全打到 agentrouter，本地服务器一条没收到）。要用 `--settings <临时文件>` 叠一层覆盖。

### 最终采用的办法：本地假服务器

`tools/图片探针假服务器-2026-10-26.py` 起一个只记录请求体、返回固定合法 SSE 的 HTTP 服务，让 CLI 把 `ANTHROPIC_BASE_URL` 指过来。

这比真 API **证据更强**：真 API 只能看到「模型答得对不对」，假服务器能看到「CLI 究竟把什么字节发了出去」。而且零额度、零外网依赖、秒级可重复。

一键复现：`bash tools/图片输入探针-2026-10-26.sh`（三个 case 全绿约 1 分钟）。

## 六、对实现的影响（Phase 2 的边界）

- **Rust**：`user_message_line(&str)` → 改成接受块数组（`Vec<ContentBlock>`）。纯函数、可单测，`proto.rs` / 事件语义**零改动**（读通道不变）。
- **前端**：Composer 的 `onPaste` 现在只弹 toast，改成读 `clipboardData.files` → 校验 → base64 → 随消息发出。
- **消息模型**：用户消息的 `content` 要能承载图片，`ccReducer` / `CcMessage` 需加一种块类型，否则回显时看不到自己发的图（现在只有 text）。
- **远端会话**：base64 要过 SSH 隧道，5 MB 图 ≈ 6.7 MB base64。**优先测 `url` 形态**；远端本地文件无法直接给 URL 时再退回 base64，并在 UI 上给出体积提示。
- **审计**：不要把 base64 写进审计日志（体积爆炸），只记 `{count, 总字节, 格式}`。

## 八、前端落地时踩到的坑（2026-10-26，探针之后）

协议通了只说明「发得出去」，**从剪贴板到发出**这一段还有三个坑，都是实测撞出来的：

### 1. `createImageBitmap` 会永不 settle

同一张 `File`，在主线程直接 `await createImageBitmap(f)` **成功**；经由组件里的
异步链路（`addFiles` → `loadFile` → `createImageBitmap`）再解一次，promise
**既不 resolve 也不 reject**。表现是 chip 永远停在虚线骨架、发送按钮永远等不到图，
而且没有任何错误可查。

修法：改用 `new Image()` + `await img.decode()`。它走同一条解码器，但没有那条
挂起路径，失败时给明确的 rejection（能报「这张图读不出来」而不是静默转圈）。
`drawImage` 接受 `HTMLImageElement`，缩放代码一行都不用改。

### 2. `objectURL` 不能提前 revoke

`URL.createObjectURL(file)` 的 URL 必须**等 canvas 画完**才能 revoke。提前 revoke
会让 `drawImage` 拿到一张空图 —— Chrome 上表现为全黑或全透明，**不报错**。所以
revoke 放在 `finally` 里、且在所有 `drawTo` 之后。

### 3. 缩略图不能一律转 JPEG

透明 PNG 转 JPEG 会把透明区压成**黑块**：深色主题下看不出来，浅色主题下非常刺眼。
缩略图按原类型走 —— `image/jpeg`/`image/webp` 用原格式 + q0.8，其余（PNG/GIF）转 PNG。

## 九、验证方法学：headless 截图会骗人

这一轮差点因为「截图里 chip 一直转圈」把功能判死。真相是**截图工具的问题**：

| 方式 | 结果 | 原因 |
|---|---|---|
| `msedge --headless --screenshot`（无 budget） | chip 一个都没有 | 在 effect 跑完前就截图 |
| `--virtual-time-budget=N --dump-dom` | chip 停在骨架态 | 虚拟时间让页面在异步解码**中途**冻结 |
| `--remote-debugging-port` + CDP，等真实 4s 后求值 | ✅ 全部正确 | 真实时间 |

所以：**凡是链路里有「解码 / 编码 / 网络」这类要真实帧或真实 I/O 的异步操作，
都不能用 virtual-time 截图下结论。** 工具留在 `tools/cdp真实时间核验-2026-10-26.mjs`
（`node tools/cdp真实时间核验-2026-10-26.mjs <url> <expr> [waitMs] [shot.png]`）。

顺带一个坑：轮询结果时**不能用普通单词做 break 条件**（我用了 `"thumb"`，而返回的
JSON 键名恰好是 `thumbs` ⇒ 第一次轮询就 break，拿到的是渲染前的空状态）。
