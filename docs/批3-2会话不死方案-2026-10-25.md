# 批 3-2 会话不死：方案与落地边界（2026-10-25）

依据：`docs/对话GUI开工计划-2026-10-24.md` §四（3-2）、`docs/批3多会话调研-2026-10-25.md` §四、
0-4 探针实测（`docs/CC对话协议探针报告-2026-10-24.md` 文末）。

**结论先行**：托管只能走 **tmux + FIFO + 日志** 这一条路（`--bg` 在目标环境被策略禁用，
setsid 只能证进程不死、无处读写）。这条路要动的是**对话的传输层本身** —— 全项目风险最高的
一块。所以本批**先出方案 + 探针脚本，探针在远端跑通再写产品代码**（R1 / 计划 §七.4）。
本文档即是那份「方案」，探针脚本是 `tools/3-2托管探针-2026-10-25.sh`。

---

## 一、要解决的问题

| 现象 | 现状（3-1c 之后） | 缺口 |
|---|---|---|
| 关掉 app / 断网 | 远端 claude 收到 SIGHUP，那一轮直接死 | 任务没跑完 |
| app 里关掉客户端 | 同上 | 后台任务全断 |
| 重开 app | 从 `cc_sessions` 恢复界面 + `--resume` 接回模型上下文 ✅ | 那一轮**已产出但没落盘**的内容没了 |
| 侧栏「已死」判据 | 只判「目标连接被删」 | 进程死没死判不出来（`Exit` 每轮都来） |

一句话：**界面能恢复，进程不能存活**。3-2 要补的正是后一半。

## 二、为什么只有 tmux + FIFO + 日志

我们的协议是 NDJSON over stdin/stdout（`--print --input-format stream-json`），
不是 TUI。三条候选路线的取舍：

| 路线 | 进程跨断线 | 双向通道 | 结论 |
|---|---|---|---|
| `tmux` + **TUI** attach（社区标准答案） | ✅ | ❌ 出来的是终端转义流，不是 NDJSON | 不可用（我们的 GUI 不解析屏幕） |
| `setsid` / `nohup` | ✅（0-4 已验证） | ❌ 没有 stdin 可写 | 只能兜底「任务跑完」 |
| `claude --bg` + supervisor | ✅ | 需 `claude attach`（拉进终端） | 0-4 实测：目标环境**策略禁用**（`仅限 claude-svc`） |
| **`tmux` + FIFO + 日志** | ✅ | ✅ 自己造 | **唯一可行** |

机制（探针里已经写成可执行的最小版本）：

```
远端
  mkfifo in.fifo
  tmux new-session -d -s cc-<key> "bash worker.sh"      # worker: exec 9<>in.fifo
    worker: exec 9<>"$FIFO"                              # ← 支点：fd 既是读端又是写端
            claude … <&9 >> out.log 2>&1                 #   本地写端关闭时读端拿不到 EOF
本地（一个 ssh 通道，双向）
  ssh host 'tail -n +<offset> -F out.log & exec cat > in.fifo'
    stdin  → cat → fifo → claude 的 fd 9                  （发消息 / 批审批）
    stdout ← tail ← out.log ← claude                      （收事件流）
```

三条铁律：

1. 🔴 **`exec 9<>FIFO`（读写双开）是整个方案的支点**。写成 `<FIFO` 时，本地写端一关，
   读端立刻 EOF，claude 收尾退出 —— 「断线存活」当场失效，而**现象和成功一模一样**
   （日志还在、会话看起来在跑），只有隔一会儿回来才发现它已经死了。探针 [4] 专门验这一条。
2. 🔴 **不能 attach 到 TUI**：我们要的是 stdout 上的 NDJSON，attach 拿到的是屏幕。
   tmux 在这里只当**进程宿主**用，不参与 IO。
3. 🔴 **`cat > fifo` 没有读者时会永久阻塞**：`claude` 死了以后这条 ssh 就挂在那儿。
   装配时要给它加超时/存活探测（探针里是 `timeout 5`），否则「关不掉的后台 ssh」会成为
   新的资源泄漏。

## 三、产品形态（决定了要改哪些地方）

| 维度 | 决定 | 理由 |
|---|---|---|
| 范围 | **只托管远端会话**（`connection_id` 非空） | 本机没有 tmux；本机进程本来就跟 app 同生共死，托管无从谈起 |
| 开关 | 配置项 `cc_hosted_sessions`，**默认关** | 换掉传输层是大事；默认开会让所有既有用户的远端对话在升级后走一条没被真机验证过的路 |
| 探测 | 首次托管前 `command -v tmux`，无则**静默回落到直连** | fail-open 到旧行为，比「报错不让用」好 |
| 命名 | `cc-<host_key>`，`host_key` = 内部会话 id + 启动时间戳，落库 | 重连要能找回同一个 tmux 会话 |
| 中断 | `tmux kill-session -t cc-<key>` | claude 的 stdin 是管道不是 TTY，Ctrl+C 只是往管道里写字节，没意义 |
| 关会话 | 先 kill 会话再落盘（与 `cc_close_session` 现有顺序一致） | 托管进程不跟着 app 走，漏一个就是永久孤儿 |

## 四、落地清单（探针全绿之后才开工）

### 4.1 Rust（`cc_session/`）

1. `channel::hosted_remote_command(ssh_args, dest, claude_path, spec, key, offset)`
   —— 纯函数，产出 `(program, args)`，**可以完全用单测钉住**（脚本内容、走 base64 单参、
   参数逐个单引号、offset 出现在 `tail -n +N` 里）。这一段先写、先测，不碰运行时。
2. `hosted.rs`：`HostedSession { key, offset }`，负责
   - attach：起那条双向 ssh，读线程喂 `pump()`，写端继续用现有 `StdinBox` 语义；
   - offset 记账：每消费一行 `offset += len`，**落盘到 `cc_sessions.hosted_offset`**（新列）；
   - 存活：`tmux has-session`（一条短 ssh，只在侧栏要显示状态时调，不轮询）。
3. `manager::CcSession`：`Run` 之外的第二种 transport（`Direct` / `Hosted`）。
   🔴 所有「进程活着 ⇒ 直接 send」的判断必须走同一层抽象，否则两套 transport 会漂。
4. 「已死」判据：托管会话 `has-session` 失败 ⇒ `dead`（`lib/ccPaneMeta.ts` 只需多一个输入位，
   分支早就留好了）。

### 4.2 前端

- 设置页一个开关（`cc_hosted_sessions`），说明写清「只影响远端、需要远端有 tmux」；
- 侧栏五态的 `dead` 从「连接被删」扩到「托管会话没了」；
- 恢复历史时如果那条是托管的，先 `has-session` 再决定「接着跑」还是「提示已结束」。

### 4.3 不能承诺的事（要写进界面）

- **本机会话仍然不能跨 app 退出存活**（没 tmux，也不打算引入）；
- 托管期间的 stdout 有延迟（`tail -F` 的轮询间隔），打字机效果会比直连钝一点；
- 远端磁盘上会留 `~/.cc-bridge/hosted/<key>.{in,out}`，需要一条「清理陈旧会话」的运维动作。

## 五、验收标准（探针 + 产品两层）

探针（远端，`tools/3-2托管探针-2026-10-25.sh`，两段之间必须真断线）：

| # | 判据 | 不通过的含义 |
|---|---|---|
| 1 | tmux 会话跨断线存活 | 整条路线不成立 |
| 2 | 断线期间心跳持续增长 | 进程被 SIGHUP 收走 |
| 3 | 重连后写进 FIFO 的行出现在日志 | 双向通道不能复用 |
| 4 | 进程没被 EOF 杀掉 | `exec 9<>` 写错成了 `<` |

产品（探针全绿之后）：

- 关窗 3 分钟后重开：那一条会话的事件流补上了断线期间的全部内容（offset 无重无漏）；
- 断线期间用户在远端产生的**未决审批**：重连后仍可批（事件流里有 ask、进程还等着）；
- 侧栏「已死」只对真死的托管会话亮，活着的不会误报（`Exit` 每轮都来，不能当判据）；
- 关掉 app 而**不**关会话：远端进程继续跑（`has-session` 仍真），这是本批的核心价值。

## 六、为什么这一批到此为止

- 3-2 的代码量集中在**传输层**，而传输层的失败模式是「看起来正常、其实内容丢了」
  （offset 错一行 ⇒ 重复或漏事件），本地没有 tmux 也没有第二个 Linux，**无法在写代码的
  这台机器上验证任何一条判据**；
- 前四批（0/1/2/3-1）建立的纪律是「探针结论落文档再开工」。这里保持同一条纪律：
  探针脚本已就绪，跑一轮（约 5 分钟，需要真的断开一次 SSH）拿到结论后，4.1 的纯函数部分
  当天可以写完并单测覆盖；
- 因此本批**交付**：本文档 + 探针脚本 + 明确的产品形态与验收标准；**不交付**：未经验证的
  传输层代码（宁可不写，也不把一条「可能悄悄丢事件」的路放进默认路径）。
