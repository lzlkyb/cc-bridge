# 隧道启动认证耗时 11 秒：排查与修复任务书

> 写于 2026-11-16。读者是接手这件事的另一个 AI。文中每条结论都标了是「实测」还是「推断」，请勿把推断当事实继续往下推。
> 项目：cc-bridge（Tauri 2 + React/TS + Rust 的桌面 MCP 桥）。相关子系统：托管 SSH 反向隧道（稳定连接）。

---

## 一、要解决的问题

冷启动应用后，接入卡会显示「隧道通道正在重连」十几秒才变绿。用户的实际感受是「打开软件总要转 5 秒以上」。

**现状拆解（实测，2026-11-16 19:42 那一次启动）：**

| 事件 | 时刻 | 距应用启动 |
|---|---|---|
| `cc-bridge-desktop.exe` 进程启动 | 19:42:17 | — |
| 正式隧道 `ssh.exe` 进程出现 | 19:42:29 | +12 s |
| 恢复凭据 `ssh_tunnel_sessions/*.json` 落盘（= 隧道真正就绪） | 19:42:40 | +23 s |

即：**单轮「ssh 启动 → 认证完成 → 远端 guard 就绪」≈ 11 秒**（19:42:29 → 19:42:40）。

更早一次（17:03:08 启动 → 17:03:35 ssh → 17:03:48 就绪）是 27 秒，但那一次含一轮「回收旧会话」的额外认证，见第五节。

## 二、已经实测确认的事实

### 2.1 SSH 传输层不慢

用 Python 逐行读 `ssh -vv` 的 stderr 并打时间戳（BatchMode，不完成认证）：

| 阶段 | 耗时 |
|---|---|
| `debug1: Connection established.` | 197 ms |
| `Remote protocol version 2.0 ... OpenSSH_8.9p1 Ubuntu-3ubuntu0.18` | 217 ms |
| `debug1: kex: algorithm: sntrup761x25519-sha512@openssh.com` | 227 ms |
| `debug1: SSH2_MSG_SERVICE_ACCEPT received` | 316 ms |
| `debug1: Authentications that can continue: publickey,password` | 331 ms |
| `Permission denied (publickey,password)`（无密钥，正常退出） | 347 ms |

复现命令（PowerShell 或 bash 均可，不会提交任何口令）：

```python
import subprocess, time
t0 = time.time()
p = subprocess.Popen(
    ['ssh','-vv','-o','BatchMode=yes','-o','ConnectTimeout=8',
     '-o','NumberOfPasswordPrompts=0','<user>@<host>','exit'],
    stderr=subprocess.PIPE, stdout=subprocess.DEVNULL, text=True, errors='replace')
for line in p.stderr:
    ms = (time.time()-t0)*1000
    s = line.strip()
    if any(k in s for k in ('Connection established','remote software version',
                            'SSH2_MSG_SERVICE_ACCEPT','Authentications that can continue',
                            'Next authentication method','kex: algorithm')):
        print(f'{ms:7.0f}ms  {s[:95]}')
```

### 2.2 因此可以排除的两项（都不成立）

- **`UseDNS` 不是原因。** 该项若开启，延迟出现在 `SSH2_MSG_SERVICE_ACCEPT` 之后（10-30 秒）。实测 316ms 就过了那一行。
- **GSSAPI 不是原因。** 服务端只提供 `publickey,password`，列表里没有 gssapi，客户端连尝试的机会都没有。

> ⚠️ 之前一版结论据「27 秒 ÷ 2 次 SSH」推出「单次认证 13 秒、卡在认证前」，方向是错的。时间确实约 11 秒一轮，但慢在**传输层建好之后**，不在传输层。

### 2.3 结论：11 秒落在「密码校验 + 会话建立」这一段

已经能确定 11 秒在 `ssh.exe` 启动到凭据落盘之间，且传输层只占 0.35 秒，剩下 10.6 秒在：密码认证（`pam_unix` → NSS）或会话建立（`pam_systemd` → systemd-logind、`pam_motd` → update-motd 脚本）。

**尚未区分是哪一边。** 这是本文档要交给下一位去定位的第一件事。

## 三、连接复用这条路已排除（不要再花时间）

业界标准解法是 `ControlMaster` + `ControlPath` + `ControlPersist`（第二次连接 <100 ms）。**Win32-OpenSSH 不支持**：它需要 AF_UNIX 套接字传文件描述符，原生 Windows 客户端没有实现，写了会直接报 `getsockname failed: Not a socket`。

- 佐证一：<https://github.com/NousResearch/hermes-agent/pull/50753>（2026 年，项目专门加平台判断跳过这三个选项，否则 Windows 上 100% 失败）
- 佐证二：<https://github.com/lollipopkit/flutter_server_box/issues/1262>（明确写 "Windows has no ControlMaster: Win32-OpenSSH does not implement connection multiplexing"）
- 佐证三：<https://renode.space/blog/ssh-config-file-and-jump-hosts>（"Windows OpenSSH does not support it ... a ControlMaster line produces errors rather than speed"）

仅存的两条歪路，**不建议**：

- 走 WSL 的 ssh（支持 mux），但要求用户装 WSL 并在两个世界之间传凭据；
- 内置 PuTTY 的 plink（支持 `-share` 连接共享），代价是把整条 pty / 端口转发层换掉，回归风险与工作量都大。

结论：**这件事只能从「让单次认证变快」或「减少认证次数」两侧解决，没有第三条路。**

## 四、下一步：先定位 11 秒到底在哪（必做）

### 4.1 两条 `Measure-Command`（需要用户在 Windows 终端里跑，各要一次密码）

```powershell
Measure-Command { ssh <user>@<host> exit }
Measure-Command { ssh -tt <user>@<host> 'python3 -c "print(1)"' }
```

判读：

| 结果 | 结论 | 去哪一节 |
|---|---|---|
| 两条都 ≈10 秒 | 密码认证或会话建立慢（与 tty 无关） | 4.3 的 PAM 分支 |
| 只有带 `-tt` 的慢 | tty 相关：motd / update-motd 脚本 | 4.3 的 motd 分支 |
| 两条都 <1 秒 | **矛盾**：慢在我们的调用参数或进程链路，不在服务器 | 4.4 |

> 🔴 **安全约束：绝对不要用错误口令反复尝试登录。** 这台服务器可能是公司 AD/LDAP 后端，多次失败会锁定用户账号。任何需要口令的测量都必须由用户本人做，且一次成功即可。

### 4.2 服务器侧只读排查（不改任何东西）

```bash
grep -vE '^\s*#|^\s*$' /etc/pam.d/sshd
systemctl status systemd-logind --no-pager | head -5
journalctl -u systemd-logind --since "10 min ago" --no-pager | tail -20
ls /etc/update-motd.d/ 2>/dev/null
sudo sshd -T | grep -iE 'usedns|gssapi|usepam|printmotd|maxsessions'   # 无 sudo 就跳过
ls -l /etc/ssh/sshd_config.d/ 2>/dev/null
```

重点看 `/etc/pam.d/sshd` 里是否出现 `pam_systemd.so`、`pam_motd.so`、`pam_sss.so`、`pam_ldap.so`。

### 4.3 两类已知病因的修法（网上有实测案例）

**A. `pam_systemd` → systemd-logind 的 D-Bus 响应慢**

症状：`ssh -v` 显示认证已完成，但 shell / 命令迟迟不出现。根因常是 logind 被任务数限制拖住。

修法：`/etc/systemd/logind.conf` 里 `UserTasksMax=8192`，然后 `systemctl restart systemd-logind`。
有实测案例 `time ssh host true` 从 **15.2 s 降到 0.3 s**（<https://blog.csdn.net/hanchenxing/article/details/168770864>）。应急可临时注释 `/etc/pam.d/sshd` 的 `session required pam_systemd.so`，但会丢 cgroup 会话管理，不推荐长期用。

**B. `pam_motd` / `update-motd.d` 脚本阻塞**

典型是 `landscape-sysinfo` 之类访问网络，把登录拖住十几秒（<https://askubuntu.com/q/11538>）。
修法：`/etc/pam.d/sshd` 注释 `session optional pam_motd.so`，或把 `/etc/update-motd.d/` 里不用的脚本 `chmod -x`。

**C. `pam_unix` 背后的 NSS（SSSD / LDAP / AD）**

修法是修目录服务缓存，或让该账号改走密钥认证（见 4.5）。

### 4.4 如果两条命令都快（说明慢在我们自己）

这时需要在本仓库内部找，别去动服务器。已知的可疑点：

- `desktop/src-tauri/src/commands/ssh_tunnel_cmds.rs:464`：托管隧道固定加 `-tt -v`。注释说明原因：Windows OpenSSH 需要 tty 模式才能及时转发心跳帧。**若 `-tt` 是慢的来源（motd 只在有 tty 时跑），需要重新评估这个约束**——先把心跳失败的现象复现清楚，再讨论能否改成 `-T` + 另一种心跳通道，不要直接删参数。
- `desktop/src-tauri/src/commands/ssh_tunnel_cmds.rs:467`：`ConnectTimeout=10`。若握手超时，这里会白等 10 秒。
- 进程链路里有没有额外的固定等待：`commands/ssh_tunnel_process.rs` 里只有两处 `sleep(200ms)`，`read_loop` 见到提示符立即回填凭据（`reply_to_prompt`），没有人为延时。

### 4.5 密钥认证（覆盖面最广的一招，但不是万能）

如果慢在密码校验（分支 A/C 的一部分），换 ed25519 密钥可以绕开它：

```bash
ssh-keygen -t ed25519
# 把 ~/.ssh/id_ed25519.pub 追加到服务器 ~/.ssh/authorized_keys
```

cc-bridge 已经支持 `SshConnection.keyPath`，**无需改代码**。

⚠️ 但如果慢在 `pam_systemd`（会话建立阶段），换密钥**没有用**：认证和会话建立是两段。

## 五、已经做完的部分（不要重做）

托管隧道启动时会先单开一条 SSH 去回收上次残留的远端监听（`commands/ssh_tunnel_cmds.rs:701` `reclaim_previous`）。原先这条回收**每次启动都必然执行**，因为恢复凭据只在回收成功后才删除，正常停止时不清。

已改成：正常停止时清凭据，异常退出（崩溃 / 断电）时保留。

- `state.rs:100` `SshTunnel::release_receipt()`：清掉本实例写入的那份凭据。`forget` 自带归属校验，另一个实例接管过端口后写的凭据删不掉。
- `commands/ssh_tunnel_cmds.rs:482` `stop_and_release()`：用户断开、稳定连接停止时用。
- `state.rs` 的 `kill_all_ssh_tunnels()`：应用退出、SSH 总开关关闭时用。
- **不释放**：`start_plan` 重启、`forward_takeover` 替换规则、登录信息变更。这三条后面紧跟一次重启，旧远端监听可能还在释放端口，凭据必须留着。

远端 guard 脚本 `stable_remote/tunnel_guard.py:12` `LEASE_SECONDS = 45`，`:162` `watchdog()` 在会话 EOF（`:174`）或 45 秒无心跳（`:168`）后自行终止监听——这是「正常停止后不需要回收」的前提。

净效果：启动少一整轮认证（约 11 秒量级）。门禁已过（fmt / clippy -D warnings / cargo test 1041 通过）。

## 六、红线（继承本项目既有约束）

1. **不动「退出即杀」的安全边界。** `main.rs:1103` 在 `RunEvent::Exit` 里主动杀掉 ssh 进程，原因写在 `main.rs:1094-1099`：用户退了应用就不该还有活着的 sshd 会话。任何「让隧道跨重启常驻」的方案都属于显式 opt-in + 显眼提示，不能默认开启。
2. **不做弹窗确认 / 审批门。** 安全靠白名单 + 自动备份 + 全审计。
3. **改 Rust 必须重编译并跑门禁**：`cargo fmt --check`、`clippy --all-targets --no-default-features -- -D warnings`、`cargo test --no-default-features`（跑前补 `PATH`，跑时用独立 `CARGO_TARGET_DIR`，避免和 dev 实例抢 `target` 锁）。
4. **判成败的命令不要接管道**（`| tail` 会让上游收 SIGPIPE 提前退出，屏幕上却像成功）；一律 `cmd > /tmp/x.log 2>&1; echo "EXIT=$?"`。
5. **不要用错误口令试探登录**（见 4.1）。
6. 结论要跑出来，不能推出来。本文档里「推断」与「实测」已分开标注，交接时请保持这个习惯。

## 七、验收标准

修完后应该能同时满足：

1. 冷启动到「隧道已连通」的总时间 < 3 秒（当前 11-23 秒）。
2. 服务器终端里 `time ssh <user>@<host> exit` < 1 秒。
3. 隧道断开后自动重连不再需要十几秒（`ServerAliveInterval=10`，`RETRY_MIN=2s`）。
4. `cargo test --no-default-features` 全绿，且新增用例在实现回退时确实变红。
