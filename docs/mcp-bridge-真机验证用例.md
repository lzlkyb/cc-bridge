# 外挂 MCP 桥 · 真机验证用例

> 对象：方案 2（多项目 `cwd`）+ 方案 3（超时保留连接）。
> 单元测试（Rust 240 条）已覆盖逻辑分支，**本文只管单测覆盖不到的那部分**：
> 真实子进程、真实超时、真实 HTTP 链路。
> 日期：2026-08-07

---

## 0. 判定原则（先说清楚，否则后面的"通过"不值钱）

### 0.1 不能拿"第二次变快了"当证据

方案 3 要证的是**连接没被销毁**。但"第二次调用变快"有至少三个可能来源：

1. 连接复用了（我们想要的）；
2. codegraph 自己有共享 daemon，即使进程重启也能秒回（**上一轮实测已经看到它这么干**）；
3. 操作系统文件缓存热了。

所以耗时只作为**辅助**指标。硬指标是：

> **同一个 `SessionKey`（server + cwd）对应的外部子进程 PID，在超时前后必须完全相同。**

PID 不变 = 进程没被杀过 = 连接没被重建。这条无法被上面三种巧合伪造。

### 0.2 进程归属必须沿父链上溯确认

本机同时存在**另一组 codegraph 进程**：本地 `claude` CLI 把 codegraph 当成自己的 MCP server
拉起来的（实测 PID 13720/12308/24636，父进程 `claude` PID 21680，14:46 启动，与 cc-bridge 无关）。

**按进程名匹配会把它算进来，得出完全错误的结论。** 因此采集 PID 时必须：

```
候选进程 → 沿 ParentProcessId 上溯 → 祖先中出现当前 dev 的 cc-bridge-desktop.exe → 才计入
```

脚本 `testroot/mcp_bridge_verify.py` 里的 `descendants_of()` 实现了这条。

### 0.3 每条用例都要能说出"失败长什么样"

只写预期不写反例的用例，跑出来是什么都能解释成通过。下面每条都写了**反例**。

### 0.4 跑进程层判据前必须先清空连接池

第一轮实测直接栽在这里：测试开始时池里已经挂着 **10 个** codegraph 进程
（前面手工探测留下的，`IDLE_TTL` 是 15 分钟，不会自己消失）。于是 T5 里两个项目
都是 **0.0s 秒回复用**、根本没走 spawn，"没有新进程"被误判成了"在串项目"。

判据本身没错，错的是基线。脚本里的 `reset_pool()` 在 T5 前杀光桥派生的 server 进程；
紧接着的第一次调用会拿到一次 `写入 server 失败：管道正在被关闭`（旧会话被丢弃），
`proxy_settled()` 专门吃掉它，不让它污染判断。

## 1. 前置条件

### 1.1 项目分两层（重要）

| 层 | 项目 | 规模 | 用于 |
|---|---|---|---|
| SLOW | `C:\work\aier` | 13176 文件 / 440526 节点 / 1.5GB | **仅** T2–T4 |
| A | `…\cc-bridge`（本仓库） | 211 文件 / 2795 节点 / 7.38MB | T5–T8 |
| B | `…\clipboard-manager-tauri` | 未建索引 | T5–T8 |

**为什么 T2–T4 离不开大项目**：这三条验的是**超时路径**。小项目 1.7s 就返回，
根本不存在"被放弃的响应"可以迟到，也就无从验起。带 `--skip-slow` 可跳过这三条，
代价是超时路径本轮无证据——脚本会在汇总里明确标出来，不会静默当成通过。

> B 未建索引是**故意**保留的：codegraph 报错时会把它实际搜索的目录原样回显，
> 这让 T5a 能直接看到 cwd 到底进没进那个进程，而不是从 PID 推测。

### 1.2 环境

| 项 | 要求 | 怎么查 |
|---|---|---|
| 运行的是 dev 版 | 进程路径含 `src-tauri\target\debug` | `Get-Process -Id <7823的PID>` 看 `Path` |
| 端口 | 7823 在 LISTENING | `netstat -ano \| grep 7823` |
| 外挂桥总开关 | `external_mcp_enabled = true` | 设置页 / 配置库 |
| codegraph | `enabled=true`，`allow_remote_cwd=true`，`cwd=null` | 同上 |
| 白名单含 | `C:\work\aier`、`D:\ncc\1909home` | `list_allowed_roots` |

> ⚠️ 若 7823 被**安装版**（`D:\soft\cc-bridge\cc-bridge-desktop.exe`）占着，全部用例作废——
> 安装版没有本次改动，会返回 `Unknown tool: mcp_proxy`。上一轮就是栽在这里。

## 2. 用例

### T1 · 工具可见 + args schema 是 object【回归】

**动作**：`tools/list`。

**预期**：
- 列表含 `mcp_proxy`、`mcp_list_servers`；
- `mcp_proxy.inputSchema.properties.args.type == "object"`。

**为什么单独列这条**：这个字段曾经是 `{}`（无类型）。客户端于是把参数当**字符串**发过来，
桥原样转发，外部 server 收到一个没有任何字段的调用，还返回了它自己一套看着挺合理的错误——
参数**静默丢失**，227 条单测全部没发现（单测直接喂 `Value::Object`，绕开了这条路）。
这是本次最贵的一个 bug，必须在真机链路上钉死。

**反例**：`args` 无 `type`，或缺任一工具 → 跑的不是新版本，后面全部作废。

---

### T2 · 冷启动首调（建立基线）

**动作**：`mcp_proxy(server="codegraph", tool="codegraph_status", cwd="C:/work/aier")`。

**采集**：耗时、返回内容或错误、调用后的桥派生进程集合 **S1**。

**预期**：二者之一都算通过——
- 成功返回 status；或
- 超时报错，且错误文案含"连接保留"字样（方案 3 的新文案）。

且**无论哪种，S1 必须非空**：进程已经起来了。

**反例**：
- 超时了但文案还是旧的"连接已销毁/不可用" → 方案 3 没生效；
- S1 为空 → 进程根本没起来，不是超时问题而是 spawn 失败，转去看 stderr。

> 上一轮实测：`C:\work\aier` 是个 1.5GB 索引的大项目（13176 文件 / 440526 节点），
> 首调超过 60s 是**预期内**的，不是缺陷。这条用例正是靠它来制造真实超时。

---

### T3 · 超时后重试复用同一进程【方案 3 核心】

**动作**：T2 之后**立刻**用完全相同的参数再调一次。

**采集**：耗时、返回、进程集合 **S2**。

**预期（硬）**：`S2 == S1`，PID 逐个相同。

**预期（软）**：耗时明显短于 T2；最终拿到真实 status 数据。

**反例**：`S2 ∩ S1 == ∅`（全是新 PID）→ 连接被销毁重建了，方案 3 失效，退回了旧行为。

**顺带验证的东西**：`RETRY_BACKOFF = 30s`。若超时错误被登记成"启动失败"，
30 秒内的重试会被退避直接short-circuit 掉、连进程都不碰。代码上超时不走 `note_failure`
（那条只在 `connect` 失败时登记），这条用例用实际行为证明它。
若 T3 秒回一个"上次失败，稍后重试"类文案 → 退避误伤，是 bug。

---

### T4 · 迟到的响应不串号【方案 3 最危险的失效模式】

**动作**：T3 之后立刻调一个**不同的**只读工具（从 `mcp_list_servers` 拿到的清单里另选一个）。

**预期**：返回的是**该工具**的结果。

**反例**：返回的内容其实是上一条 `codegraph_status` 的（节点数/文件数那套）
→ 迟到响应被错当成本次结果，**这是保留连接可能带来的唯一真实风险**，必须为零。

**理论依据**（用例要验的就是它成不成立）：请求 id 单调递增且严格串行
（所有方法取 `&mut self`，编译器保证不交错），所以被放弃那条的响应迟到时 id 必定
**小于**下一个期待值，会被 `pump` 里的 `_ => continue` 丢掉。单测
`timeout_keeps_connection_usable_and_drops_late_reply` 已在假 reader 上验过，这里验真链路。

---

### T5 · 两个 cwd = 两个进程且不串项目【方案 2 核心】

先 `reset_pool()` 清空连接池（见 0.4），再依次调 A、B。拆成两条独立判据：

#### T5a · 内容层（更硬）

从响应里提取"这是哪个项目"的**指纹**，两种形态都能认：
- 已建索引（A）→ status 里的 `Files indexed:** N`；
- 未建索引（B）→ codegraph 报错时回显的**实际搜索目录**。

**预期**：两边指纹不同，且都不是 `unknown`。

**反例**：两边指纹**相同** → cwd 被忽略，两个项目拿到了同一份数据。
这正是 stdio 的 cwd 在 spawn 时就固定带来的风险：若复用了错的会话，
第二个项目实际操作的是第一个项目的目录，**静默串项目**。

#### T5b · 进程层

**预期**：B 带来一组**新的** PID，且 A 的 PID 仍在（两组共存）。

**反例**：
- 没有新进程 → 两个项目共用了一个进程（先确认不是 0.4 那个脏基线问题）；
- A 的 PID 消失 → 新会话把老会话踢了，"轮流用"场景下会反复冷启动。

> ⚠️ **不要期待 `mcp_list_servers` 里有 `liveCwds`**。第一版用例把它写成了预期，
> 实测恒为空。查了代码：该字段只存在于 `mcp_bridge_cmds.rs` 里给设置页 UI 用的结构体
> （`ServerRow` 显示"运行中：N 个目录"），MCP 工具的 `describe()` 从不输出它。
> 这是设计如此，不是缺陷——运行时会话数是给人看的运维信息，没必要给远程模型。

---

### T6 · 同 cwd 复用，不重复起进程

**动作**：重复 T5 的调用。

**预期**：进程集合与 S3 完全相同，不新增。

**反例**：每次调用都多一组进程 → 池的 key 没命中（大小写？斜杠方向？尾部反斜杠？），
会持续泄漏进程。这条是 `SessionKey` 规范化的实测。

---

### T7 · 越界 cwd 被拒，且拒在 spawn 之前

**动作**：`cwd="C:/Windows"`（白名单外）。

**预期**：
- 报错，文案带白名单提示；
- **进程集合不变**——一个都不许新起。

**反例**：报错了但多了一组进程 → 校验发生在 spawn 之后，等于先把 server 拉起来
再说"不许"，白名单形同虚设。

---

### T8 · 致命错误仍然销毁连接

**动作**：手工 `taskkill /T /F` 掉桥派生的 codegraph 进程树 → 调用一次 → 再调用一次。

**预期**：
- 第一次报错（进程已退出 / 连接不可用）；
- 第二次产生**全新 PID**，且能正常返回。

**反例**：第二次仍然复用那个已死的会话、一直报错 → 方案 3 把不该留的也留住了，
变成"永久坏死"。这条是方案 3 的**对照组**，缺了它，方案 3 就只证明了一半。

## 3. 本轮**不**跑的用例（明确标注，不假装覆盖）

| 用例 | 为什么不跑 | 现有覆盖 |
|---|---|---|
| 关掉 `allow_remote_cwd` 后传 cwd 应被拒 | 需要改配置并重启 dev，成本高于收益 | 单测 `rejects_cwd_when_switch_is_off` |
| 把 cc-bridge 自己配成外挂应被拒（S8 自引用） | 同上，且需要临时写脏配置 | 单测（`session.rs` 里 `cc-bridge 自己` 那条） |
| 空闲 15 分钟后回收（`IDLE_TTL`） | 要挂机 15 分钟 | 单测覆盖了 `sweep_idle` 逻辑；真机未验 |
| 客户端中途断开时的会话清理 | 需要构造"发完就断"的客户端 | 代码上已把清理挪进 `spawn_blocking`；真机未验 |

## 4. 执行方式

```bash
# 在 cc-bridge 项目根目录
python testroot/mcp_bridge_verify.py
```

脚本自己从配置库读 token（**不打印**、不写进任何文件），逐条跑 T1–T8，
每条打印"实测值 / 预期 / 判定"，最后给汇总表。

`testroot/` 已在 `.gitignore` 里，脚本不入库。
