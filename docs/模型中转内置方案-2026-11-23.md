# 模型中转内置方案

> 2026-11-23 · 状态：方案 A 已确认，按本文实施 · 未改任何功能代码
>
> 已确认的四项：**A 内建纯 Rust 中转** / **同时支持 Anthropic 与 OpenAI 两类上游** / **远端接入两种方式都支持，默认推荐 SSH 隧道** / **配置入口放设置页分组**

## 一、要解决的问题

现在这套中转是 `D:\AItool\litellm`：Python venv + LiteLLM 1.110.2 + `start.bat` + `relay.conf` + 两个手写脚本（`strip_tool_changes.py` 剥离协议外块、`rotate_stream.py` 日志滚动）。远端 Linux 的 Claude Code 靠 `ANTHROPIC_BASE_URL` 指回 Windows 本机。

链路是通的（`/v1/messages` 实测 200），但日常使用的摩擦点很具体：

| 痛点 | 现在的样子 | 后果 |
|---|---|---|
| 进程无守护 | 手动双击 `start.bat`，关窗口就断 | 重启电脑、崩溃后要人记得去拉 |
| 改配置要重启 | 编辑文本 `relay.conf` → 重启 → 两端同步模型名 | 已经踩过：conf 改名后远端仍在用旧名，直接「模型不存在」 |
| 日志要另开窗口 | `Get-Content relay.log -Wait` | 日志滚动还得单独写个 142 行 Python 脚本 |
| 远端要手工配三件套 | `ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_MODEL` | 名字一错就报错，且错因不直观 |
| 与 cc-bridge 割裂 | 面板里点「开对话」，跑的是远端自己的 key | 中转只服务「自己敲命令」的场景 |
| 不可移植 | 换机器要重装 venv + litellm | venv 还套着两层 python.exe |

## 二、cc-bridge 已经有的底子

| 资产 | 位置 | 能直接复用什么 |
|---|---|---|
| axum HTTP 服务 | `mcp/http.rs` | 路由与中间件写法；中转要**独立端口 + 独立 Router**，不挂进 :7823 |
| SSH 端口转发 | `ssh_tunnel.rs`（`-L/-R/-D` 全支持） | 一条 `ForwardKind::Remote` 规则把本地中转送到远端 `127.0.0.1` |
| CC 会话启动 | `cc_session/channel.rs` | `remote_command` 的启动脚本里已在 `export CLAUDE_CODE_EMIT_SESSION_STATE_EVENTS=1`，加三行 env 即可 |
| 配置存储 | `config.rs` + SQLite | 新增 relay 配置段，走同一套原子更新 |
| 审计/日志 | `audit.rs`、`journal.rs` | JSONL + 保留策略的滚动思路可直接搬 |
| 常量时间比较 | `security/` | 中转 token 校验直接复用 |
| 进程封装 | `mcp::bridge::spawn` | 需要时再用（JobObject 那套已踩平） |

**唯一缺口是 HTTP 客户端**：`reqwest` 目前只在 `dev-dependencies`（供集成测试），要转正并开 `stream` feature。

## 三、为什么是方案 A

| 维度 | A 内建 Rust | B 托管 LiteLLM | C 只下发配置 |
|---|---|---|---|
| 日常操作 | 面板开关一次，之后常驻 | 仍依赖外部 venv | 仍要手工起进程 |
| 新增体积 | +0.5~1MB（待实测） | 数百 MB | 0 |
| 安装包红线（≤20MB） | 可控 | 破线 | 不受影响 |
| 与对话页联动 | 同进程，天然 | 需跨进程协调 | 需跨进程协调 |
| 换机器 | 装 exe 即可 | 重装 Python 环境 | 同现状 |
| 多上游适配 | 自建抽象层（见 §4.5） | 最全 | 取决于外部 |
| 工作量 | 大 | 中 | 小 |

## 四、详细设计

### 4.1 模块划分

```
src-tauri/src/relay/
├── mod.rs          模块文档 + 对外 API（start / stop / status / reload）
├── config.rs       RelayConfig / Provider / Route，serde 默认值齐全
├── server.rs       axum Router + 生命周期（绑定失败给人话，不吞错）
├── auth.rs         token 校验（subtle 常量时间比较）
├── rules.rs        清洗规则表（纯函数：strip_blocks / clamp_max_tokens / drop_thinking / drop_cache_control）
├── route.rs        客户端模型名 → (provider, upstream_model)
├── log.rs          JSONL 请求日志 + 滚动
└── upstream/
    ├── mod.rs      UpstreamKind { AnthropicCompatible, OpenAiCompatible }
    ├── anthropic.rs  透传路径（几乎不碰 body）
    └── openai/
        ├── request.rs   Anthropic Messages → OpenAI chat/completions
        ├── response.rs  OpenAI 响应 → Anthropic message（非流式）
        ├── stream.rs    OpenAI chunk → Anthropic SSE 事件序列
        └── schema.rs    tools / tool_choice / finish_reason / usage 映射
```

前端：

```
src/components/relay/
├── RelayCard.tsx            总开关 + 状态 + 监听地址
├── RelayProviderForm.tsx    上游地址 / 密钥 / 协议类型（Anthropic 兼容 / OpenAI 兼容）
├── RelayRouteTable.tsx      客户端名 → 上游名 映射表
├── RelayAccessGuide.tsx     两条接入路径的指引（隧道转发规则 / 内网地址 + 命令）
└── useRelaySettings.ts      表单状态与保存
```

### 4.2 一条请求怎么走

```
POST /v1/messages
  → auth     校验中转 token（失败 401，与上游错误体区分开）
  → parse    serde_json 读 body（只为取 model 与 messages）
  → rules    按启用规则清洗
  → route    客户端模型名 → (provider, upstream_model)
  → dispatch 按 provider.kind 分流：
       Anthropic 兼容 → 改 model、换鉴权头，其余逐字节透传
       OpenAI 兼容    → 转换请求 → 转发 → 转换响应/事件流
  → log      模型 / 状态码 / 用量 / 耗时 落 JSONL（默认不记 body）
```

### 4.3 透传路径的五条铁律

LiteLLM 能跑稳的根本原因是它足够“笨”。自己写反而更容易做对：

1. **body 除必要改写外逐字节转发**。`thinking`、`cache_control`、`tools`、`metadata`、`?beta=true` 全部原样。
2. **响应不解析**。SSE 按 chunk 直通；一旦中间层反序列化再序列化，打字机效果和缓存字节稳定性都会出问题。
3. **错误体原样回**。远端要看到上游原始报错。上次那个 400 就是因为被包成 `litellm.BadRequestError` 才难定位。
4. **不设自己的超时**。长思考 + 128k `max_tokens` 可能跑几分钟，超时策略归客户端。
5. **不改 query 与 header 大小写**。`anthropic-beta`、`anthropic-version` 敏感，原样透传。

### 4.4 清洗规则表

现在硬编码在 Python 里的逻辑，改成可配规则：

| 规则 | 作用 | 透传路径 | OpenAI 路径 |
|---|---|---|---|
| `strip_blocks` | 剥指定 type 的内容块（`tool_addition` / `tool_removal`），空消息 `content` 置 `""` | ✅ 必需 | 转译前剥 |
| `clamp_max_tokens` | `max_tokens` 钳到上游上限 | 预留 | ✅ 必需（CC 发 128k） |
| `drop_thinking` | 剥 `thinking` 配置与块 | 预留 | ✅ 必需 |
| `drop_cache_control` | 移除 `cache_control` 标记 | 预留 | ✅ 必需 |

规则是纯函数，喂录制样本做回归——这类逻辑不能只靠联网手测。

### 4.5 上游适配层（OpenAI 兼容是本方案的最大变量）

`UpstreamKind` 分为两路，**共用鉴权、路由、日志、规则表**，只有「怎么把请求发出去、怎么把响应翻回来」不同。

#### 请求映射（Anthropic → OpenAI）

| Anthropic | OpenAI | 注意 |
|---|---|---|
| `system`（string 或 block 数组） | 首条 `{role:"system"}` | block 数组拼成字符串 |
| `content[].text` | `content` 字符串或 parts | 纯文本时用字符串更省 |
| `content[].image`（base64 / url） | `{type:"image_url", image_url:{url}}` | base64 要拼成 `data:image/png;base64,...` |
| `content[].tool_use` | assistant 的 `tool_calls[{id, type:"function", function:{name, arguments}}]` | `arguments` 是 **JSON 字符串**，不是对象 |
| `content[].tool_result` | 独立 `{role:"tool", tool_call_id, content}` | 结构差异最大的地方：Anthropic 把结果塞在 user 消息里，OpenAI 要拆成独立消息 |
| `content[].thinking` | 丢弃（或厂商私有 `reasoning_content`） | 默认丢，字段名各厂商不统一 |
| `cache_control` | 丢弃 | 缓存失效，成本会上升，界面要提示 |
| `tools[].input_schema` | `tools[].function.parameters` | 结构基本一致 |
| `tool_choice: auto / any / tool` | `"auto"` / `"required"` / `{type:"function",...}` | `any` → `required` 这条最容易漏 |
| `max_tokens` | `max_tokens` | 新模型可能要 `max_completion_tokens`，按 provider 配 |
| `stop_sequences` | `stop` | |
| `?beta=true`、`anthropic-*` 头 | 不转发 | |

#### 响应映射（OpenAI → Anthropic，非流式）

| OpenAI | Anthropic |
|---|---|
| `message.content` | `content:[{type:"text",text}]` |
| `message.tool_calls[]` | `content:[{type:"tool_use",id,name,input}]`；`arguments` 解析失败要回可诊断错误，不能静默变空对象 |
| `finish_reason: stop` | `stop_reason: end_turn` |
| `length` | `max_tokens` |
| `tool_calls` | `tool_use` |
| `usage.prompt_tokens / completion_tokens` | `input_tokens / output_tokens` |
| 无 `id` | 自造 `msg_` 前缀 id |

#### 流式映射（决定能不能用的地方）

OpenAI chunk 序列 → Anthropic 事件序列：

```
message_start
  content_block_start(index=0, type=text)
    content_block_delta(text_delta) × N
  content_block_stop(0)
  content_block_start(index=1, type=tool_use, id, name)
    content_block_delta(input_json_delta, partial_json) × N
  content_block_stop(1)
message_delta(stop_reason, usage)
message_stop
```

四个必须处理的坑：

1. **`tool_calls` 是分片的**：`delta.tool_calls[].index` 要聚合，`id` / `name` 只在首片出现，后续片只有 `arguments` 片段。
2. **block index 必须严格递增**：Claude Code 按 index 归并，跳号或复用会让工具卡死。
3. **空 delta 要跳过**：只有 `role` 没有内容的 chunk 若照发，会多出一个空 text block。
4. **`usage` 可能不来**：请求时加 `stream_options:{include_usage:true}`；上游不认就退化为估算，界面标明「估算值」。

#### 这一路的代价（必须承认）

- 代码量大约是不含转换时的 2 倍，主要压在 `stream.rs` 与 `schema.rs`
- LiteLLM 的体积就在这些边角：多模态、thinking、并行工具调用、`tool_choice` 变体、厂商私有字段
- 这类问题**不会一次测完**，只能靠真实会话逐步收敛；要做好「先跑通主路径，再逐个补边角」的准备
- 建议实现顺序：文本流式 → tool_use 流式 → 多模态 → thinking 透传

### 4.6 配置与密钥

```sql
relay_provider(id, name, base_url, api_key, kind, auth_style, max_tokens_limit, enabled)
relay_route(id, client_model, provider_id, upstream_model, enabled)
```

监听范围这类单例配置放 `BridgeConfig`，不进 provider 表：

```
relay_enabled        总开关
relay_listen         127.0.0.1 | 0.0.0.0
relay_port           默认 4100
relay_lan_ip         内网直连时对外展示的地址（多网卡可手动指定）
relay_token          独立于 MCP token
relay_log_keep       请求日志保留行数
```

- `kind`：`anthropic` / `openai`
- `auth_style`：`x-api-key` / `bearer`（千问那条现在是前者）
- `max_tokens_limit`：`clamp_max_tokens` 的上限，按 provider 配
- 密钥沿用现有 token 的处理方式（SQLite + 面板掩码），**不引入新的加密依赖**
- 配置热生效：`Arc<RwLock<Arc<RelayConfig>>>` 换快照，不重启监听

### 4.7 对话页自动接上

`LaunchSpec` 增加 `env: Vec<(String, String)>`：

- 本机会话：spawn 时 `.envs()`
- 远端会话：`remote_command` 脚本里 `export`（位置现成）

只注入三项：

```bash
export ANTHROPIC_BASE_URL='http://127.0.0.1:4100'
export ANTHROPIC_AUTH_TOKEN='<中转 token>'
export ANTHROPIC_MODEL='<映射表里的客户端名>'
```

**`BASE_URL` 按会话位置与接入模式取值，不能写死**（这是最容易埋错的一行）：

| 会话位置 | 隧道模式 | 内网直连模式 |
|---|---|---|
| 本机 | `http://127.0.0.1:4100` | `http://127.0.0.1:4100` |
| 远端 | `http://127.0.0.1:4100`（隧道已把该端口映射回本机） | `http://<本机内网IP>:4100` |

远端 + 隧道模式下用 `127.0.0.1` 是**对的**：那条路走的是远端自己的回环地址，由隧道转发回本机。实现时若图省事直接拼内网 IP，隧道模式反而会失败。

对话页顶部给「走中转 / 走原生」切换，默认跟随全局开关。模型名从此只有面板一处定义。

### 4.8 远端独立 Claude Code 的接入（两条路，默认推荐隧道）

中转的监听范围是个开关，不是写死的：

| | 隧道模式（默认） | 内网直连模式 |
|---|---|---|
| 中转监听 | `127.0.0.1:4100` | `0.0.0.0:4100` |
| 远端 `ANTHROPIC_BASE_URL` | `http://127.0.0.1:4100` | `http://<本机内网IP>:4100` |
| 依赖 | 该连接已建立 SSH 会话 | 两端在同一网段 / VPN |
| 传输 | SSH 加密，证书级主机认证 | 明文 HTTP，token 过网线 |
| 端口可达性 | 同网段扫不到 | 同网段任何人可探测 |
| 适合 | 跨网络、公网中转、长期使用 | 同一内网、临时调试、隧道建不起来时 |

两种模式界面都给，**默认选隧道并排在第一**，切到内网直连要过一次确认弹窗。

#### 隧道模式

- 「接入指引」卡片一键创建 `ForwardKind::Remote` 规则（本地 `127.0.0.1:4100` → 远端 `127.0.0.1:4100`）
- 给三行可复制的 `export`，模型名从映射表读，不会手抄错
- 隧道断开时远端会立刻失败，界面要能把「隧道未连」和「上游报错」区分开——这两种错误在远端长得一样

#### 内网直连模式

不是简单把 bind 地址改成 `0.0.0.0` 就完事，必须同时满足四条，否则等于把额度公开：

1. **token 不可为空**：这个模式下配置里没有 token 就拒绝启动，不允许「空 token 也能通」
2. **401 封禁**：复用现有 `mcp/http.rs` 的 `remote_ban` 策略（连续错误 N 次后连正确 token 也拦），不另造一套
3. **限流**：复用现有 `rate_limit_max_requests` / `rate_limit_window_ms`，按来源 IP 计
4. **来源可见**：请求日志记录来源 IP，界面状态卡显示「当前对内网开放」的醒目提示与实际地址

地址显示复用 `network.rs` 的多网卡探测，不要把 `0.0.0.0` 当地址给用户抄——那不是能连的地址。多网卡时会选错，这是已知坑（`fix: 修复多网卡 IP 选错`），选错时让用户能手动指定。

还有一件容易被忽略的事：**Windows 上端口要放行才有用**。复用现有 `firewall.rs` / `firewall_diag.rs` 的检测与提示，不要另写一套「请手动加规则」的文案——加规则需要管理员权限，用户照抄也加不上时，界面得给可执行的下一步（提权按钮或明确指引），否则表现为「配置都对，远端连不上」。

**明文这件事要写在界面上**：内网直连时 token 是明文过网线的，同网段抓包可见。这是默认推荐隧道的技术理由，不是习惯偏好。

### 4.9 UI 落点

7 个顶级 tab 不动，配置进「设置」页新增分组「模型中转」：

- 分组顶部：状态卡（开关 / 监听地址 / 今日请求数 / 用量），样式对齐现有 `HealthCard`；内网直连时状态卡换成警示配色并标注「对内网开放」
- **监听范围选择器**：两个单选（`仅本机 + SSH 隧道` 默认选中 / `内网直连`），选中后者时就地展开确认区——勾选「我知道同网段可以访问」才能保存，并显示将要暴露的实际地址
- 中部：provider 表单 + 映射表
- 底部：接入指引（按当前模式生成不同内容：隧道模式给转发规则，直连模式给内网地址 + 三行 export）
- 请求日志复用「日志」页的筛选形态，加来源标签与来源 IP 列

这个功能是「配一次长期常驻」，不是高频操作页，不适合占顶级 tab。

### 4.10 安全约束

1. 默认只听 `127.0.0.1`；切内网直连要二次确认，且该模式下 token 为空直接拒绝启动
2. 中转 token 与 MCP token **分开**，避免一串两用
3. 内网直连时，令牌校验、限流、401 封禁三件必须同时生效——只开监听不加约束等于公开额度
4. 请求日志默认只记元数据；记 body 需显式开调试开关，并标注体积风险（那 937KB 的日志就是教训）
5. 日志与错误信息里密钥一律打码
6. 内网直连是明文 HTTP，界面必须写明这一点；不做「悄悄降级」

## 五、分期与验收

> P2 与 P3 顺序可交换：想先验证 OpenAI 上游就把 P3 提前，两者互不依赖。

### P0：准备 —— ✅ 已完成（2026-11-23）

**结论：体积代价 ≈ 0，不必改用 `hyper-util`。**

原计划是「`reqwest` 转正后实测体积」，实测推翻了这条路径的两个假设：

1. **`reqwest` 早就在正式依赖树里**。`tauri-plugin-updater 2.14.1` 依赖 `reqwest 0.13.5`，
   它本来就链接进 exe。而 `dev-dependencies` 里那条 `0.12` 只服务集成测试、不进 release
   构建——**照原计划「把 dev-deps 的 reqwest 转正」会同时链接两份 reqwest**，体积翻倍且
   零收益。所以最终声明的是 `reqwest = "0.13"`，与 updater 复用同一份编译单元。
2. **0.13 的 feature 名与 0.12 完全不同**：`rustls-tls` / `rustls-tls-manual-roots` 都不存在了，
   取而代之是 `rustls`（aws-lc-rs + platform-verifier）和 `rustls-no-provider`。updater 开的是
   `rustls-no-provider` + `rustls-platform-verifier`，**系统根证书被信任**——原文担心的
   「只用 webpki roots 会不认 Clash MITM CA」在这条链上不存在。

实测数字（`cargo build --release`，同一 target 目录增量构建）：

| | 基线（无 relay 模块） | 加 reqwest 声明 + 流式转发代码 | 增量 |
|---|---|---|---|
| exe | 27,454,464 B（26.18 MiB） | 28,332,544 B（27.02 MiB） | **+878,080 B（+857.5 KiB）** |
| 安装包（按 0.46 压缩比估算） | 12.03 MB | ≈ 12.42 MB | +0.39 MB |

增量拆开看：

| 组成 | 体积 | 说明 |
|---|---|---|
| reqwest 本体（流式转发代码路径） | **+26 KiB** | 复用 updater 那份 0.13，几乎不花额外成本 |
| rustls crypto provider（aws-lc-rs） | **+831 KiB** | 唯一的大头，见下面的取舍 |

**红线 20MB，实测安装包约 12.42MB，余量 7.5MB —— 不必换 `hyper-util`。**

**为什么必须写一段真实代码才能测准**：只加 `Cargo.toml` 声明、代码里不引用，linker 会把
未实例化的泛型全剔除，测出来是假的零增量。所以 P0 建了 `src/relay/mod.rs` 的探测骨架
（`probe()`：构造请求 → 发送 → `Response::chunk()` 逐块读），并经 Tauri 命令表注册
（`commands::relay_probe`）——命令表是运行时可调用路径，LTO 不敢删。

**已验证代码真在二进制里**：`grep -a` 能在 exe 中命中 `中转探测` / `请求未送达` /
`构建 HTTP 客户端失败` / `读取响应体失败` / `relay_probe`。注意本机 `strings` 命令失效
（返回 0 行），查二进制字符串要用 `grep -a`。

### P0 踩到的三个坑（P1 前必读）

**1. dev-dependencies 的 reqwest 必须与正式依赖同版本。**
原 dev-deps 声明 `reqwest = "0.12"`，正式依赖是 `0.13`（复用 updater）。两者并存时，
`#[cfg(test)]` 里的 `reqwest::Client` 直接报：

```
error[E0464]: multiple candidates for `rlib` dependency `reqwest` found
```

测试根本编不过。已把 dev-deps 也升到 0.13。迁移只需改一处 API：
`use_rustls_tls()` → `tls_backend_rustls()`（前者在 0.13 已 deprecated，`clippy -D warnings`
下会亮红）。`gzip(bool)`、`Certificate::from_pem`、`add_root_certificate` 三个都在，无需改动。

**2. 必须用 `rustls` feature，不能用 `rustls-no-provider`。**
tauri-plugin-updater 用的是 `rustls-no-provider`——那是空壳，**不装加密 provider**。
直接照抄会让 13 个 over-the-wire 测试全部 panic：

```
No rustls crypto provider is configured. When using the `rustls-no-provider`
feature you must install a crypto provider before building a Client.
```

那 831 KiB 就是买这个 provider（aws-lc-rs）的钱。**不要为了省体积改回
`rustls-no-provider` 然后赌 updater 会先装好 provider**——中转不能赌别的模块的初始化时机。

**3. 测试必须带 `--no-default-features`。**
`cargo test` 裸跑会以 `0xc0000139 STATUS_ENTRYPOINT_NOT_FOUND` 崩掉——这是项目**既有**问题：
默认开的 `notifications` feature 拉入 `tauri-plugin-notification` → `AppHandle` → GUI DLL 链
（tao / webview2-com），测试二进制在 main 之前加载失败。正确命令：

```bash
cargo test --no-default-features
cargo clippy --all-targets --no-default-features -- -D warnings
```

已记在 `CLAUDE.md` 第 73 行与 `docs/dev-setup.md`，排查时不要再当成代码问题。

依赖声明附带的取舍（已写进 `Cargo.toml` 注释）：

- **不开 gzip**：中转是热路径，解压全量再转发多一次内存拷贝；千问的 SSE 响应本身不带
  `content-encoding`。真需要时再评估（0.13 的 gzip 走 `tower-http/decompression-gzip`，
  已经不再是 flate2，增量比 0.12 时代更小）。**dev-deps 开 gzip 不会泄漏到 release**——
  `cargo build --release` 的依赖图不含 dev-dependencies。
- `default-features = false` 只关掉**本声明**带来的 default，不影响 updater 那条的 feature
  （Cargo 对同一 crate 取并集）。

**P0 验证记录**：`cargo test --no-default-features --lib mcp::` → 394 passed / 0 failed；
`cargo clippy --all-targets --no-default-features -- -D warnings` 通过；relay 单元测试通过。

## 六、风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 协议透传细节 | SSE 分块、gzip、`?beta=true` 任一处错都表现为「偶发失败」 | 录制回放做回归，不靠手测 |
| OpenAI 转换边角 | `tool_calls` 分片、block index、空 delta、usage 缺失 | 四条坑写进单测，构造 chunk 序列做断言 |
| 转换层长期维护 | 厂商字段漂移（如 `max_completion_tokens`） | 差异全部收敛到 provider 配置，不散在代码里 |
| 体积 | `reqwest` 转正可能超预期 | ✅ P0 实测：+857.5 KiB（reqwest 本体仅 26 KiB，其余是 rustls provider），安装包约 12.42MB，红线 20MB |
| 缓存失效 | OpenAI 路径丢掉 `cache_control` 后成本上升 | 界面标注，路由表里给「推荐 Anthropic 路径」提示 |
| 内网直连暴露额度 | 监听 `0.0.0.0` 后同网段可探测，token 明文过网线 | 默认不开；开启需二次确认 + token 非空 + 401 封禁 + 限流；状态卡常驻警示 |
| 单点故障 | 中转在进程内，cc-bridge 崩了远端全断 | 与现在同等；托盘已有，可加自动重启 |
| 产品定位漂移 | 从「文件桥」扩到「AI 接入中枢」 | 一期不动 README 主线叙事，作为可选能力 |
