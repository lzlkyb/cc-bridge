## 一、要解决的问题

现在这套中转是 `D:\AItool\litellm`：Python venv + LiteLLM 1.110.2 + `start.bat` + `relay.conf` + 两个手写脚本（`strip_tool_changes.py` 剥离协议外块、`rotate_stream.py` 日志滚动）。远端 Linux 的 Claude Code 靠 `ANTHROPIC_BASE_URL` 指回 Windows 本机。

链路是通的（`/v1/messages` 实测 200），但日常使用的摩擦点很具体：

| 痛点 | 现在的样子 | 后果 |
|---|---|---|
| 进程无守护 | 手动双击 `start.bat`，关窗口就断 | 重启电脑、崩溃后要人记得去拉 |
| 改配置要重启 | 编辑文本 `relay.conf` → 重启 → 两端同步模型名 | 已经踩过：conf 改名后远端仍在用旧名，直接「模型不存在」 |
| 日志要另开窗口 | `Get-Content relay.log -Wait` | 日志滚动还得单独写个 142 行 Python 脚本 |
| 远端要手工配三件套 | `ANTHROPIC_BASE_URL` / `ANTHROPIC_AUTH_TOKEN` / `ANTHROPIC_MODEL` | 名字一错就报错，且错因不直观 |
| 与 cc-bridge 割裂 | 面板里点「开对话」，跑的是远端自己的 key | 中转只服务「自己敲命令」的场景 |
| 不可移植 | 换机器要重装 venv + litellm | venv 还套着两层 python.exe |

## 四、详细设计

### 4.1 模块划分

```
src-tauri/src/relay/
├── mod.rs          模块文档 + 对外 API（start / stop / status / reload）
├── config.rs       RelayConfig / Provider / Route，serde 默认值齐全
├── server.rs       axum Router + 生命周期（绑定失败给人话，不吞错）
├── auth.rs         token 校验（subtle 常量时间比较）
├── guard.rs        来源守卫：拒浏览器 / DNS rebinding / 自转发回环
├── rules.rs        清洗规则表（纯函数：fold_tool_blocks / strip_model_suffix / clamp_max_tokens / drop_thinking / drop_cache_control）
├── sanitize.rs     三态校验：Unchanged / Sanitized(findings) / Refused，finding 记路径与归属开关（照 LiteLLM #42731）
├── fold.rs         tool_addition 折叠：抽工具定义 → 按 name 合并进顶层 tools → 块丢弃 → 空消息填占位文本
├── route.rs        客户端模型名 → 档位 → (provider, upstream_model)
├── rectify.rs      兜底重发：仅当上游错误信息带字段名时启用；当前两家上游是泛化 400，故默认关闭
├── log.rs          JSONL 请求日志 + 滚动
└── upstream/
    ├── mod.rs      UpstreamKind { AnthropicCompatible, OpenAiCompatible }
    ├── anthropic.rs  透传路径（几乎不碰 body）
    └── openai/
        ├── request.rs   Anthropic Messages → OpenAI chat/completions
        ├── response.rs  OpenAI 响应 → Anthropic message（非流式）
        ├── stream.rs    OpenAI chunk → Anthropic SSE 事件序列
        └── schema.rs    tools / tool_choice / finish_reason / usage 映射
```

前端：

```
src/components/relay/
├── RelayTab.tsx             页壳：页头 + Bento 网格（10 块）
├── RelayPageHead.tsx        标题 + 运行中徽章 + 一句说明 + 右侧两行摘要（数字都进卡了，这里只留上游与错误）
```

> 页壳不叫 `RelayCard`：它现在是整页，不是设置页里的一张卡。命名跟着形态走，否则实现时容易照着「卡片」尺度写，宽度一给就散。
>
> **`RelayStatusCard` / `RelayMetricCards` 在第 2 版里删过、第 3 版又加回来了**，加回来的理由写在 §4.9.2：卡片是只读的，加卡不等于加接触点；中转是常驻服务，用户需要一块能一眼看到「在跑 / 多少 / 出错没」的地方。但**内容是重写的**——链路是中转自己的三段，四个指标是日志能算出来的四项，不是把连接页的请求速率 / P95 / 调用增量 / 活跃命令搬过来。实现时照 `RelayMetricCards` 的字段写，别回头去抄 `MetricCards`。
>
> 原来的 `RelayProviderForm` + `RelayRouteTable` 拆成 `RelayModelForm` + `RelayAliasCard`：前者只管三个必填项，后者只管"要粘什么名字"。合成的旧结构里，`default` 档的上游模型在两个组件里各有一个输入框，是实现期最容易写成"两个 state 同步"的坑。
>
> **这些组件都不该出现 `appearance === "glass"` 之类的分支**，也不加条件 className。主题差异全部写在 `appearance.css` 的 `html[data-ui-style="glass"]` 下（§4.9.5）。允许为语义换类名，但不要为了玻璃额外套一层 DOM——「为某个主题加结构」就是第 2 版照抄页面的开端。

### 4.2 一条请求怎么走

```
POST /v1/messages
  → guard    来源守卫：浏览器 / DNS rebinding / 自转发 → 直接 4xx 拒绝
  → auth     校验中转 token（失败 401，与上游错误体区分开）
  → parse    serde_json 读 body（只为取 model 与 messages）
  → rules    确定性改写：strip_model_suffix / clamp_max_tokens / drop_thinking…
  → sanitize 按 provider 能力表一次性校验成 typed view，产出三态结果
       Unchanged      → 原样转发（不含 tool 变更块的请求走这条，body 逐字节不动）
       Sanitized(f)   → 折叠 tool_addition / tool_removal、填占位，记下 finding
       Refused(cause) → 我们自己出错误体，明确说哪个字段、该开哪个开关
  → route    客户端模型名 → 档位 → (provider, upstream_model)
  → dispatch 按 provider.kind 分流：
       Anthropic 兼容 → 改 model、换鉴权头，其余逐字节透传
       OpenAI 兼容    → 转换请求 → 转发 → 转换响应/事件流
  → rectify  （默认关闭）仅当上游错误信息确实带字段名时，折叠并重发一次
  → log      模型 / 状态码 / 用量 / 耗时 / 是否折叠过 落 JSONL（默认不记 body）
```

`sanitize` 是主路径，`rectify` 是留给未来的兜底。当前接的两家上游（千问 / DeepSeek 同一端点）
400 错误信息都是泛化的 `Request body format invalid`，从中判断不出该不该折叠，所以只能靠
provider 能力表在转发前就决定——这就是 §4.4.1 讲的「默认预折叠」。`rectify.rs` 保留代码但默认关闭。

### 4.3 透传路径的五条铁律

LiteLLM 能跑稳的根本原因是它足够“笨”。自己写反而更容易做对：

1. **body 除必要改写外逐字节转发**。`thinking`、`cache_control`、`tools`、`metadata`、`?beta=true` 全部原样。
2. **响应不解析**。SSE 按 chunk 直通；一旦中间层反序列化再序列化，打字机效果和缓存字节稳定性都会出问题。
3. **错误体原样回**。远端要看到上游原始报错。上次那个 400 就是因为被包成 `litellm.BadRequestError` 才难定位。
4. **不设自己的超时**。长思考 + 128k `max_tokens` 可能跑几分钟，超时策略归客户端。
5. **不改 query；header 的「值」原样透传**。`anthropic-beta`、`anthropic-version` 的值敏感，一个字符都不能动。头**名**的大小写会被 reqwest 规范化（`Anthropic-Beta` → `anthropic-beta`），这个差异无害，代价与原因见 §4.11。

### 4.4 清洗规则与折叠策略

现在硬编码在 Python 里的逻辑，改成可配规则：

| 规则 | 作用 | 透传路径 | OpenAI 路径 |
|---|---|---|---|
| `fold_tool_blocks` | 把 `tool_addition` 里的工具**翻译进顶层 `tools`**（按 name 去重），再丢掉块；被掏空的消息用 `Please continue.` 占位 | 整流时触发 | 转译前折叠 |
| `strip_model_suffix` | 去掉模型名尾部的 `[1m]` / `[1M]`（Claude Code 用它声明百万上下文，上游不认） | ✅ 必需 | ✅ 必需 |
| `clamp_max_tokens` | `max_tokens` 钳到上游上限 | 预留 | ✅ 必需（CC 发 128k） |
| `drop_thinking` | 剥 `thinking` 配置与块 | 预留 | ✅ 必需 |
| `drop_cache_control` | 移除 `cache_control` 标记 | 预留 | ✅ 必需 |

规则是纯函数，喂录制样本做回归——这类逻辑不能只靠联网手测。

**为什么是「折叠」而不是「剥离」**：`tool_addition` 不是无意义的噪音，它承载的是 **ToolSearch 动态注册的工具定义**。
直接丢弃等于让模型看不见这些工具，它会回答"我没有这个工具"或凭空编造——请求虽然 200，行为已经错了。
折叠进顶层 `tools` 后模型能正常认领并调用，实测见 §4.4.2。

**为什么被掏空的消息要用 `Please continue.` 而不是 `""` 或删除整条**：

- 删除整条会破坏 user / assistant 的交替，还可能让后续 `tool_result` 与它的 `tool_use` 脱钩
- 空 `content: ""` 部分上游会当成非法请求
- `Please continue.` 是 LiteLLM 在同类场景已用的占位文本，语义中性、不引入新指令

这三种做法的差别，见 LiteLLM PR #42731 的决策记录（它也明确写了「**永不删除整个消息**」）。

`strip_model_suffix` 必须单独成一条：它只动 `model` 字段，不动 `messages`。这是**预防性**的——
千问当前能接受带后缀的模型名，但 `[1m]` 是 CLI 侧声明百万上下文的私有约定，上游没有义务认它。
真出问题时的表现是 400「请求体格式无效」，和上次那个 400 长得一模一样，很难往模型名上想。
一条纯函数规则的成本远低于再查一次。

#### 4.4.1 默认预折叠——「先发后整流」在这个上游不成立

原设计是「先发后整流」：先原样发，等上游拒绝再改。理由很漂亮（保缓存前缀、上游升级自动受益）。
但**实测证明这条路在千问/DeepSeek 这个端点上走不通**，因为它的 400 错误信息是泛化的：

| 成因 | 上游返回 |
|---|---|
| `tool_addition` / `tool_removal` 块 | 400 `InvalidParameter` · `Request body format invalid` |
| 非法 `role`（`"wizard"`） | 400 `InvalidParameter` · `Request body format invalid` |
| 模型名不存在 | 400 `InvalidParameter` · `Model not exist.` |

前两行**完全一样**。错误信息里不含字段名、不含消息路径、不含 `tool_addition` 这个词。
所以「等上游告诉你哪里错了再改」这个前提不成立——你无法从响应判断该不该折叠。

> 这一点和 CLIProxyAPI 报告里 Kimi 的表现一致（泛化的 `Invalid request Error`）。
> 而 Claude Code 自身的降级逻辑恰恰依赖「错误正文里出现 `tool_addition`」来识别（sticky-reject），
> 在千问上它同样识别不出来——这解释了为什么用户看到的是纯 400 而不是自动降级。

**改成默认预折叠**，由 provider 能力表决定：

```
sanitize 阶段（转发前，无网络往返）
  provider.supports_tool_change_blocks == false
  且 body 里确实存在 tool_addition / tool_removal 块
  → 折叠（工具定义进顶层 tools / 从 tools 删名，块丢弃，空消息填占位）
  否则
  → Unchanged，body 逐字节不动
```

关键点：**这个折叠是条件触发的，不是无条件的。** 不含这些块的请求走 `Unchanged`，body 一个字节都不改，
所以 prompt 缓存前缀完全不受影响。原设计想靠「先发后整流」保住的东西，这里天然就有了。

于是收益变成三条，都比整流强：

1. **零额外往返**。整流方案每条被拒请求要重发一次，延迟翻倍；预折叠一次就对。
2. **不依赖错误信息**。在泛化 400 的网关上这是唯一可行解。
3. **仍然不丢信息**。折叠保留了工具定义（这点比剥离强，见 §4.4.3）。

代价与约束：

- **需要 provider 能力标注**。这个标注是「该上游是否接受 tool 变更块」，不是「该上游叫什么」。
  千问与 DeepSeek 在这个端点上表现完全一致（同一套校验），所以按**端点**标而不是按模型标。
- **上游哪天开始支持了，要手动关掉这个开关**。这就是原设计「自动受益」丢掉的部分——
  用一个小代价换掉一个不可行的大方案，划算。
- **保留整流框架，但默认关闭**。`rectify.rs` 只在上游错误信息确实带字段名时才启用，
  那时的判定是可靠的。当前接的两家都不满足，所以它是「留给未来的代码」而不是主路径。

**再记一笔早先写错的判断**：本节更早的版本写过「`tool_addition` 不会真的影响模型行为，剥掉也无妨」。
这是错的——它承载 ToolSearch 动态注册的工具定义，剥掉模型就看不见那些工具。
本节的方案之所以敢「直接折叠」，前提是**折叠而非丢弃**，见 §4.4.2。

#### 4.4.2 清洗器的工程结构（照 LiteLLM 的做法）

LiteLLM 在 PR #42731 里处理同一类问题（Claude Code 新字段被 Bedrock 拒），它的结构值得直接抄：

1. **校验独立成模块**，不塞进转发逻辑里。请求**一次性**校验成带类型的视图，而不是边转发边判断。
2. **每个发现是一条 finding**，记录 `请求路径`（如 `messages[1].content[0]`）和 `该由哪个开关负责`。
3. **结果只有三种**：`Unchanged` / `Sanitized(finding 列表)` / `Refused(原因)`，转发层对这三种 match。
4. **拒绝错误只有一个出口函数生成**——「哪种请求该看到哪个错误」只写在一处。

这套结构的价值不在优雅，在**可测**：finding 是纯数据结构，可以直接喂录制样本断言，不需要起服务。
我们那 5 种载荷的回放测试，就是喂给这一层。

| `thinking = {type:"adaptive", display:"updates"}` | **200** | **200** |
| 顶层 `tools` + 正常提问 | **200** + 正确调用 | **200** + 正确调用 |
| `tool_addition`（`tools` 数组形态） | **400** | **400** |
| `tool_addition`（`tool_reference` 形态，在 `role:"system"` 里） | **400** | **400** |
| `tool_removal`（`tool_reference` 形态） | **400** | **400** |
| 同一条 system 消息里 addition + removal 混合 | **400** | **400** |
| **折叠后**（工具进顶层 `tools`，块丢弃，占位文本） | **200** + 正确调用 | **200** + 正确调用 |
| **折叠后 + 流式** | **200**，`stop_reason=tool_use`，`input_json_delta` 拼成合法 JSON | 同左 |
| **折叠后 + 多轮（含已发生的 `tool_use`/`tool_result`）** | **200**，正确引用工具结果作答 | **200**，回答「北京现在是晴天，气温 18 度」 |

四条结论：

1. **这是网关级的统一校验，不是模型级差异**。两个模型（不同厂商）行为逐项一致，
   说明规则该按**端点**标注，而不是按模型标注。换模型不需要改任何逻辑。
2. **对「未知字段」宽松、对「未知 content block 类型」严格**。这就是为什么只有 `tool_*` 块炸，
   而 `output_config` / `thinking.display` 一路通行。
3. **`tool_addition` 有两种形态**，`{"tool":{"type":"tool_definition","definition":{...}}}`（内联完整定义）
   和 `{"tool":{"type":"tool_reference","name":"..."}}`（只引用名字）。两种都会 400，折叠逻辑要都处理。
   `tool_removal` 的形态与 reference 相同，但翻译方向相反（从 `tools` 删名而非并入）。
4. **折叠在多轮与流式下都成立**。多轮那条最能说明问题：折叠后模型正确引用了 `tool_result` 里的
   「晴，18 度」来回答，证明 `tool_use` / `tool_result` 的配对没有被折叠破坏。
   流式那条证明 `input_json_delta` 的分片能拼成合法 JSON，工具卡不会卡死。

三条附带事实：

- **模型名带不带日期后缀都存在**：`deepseek-v4.1-flash-1017` 与 `deepseek-v4.1-flash` 都是 200，
  `deepseek-v4.1-pro` 返回 `Model not exist.`。所以「模型不存在」是可区分的错误，不用猜。
- **`/v1/models` 与 `/models` 都返回 404**，无法枚举模型。映射表只能手填，
  填错时的表现是 `Model not exist.`（比泛化 400 好排查得多）。
- **上游返回的 model 名可能与请求的不同**：请求 `qwen4-max-preview`，响应里写 `qwen4.0-max-preview`。
  所以日志里要同时记「请求的 model」和「响应里的 model」，否则对不上号。

同时要记一笔：**`output_config` 和 `thinking.display` 现在不用处理，但规则表里要留位置**。
换到 Bedrock 或别的严格上游，这两个立刻会变成 400 源——LiteLLM 那个 PR 就是为此而写的。
判断依据是「上游严格程度」而不是「我们当前用哪家」。

### 4.5 上游适配层（OpenAI 兼容是本方案的最大变量）

`UpstreamKind` 分为两路，**共用鉴权、路由、日志、规则表**，只有「怎么把请求发出去、怎么把响应翻回来」不同。

#### 请求映射（Anthropic → OpenAI）

| Anthropic | OpenAI | 注意 |
|---|---|---|
| `system`（string 或 block 数组） | 首条 `{role:"system"}` | block 数组拼成字符串 |
| `content[].text` | `content` 字符串或 parts | 纯文本时用字符串更省 |
| `content[].image`（base64 / url） | `{type:"image_url", image_url:{url}}` | base64 要拼成 `data:image/png;base64,...` |
| `content[].tool_use` | assistant 的 `tool_calls[{id, type:"function", function:{name, arguments}}]` | `arguments` 是 **JSON 字符串**，不是对象 |
| `content[].tool_result` | 独立 `{role:"tool", tool_call_id, content}` | 结构差异最大的地方：Anthropic 把结果塞在 user 消息里，OpenAI 要拆成独立消息 |
| `content[].thinking` | 丢弃（或厂商私有 `reasoning_content`） | 默认丢，字段名各厂商不统一 |
| `cache_control` | 丢弃 | 缓存失效，成本会上升，界面要提示 |
| `tools[].input_schema` | `tools[].function.parameters` | 结构基本一致 |
| `tool_choice: auto / any / tool` | `"auto"` / `"required"` / `{type:"function",...}` | `any` → `required` 这条最容易漏 |
| `max_tokens` | `max_tokens` | 新模型可能要 `max_completion_tokens`，按 provider 配 |
| `stop_sequences` | `stop` | |
| `?beta=true`、`anthropic-*` 头 | 不转发 | |

#### 响应映射（OpenAI → Anthropic，非流式）

| OpenAI | Anthropic |
|---|---|
| `message.content` | `content:[{type:"text",text}]` |
| `message.tool_calls[]` | `content:[{type:"tool_use",id,name,input}]`；`arguments` 解析失败要回可诊断错误，不能静默变空对象 |
| `finish_reason: stop` | `stop_reason: end_turn` |
| `length` | `max_tokens` |
| `tool_calls` | `tool_use` |
| `usage.prompt_tokens / completion_tokens` | `input_tokens / output_tokens` |
| 无 `id` | 自造 `msg_` 前缀 id |

#### 流式映射（决定能不能用的地方）

OpenAI chunk 序列 → Anthropic 事件序列：

```
message_start
  content_block_start(index=0, type=text)
    content_block_delta(text_delta) × N
  content_block_stop(0)
  content_block_start(index=1, type=tool_use, id, name)
    content_block_delta(input_json_delta, partial_json) × N
  content_block_stop(1)
message_delta(stop_reason, usage)
message_stop
```

四个必须处理的坑：

1. **`tool_calls` 是分片的**：`delta.tool_calls[].index` 要聚合，`id` / `name` 只在首片出现，后续片只有 `arguments` 片段。
2. **block index 必须严格递增**：Claude Code 按 index 归并，跳号或复用会让工具卡死。
3. **空 delta 要跳过**：只有 `role` 没有内容的 chunk 若照发，会多出一个空 text block。
4. **`usage` 可能不来**：请求时加 `stream_options:{include_usage:true}`；上游不认就退化为估算，界面标明「估算值」。

#### 这一路的代价（必须承认）

- 代码量大约是不含转换时的 2 倍，主要压在 `stream.rs` 与 `schema.rs`
- LiteLLM 的体积就在这些边角：多模态、thinking、并行工具调用、`tool_choice` 变体、厂商私有字段
- 这类问题**不会一次测完**，只能靠真实会话逐步收敛；要做好「先跑通主路径，再逐个补边角」的准备
- 建议实现顺序：文本流式 → tool_use 流式 → 多模态 → thinking 透传

### 4.6 配置与密钥

```sql
relay_provider(id, name, base_url, api_key, kind, auth_style, max_tokens_limit, fold_tool_blocks, enabled)
relay_tier(provider_id, tier, upstream_model, client_alias)   -- 每个 provider 至少一行 default；其余档位行可选，缺行即回落
relay_override(id, client_model, provider_id, upstream_model, enabled)
```

表结构保留完整字段，但**用户要填的只有三个**（见 §4.6.2）。其余字段由程序写默认值：

| 字段 | 用户要不要碰 | 默认 / 来源 |
|---|---|---|
| `base_url` | **填** | 无默认，必填 |
| `api_key` | **填** | 无默认，必填 |
| `upstream_model`（default 档） | **填** | 无默认，必填 |
| `name` | 不碰 | 从 `base_url` 的域名推导（`token-plan.maas.qianwenaiapi.com` → `qianwenaiapi`），只用于页头与日志显示 |
| `kind` | 不碰 | P1 恒为 `anthropic`（透传）。OpenAI 兼容在 P3 才有，届时作为「高级」里的一个选项 |
| `auth_style` | 不碰 | 默认 `x-api-key`；首次测连通失败时自动换 `bearer` 再试一次，成功即写回。手动可改（高级） |
| `max_tokens_limit` | 不碰 | `null` = 不压。只有上游返回 `max_tokens` 超限错误时，错误条上出现「压到 8192」一键动作，点了才写值 |
| `fold_tool_blocks` | 不碰 | `true`（§4.4.1）。高级里可关 |
| `enabled` | 不碰 | `true`。单 provider 场景下没有第二个可选，UI 不暴露 |

监听范围这类单例配置放 `BridgeConfig`，不进 provider 表：

```
relay_enabled        总开关。一个键管两件事：是否监听 + 主界面「中转」tab 是否注册（默认 false）
relay_listen         127.0.0.1（隧道）| <指定网卡 IP>（直连）
relay_port           4100，不暴露给用户
relay_lan_ip         内网直连时绑定的网卡 IP（多网卡可手动指定）
relay_token          独立于 MCP token，单值，开启时自动生成（rly_ 前缀 + 随机），UI 只以掩码显示
relay_log_keep       5000，不暴露给用户
```

`relay_token` 是**单值**：一个 token 服务自己所有远端机器，可以复制到多台，但不是"按人发"。
自建场景不需要 token 表、不需要日额度闸门、不需要单个 token 回收——这些是团队共享入口才要的东西，
真要做会多出一整套用户体系，与本功能"一个人给自己用"的定位不符。

**端口、日志保留量、token 全部不给用户配。** 自建单人场景下这三项没有改的理由：端口冲突极少见（真冲突时错误信息里给「换到 4101」），日志量按行数截断够用，token 不该由人想。把它们做成设置项，等于让用户先回答三个他答不上来的问题才能用这个功能。

- 密钥沿用现有 token 的处理方式（SQLite + 面板掩码），**不引入新的加密依赖**
- 配置热生效：`Arc<RwLock<Arc<RelayConfig>>>` 换快照，不重启监听

#### 4.6.1 模型映射：默认一个，可选分档

Claude Code 会按任务复杂度请求不同**档位**的模型。但**这不等于用户必须配三份映射**——绝大多数人手里只有一个可用的上游模型，配三个档只是把同一个名字抄三遍。

所以分两层：

- **默认一档（必填）**：只填一个上游模型，所有档位的请求都落到它。这是默认形态，也是绝大多数人的用法
- **可选分档**：想让人把重活派给大模型、把写标题派给小模型的人，再展开配 `haiku` / `opus` 两档

| 档位 `tier` | 客户端环境变量 | 典型任务 | 是否必填 |
|---|---|---|---|
| `default` | `ANTHROPIC_MODEL` | 全部请求的兜底，同时顶替 `sonnet` | **必填** |
| `haiku` | `ANTHROPIC_DEFAULT_HAIKU_MODEL` | 小任务、标题生成、摘要 | 可选，留空落 `default` |
| `opus` | `ANTHROPIC_DEFAULT_OPUS_MODEL` | 重活 | 可选，留空落 `default` |

**`sonnet` 档不再单独提供，被 `default` 吸收了。** 默认档的映射名定为 `claude-sonnet-5-5`（§4.6.3），这个名字本身就在 sonnet 的位置上——再给一个独立的 `sonnet` 档，两档会争同一个名字，只能靠「谁先匹配」决定，等于把复杂度转嫁给用户。而 Claude Code 主模型本来就是 sonnet，`default` 顶替它也不损失任何表达力：想改主力模型，改 `default` 那一格就是改 sonnet。三档正好对应「兜底 / 轻 / 重」。

原先设计里的 `fable` 与 `subagent` 不提供：`fable` 未配时客户端自己降级到 opus，等于多一个可以留空的行；`subagent` 不设时子代理沿用主模型。留着它们，面板上能配、日志里认、但永远没有请求走到。

解析顺序（`route.rs`）：

```
1. client_model 精确等于某个已配置档的 client_alias → 用该档（精确命中，不记回落）
2. 否则 relay_override 精确命中 client_model        → 用它
3. 否则 client_model 含档位关键词，且该档已配置      → 用该档的上游模型
4. 否则                                            → default 档（这就是「只配一个也能跑」的全部机制）
5. default 档也没配                                → 拒绝，返回可诊断错误
```

**第 4 条是本方案最重要的一行。** 早先的写法是「未命中的档位一律拒绝」，理由是「不要静默回落，否则配漏了会表现成模型答得不对」。那个理由本身没错，但它把代价算错了：拒绝意味着**只配一个模型的人，第一次生成标题就 400**，而他其实完全不需要分档。正确做法不是要求用户配四份，而是让未配置的档位由 `default` 兜住——「少配」和「配错」是两件事，前者该兜底，后者才该报错。

那么怎么区分两者？靠**日志把回落记下来**：每条请求记两列——客户端原名、实际命中的档位；发生回落时额外标一个 `fellBack: true`。用户配了 `haiku` 却发现请求都写着「回落」→ 说明 alias 抄错了，一眼能看到。这样既没让多数人多配，也没把配错藏起来。**可诊断性靠日志，不靠拒绝。**

**第 1 条必须排在最前面，这是 `claude-sonnet-5-5` 这个默认名带来的硬约束。** 默认 alias 里天然含 `sonnet`，如果关键词匹配优先，那么请求自己的 default alias 会被第 3 条按关键词判成 sonnet 档——结果虽然靠第 4 条兜回 default，但日志会记成「sonnet 档未配置已回落」，用户永远看到一条假的回落信号，§4.6.1 那套「配错 alias 一眼能看到」的诊断就废了。**精确匹配本身最便宜也最可信，没有理由排在关键词后面。**

**为什么关键词不能取消、只留精确匹配**：Claude Code 发的是带日期的模型名（`claude-sonnet-4-5-20250929`），精确匹配永远不中。第 1 条负责认出我们自己发出去的名字，第 3 条负责接住客户端自己拼的原生名——面板生成的 alias 和用户手填的原生名都含档位关键词，一套逻辑覆盖。只配一档时，这些名字全都会走到第 4 条落到 `default`，正是我们想要的。

#### 4.6.2 只让人填三个值

这是对「配置的地方太多」的直接回答，也是后续加任何字段前要先过的一道闸。

第一版设计里用户要碰约 20 个点：8 个上游控件、一张映射表、两枚接入方式大卡、交付方式切换、4 条命令、防火墙按钮、远端 `source`。这些点**单个看都有理由，合起来等于让用户先通过一场考试才能用功能**。

判据只有一条：**这个控件的答案，是不是由用户决定？**

| 类型 | 例子 | 处理 |
|---|---|---|
| 能推导 | 名称（从域名）、映射名（从档位）、监听地址（从接入方式） | **不出现**，程序算 |
| 有唯一合理默认 | 鉴权方式（`x-api-key`）、折叠（开）、端口（4100）、日志量（5000） | **不出现**，给默认值；排障时才在「高级」露出 |
| 只有一种取值 | 接口类型（P1 只有 Anthropic）、启用（单 provider） | **不出现**，等第二个取值出现时再加控件 |
| 用户确实知道答案 | 上游地址、密钥、模型名 | **出现**，且只这三个 |

所以默认形态就是三格：

```
上游地址  [https://token-plan.maas.qianwenaiapi.com]   [测连通]
密钥      [••••••••••••3f9a]                            [更换]
模型      [qwen4-max-preview]
```

三个值全在用户的上游控制台里，抄过来就完事。**判断标准：一个从没看过文档的人，能不能凭手里的东西把这三格填上。** 填不上就说明这个字段不该出现。

这条闸要长期有效，因为"多暴露一个字段"的诱惑会反复出现：

- 上游报 `max_tokens` 超限 → 想在表单里加一个「上限」输入框。**正解**是错误条上给一键「压到 8192」，用户点一次就解决，且只在真出错时才出现
- 想支持 OpenAI 兼容上游 → 想加一个「接口类型」单选。**正解**是 P3 做转换层时，用「高级」里一个下拉解决，默认永远 Anthropic
- 想让人区分多个上游 → 想加「名称」输入框。**正解**是从域名推导；真有多上游需求时（P4），名称随「添加供应商」这个动作一起出现，而不是在第一行先问一次

省下来的不只是控件，还有它们衍生的问题：每个可见字段都要有校验、有错误提示、有"填错了怎么办"的文案。三格之外的字段越多，出错时要解释的分支越多。

#### 4.6.3 映射名只显示一个

`client_alias` 用**长得像真模型名**的形态生成，不用 `relay-` 前缀。**UI 上默认只出现 `claude-sonnet-5-5` 一个名字**，放在「远端填这个名字」卡片里，带复制按钮。

改这个名字不是为了好看，是为了**省掉一次改写**：客户端本来就按 `claude-sonnet-*` 的形态发请求，default 的别名也长成这样，两边对得上——用户不必理解「我的模型被换了个名字」，日志里客户端原名和实际路由也不会显得像两套系统。而 `relay-default` 这种名字一看就是人造的，会让人以为还要再对应一层。

原先的设计是一张「档位 / 上游模型 / 映射名」三列表格，`default` 行还带一个上游模型输入框——但那个值和左边「模型」格是同一个，等于让人填两遍。现在：

- `default` 档的上游模型：只在左边「模型」填一次
- 右侧只显示结果（`claude-sonnet-5-5`）+ 一句话说明「上游叫什么、以后换成什么，它都不变」
- 分档是折叠项，展开才出现 `haiku` / `opus` 两行（`sonnet` 已并入 `default`）

「档位命中」三条横条也**只在展开分档后才显示**。原因是只配一档时那三条里两条是灰的（表示回落），视觉上等于「你的配置有问题」——而实际上那正是正确状态。未分档时换一句话：「现在只有一个模型，全部档位的请求都走它」。这条比横条更准确，也不会被误读。

生成规则：

| 档位 | 映射名 | 说明 |
|---|---|---|
| `default` | `claude-sonnet-5-5` | 固定值，不从上游名派生 |
| `haiku` | `claude-haiku-5-5` | 同上，固定后缀 `-5-5` |
| `opus` | `claude-opus-5-5` | 同上 |

`client_alias` 由面板生成，要求四条：

1. **短、可读、能手抄**——默认手工配置，用户要把它粘进远端文件，`claude-sonnet-5-5` 这种长度合适，不要生成带随机后缀的名字
2. **绝不拼上游真名**。这是改名为拟真形态后必须守住的底线：上游叫 `qwen4-max-preview`，alias 仍是 `claude-sonnet-5-5`。一旦把上游名拼进去（`claude-sonnet-distill`），既暴露了上游、又会让关键词匹配多出一种误判来源。**alias 只由档位决定，与上游完全解耦**，这条没有例外
3. **关键词冲突靠解析顺序解决，不靠改名回避**。`claude-sonnet-5-5` 含 `sonnet`，所以 §4.6.1 第 1 条「alias 精确匹配优先」不能省——它是这个命名的配套前提，不是可选优化
4. **一旦定下别轻易改**。托管会话会自动跟上，但手工配置的远端不会，改了就得让人重新复制一次配置。这个代价要写在界面上，别让用户自己发现

### 4.7 对话页自动接上

`LaunchSpec` 增加 `env: Vec<(String, String)>`：

- 本机会话：spawn 时 `.envs()`
- 远端会话：`remote_command` 脚本里 `export`（位置现成）

注入规则：**两个基础变量一定注入，档位变量只注入「已配置」的那几个**。

默认（只配一档）就是三个：

```bash
export ANTHROPIC_BASE_URL='http://127.0.0.1:4100'
export ANTHROPIC_AUTH_TOKEN='<中转 token>'
export ANTHROPIC_MODEL='<default 档别名>'
```

用户展开配了 `haiku` / `opus` 时，才对应追加：

```bash
export ANTHROPIC_DEFAULT_HAIKU_MODEL='<haiku 档别名>'   # 仅当该档已配置
export ANTHROPIC_DEFAULT_OPUS_MODEL='<opus 档别名>'     # 仅当该档已配置
```

**未配置的档位一概不注入，不要给它注入一个指向 default 别名的值。** 不注入时客户端会用自己的原生模型名（`claude-3-5-haiku-…`）去请求，中转按 §4.6.1 第 3 条识别出档位、发现没配，落回 `default`——一条路径、一个解释。反过来给它注入 default 的别名，表面上也是落 default，但日志里会显示「命中 default 档」而不是「haiku 档未配置已回落」，用户配错 alias 时就看不出来了。

**`ANTHROPIC_DEFAULT_SONNET_MODEL` 专门不注入。** `sonnet` 档已被 `default` 吸收（§4.6.1），客户端发的 sonnet 请求会带着原生名进来，按关键词走到「该档未配置 → 落 default」，落到 `claude-sonnet-5-5` 上——名字和档位在对的地方，不需要多注入一行。真要注入，反而会在日志里把每个 sonnet 请求记成「命中 default 档」，把这条判断链藏起来。

也就是说：**注入变量数 = 2 + 已配置档位数**，默认 3 个，三档全配 5 个。这个数字不稳定是特性，不是缺陷。

这段 `export` 是**程序内部注入**（本机 `spawn` 的 `.envs()`、远端 `remote_command` 的前置脚本），
不是给用户复制的交付物。给用户看的只有 §4.8.3 那份 settings 文件。两者不冲突：托管会话由程序管环境，
独立的 `claude` 由配置文件管，互不干扰。

**`BASE_URL` 按会话位置与接入模式取值，不能写死**（这是最容易埋错的一行）：

| 会话位置 | 隧道模式 | 内网直连模式 |
|---|---|---|
| 本机 | `http://127.0.0.1:4100` | `http://127.0.0.1:4100` |
| 远端 | `http://127.0.0.1:4100`（隧道已把该端口映射回本机） | `http://<本机内网IP>:4100` |

远端 + 隧道模式下用 `127.0.0.1` 是**对的**：那条路走的是远端自己的回环地址，由隧道转发回本机。实现时若图省事直接拼内网 IP，隧道模式反而会失败。

对话页顶部给「走中转 / 走原生」切换，默认跟随全局开关。**全局开关（§4.9.1）关着时这个切换不显示**——否则会出现「会话按中转配好了，但服务根本没起」这种只有报错才知道的状态。托管会话的模型名只在面板定义一处；手工配置的远端要粘一次（见 §4.8.3），改了映射名就得让人重新复制。

### 4.8 远端独立 Claude Code 的接入（自建场景：中转在自己电脑）

这一节的前提必须先写清，后面所有取舍都由它决定：

- 中转跑在**我自己这台电脑**的 cc-bridge 里，服务**我自己的**远端机器。不是团队共享入口，不做按人发 token，不做日额度闸门。
- 每个人的上游、密钥、模型档位都不一样，所以**任何一处都不能预设默认值**：首次进入是空表单，不是填好的千问模板。文案里也不许出现"默认走某某模型"。
- 远端可能是公司内网的 Linux，也可能是公网云主机。所以两条接入路都得有，且都得当一等公民，不能把一条写成"临时调试"。

| | 隧道模式 | 内网直连模式 |
|---|---|---|
| 中转监听 | `127.0.0.1:4100` | `<本机某张网卡的 IP>:4100` |
| 远端 `ANTHROPIC_BASE_URL` | `http://127.0.0.1:4100` | `http://<本机网卡IP>:4100` |
| 依赖 | 该连接已建立 SSH 会话 | 两端在同一网段 / VPN |
| 传输 | SSH 加密，证书级主机认证 | 明文 HTTP，token 过网线 |
| 端口可达性 | 同网段扫不到 | 同网段可探测（具体网卡范围内） |
| 适合 | 跨网络、公网远端、长期使用 | 同一内网 / VPN、隧道建不起来时 |

两种模式界面都给，**默认选隧道并排在第一**，切到内网直连要过一次确认弹窗。理由不是习惯偏好：隧道对远端只有一个前提——那条 SSH 连接在线；内网直连要额外满足防火墙已放行、网段可达、本机 IP 不变三件事，失败面明显更大。

**监听绑具体网卡 IP，不绑 `0.0.0.0`**。`0.0.0.0` 会把 VirtualBox / Hyper-V 那些虚拟网卡一并暴露（本机就存在 `192.168.56.1` 这类），实际暴露面比用户以为的大。代价是 DHCP 换 IP 后监听失效——这件事已经有现成机制：`TrayTip IP_CHANGED` 会报新地址，中转跟着提示用户重启监听即可，不需要额外造检测。多网卡时用 `network.rs` 探测 + 手动指定兜底（已知坑：`fix: 修复多网卡 IP 选错`）。

#### 4.8.1 隧道模式

- 「接入指引」卡片一键创建 `ForwardKind::Remote` 规则（本地 `127.0.0.1:4100` → 远端 `127.0.0.1:4100`）
- 隧道断开时远端会立刻失败，界面要能把「隧道未连」和「上游报错」区分开——这两种错误在远端长得一样
- 隧道模式下远端 `ANTHROPIC_BASE_URL` 填 `127.0.0.1` 是对的：那走的是远端自己的回环，由隧道转回本机。填内网 IP 反而失败。这条要写进指引，否则十个人有九个会填错

#### 4.8.2 内网直连模式

不是把 bind 地址换掉就完事，必须同时满足四条。单人自建也一样——防的是同网段邻居蹭你的额度，不是防同事：

1. **token 不可为空**：这个模式下配置里没有 token 就拒绝启动，不允许「空 token 也能通」
2. **401 封禁**：复用现有 `mcp/http.rs` 的 `remote_ban` 策略（连续错误 N 次后连正确 token 也拦）。自建场景只有一个 token，按 IP 封不存在"误伤自己人"，直接复用，不另造一套
3. **限流**：复用现有 `rate_limit_max_requests` / `rate_limit_window_ms`，按来源 IP 计
4. **来源可见**：请求日志记录来源 IP，界面在页头把徽章切成橙色并显示「对内网开放 · 10.0.19.194:4100」的实际地址（直连时不能只靠一行说明文字提醒）

地址一律给人能连的形态：不要把 `0.0.0.0` 当地址给用户抄，那不是能连的地址。

还有一件容易被忽略的事：**Windows 上端口要放行才有用**。复用现有 `firewall.rs` / `firewall_diag.rs` 的检测与提示，不要另写一套「请手动加规则」的文案——加规则需要管理员权限，用户照抄也加不上时，界面得给可执行的下一步（提权按钮或明确指引），否则表现为「配置都对，远端连不上」。

**明文这件事要写在界面上**：内网直连时 token 是明文过网线的，同网段抓包可见。这是默认推荐隧道的技术理由，不是习惯偏好。

#### 4.8.3 远端怎么配：一份 settings 文件，默认手工

**不再提供「复制一串 export 粘到 shell」这种交付物**。两个原因：export 只在当前终端有效，关一次窗就没了；而且它会把远端所有会话都改走中转，连本来该用订阅额度的那些也一起劫持。

改为一份**与原生 `claude` 并存**的配置文件。远端照常 `claude` 走订阅额度，另起一个入口走中转，两者互不影响，随时能退回去：

```bash
mkdir -p ~/.claude
cat > ~/.claude/own-model.json <<'EOF'
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://<地址>:4100",
    "ANTHROPIC_AUTH_TOKEN": "<token>",
    "ANTHROPIC_MODEL": "<default 档别名>"
  }
}
EOF
echo "alias claude-own='claude --settings \"\$HOME/.claude/own-model.json\"'" >> ~/.bashrc
source ~/.bashrc
```

**默认就这三行，只有一个模型映射。** 用户不需要为「Claude Code 会切档」这件事做任何准备——`haiku` / `sonnet` / `opus` 的请求到了中转会被 `default` 兜住（§4.6.1 第 4 条）。这一点必须写进指引，否则用户看到别人的配置文件里有一堆 `ANTHROPIC_DEFAULT_*` 就会以为自己也缺了什么东西，然后开始抄自己不懂的行。

只有明确配了分档的人，文件里才多出对应行：

```json
    "ANTHROPIC_DEFAULT_HAIKU_MODEL": "<haiku 档别名>",
    "ANTHROPIC_DEFAULT_OPUS_MODEL": "<opus 档别名>"
```

**没有 `ANTHROPIC_DEFAULT_SONNET_MODEL` 这一行，永远不加。** `sonnet` 已被 `default` 吸收，`ANTHROPIC_MODEL` 那一行就是它（§4.6.1）。写两行指向同一个别名，等于让人以为配漏了一个档。

**无论几个档，值都填映射名，不填上游真名。** 文件里出现的只能是面板生成的 `claude-*-5-5`，上游叫什么（`qwen4-max-preview` 还是别的）一个都不许写进去。这是「远端不用返工」的唯一保障：换上游、换模型、换供应商时只改面板，远端这份文件一个字都不用动。实现时别图省事把上游名直接写进去——那样每换一次上游就要挨台机器改文件。

分档是**后来想起来才加的**功能，所以加档时必然要改这份文件。这时只有一条要注意：**新加的行必须是已配好的档位**，别把面板上留空的行也抄进去——留空档位注入一个指向 `default` 的别名，会让日志里失去「该档未配置已回落」这个信息（§4.7）。

三个照做才能用的细节（不照做会返工，且现象都不指向原因）：

1. **heredoc 用 `<<'EOF'` 带单引号**，否则 `$HOME` 之类会被本地 shell 提前展开
2. **alias 里保留字面的 `$HOME`**，不能写成展开后的绝对路径。否则换台机器就指向不存在的目录，表现是「启动后仍是 Claude，而且没有任何警告」
3. **不要 `chmod 600`**。这文件是用户自己读，正常 umask 出来的 644 就够；600 在换用户、换机器、被服务化进程读取时会读不到，而且报错只说「读配置失败」

**`alias claude-own` 这一步是推荐做法，不是可选的装饰。** 不给 alias，就得每次手打 `claude --settings ~/.claude/own-model.json`；实际用不了几天就会嫌麻烦，然后有人开始 `export`、或者干脆去改全局 `settings.json`——那两条路都会把「与订阅额度并存」这个前提破坏掉，而这恰恰是整份远端配置唯一的价值。

写了 alias 之后：日常就一个词 `claude-own`，`claude-own -c` 接着上次会话，`claude-own -r` 从历史里挑；要回到订阅额度就用 `claude`。两个入口互不影响，谁也不会踩到谁。所以指引里默认就带这一步，不要写成「可选：你也可以加个别名」那种口吻——写成可选，用户就会跳过，跳过就等于没配。

面板负责把 `<地址>` / `<token>` / `<档位别名>` 替换成实际值，其余一字不差。交出的是**一个整体可复制的代码块**，不是三五个能漏掉一个的变量——这是去掉 export 之后反而变简单的地方。

**默认手工，自动是并排的第二个动作**：

- **默认手工**：主按钮「复制整块配置」，用户自己粘。远端环境差异太大——shell 是 bash 还是 zsh、家目录有没有被接管、有没有 sudo 限制——自动写容易踩别人的环境，出问题还难解释
- **自动写入**：次要按钮「或直接写进远端」，由 cc-bridge 经已建立的 SSH 会话写入。**不要做成「手工 / 自动」的模式切换**：那不是两种模式，是「复制」和「帮我写」两个动作，切换器会让人以为选错了要付出代价。做成并排按钮后，想自动的人直接点，想手工的人直接复制，谁都不用先理解「模式」这个词

自动写入要做对四件事：
1. 写前**备份**已有 `own-model.json`（用户可能自己改过）
2. 文件模式**沿用目标已有模式**，不主动 chmod，也不改属主
3. `.bashrc` 追加**必须幂等**——已有同一行就跳过。否则点一次多一行，反复点到 `.bashrc` 里堆十几条一样的 alias
4. 目标 shell 是 zsh 时写 `~/.zshrc`，不是 `~/.bashrc`。写完要提示「新开终端或 `source` 才生效」，因为当前会话不会自动重载

**卸载也要给**：删掉 `.bashrc` 里那一行 alias 即可，配置文件留着不影响任何东西。用户第一次配就会问「不想用了怎么退」，这是个必答项不是加分项。

### 4.9 UI 落点：主界面顶级 tab + 设置里的开关

现有工作区 5 项（连接 / 终端 / 安全 / 日志 / 对话），中转作为**第 6 项追加在末尾**。它默认不存在——开关在「设置 › 网络与接入」第一行，默认关闭。

**为什么从设置页挪上来**：设置页的阅读卡再宽也只有 1056，而这一页内容不少（服务状态、上游、映射、接入、日志），塞进去等于把设置页拉长一倍；而且它和「端口 / HTTPS」不同轴，是常驻服务的运行态。放到主界面宽度够了，也能一眼看到服务在跑没有。

#### 4.9.1 开关的语义：一个管两件事

左侧是否出现这一页 **＋** 中转服务是否监听。不拆成两个：

| 拆开会出现的状态 | 为什么不行 |
|---|---|
| 服务在跑但页面看不见 | 用户没法从界面确认它在跑，只能去翻日志 |
| 页面在但没有服务 | 所有请求直接失败，得像排查故障一样查原因 |

自建单人场景不需要这两种组合。所以**页面内不放总开关**——页里的「停止中转 / 重启」是服务动作（与连接页顶部那颗启停按钮同性质），真正的总开关只有设置里那一个。两处总开关必然打架。

开关放在「设置 › 网络与接入」第一行，默认关闭，**描述里必须写清「开启后左侧出现中转页」**（默认关闭＝功能不可发现，详见 §4.9.4）。设置页这一块**只有这一行**，不再有端口 / token / 日志量。

#### 4.9.2 布局：借连接页的样式与卡片几何，内容按中转重写

先纠正一个判断错误。前一版把「卡片多」等同于「要填的多」，于是把状态卡、指标卡全砍了，只留两栏表单。**这个等式不成立**：卡片是只读的，加四张不会让用户多填一个字段；接触点（真正要人回答的控件）仍然只有 6 个。两件事要分开算。

而且中转不是一次性配完就走的功能。它是个常驻服务，用户会反复回来确认「还在不在跑、今天走了多少、上游有没有报错」——这跟连接页的处境一样，所以它同样需要一块看板。把它做成纯配置页，等于每次想知道状态都得去翻日志页。

| ⑤ 接入（全宽） | 分段切换 → 前置条件 → 全宽代码块 → 两个动作按钮 | `.stable-method-toggle`＋`.connect-main-code` |
| ⑥ 请求日志<br>（`1/9` · 8 列） | 时间 / 来源 / 档位 / 上游模型 / 改写 / 状态 / 首字（7 列）＋「打开日志页」 | `Table` / `LogRow` 的 `th h-10`、`td px-3 py-2.5` |
| ⑦ 档位分布<br>（`9/13` · 4 列） | default / haiku / opus 三条命中 ＋ 一句「灰色 = 回落」 | `.hits` 横条 |

**四个指标之所以是这四个**：全部能由现有日志字段算出来（时间 / 来源 / 档位 / 改写 / 状态 / 首字），**没有一个是为了撑版面编的**。`token` 用量要额外解析上游 `usage` 字段，留到 P1 之后；档位分布从映射名卡里搬出来独立成卡，因为它回答的是运行数据、不是配置。

**页头摘要同步精简**：原来那行「今日 1,284 次 · 折叠 37 次 · 首字 412ms」现在全在卡片里，页头只留「上游 qianwenaiapi · 已连通 182ms / 最近错误 1 次」，否则同一组数字在一屏里出现两次。

4 列宽带来的两个必须遵守的细节：

- **表单改成标签在上、控件占满整行**（`pathrows stacked`）。4 列宽按「标签左 / 控件右」排，输入框只剩不到 200px，`https://token-plan.maas.qianwenaiapi.com` 和密钥掩码都会被截断——这是稿上实测出来的
- **接入区块要在卡里，不要再用 `primary/.045` 淡底整块**。白卡里再套一层淡紫等于卡中卡，代码块自己已经有 `--glass-inset` 底色

必须在稿上保留的几条：

- **地址文案不能写「仅本机可访问」**。隧道模式监听的确是回环，但远端经隧道照样能访问，写「仅本机」会让人以为远端连不上。正确说法是「不对内网暴露」——说的是暴露面，不是访问来源
- **接入方式用分段切换**（`隧道连接` 带「推荐」小徽章 / `IP 直连`），不是两枚并排大卡。切到直连时三处联动：`BASE_URL` 那行变内网 IP、前置条件换成橙色警告（同网段可探测、token 走明文、防火墙放行 4100）、页头徽章转橙「对内网开放」。只变一处会让人以为还在隧道里
- **模型三项就是全部必填**：上游地址、密钥、模型
- **映射名只有一个可复制的大号名字**。不做「档位 / 上游模型 / 映射名」三列表格（`default` 行的上游模型和左边「模型」是同一个值，等于让人填两遍）
- **档位命中只在展开分档后出现**：未分档时不显示三条灰条——只配一档时全灰，第一眼会被读成「我配错了」。展开后灰色 = 该档未配置、请求落到 default；**配了 haiku 却全是灰的，说明远端那份文件里的映射名抄错了**
- **两种模式产出同一份 settings 文件**，差别只在 `BASE_URL` 那一行。**不做「手工 / 自动」模式切换**，是两个并排动作：「复制整块」（主）与「直接写进远端」（次）
- **代码块必须全宽**：`echo "alias claude-own='claude --settings …'"` 这一行在窄栏里会被横向截断，而它恰好是最容易抄错的一行。注释要写成「先备份原文件，之前配过也没关系」——否则用户会担心覆盖掉自己已有的配置
- **日志内嵌最近 5 条 + 「打开日志页」跳转**。完整回溯仍归日志页（那里已有筛选与详情面板，不重造）

**关闭态也用同一套卡片**，不要退回一张居中占位卡：状态卡换 `--stopped` 灰渐变、标题「未在监听」、按钮换成「重新打开中转」；四张指标一律 `—`（显示 0 会让人以为在跑但没流量）；上游卡与映射名卡保留可编辑，标「待生效」。底部一张全宽「怎么开回来」三步。配置都还在，这才符合「重新打开不用再填一遍」。

#### 4.9.2.1 空状态即引导

首次开启开关后，用户面对的是三格空表单。不要做成「空白 + 若干空字段让你自己猜」，而是：

- 页头的运行中徽章此时换成中性态（不绿），说明那行改成「还没配上游：Claude Code 的请求先到这里，再由这里送到上游模型」——把「这一页是干什么的」放在第一落点
- **状态主卡的 headline 换成「未配置上游」**，链路第三段显示灰色「未设置」，四张指标一律 `—`（此时没有任何请求，显示 0 是假的）。这一屏只有三格表单是「活」的，视觉上自然把视线引过去
- 三格里的第一格（上游地址）默认聚焦
- 三格之外的说明写一句「三个值都在你的上游控制台里，别的不用管」——明确告诉他不需要准备别的
- 保存成功后，映射名卡与下方代码块才从「待填写」变成可用状态（未填时复制按钮禁用，点了提示先填模型），状态卡的 headline 换成上游模型名

这一条的意义在于：**默认关闭的功能，第一次打开的那十秒决定了用户会不会用下去。** 一个空表单配六个字段会让人直接关掉；三个空字段加一句「别的不用管」才留得住。

#### 4.9.3 导航注册：5 处联动，其中 3 处会直接出错

一个默认隐藏的 tab 不只是「渲染时 if 一下」：

| # | 位置 | 现状 | 不处理的后果 |
|---|---|---|---|
| 1 | `SideNav.tsx:23` 的 `WORKSPACE_NAV` | 静态数组，被 `App.tsx:19` 与 `CommandPalette.tsx:14` 两处直接引用 | 关闭后侧栏与命令面板仍然显示「中转」 |
| 2 | `App.tsx:321` 的 Ctrl 数字键 | `e.key <= String(WORKSPACE_NAV.length)` 用数组长度做边界 | 关闭后按 `Ctrl+6` 导航到不存在的页，直接白屏 |
| 3 | `App.tsx:295` 的 `lastWorkspaceTabRef` | 记录离开设置前的工作区页 | 在设置里关掉后点「返回工作区」，回到已经被移除的页 |
| 4 | 命令面板 | 由同一数组生成「前往：X 页」 | 关闭时仍能搜到并跳过去 |
| 5 | 冷启动 | 开关状态是异步读的 | 先按默认值渲染再改，闪一下又消失 |

统一处理：

- **导航数组改成由 App 按开关算出可见项，再传给侧栏与命令面板**，两边不再各自引用常量
- 快捷键边界按**可见项**算，不按数组长度
- 冷启动初值用 `undefined` 表示「还没读到」，未知一律按不可见处理——**晚半秒出现可以，闪一下不行**

#### 4.9.4 交互约定

| 动作 | 行为 |
|---|---|
| 开启 | 立即建监听 → 左侧出现「中转」→ **自动跳到该页**（刚打开就是为了配它） |
| 关闭 | 二次确认，文案点明「远端已配好的 `claude-own` 会立刻连不上，进行中的请求会断」→ 停服务 → 移除导航 → **跳回关闭前的那个工作区页** |
| 关闭时渲染 | 不要 keepMounted：整页卸载，顺便停掉日志轮询。开着时也不该在后台空转 |
| 命名 | tab 叫「中转」（两个字，与其他项字数一致），页标题写「模型中转」，图标用现有的 `gitBranch` |
| 快捷键 | `Ctrl+6`。新项追加在数组末尾，`Ctrl+1~5` 完全不变（代码注释本来就规定新项只能追加末尾） |

**可发现性要提前认账**：默认关闭意味着没人知道有这功能，唯一入口是设置里那一行，所以它的描述必须写清「开启后左侧出现「中转」页」，让人知道会多出什么。首次启动的引导提示先不加。

**默认路径的接触点必须 ≤ 6 个**，这条作为验收项而不是愿望：① 设置里那一个开关 ② 上游地址 ③ 密钥 ④ 模型 ⑤ 复制整块 ⑥ 远端粘一次。任何新加的可交互控件都要先回答「它属于 §4.6.2 的哪一类」，答「用户确实知道答案」才能进默认视图，否则进「高级」。加完控件再回数一遍，超过 6 就是设计退化了。

#### 4.9.5 柔光玻璃主题：组件不感知主题，CSS 属性选择器兜住

设置 › 外观里有第二套界面风格（`appearance: "classic" | "glass"`，UI 上叫「柔光玻璃」），挂在 `<html data-ui-style="glass">` 上。中转页必须一开始就适配，否则切换主题会露出实色卡，跟连接页并排站着像两套应用。

**先把一个误解消掉：这套主题不是 `backdrop-filter` 毛玻璃。** `appearance.css:48` 原话是 *"Soft gradients already contain blurred color: cards need no live blur layer"* —— 卡片是「半透明渐变 + 定向投影」的叠层，全项目只有弹层真用 blur（`252-257`：menu / listbox / dialog / toast）。给 `.bento-card` 加 `backdrop-filter` 不会更像玻璃，只会在滚动时反复重算模糊。

由此推出三条必须照做的事实：

**1. 半透明卡只有在「背后有颜色」时才成玻璃。** 玻璃卡的 `--glass-panel` 是 64%→30% 的白渐变，背后那层是应用根容器 `.app-boot-fade`（`App.tsx:397`）的三色径向光晕（`appearance.css:49-63`），不是实色底。换成 #f5f7fa 之类的纯色，64% 白叠上去只会得到一片死白。所以这一步是配套的：**换面料必须同时换画布光晕**。顺带 `.app-side` / `.app-topbar` 在玻璃下背景与边框全部透明（`66-71`），让同一块背景透上来，不要给侧栏单独染色。

**2. 状态大卡在玻璃下是另一套面料，卡里所有白色层级全部失效。** classic 是 `linear-gradient(160deg, primary, primary/.72)` + 白字；玻璃换成 `--glass-status-panel`（淡蓝 182,211,240 → 淡紫 193,188,232）+ `--glass-status-ink`（#1b2948 深藏青）。这意味着 `.status-eyebrow` / `.status-sub` / `.chain-seg` / `.status-headline code` / `.status-target` / `.status-local` / `.mini-act` / `.mini-act-row` 里每一处 `rgba(255,255,255,*)` 都要换，**漏一条就是白字压白底**。稿里已逐条换成 ink / muted 两档。

这也是为什么 `mini-act-row` 里那个 429 **必须从内联 `style="color:#fecaca"` 改成类**：内联样式优先级高于任何选择器，玻璃下浅底上根本看不见，主题也覆盖不了。

**3. 关闭态要新增一档中性变体 —— 这是本方案唯一一处刻意偏离现有实现。** 真实代码里 live 与 stopped 共用同一块面料（`appearance.css:139` 的 `:is(.status-card--live, .status-card--stopped)`），在 classic 的深紫 / 灰蓝两色下没问题；但玻璃下两者都会变成同一块淡蓝紫，而「停没停」是这一页最该一眼看出的信息。所以给 stopped 加一档去饱和的中性灰蓝（`rgb(206 215 227) → rgb(193 199 213)`，深色对应 `66 77 96 → 55 62 78`），字色仍用 ink，对比不变。**实现时要新增这条，不能只照抄 appearance.css。**

另一处偏离更小：真实实现给状态卡的两个按钮都用了 `--glass-inset`，主次会不分。稿里让主动作走 `--glass-floating`（近实白）、次要动作走 `--glass-inset`，保住「实 vs 虚」的层级。

**实现方式：组件里不要出现任何主题分支。** 不写 `appearance === "glass" ? … : …`，也不加条件 className。所有差异都写在 `appearance.css` 里以 `html[data-ui-style="glass"]` 开头，组件只挂语义类名。这条不是洁癖——`appearance.css` 从第一天就是这么长的（注释里反复写「classic 主题零变化」），加一处 JS 分支，后面每加一个主题就要动一次组件。

这页需要 glass 覆盖的选择器，按面料归类：

| 面料 | 选择器 | 覆盖成 |
|---|---|---|
| 面板（可透） | `.bento-card` `.metric-card` | `--glass-panel` + `--glass-edge` + `--glass-depth`，**hover 保持同一投影**（别退回 `--sh-card`） |
| 状态卡 | `.status-card` | `--glass-status-panel` + ink；`--glass-depth` 前置一条 `inset 0 0 0 1px var(--glass-edge)` 保几何 |
| 近实底（不能透） | `.tinp` `.maskrow code` `.connect-main-code` `.prereq` `.alias-box` | `--glass-inset` + `--glass-chrome-edge` 边 |
| 数据面 | `table.log thead th` | `--glass-data-header`。**表头必须不透明**——实现时 thead 是 sticky 的，半透明底会让滚上来的行透出来 |
| 控件 | `.stable-method-toggle` 选中块、`.sw:not(.on)` | 选中块改 `--glass-floating`（`primary/.09` 在蓝白底上会混成脏紫）；关态开关改 `--glass-switch-off` + 内描边 |
| 语义色补偿 | `.metric-card.tone-ok/.tone-warn` | 浅色下 `color-mix(… 88%/92%, black)`，同 `appearance.css:544-553` 的判据；深色不套 |

**回退两条不能省**：`prefers-reduced-transparency: reduce` 时全部面料退回 `hsl(var(--card))`（否则系统开了减少透明度，这页仍然半透）；`forced-colors: active` 时退回 `Canvas` / `CanvasText`。

验收加一条：**切换 经典 / 柔光玻璃 时页面结构不能变**——卡片位置、行列跨度、文字换行位置都应一致，只允许面料与状态卡字色变化。这条能一次性抓出「把主题差异写进布局」的错误。

### 4.10 安全约束

1. 默认只听 `127.0.0.1`；切内网直连要二次确认。该模式下 token 必须非空——token 由开启时自动生成（`rly_` + 随机），UI 不给清空入口，所以这条天然满足；实现上仍要在监听前断言一次，不依赖"UI 没给入口"这种间接保证
2. 中转 token 与 MCP token **分开**，避免一串两用
3. 内网直连时，令牌校验、限流、401 封禁三件必须同时生效——只开监听不加约束等于公开额度
4. 请求日志默认只记元数据；记 body 需显式开调试开关，并标注体积风险（那 937KB 的日志就是教训）
5. 日志与错误信息里密钥一律打码
6. 内网直连是明文 HTTP，界面必须写明这一点；不做「悄悄降级」
7. **浏览器来源一律拒绝**，无关于监听范围。`127.0.0.1:4100` 这个端口**任何网页都能访问**，
   这是回环地址不等于安全边界的典型：恶意页面可以用 no-cors POST 打请求、用 WebSocket
   探测端口、或用 DNS rebinding 把域名的解析结果换成本机回环。判定条件：带 `Origin` 头、
   `Sec-Fetch-Site` 不是 `none`、或 `Upgrade` 头存在，三者任一即拒（Claude Code 这类 CLI
   客户端不会发这些）。这条在内网直连模式下同样生效。
8. **`Host` 头白名单**，防 DNS rebinding 的第二道闸：只接受配置里的监听地址、`127.0.0.1`、
   `localhost`、`[::1]` 四种形态，其余 421。攻击方式是把 `evil.com` 的 A 记录指到 127.0.0.1，
   此时浏览器仍认为在访问 evil.com——`Origin` 与 `Host` 校验合起来才挡得住。
9. **自转发防护**：provider 的 `base_url` 若是中转自己（本地回环 + 本端口，或本机内网 IP +
   本端口），保存时就拒绝并说明原因。否则一次请求会自己调自己，瞬间打满线程栈。
10. **响应体上限边收边判**：设总上限（默认 64MB），**每收到一个 chunk 就累加判断，超了立刻断流**，
    而不是收完再比——否则超大 body 仍然完整进了内存，限制形同虚设。这个上限只约束非流式的
    兜底路径，SSE 是边收边转发，不攒全量。
11. **入站鉴权两种头都认**：`Authorization: Bearer <token>` 与 `x-api-key: <token>` 等价。
    Claude Code 配 `ANTHROPIC_AUTH_TOKEN` 时发前者，配 `ANTHROPIC_API_KEY` 时发后者；只认一种会让
    照着别人教程配的用户收到 401，而 401 与「token 填错」在表面上完全一样，排查会绕远路。
12. **写远端配置文件时不动属主与模式**：模式沿用目标已有值，覆盖前备份（详见 §4.8.3）。
    主动 `chmod 600` 会让后续换用户/换机器读取失败，且报错只说「读配置失败」。

### 4.11 实现细节清单（P1 必查，都是踩过一次会花半天的问题）

| 项 | 要求 | 不做的后果 |
|---|---|---|
| Body 上限 | 调到 32MB（axum 默认 2MB） | Claude Code 的大 payload 实测到过 937KB 量级，加历史与工具定义很容易破 2MB，表现为 413 或「请求体截断」 |
| IPv6 监听地址 | 拼接必须带方括号 `[::1]:4100` | 拼成 `::1:4100` 直接 bind 失败，错误信息还看不出原因 |
| Windows 端口复用 | 监听 socket 不可继承；重启前先等旧 socket 释放，或复用 `axum-server` 的 graceful shutdown | 重启必报 `10048 Address already in use`，而且旧进程可能已经不在任务管理器里 |
| 启动幂等 | 已在运行时再次「启动」返回 409 + 当前地址，不要起第二个监听 | 两次点击 → 两个实例抢同一端口，日志交错 |
| 优雅停止 | 5 秒超时，超时后强制 | 停在流式响应上时关不掉窗口 |
| 绑定失败文案 | 端口被占 → 指出占用进程与建议端口，不吞错误 | 用户只看到「启动失败」 |
| header 值透传 | 头**名**大小写不做保真（reqwest 会规范化），但 `anthropic-beta` / `anthropic-version` 的**值**必须原样 | beta 特性静默失效，表现为「某些功能上游不认识」 |
| 日志时间基准 | 用 UTC 存、界面按本地时区显示 | 跨时区排查时反复算错 |

导航注册那一组（一个默认隐藏的 tab 会牵动的地方，§4.9.3 有完整说明）：

| 项 | 要求 | 不做的后果 |
|---|---|---|
| 导航数组唯一来源 | 由 App 按开关算出可见项，传给 `SideNav` 与 `CommandPalette`，两边不再引用 `WORKSPACE_NAV` 常量 | 关闭后侧栏没了、命令面板还能搜到并跳过去 |
| Ctrl 数字键边界 | 按**可见项数**算，不按常量长度 | 关闭后 `Ctrl+6` 导航到不存在的页，白屏 |
| 关闭时的页面兜底 | 关闭前记下当前页；若正停在中转页则跳回那个页 | 界面停在一个已卸载的页上，只剩空壳 |
| 冷启动初值 | 开关状态用 `undefined` 表示未读到，未知按**不可见**处理 | 先出现再消失，闪一下让人以为点错了 |
| 不要 keepMounted | 关闭即卸载整页 | 日志轮询在后台常驻，关了还在请求 |
| `hidden` 与 `display:flex` 冲突 | 折叠项不要只加 `hidden` 属性；若父级类有 `display:flex`（如 `.nav-item`），加 `[hidden]{display:none!important}` 兜底，或直接条件渲染 | 「关闭态」的项仍然显示，看起来像开关没生效 |
| 折叠项的状态归属 | 高级 / 分档 / 直连确认区的展开状态**只存在组件里**，不落盘、不跨会话记忆 | 上次展开过、下次进来还是展开的，页面一进来就是一屏表单 |
| `hidden` 与 `display` | 用条件渲染，不要只加 `hidden` 属性 | `.nav-item{display:flex}` 会覆盖 `[hidden]` 的 `display:none`，项还在那（设计稿里踩过） |

### P0：准备 —— ✅ 已完成（2026-11-23）

**结论：体积代价 ≈ 0，不必改用 `hyper-util`。**

原计划是「`reqwest` 转正后实测体积」，实测推翻了这条路径的两个假设：

1. **`reqwest` 早就在正式依赖树里**。`tauri-plugin-updater 2.14.1` 依赖 `reqwest 0.13.5`，
   它本来就链接进 exe。而 `dev-dependencies` 里那条 `0.12` 只服务集成测试、不进 release
   构建——**照原计划「把 dev-deps 的 reqwest 转正」会同时链接两份 reqwest**，体积翻倍且
   零收益。所以最终声明的是 `reqwest = "0.13"`，与 updater 复用同一份编译单元。
2. **0.13 的 feature 名与 0.12 完全不同**：`rustls-tls` / `rustls-tls-manual-roots` 都不存在了，
   取而代之是 `rustls`（aws-lc-rs + platform-verifier）和 `rustls-no-provider`。updater 开的是
   `rustls-no-provider` + `rustls-platform-verifier`，**系统根证书被信任**——原文担心的
   「只用 webpki roots 会不认 Clash MITM CA」在这条链上不存在。

实测数字（`cargo build --release`，同一 target 目录增量构建）：

| | 基线（无 relay 模块） | 加 reqwest 声明 + 流式转发代码 | 增量 |
|---|---|---|---|
| exe | 27,454,464 B（26.18 MiB） | 28,332,544 B（27.02 MiB） | **+878,080 B（+857.5 KiB）** |
| 安装包（按 0.46 压缩比估算） | 12.03 MB | ≈ 12.42 MB | +0.39 MB |

增量拆开看：

| 组成 | 体积 | 说明 |
|---|---|---|
| reqwest 本体（流式转发代码路径） | **+26 KiB** | 复用 updater 那份 0.13，几乎不花额外成本 |
| rustls crypto provider（aws-lc-rs） | **+831 KiB** | 唯一的大头，见下面的取舍 |

**红线 20MB，实测安装包约 12.42MB，余量 7.5MB —— 不必换 `hyper-util`。**

**为什么必须写一段真实代码才能测准**：只加 `Cargo.toml` 声明、代码里不引用，linker 会把
未实例化的泛型全剔除，测出来是假的零增量。所以 P0 建了 `src/relay/mod.rs` 的探测骨架
（`probe()`：构造请求 → 发送 → `Response::chunk()` 逐块读），并经 Tauri 命令表注册
（`commands::relay_probe`）——命令表是运行时可调用路径，LTO 不敢删。

**已验证代码真在二进制里**：`grep -a` 能在 exe 中命中 `中转探测` / `请求未送达` /
`构建 HTTP 客户端失败` / `读取响应体失败` / `relay_probe`。注意本机 `strings` 命令失效
（返回 0 行），查二进制字符串要用 `grep -a`。

### P0 踩到的三个坑（P1 前必读）

**1. dev-dependencies 的 reqwest 必须与正式依赖同版本。**
原 dev-deps 声明 `reqwest = "0.12"`，正式依赖是 `0.13`（复用 updater）。两者并存时，
`#[cfg(test)]` 里的 `reqwest::Client` 直接报：

```
error[E0464]: multiple candidates for `rlib` dependency `reqwest` found
```

测试根本编不过。已把 dev-deps 也升到 0.13。迁移只需改一处 API：
`use_rustls_tls()` → `tls_backend_rustls()`（前者在 0.13 已 deprecated，`clippy -D warnings`
下会亮红）。`gzip(bool)`、`Certificate::from_pem`、`add_root_certificate` 三个都在，无需改动。

**2. 必须用 `rustls` feature，不能用 `rustls-no-provider`。**
tauri-plugin-updater 用的是 `rustls-no-provider`——那是空壳，**不装加密 provider**。
直接照抄会让 13 个 over-the-wire 测试全部 panic：

```
No rustls crypto provider is configured. When using the `rustls-no-provider`
feature you must install a crypto provider before building a Client.
```

那 831 KiB 就是买这个 provider（aws-lc-rs）的钱。**不要为了省体积改回
`rustls-no-provider` 然后赌 updater 会先装好 provider**——中转不能赌别的模块的初始化时机。

**3. 测试必须带 `--no-default-features`。**
`cargo test` 裸跑会以 `0xc0000139 STATUS_ENTRYPOINT_NOT_FOUND` 崩掉——这是项目**既有**问题：
默认开的 `notifications` feature 拉入 `tauri-plugin-notification` → `AppHandle` → GUI DLL 链
（tao / webview2-com），测试二进制在 main 之前加载失败。正确命令：

```bash
cargo test --no-default-features
cargo clippy --all-targets --no-default-features -- -D warnings
```

已记在 `CLAUDE.md` 第 73 行与 `docs/dev-setup.md`，排查时不要再当成代码问题。

依赖声明附带的取舍（已写进 `Cargo.toml` 注释）：

- **不开 gzip**：中转是热路径，解压全量再转发多一次内存拷贝；千问的 SSE 响应本身不带
  `content-encoding`。真需要时再评估（0.13 的 gzip 走 `tower-http/decompression-gzip`，
  已经不再是 flate2，增量比 0.12 时代更小）。**dev-deps 开 gzip 不会泄漏到 release**——
  `cargo build --release` 的依赖图不含 dev-dependencies。
- `default-features = false` 只关掉**本声明**带来的 default，不影响 updater 那条的 feature
  （Cargo 对同一 crate 取并集）。

**P0 验证记录**：`cargo test --no-default-features --lib mcp::` → 394 passed / 0 failed；
`cargo clippy --all-targets --no-default-features -- -D warnings` 通过；relay 单元测试通过。

### P1：内建中转（Anthropic 透传，可替代现有 LiteLLM）

- `relay/` 骨架 + 规则表 + 三态清洗器 + 折叠 + 档位路由 + 配置表 + **主界面 tab 与设置开关** + 请求日志
- 验收：
  - 回放现有 5 种载荷（普通 / `tool_addition` / `tool_removal` / 128k `max_tokens` / 大 body）全部 200
  - **折叠正确性**（最关键的一条）：构造「工具只在 `tool_addition` 里、顶层 `tools` 为空」的请求，
    折叠后上游 200 **且模型真的调用了那个工具**——只看 200 不算通过，必须断言响应里出现对应的
    `tool_use` block。这个用例对应 §4.4.3 的实测，是我们和 LiteLLM「只剥离」方案的本质差别
  - **两种 `tool_addition` 形态**都要覆盖：`tool_definition`（内联完整定义）与 `tool_reference`（仅名字）
  - **块在 `role:"system"` 消息里**的情况也要覆盖（这是实际踩到的形态，不是 assistant 消息）
  - **空消息占位**：一条消息只有 `tool_addition` 块时，折叠后该消息保留在原位且内容为 `Please continue.`，
    前后消息的 user/assistant 交替不被破坏
  - **工具重名覆盖**：顶层 `tools` 已有同名项、`tool_addition` 里定义不同 → 以 `tool_addition` 为准，去重后只有一项
  - **档位路由**：已配置的每个 alias 各打一次，落到的上游模型与面板配置一致；`claude-sonnet-4-5-20250929` 这种带日期的原生名在配了 haiku/opus 档时命中对应档
  - **只配一档也能跑通**：只填 `default`，然后依次请求 `claude-3-5-haiku-…` / `claude-sonnet-4-5-…` / `claude-opus-…` 三种原生名，**三次全部 200 且落到 default 的上游模型**。这是默认形态的主用例，比下面那条更重要
  - **回落可诊断**：上一条的每个响应，日志里 `tier` 记实际档位（`haiku` 等）、`fellBack=true`，并记下客户端原名；面板日志行能看出「这档没配、用的 default」
  - **配了分档就按档走**：同时配 `default` 与 `haiku`，再请求同一个 haiku 原生名，落到 haiku 的上游模型且 `fellBack=false`——证明分档确实生效，不是永远落 default
  - **精确匹配优先于关键词（默认名的必测项）**：只配 `default`（alias `claude-sonnet-5-5`），请求 `claude-sonnet-5-5`，必须落 `default` 档且 **`fellBack=false`**。如果这里出现 `fellBack=true`，说明关键词匹配抢在了精确匹配前面，日志会被假的回落信号污染
  - **alias 与上游解耦**：把 `default` 档的上游填成 `claude-sonnet-distill`（名字里含 `sonnet`），验证 UI 显示的 alias 仍是 `claude-sonnet-5-5` 而不是被拼成 `claude-sonnet-distill`
  - **sonnet 走 default**：不配 haiku/opus，请求 `claude-sonnet-4-5-20250929`，落 `default` 的上游模型；确认环境变量里**没有** `ANTHROPIC_DEFAULT_SONNET_MODEL`
  - **预折叠的触发是条件式的**：不含 `tool_*` 块的请求必须产 `Unchanged`，上游收到的 body 与客户端发出的**逐字节一致**；
    含块的请求才产 `Sanitized`。这一条同时守住「prompt 缓存前缀不被普遍破坏」和「不白改请求」
  - **泛化 400 不误判**：构造非法 `role` 的请求（同样 400 `Request body format invalid`），
    验证它**不会**被当成 `tool_*` 问题去折叠——这是「按 provider 能力表预折叠」而非「按错误信息猜」的直接验收
  - **兜底整流默认关闭**：`rectify` 开关为 false 时，一次 400 不应产生任何重发（日志里只有一条上游请求）
  - **确定性改写不影响正常请求**：同一请求连发两次，上游收到的 body 完全一致（这是 prompt 缓存能命中的前提）
  - **可观测**：被折叠过的请求，响应头带 `x-relay-sanitized`，日志记 finding 路径（`messages[3].content[0]`）
  - **来源守卫**：带 `Origin` 头 / `Sec-Fetch-Site: cross-site` / 非白名单 `Host` 的请求分别被拒；正常 CLI 请求不受影响
  - 自转发：provider 填成本机同端口时保存被拒并说明原因
  - 流式打字机不退化，首 token 延迟对比 LiteLLM 不劣于 +50ms
  - 日志滚动生效，稳态行数有上限
  - **开关与导航（默认关闭是主路径，必须逐条过）**：
    - 默认状态启动：侧栏只有 5 项，命令面板搜不到「中转」，按 `Ctrl+6` **什么都不发生**（不报错、不导航、不白屏）

    - 关闭开关：二次确认后停监听、移除导航；**若当时正停在中转页，自动跳回关闭前的那个工作区页**
    - 关掉后按 `Ctrl+1~5` 仍然正确，证明边界是按可见项算的
    - 冷启动：把配置读取人为延迟 500ms，界面**不出现**「中转页先出现再消失」

  - **默认路径的接触点计数（§4.6.2 的落地验收）**：
    - 全新配置下，从「打开开关」到「远端第一次请求成功」，用户操作过的可交互元素**不超过 6 个**（开关 / 上游地址 / 密钥 / 模型 / 复制 / 远端粘贴）

- 接入指引卡片：主按钮**复制整块配置**（并存式 settings 文件 + alias，一条命令可复制），次按钮**直接写进远端**；隧道模式额外给转发规则，直连模式额外给内网地址与防火墙放行。不做「手工 / 自动」模式切换（§4.8.3）
- 「自动写入远端」作为可选项，四件事必须做到：先备份、沿用原权限、`.bashrc` 追加幂等、检测到 zsh 就写 `~/.zshrc`
- 监听范围切换（含二次确认、空 token 拒绝启动、401 封禁接线）
- 验收：
  - 面板里新建远端会话，不发任何命令即走中转
  - 远端会话里 `env | grep ANTHROPIC_` 默认能看到**三项**（`BASE_URL` / `AUTH_TOKEN` / `ANTHROPIC_MODEL`），值与面板一致；展开配了分档后，已配置的 `ANTHROPIC_DEFAULT_*` 才出现，**留空的档位一个变量都不出现**
  - 连续跑一轮「生成标题 → 主对话 → 派子代理 → 压缩上下文」，**全程不出现「模型不存在」**。这个用例必须**在只配一档的状态下跑一遍**（默认形态），再在配了分档的状态下跑一遍——只测后者会漏掉回落路径
  - 远端独立 CC：照抄手工配置块之后，`claude-own` 跑通一次真实对话；同时 `claude` 仍走订阅额度，`/model` 显示的还是原模型（证明两者真的互不影响）
  - 自动写入连点两次，`.bashrc` 里只有一行 alias（幂等），且生成了 `.bak`

## 六、风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 协议透传细节 | SSE 分块、gzip、`?beta=true` 任一处错都表现为「偶发失败」 | 录制回放做回归，不靠手测 |
| 预折叠开关依赖手工维护 | 上游开始支持 `tool_*` 块后，我们的预折叠反而削掉了原生能力；但我们无法自动感知 | 能力表按端点标注，界面显示「当前对该上游启用了折叠」；升级时先在设置页关掉开关试一次，正常就保持关闭 |
| 泛化 400 无法归因 | 千问/DeepSeek 对「块不认」和「role 非法」返回同一句话，日志里分不清 | 不靠错误信息归因：转发前用能力表决定是否折叠；折叠过的请求在日志里带 `sanitized` 标记，未折叠的 400 就是别的原因 |
| 端点是统一网关 | 同一端点下所有模型（含不同厂商）共享校验规则，换模型看似该改配置其实不用 | 能力表按**端点**标注而非按模型；新增模型时只验证一次基线 + 一次含块请求 |
| 档位匹配歧义 | 客户端模型名可能同时含多个档位关键词 | 固定优先级 haiku > sonnet > opus，**且只在该档已有配置时命中**；否则继续往下走到 `default`。命中的关键词与是否回落都写进日志 |
| 回落掩盖配错 | 未配置的档位自动落 `default` 后，「忘了配」和「配了但 alias 抄错」表现一样，都是「能用但答得一般」 | 日志为每条请求记「客户端原名 + 实际档位 + `fellBack`」，界面状态区给出「近 N 条里有 M 条发生档位回落」；回落不报错，但必须可见 |
| 分档被误当成必填 | 用户看到文档/别人的配置里有 `ANTHROPIC_DEFAULT_*`，以为自己也缺 | 指引里默认只给一行 `ANTHROPIC_MODEL`，并明写「其余档位不配也能跑」；面板上分档是折叠起来的 |
| 窗口期兼容性 | 上游升级后开始支持状态块，预折叠配置反而削掉能力 | 预折叠**默认开启**（§4.4.1），但做成 provider 级开关：升级后先在设置页关掉试一次，正常就保持关闭 |
| **折叠改变了对话内容** | 折叠后模型看到的 tools 数组与客户端原本要发的不完全一致（多出了动态注册的项） | 这是**必要的不一致**——不折叠模型就完全看不见这些工具。但必须可观测：响应头标 `x-relay-sanitized`，日志记 finding 路径，界面能查到「本次请求被改写了什么」 |
| **工具重名但定义不同** | MCP 重连后同名工具的 schema 变了，折叠进顶层 `tools` 时会撞上原有项 | 按 `name` 去重时**用 tool_addition 里的较新定义覆盖**，不是跳过。这与 ToolSearch 的语义一致（后宣告的生效） |
| 静默改写不可见 | 用户只觉得「模型好像忘了我的 MCP 工具」，查不出是中转改的 | 采纳 Anthropic 对 gateway 的要求：**为调用方恢复时要说明**。日志 + 响应头 + 设置页计数三处留痕 |
| OpenAI 转换边角 | `tool_calls` 分片、block index、空 delta、usage 缺失 | 四条坑写进单测，构造 chunk 序列做断言 |
| 转换层长期维护 | 厂商字段漂移（如 `max_completion_tokens`） | 差异全部收敛到 provider 配置，不散在代码里 |
| 体积 | `reqwest` 转正可能超预期 | ✅ P0 实测：+857.5 KiB（reqwest 本体仅 26 KiB，其余是 rustls provider），安装包约 12.42MB，红线 20MB |
| 缓存失效 | OpenAI 路径丢掉 `cache_control` 后成本上升 | 界面标注，路由表里给「推荐 Anthropic 路径」提示 |
| 内网直连暴露额度 | 监听 `0.0.0.0` 后同网段可探测，token 明文过网线 | 默认不开；开启需二次确认 + token 非空 + 401 封禁 + 限流；页头徽章直连时常驻橙色警示 |
| 单点故障 | 中转在进程内，cc-bridge 崩了远端全断 | 与现在同等；托盘已有，可加自动重启 |
| **默认关闭 = 功能不可见** | tab 默认不存在，用户根本不知道有这个能力；入口只在设置第二层 | 开关那一行的描述明写「开启后左侧出现「中转」页」，让人知道会多出什么。先不加首次启动引导，用一段时间没人发现再补一次性提示 |
| **关闭误触会断远端** | 一次误点就让所有远端 `claude-own` 立刻失败，正在跑的会话当场中断 | 关闭走二次确认并写明影响；开关状态**持久化**，重启后与上次一致，不会悄悄变回开启或关闭 |
| **简化过度：三格装不下真实需求** | 把 20 个控件压到 3 个，某些上游确实要调（鉴权方式特殊、必须 clamp `max_tokens`、需要关折叠） | 每个被删的项都有明确去处：**高级设置**（鉴权 / max_tokens / 折叠）、**错误时的动作**（一键压到 8192）、**P3 的选项**（OpenAI 兼容）。§4.6.2 逐个记了「为什么删」，加回任何一项前先看那一节 |
| **默认值不适用** | `max_tokens` 不压 → 上游直接 400；`x-api-key` 猜错 → 401；折叠开着但上游已原生支持 → 能力被削 | ① 测连通失败时自动换 `bearer` 再试一次；② 400 错误条给「压到 8192」一键动作，不预设上限；③ 折叠开关留在高级里，升级上游后先关掉试一次（见上一条风险） |
| **高级设置里的项更难被发现** | 折叠开关、鉴权从主视图移进折叠区，排障时想不到去那里找 | 页脚一行写明「三个值都在上游控制台里，别的不用管」，同时「高级设置（3 项，都已有默认值）」的文案点明**有 3 项**，不是隐藏功能；错误提示里出现相关字段名时，直接指到高级区 |
| 产品定位漂移 | 从「文件桥」扩到「AI 接入中枢」 | 一期不动 README 主线叙事，作为可选能力 |

### 明确不跟的

### 一个产品层面的判断

cc-switch 的本地代理本职就是「把 Claude Code 接到任意供应商」，模型映射、格式转换它都有，而且这台机器上已经装着。本方案的差异化价值只有三条：**远端会话自动注入**、**与 SSH 隧道 / 连接管理集成**、**一个应用搞定**。所以真正的护城河在 P2，不在 P1——P1 是把地基做扎实，P2 才是别人没有的那部分。

## 附录 B：第二轮调研（2026-11-23）

cc-switch 之外又看了四个项目，重点是「有没有比我们更好的处理方式」。结论：**有一个必须要改的设计（折叠优于剥离），其余是佐证与边界确认。**

| 项目 | 语言 | 体量 | 与本方案的关系 |
|---|---|---|---|
| **BerriAI/litellm**（PR #42731） | Python（核心 Rust 化中） | 巨型 | **同一问题的官方解法**，清洗器结构直接抄 |
| **router-for-me/CLIProxyAPI** | Go | 59.3k ★ / 9.1k fork | 场景最接近（专门把各类 CLI 转成兼容 API），issue #7570 是最详尽的现场报告 |
| musistudio/claude-code-router | TypeScript + Electron | 38k ★ | 已演变成桌面应用 + 多 agent 控制面，对「内建进 cc-bridge」没有参考价值 |
| majiayu000/litellm-rs | Rust | 124 ★ | 太小（18 fork），架构未成型，不值得依赖或抄 |

### B.1 决定性的一条：折叠，不是剥离

**CLIProxyAPI issue #7570** 的建议原文：

> fold `tool_addition` tools into the top-level `tools` array (dedup by name) and drop the block, or drop the blocks and emit a no-op placeholder

这份报告还确认了两件我们排查时没定论的事：

1. 这些块**也出现在 `role:"system"` 消息里**，不只是 assistant（我们上次抓到的正是 system 消息里那几条）
2. 在 680 条消息、1.4MB 的请求里，**只有那两个 system 消息里的 3×`tool_addition` + 3×`tool_removal` 是 400 的唯一原因**——460 个 tools、thinking 块、image 块、`cache_control`、`context_management`、`thinking: adaptive`、`output_config` 全部单独通过

第 2 点和我们自己的实测互相印证（§4.4.3），可以放心把「清洗范围」收窄到只处理这一类块。

**「占位」的具体文本**来自 LiteLLM PR #42731：`Please continue.`。它的理由也一并抄了——
「**永不删除整个消息**，因为那会破坏 user / assistant 交替，还可能让 tool_result 与它的 tool_use 脱钩」。

### B.2 三个字段的真实优先级（实测校准）

LiteLLM 那个 PR 列了 Claude Code 新发、Bedrock 会拒的三个字段。我们照抄会浪费精力，因为千问端点只对其中一个严格：

| 字段 | 千问 | Bedrock | 本期处理 |
|---|---|---|---|
| `tool_addition` / `tool_removal` 块 | ❌ 400 | ❌ 400 | **折叠**（必须） |
| `messages[N].output_config` | ✅ 200 | ❌ 400 | 规则表留位，不实现 |
| `thinking.adaptive.display = "updates"` | ✅ 200 | ❌ 400 | 规则表留位，不实现 |

判据是「上游严格程度」而不是「我们当前用哪家」。所以规则表按 **provider 能力标注** 而不是全局开关——同一份代码接 Bedrock 时自动多剥两个字段，接千问时不动作。

### B.3 采纳的工程手法

| 手法 | 来源 | 价值 |
|---|---|---|
| 校验独立成模块，一次校验成 typed view | LiteLLM #42731 | 纯数据可单测，不用起服务 |
| finding 记录「请求路径 + 归属开关」 | 同上 | 错误信息能直接告诉用户该开哪个开关，而不是甩一个 schema 错误 |
| 三态 `Unchanged / Sanitized / Refused` | 同上 | 转发层只 match 三种，没有第四种隐式路径 |
| 拒绝错误单一出口函数 | 同上 | 「哪个请求看哪个错误」只写一处 |
| 默认拒绝而非静默改写 | 同上 | 改对话内容会改变模型看到的东西，这个决定该由用户做 |

最后一条值得单独说：LiteLLM 的默认行为是**拒绝并告诉你该开哪个开关**，不是默默剥掉。理由是 `output_config` 的 effort level 会改变模型思考的力度，`tool_addition` 是模型自己之前说过的话的一部分，**删掉任何一个都改变了模型看到的对话**。

我们的取舍不同：**默认折叠并告知**（在响应头或日志里标 `x-relay-sanitized: fold_tool_blocks`），因为这是「桌面客户端里的个人中转」，用户不该为每次协议升级去翻配置。但**告知**这一条不能省——不然用户会发现「模型好像看不见我的 MCP 工具」却查不出原因。

### B.4 明确不跟的（本轮新增）

| 做法 | 为什么不跟 |
|---|---|
| 学 musistudio/CCR 做 Electron + 多 agent 控制面 | 那是独立产品的体量，我们只是给 cc-bridge 加一个模块 |
| 学 CLIProxyAPI 支持 6 家 CLI × 4 种上游协议 | 范围失控；本方案只需要 Anthropic 透传 + OpenAI 兼容 |
| 把 `tool_removal` 也翻译进顶层 `tools` | 它表示「移除工具」，翻译方式是**从 tools 数组里删掉同名项**，不是加。要单独写，别和 addition 混在一个函数里 |
