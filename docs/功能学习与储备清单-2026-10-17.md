# 功能学习与储备清单（2026-10-17）

来源：直接竞品调研（easy-local-mcp / omnidrive-mcp / fylane / webai-localbridge / mcp-proxy）+ 2026 MCP 生态与 Claude Code 生态流行项目。
筛选原则：符合 cc-bridge 定位（双向桥、本地优先）；**兼容 R17 哲学**（不做审批弹窗，安全靠白名单+审计+备份+自动熔断）；不引入重型依赖（Docker/Postgres 类方案一律排除）。

---

## 一、建议做（低成本高契合）

### 1. 「AI 改动可撤销」面板 ⭐ 最推荐
- **来源**：fylane 的「已批准修改 7 天内可撤销」。
- **现状**：cc-bridge 已有自动写入备份（写前快照），但备份只服务于数据安全，用户**看不见**它。
- **做法**：文件管控/安全页加一个「近期 AI 改动」视图——列出备份记录的时间/文件/diff 摘要 + 一键还原。备份引擎已有，只缺 UI 串联。
- **价值**：把「出事能救回来」从隐含能力变成用户可感知的卖点；这是 fylane 39 star 评论区最被称道的点。
- **成本**：低-中（纯前端 + 已有备份查询接口）。

### 2. 白名单 ignore 规则（.mcpignore 式）
- **来源**：omnidrive 的 .mcpignore；universal-dev-mcp 的目录范围控制。
- **现状**：cc-bridge 有白名单根目录 + 扩展名限制，但根目录**内部**的噪音/敏感文件（.git、node_modules、.env、密钥文件）无法排除。
- **做法**：白名单根目录支持 per-root 排除模式（glob 列表，配置界面一个 textarea + 预置模板按钮「排除 .git/node_modules/.env」）。
- **价值**：安全纵深明显增强（AI 永远看不到 .env）；对外宣传点。
- **成本**：中（Rust 侧路径匹配 + 配置项 + 前端）。

### 3. 外挂 MCP 桥：工具级暴露粒度
- **来源**：MetaMCP（⭐2.7k）的 namespace/工具过滤。
- **现状**：外挂桥按 server 级勾选暴露；一个 server 一开就是全量工具。
- **做法**：勾选粒度下探到工具级（ServerRow 展开后列工具复选框）。
- **价值**：最小暴露面原则的自然延伸；用户"只想给远程一个 search 工具"的诉求真实存在。
- **成本**：中（mcpbridge 模块已有工具清单缓存 ToolList，差勾选持久化与过滤下发）。

### 4. 用量报告对齐 ccusage
- **来源**：ccusage（⭐13k）的按天/会话/成本细分。
- **现状**：Token 用量卡已有 7 天估算 + KPI。
- **做法**：加「按工具/按客户端细分」维度 + CSV 导出（日志页导出已有同款基建）。
- **成本**：低。属于把已有数据多切一刀。

## 二、可选项（有价值，等真实需求）

### 5. 出站 Relay 接入模式（第三种传输）
- **来源**：easy-local-mcp 的核心架构：Agent 出站连 Relay，免公网 IP/免自签。
- **场景**：公司内网/校园网无法入站的用户，目前 cc-bridge 模式 B 跨公网靠 HTTPS 自签直连（要求本机可达）。出站 Relay 是另一种解。
- **代价**：需要维护一个 Relay 服务（或让用户自托管）——这是从「纯本机软件」迈向「要运营服务」的分水岭，与轻量定位有张力。
- **建议**：先不做；若用户反馈集中再立项。可先在 README 里写清两种跨公网方案对比。

### 6. OAuth 2.1 远端认证
- **来源**：MCP 官方规范方向，2026 所有网关（mcp-proxy/agentgateway/mcp-gateway）标配。
- **判断**：对个人工具 Bearer token 足够；OAuth 的价值在多人/团队场景。等「外挂桥」出现团队用户再做。

### 7. 工具输出压缩（rtk 式）
- **来源**：rtk（命令输出进上下文前压缩 60–90% token）。
- **做法**：run_command 返回可配截断/压缩档位（已有截断的话只是加策略）。
- **判断**：远端 Claude Code 的上下文管理属用户侧配置，桥越俎代庖可能好心办坏事。观察。

## 三、明确不做

- **AI 文件浏览器（webai-localbridge）**：给无 MCP 的网页 AI 开只读 Web 入口——扩大攻击面，与最小暴露面哲学冲突。
- **Docker/Postgres 网关类形态**（MetaMCP/MCPJungle/IBM context-forge）：那是服务器运维场景，cc-bridge 是桌面软件。
- **审批制工作流（fylane 的弹窗确认）**：直接违反 R17；我们的对位方案是白名单+审计+备份+自动熔断（第 1 项的可撤销面板是它的无弹窗替代）。
- **多设备 Zone 集中管理（easy-local-mcp）**：单机定位，等真实多机用户。
- **agent 编排/记忆/skills 类**（claude-mem、superpowers 等）：桥不越界做 agent。

## 四、生态趋势判断（用于 roadmap 排期）

1. **MCP 已是事实标准**：官方 GitHub MCP server ⭐30k+，客户端矩阵（Claude/Cursor/ChatGPT/Gemini）全部支持——cc-bridge 押注 MCP 的方向正确。
2. **传输层在收敛**：SSE → Streamable HTTP 迁移进行中，网关类工具都开始弃 SSE。cc-bridge 的 SSE 迁移警告（已上线）踩在点上，Streamable HTTP 支持值得排进传输层 roadmap。
3. **安全/治理是下一个差异化战场**（80aj 评论同判断）：纯「能执行」已不稀缺，路径白名单/审计/可撤销正在成为基线。cc-bridge 这块已经领先同类，继续加码。
