## 一、P1（必修：功能不通 / 安全 / 首次安装必现）

### B1 ✅ 接入工具切换永远不落盘（`connectClient` 被 serde 静默丢弃）

- 位置：`commands/config_cmds.rs:32-128`（`ConfigPatch`）
- 证据：

  ```rust
  // ConfigPatch 字段列表止于 multi_device_mode（第 124-127 行），没有 connect_client
  #[serde(rename = "multiDeviceMode")]
  pub multi_device_mode: Option<bool>,
  ```

  ```tsx
  // ConnectTab.tsx:172
  void invoke("save_config", { patch: { connectClient: t } }).then(onRefresh);
  ```

- 症状：`ConfigPatch` 无 `deny_unknown_fields`，`connectClient` 被 serde 静默吞掉，`save_config` 返回 `ok:true`、`changed:[]`。**连接页切到 Codex/WorkBuddy 后，界面显示新工具，但托盘「复制 IP 替换命令」、IP 横幅、连接命令仍按 claude-code 生成**——正是代码注释里要防的那件事。
- 佐证：`config.rs:171` 有 `connect_client` 字段、`status.rs:68` 已能读出并下发，说明只差写入通道。
- 修法：`ConfigPatch` 增 `#[serde(rename="connectClient")] connect_client: Option<String>` + `apply_field!`；前端保存后校验 `changed` 命中键。

### B2 ✅ 「命令会话持久化」开关双端断裂

- 位置：`commands/config_cmds.rs:32`（无字段） + `commands/status.rs`（无 `sessionCwdEnabled` 下发）
- 证据：`src/lib/types.ts:57` 声明了 `sessionCwdEnabled: boolean`，`AdvancedGroup.tsx:54` 用它渲染并保存；但后端 `ConfigPatch` 与 `StatusResponse` 都没有该字段（仅 `config.rs:148` 的 `BridgeConfig` 与 DB 读写有）。
- 症状：设置页拨开关 → 不落盘、弹回；治理胶囊永远显示「会话持久化 关」。与 B1 同根因（写通道 + 读通道各缺一半），可一并修。
- 修法：`StatusResponse` 增 `#[serde(rename="sessionCwdEnabled")]`；`ConfigPatch` 增同名字段 + `apply_field!`。

### B3 ✅ WorkBuddy scoped sed 的 `\{` 非法 → 多设备 IP 修复 100% 失败

- 位置：`network.rs:270` 与 `src/lib/utils.ts:232`（前后端逐字同款）
- 证据：

  ```rust
  _ => format!("/\"{entry}\": \\{{/,/\"Authorization\"/"),
  // Rust 字符串 "\\{" → 实际输出 \{
  ```

- 症状：GNU sed 对 BRE 中的 `\{` 要求后接区间，单独出现直接 `sed: -e expression #1: Unmatched \{`，退出码 1、文件未改。**多设备 + WorkBuddy 的所有 IP 修复命令必然报错**（Codex 的 `/^\[` 是合法写法，不受影响）。
- 修法：`\\{` 改 `{{`（输出裸 `{`）；补一条「字符串里不含反斜杠+花括号」的断言，或直接拿真实 sed 跑一条用例。

### B4 ✅ `Instant::now() - 60s` 开机不满 60 秒时 panic，`get_status` 命令卡死

- 位置：`commands/status.rs:377`；同款 `ip_watch.rs:61`（- 200ms）
- 证据：

  ```rust
  let cutoff = Instant::now() - Duration::from_secs(60);
  ```

- 症状：Windows 快速启动 + 开机自启时，登录后首轮 5s 轮询必过此行；Windows 的 `Instant` 以**系统启动**为原点，减法下溢直接 panic（`ban.rs` 早已为此把测试窗口从 3600s 改 120s 并留了注释，这里是同写法漏改）。
- 修法：`Instant::now().checked_sub(...).unwrap_or_else(Instant::now)`，或改正向比较 `now.duration_since(t) < 60s`。

### B5 ✅ 导出配置带出 SSH 凭据密文（脱敏不变量被新字段打破）

- 位置：`commands/config_cmds.rs:630-646`（`export_config_json`）
- 证据：

  ```rust
  let mut export = config.clone();
  export.token = String::new();            // 只清了 token
  export.external_mcp_enabled = false;     // 和外部 MCP
  export.external_mcp_servers = vec![];
  serde_json::to_string_pretty(&export)    // ssh_connections 原样序列化
  ```

- 症状：`ssh_connections` 含 `encrypted_password` / `encrypted_passphrase`。导出文件一旦被转发/备份/塞进工单，等于外发凭据密文——与 M1 修 token 的理由完全同类，属新字段没跟上不变量。注释里「脱敏不变量不能只靠人看」正说明这类遗漏必须由代码守。
- 修法：导出时清空或抹掉 `ssh_connections` 的密文字段（或整组与 external_mcp 同策略不导出）；补一条单测断言导出 JSON 不含 `encrypted_`。

### B6 ✅ 导入配置整体替换 `ssh_connections`，不拆 helper、不杀会话

- 位置：`commands/config_cmds.rs:690-704`（`import_config_inner`）
- 证据：只保留了 `external_mcp_*` 两组，随后 `*state.config.write().await = incoming;`。对比 `save_config` 路径在 `ssh_cmds.rs:1177-1181` 专门调 `state.drop_ssh_helper(&conn.id)`，注释写明不拆的后果是 `rm -rf` 执行在旧主机。
- 症状：导入一份改过 host / 删过连接 / 把 `ssh_enabled` 置 false 的配置后，**常驻 helper 仍连着旧主机**，文件面板的删除操作打在旧机器上；关掉 ssh 开关也不会触发断路器（`config_cmds.rs:299-303` 那条）。
- 修法：导入后按 id 差集 `drop_ssh_helper`；`incoming.ssh_enabled == false` 时复用 `kill_all_ssh_sessions()` + `kill_all_ssh_helpers()`。

### B7 ✅ `save_full_config` 漏写 `connect_client` / `has_onboarded` → 导入后重启配置分叉

- 位置：`config.rs:755-790`（`save_full_config` 尾部）
- 证据：只写了 `device_id` / `multi_device_mode` / `external_mcp_*`；`import_config_inner` 是先落库再整体替换内存。
- 症状：导入后界面按新配置跑，重启回到旧值；`has_onboarded` 丢失会让老用户重新看到引导。
- 修法：补齐两个键，并让 `save_full_config` 的字段清单与 `apply_field!` 分支对齐（用同一条单测表驱动，防再漏）。

### B8 ✅ 嵌套 batch 可用 `mcp__<server>__batch` 绕过（放大攻击面）

- 位置：`mcp/tools/batch.rs:43` + `mcp/http.rs:786-792`
- 证据：

  ```rust
  if op.tool == "batch" { return Err("nested batch is not allowed") }   // 只比字面量
  ```

  ```rust
  let rest = name.strip_prefix("mcp__")?;   // dispatch 会剥前缀再查表
  let stripped = &rest[idx + 2..];
  tools.iter().find(|t| t.name == stripped)
  ```

- 症状：`{"tool":"mcp__cc-bridge__batch","arguments":{"operations":[…100 条…]}}` 通过校验后被 dispatch 解析回 `batch` 并递归执行，每层 100 条 → 指数放大（100^深度）。这是 batch「零新攻击面」设计的前提被打破。
- 修法：`validate_batch` 用与 dispatch 同一套 `resolve_tool_name` 解析后再判 `== "batch"`；并加 task_local 深度计数（硬上限 1）。

### B9 ✅ 首次安装时自动选 IP 被当成「用户点选」→ 弹出假的「网络地址已变化」横幅

- 位置：`App.tsx:97-100` + `ConnectTab.tsx:84-86`
- 证据：

  ```tsx
  // ConnectTab：首次接入自动选第一个，不区分 byUser
  if (!selectedIp && !status?.lastSelectedIp) { onSelectIp(lanIps[0]); return; }
  ```

  ```tsx
  // App.handleSelectIp 默认 byUser = true
  if (byUser) { setIpResolvedByUser(true); setPendingCmd(null); }
  ```

  ```tsx
  // 横幅条件只看 (ipChanged || ipResolvedByUser)
  {(status?.ipChanged || ipResolvedByUser) && !dismissed && <IpChangedBanner … />}
  ```

- 症状：**全新安装必现**——首屏刚加载完就出现橙色「网络地址已变化，请更新远程命令」，而地址根本没变。`ipResolvedByUser` 只有「复制 sed」能复位，误置后会一直挂着。
- 修法：自动路径显式传 `byUser=false`（或拆 `autoSelectIp`）；或 `handleSelectIp` 里仅当 `status?.ipChanged` 为真才置 `ipResolvedByUser`。

### B10 ✅ 重生成 Token 后生成「旧换旧」的空操作 sed

- 位置：`TokenManager.tsx:52-56`
- 证据：

  ```tsx
  const old = status?.token ?? "";
  await invoke("regenerate_token");   // 返回值被丢弃
  setOldToken(old);
  onRefresh();                        // 未 await，status.token 仍是旧值
  ```

  ```tsx
  const tokenSedCommand = useMemo(
    () => buildTokenSedCommand(oldToken, status?.token ?? "", ...));
  ```

- 症状：点确认后立刻显示「Token 已更新」+ 一条 `s#Bearer old#Bearer old#g`；复制到远端执行完照样 401，而用户以为已更新。
- 修法：`const next = await invoke<string>("regenerate_token")`，用返回值直接生成命令并本地立即显示，refetch 完成前保持「生成中」态。

## 三、UX 缺陷（按用户痛感排序）

### U1 ✅ 顶栏启停服务失败完全静默

- 位置：`components/layout/Header.tsx:80-89`
- 证据：

  ```tsx
  try { await invoke(running ? "stop_mcp_server" : "start_mcp_server"); onChanged?.(); }
  finally { setBusy(false); }   // 没有 catch
  ```

### 发现的假绿测试（已修）

`write_files::tests::preserves_crlf_of_existing_file` 用 `run.bat` 做夹具，但默认 `allowed_extensions` 白名单（`config.rs:254`）**不含 `.bat`**。于是链条是：

```
assert_extension_allowed → Err(".bat is not in the allowed list")
  → write_single 返回 Err
  → handle 把它塞进 results{ok:false}，**仍返回 Ok**
  → 测试 .expect("write") 通过
  → 读回的是没被碰过的原文件 → CRLF 完好 → 断言成立
```

这条测试从写下起就没验证过任何东西：把判据改回 `f.content.contains("\r\n")` 它照样绿。

**修法**：夹具改 `run.txt`（白名单内）+ 新增 `written_ok(&Value)` 辅助函数解析 `content[0].text`，断言 `results[0].ok === true`。修完后同样注入缺陷，测试准确红在「CRLF 原文被翻成 LF 了」，并打印出实际写出的 LF 字节。

> ⚠️ **通用教训**：`handle` 的**软失败**语义（单文件失败是 `ok:false`，不是 `Err`）是所有「写完后读回文件断言」类测试的假绿温床。同类新测试必须先用 `written_ok()` 确认写入成功。`keeps_lf_of_existing_file` 原本就用 `.txt` + 内容断言，天然有效，但也补了 ok 断言保持口径一致。
