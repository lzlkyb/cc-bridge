# 同类软件的文件传输架构调研（GitHub 实测）

> 写于 2026-11-23 23:00。起因：用户问「我们这个架构下面做得好的文件传输是怎么做的，他们速度很快」。
> 本文**只调研、不改代码**。所有结论标注来源（仓库 + 文件 + 代码行），推断单独标注。
> 关联文档：`docs/终端文件浏览慢-定位与方案-2026-11-23.md`（我们的慢因定位）、`docs/B方案验证-2026-11-17.md`（已否决方案，本文 §6 说明为何不矛盾）。

---

## 0. 结论速览

**同类软件快的根本原因只有一句话：它们不调用外部 `ssh.exe`，而是内置 SSH 协议栈，于是一条连接上多路复用所有操作。**

| | 同类软件（Tabby / Yazi / Shelly SSH / fileterm…） | 我们 |
|---|---|---|
| SSH 实现 | **内置协议栈**（russh / ssh2 / x/crypto） | 外部 `ssh.exe` / `scp.exe` |
| 连接模型 | **一条长连接，多 channel 复用** | 三条独立路径：PTY 终端 / helper shell / 一次性 scp |
| 列目录 | SFTP `readdir` 协议原语 | `ls -la` 文本解析 |
| 传输 | 流式 `AsyncRead`/`AsyncWrite` | scp 子进程 |
| Windows ControlMaster | **不存在这个问题**（没有外部进程） | 这就是我们每次付 11 秒的根源 |
| 大文件 | 流式，无缓冲上限 | helper 4 MB 缓冲会吃掉哨兵（P0-1） |

**最值得抄的一点**：`russh` 官方示例显示，**建立一条 SFTP 通道只要 5 行**，之后 `read_dir` / `metadata` / `open_with_flags` / `write_all` 全部零握手，且 `authenticate_password` **原生支持密码认证**（我们正是密码认证）。

## 1. 调研对象与实测记录

### 1.1 Tabby（最主流开源终端，Electron + Angular）★最直接对照

源码：`Eugeny/tabby` → `tabby-ssh/src/components/sftpPanel.component.ts`

**关键代码（`ngOnInit`）**：

```ts
@Input() session: SSHSession        // ← 终端那条 SSH 会话，由外部注入
...
async ngOnInit (): Promise<void> {
    this.sftp = await this.session.openSFTP()      // ★ 在终端的连接上开 SFTP 子系统
    try { await this.navigate(this.path) } ...
}
```

**这就是答案本身**：SFTP 面板**不新建连接**，而是拿终端那条 `SSHSession` 去 `openSFTP()`。终端和文件面板共享同一条 SSH 连接。

其余实现细节（同文件）：
- 列目录：`this.fileList = await this.sftp.readdir(this.path)` —— SFTP 原语，返回结构化条目（含 `isDirectory` / `isSymlink` / `mode` / `size`）
- 排序在前端做：`dirKey(b) - dirKey(a) || a.name.localeCompare(b.name)`
- 上传：`await Promise.all(transfers.map(t => this.uploadOne(t)))` —— **并发上传**
- 下载文件夹：**边递归边算总大小**（`calculateFolderSizeAndUpdate` 与 `downloadFolderRecursive` 通过 `Promise.all` 并行，`transfer.setTotalSize(totalSize)` 实时更新），取消靠 `transfer.isCancelled()` 轮询
- 软链处理：`readlink` → `stat` 判断目标是否为目录，是则进入、否则按文件下载

### 1.2 Yazi（Rust 终端文件管理器，以快著称）

源码：`sxyazi/yazi` → `yazi-sftp/` crate（`russh-sftp` 的 fork）+ `yazi-vfs`

`yazi-sftp/src/session.rs` 的 `Session::make(stream: ChannelStream)`：

```rust
let (tx, mut rx) = mpsc::unbounded_channel();
// 写任务：把请求包丢进 channel
// 读任务：收到包后按 packet.id() 找到 callback 并投递
if let Ok(packet) = crate::from_bytes(&buf)
    && let Some(cb) = me_.callback.lock().remove(&packet.id()) {
        cb.send(packet).ok();
}
```

- **一条 `ChannelStream` 承载全部 SFTP 操作**，用**请求 ID 做多路复用**（`Id::next()` 递增）
- 默认超时 45 秒：`send_with_timeout(input, Duration::from_secs(45))`
- 单包上限 1 MB：`if len > 1024 * 1024 { return Err(...) }` —— 二进制帧不会膨胀，所以敢卡这么死
- Fork 的动机（crate 说明）：支持非 UTF-8 路径、拿 `nlink`/`username`/`group`、包长预计算减少分配、`AsyncRead`/`AsyncWrite` 不克隆缓冲
- Drop 时 `self.tx.send(vec![])` 通知读写任务收工

### 1.3 russh 官方 SFTP 示例（我们最可能直接抄的）

源码：`warp-tech/russh` → `russh/examples/sftp_client.rs`

```rust
let mut session = russh::client::connect(Arc::new(config), ("localhost", 22), sh).await?;
if session.authenticate_password("root", "password").await?.success() {
    let channel = session.channel_open_session().await?;
    channel.request_subsystem(true, "sftp").await?;
    let sftp = SftpSession::new(channel.into_stream()).await?;

    for entry in sftp.read_dir(".").await? { ... }        // 列目录
    let attrs = sftp.metadata(path).await?;               // stat
    let mut file = sftp.open_with_flags(name, OpenFlags::CREATE | OpenFlags::WRITE | OpenFlags::READ).await?;
    file.write_all(b"magic text").await?;                 // 流式写
    file.read_to_string(&mut str).await?;                 // 流式读
}
```

**五个事实**：
1. `authenticate_password` 原生支持**密码认证** —— 我们的用户 `lizuliang@10.0.19.194` 正是密码认证，没有障碍。
2. 建立 SFTP 通道 = `channel_open_session()` + `request_subsystem("sftp")` + `SftpSession::new()`，**5 行**。
3. 之后 `read_dir` / `metadata` / `open_with_flags` / `write_all` / `read_to_string` 全部走这条 channel，**零额外握手**。
4. 文件句柄实现 `AsyncRead` + `AsyncWrite` —— **天然流式，不存在「缓冲吃不下」的问题**（我们的 P0-1 4 MB 哨兵事故在这个模型里不会发生）。
5. `channel_open_session()` 可多次调用 —— 一条连接上开多个 channel，**列目录与传输可并行**（对应我们的 P1-4 忙态锁死）。

### 1.4 四个 Tauri 同类项目（证明这条路在我们同类软件里是主流）

| 项目 | 栈 | 值得抄的点 |
|---|---|---|
| **Shelly SSH**（`WEP-56/shelly-ssh`） | **Tauri 2 + React + TS + russh + russh-sftp + portable-pty + SQLite + keyring** | 与我们的桌面形态最接近：russh 做 SSH/SFTP，portable-pty 只用于**本地** PTY；SFTP 用 **job queue 模型**，进度经事件回流 UI，长任务可取消 |
| **Terminal-R**（微软商店） | Tauri 2 + russh + portable-pty + xterm | 密码/私钥认证 + SFTP 浏览器 + 点路径直接开文件（与我们「从终端点路径进面板」同需求） |
| **Reach**（`alexandrosnt/reach`） | Tauri v2 + Tokio + russh + Svelte | SFTP 浏览器 + 拖放传输 + 行内编辑 + ProxyJump + 端口转发，一套 russh 全包 |
| **fileterm**（`St0ff3l/fileterm`） | Tauri v2 + russh/russh-sftp + tokio | **虚拟滚动文件列表**（直接对应我们 P2-1）；**传输中心**：断点续传 / 进度 / 速度 / 取消 / 递归文件夹；架构纪律写进 README：*renderer 永不直接访问 SSH/SFTP 客户端，全部经 Rust commands/events*，*传输进度进同一个 transfer 系统，不各组件自持* |

> 这四个项目说明：**「Tauri + russh + russh-sftp」已经是这类桌面 SSH 客户端的成熟选型**，不是我们自己在冒险。

## 2. 共同架构抽象（五条，按对我们的价值排序）

1. **内置协议栈，一条长连接多路复用**。终端 channel、SFTP channel、端口转发 channel 跑在同一条 TCP 连接上。ControlMaster 的需求从根本上消失。
2. **用协议原语，不用 shell 文本解析**。`readdir` 返回结构化条目（含 mode/size/is_dir/is_symlink），不需要解析 `ls -la` 的第 6 列是不是 epoch。我们 `ssh_cmds.rs:892` 的 `parse_ls` 还要区分 GNU/BSD 两种日期格式——这类代码在 SFTP 模型里整块消失。
3. **流式 I/O + 进度事件 + 可取消**。文件句柄即 `AsyncRead`/`AsyncWrite`，大文件不需要先整块读进内存；进度通过事件流回 UI（fileterm/Shelly 都这么做）。
4. **连接/会话与 UI 解耦，状态放 Rust 侧**。`HashMap<connection_id, SftpSession>`，UI 只发命令收事件。
5. **凭据不进长生命周期结构**。`authenticate_password(user, pw)` 一次性调用，密码不出现在 session 对象里——与我们的红线（凭据只在登录一瞬存在）天然一致。

## 3. 我们的架构差距（对照 §2）

| # | 现状 | 代码位置 | 同类怎么做 |
|---|---|---|---|
| 1 | 终端用 PTY 起外部 `ssh.exe` | `ssh_helper.rs` / `spawn_capture` | 内置 russh，channel 即终端 |
| 2 | 文件面板三条独立路径：helper shell / 一次性 ssh / scp | `ssh_cmds.rs:1114` `run_via_helper`、`:1269` `spawn_capture`、`run_scp` | 一条连接多 channel |
| 3 | 列目录 = `ls -la` + GNU/BSD 双语法解析 | `ssh_cmds.rs:892` `parse_ls` | `sftp.read_dir()` |
| 4 | 传输 = scp 子进程，每次新连接 | `ssh_cmds.rs:2347` `ssh_sftp_get` | `sftp.open()` + 流式读写 |
| 5 | 大文件/大目录撞 4 MB 缓冲上限 | `ssh_helper.rs:44` `MAX_BUF` | 流式，无此上限 |
| 6 | 忙态锁死整个面板 | `SshFileBrowser.tsx:91` | 多 channel 并行 + job queue |

**结论**：我们的慢**不是参数没调好，是架构代差**。A 方案（让 scp 也走 helper）是在现有架构里做最优，能把 11–26 秒压到 1 秒级；但只要还依赖外部 `ssh.exe`，「每条连接 11 秒」这个天花板就永远在，且 helper 的 ConPTY 文本通道天生带着 4 MB 缓冲、哨兵、回显、GNU/BSD 双语法这一串脆弱点。

## 4. 新增方案 D：内置 russh（只迁文件面板，不动终端）

### 4.1 形态

```
┌─────────────────────────── cc-bridge ───────────────────────────┐
│  终端（xterm.js）                  文件面板                      │
│  └─ PTY + 外部 ssh.exe  ← 不动     └─ russh 长连接（新增）        │
│     付 1 次 11 秒                      ├─ channel: sftp subsystem │
│                                        │   read_dir / metadata    │
│                                        │   open / read / write    │
│                                        └─ 可再开多个 channel 并行 │
└──────────────────────────────────────────────────────────────────┘
```

**只迁文件面板，终端继续用 PTY ssh.exe。** 理由：终端要扛 xterm 交互、resize、信号、TTY 语义，回归面极大；而文件面板本来就不需要 PTY 交互，边界就是 `ssh_file_cmds.rs` + `ssh_cmds.rs` 里的 sftp 部分命令。

### 4.2 收益

| 操作 | 现在 | 迁后 |
|---|---|---|
| 列目录 / 进目录 / 刷新 | 11 s（或 26 s） | **< 0.5 s**（零握手） |
| 双击读文件 | 11 s | < 0.5 s |
| 保存 | 11 s | < 0.5 s |
| 下载 / 上传 | 11 s（scp 新进程） | 流式，**小文件 < 0.5 s，大文件只受带宽限** |
| 新建 / 删除 / 重命名 | 11 s | < 0.5 s |
| 5 万条目大目录 | 15 s 超时 + 拆 helper + 再 11 s | readdir 流式返回，配上前端虚拟滚动（抄 fileterm） |

**顺带解决的既有缺陷**：P0-1（4 MB 缓冲吃哨兵，流式模型里不存在）、P1-4（忙态锁死，多 channel 可并行）、P2-1（虚拟化，fileterm 有现成范式）、P1-3（两次列目录，readdir 一次拿全量再定位）。

### 4.3 代价与风险（如实列）

1. **依赖与编译**：新增 `russh` + `russh-sftp` + `russh-keys`（约 3 个主 crate，传递依赖若干）。需指定 crypto backend（`aws-lc-rs` 或 `ring`）。⚠️ 本项目 2026-11-23 刚踩过 reqwest 的 `rustls-no-provider` 坑——**同样必须显式选带 provider 的 feature，不能靠「别人会装」**。aws-lc-rs 已在依赖树里（axum-server dev 链），选它预计不显著增加编译量。
2. **连接数 +1**：终端一条 + 文件面板一条。sshd `MaxSessions` 默认 10，可接受；但 `MaxStartups`（默认 `10:30:60`）在并发登录时可能丢包——**建连要串行化，别和终端登录抢**。
3. **回归面**：文件面板的命令层要重写（`ssh_file_cmds.rs` 的 read/write/mkdir/remove + `ssh_cmds.rs` 的 sftp list/get/put），但边界清晰、可灰度：**先只把「列目录」迁到 russh，其余仍走旧路径**，对比验证后再逐个迁。
4. **凭据纪律不变**：`authenticate_password` 一次性调用，密码不进 session 结构，符合现有红线。**不需要 askpass、不需要临时脚本、不落盘**（这一点比 B1 方案干净）。
5. **不需要服务器任何改动**：Ubuntu 8.9 默认带 `Subsystem sftp /usr/lib/openssh/sftp-server`（B 方案报告 §3.3 已从 banner 推断，仍需一次真机确认）。
6. **仍要处理认证慢本身**：russh 建连同样要付那 11 秒 PAM（一次性），所以「第一条连接仍慢、之后全快」——但因为我们**只在连上时建一次并长驻**，用户感知就是第一次进面板慢一下，之后全程秒开。若同时推进方案 B（修服务器 PAM / 换 ed25519 密钥），连这一次也省掉。

### 4.4 为什么这和 11-17 否决的 B 方案不矛盾

| | B 方案（已否决） | 方案 D（本次新增） |
|---|---|---|
| 通道 | **ConPTY** 里跑 `sftp-server` | tokio 直连，**不经过 ConPTY** |
| 协议 | **手写** SFTP v3 帧编解码 + 状态机（估 700 行） | 用成熟 crate `russh-sftp` |
| 否决的实证 | ConPTY 双向二进制不安全（实测帧头变形）、Windows 无 `stty raw` | 不适用 |
| ROI 计算前提 | 手写 700 行 + 全套测试 + 取消机制重写 | 库已实现 `AsyncRead`/`AsyncWrite` + 取消可用 `drop` |
| 生态验证 | 无同类先例 | Shelly SSH / Terminal-R / Reach / fileterm 四个 Tauri 项目已在生产用 |

**B 方案否决的是「借 ConPTY 讲二进制」和「手写协议」这两件具体事，不是「内置 SFTP」这个方向。**

## 5. 路线建议

| 阶段 | 动作 | 预期 | 依赖 |
|---|---|---|---|
| **近期（不动架构）** | A0 埋点 + 修 P0-2（256 KB 截断）+ 若 C2 成立则 A3 列目录瘦身 | 故障可见、数据不丢、大目录可用 | 无，可立即做 |
| **中期（治本）** | **方案 D**：文件面板迁 russh，按「列目录 → 读 → 写 → 传输」顺序灰度 | 文件面板全操作 11–26 s → < 1 s | 一次真机确认 sftp-server 存在 |
| **并行（若有权）** | 方案 B：修服务器 PAM 11 秒或换 ed25519 密钥 | 连 russh 建连也变快，终端/隧道/转发全受益 | 服务器权限 |

**推荐**：近期三项与方案 D **并行推进**——近期三项不依赖任何未验证假设，方案 D 是唯一能根治「每次 11 秒」的路。

## 6. 待验证项

1. **远端 sftp-server 存在与版本**（B 方案报告 §3.3 只有 banner 推断，未直连）——方案 D 的前置条件，一次真机命令可确认：`ssh lizuliang@10.0.19.194 "subsystem=sftp /usr/lib/openssh/sftp-server; echo \$?"` 或直接看 `/etc/ssh/sshd_config`。
