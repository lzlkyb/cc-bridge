# 批 4-2 审批即审计（方案）

> 状态：**方案待拍板**（两个决策点见 §6）。2026-10-25。

## 一、要回答的问题

用户在对话里点过一串「允许」，事后想知道两件事：

1. **每个「允许」实际改了什么**（不是「这一轮改了什么」，是「我点头的那一下改了什么」）
2. **能不能撤回**，最好一次把某个点 / 某一段的改动一起撤回

行业里 CC Desktop 的 checkpoint 能做到第 2 件的「回到某一轮」，但它是**快照式**的（每轮存一份代码状态），
且没有审计链——你只能回到某个点，说不清「谁在什么时候以什么理由改的」。我们要走的是另一条路线：
**备份 + 审计链**。这条路线天然带证明（谁、何时、什么工具、什么参数、有没有备份），代价是覆盖不到没有备份的改动。

## 二、调研结论（决定了方案能做成什么样）

### 2.1 审批点与工具调用是**精确**关联的，不用猜

```
permissionAsk.toolUseId  ===  CcMessage(kind:"tool").id  ===  toolUse.id
```

`ccReducer` 的 `case "toolUse"` 直接拿 `event.toolUseId` 当消息 id（`ccReducer.ts:238-241`），
而 `PermissionAsk` 事件（`proto.rs:82-89`）带 `tool_use_id`。所以「这次审批放行的是哪次调用」是查表，不是时间窗匹配。

顺带解决一个原本担心的问题：**同一文件多次改动不会歧义**——每次改动有自己的 toolUseId。

### 2.2 改文件的工具分两类，可还原性完全不同

| 类别 | 工具名 | 走桥 | 有备份 | 入参里的原始内容 |
|---|---|---|---|---|
| CC 内置 | `Edit` / `MultiEdit` / `NotebookEdit` / `Write` | ❌ | ❌ | Edit 有 `old_string`+`new_string`；**Write 只有新内容** |
| 桥工具 | `write_files` / `edit_files` / `delete_files` / `move_files` / `copy_files` / `notebook_edit` | ✅ | ✅ `backupPath`+`targetPath` | 参数全文在审计里 |

这张表是方案的核心约束：**最常用的改文件方式是 CC 内置 Edit/Write，而它们没有备份。**

### 2.3 历史落盘保住了入参

`cc_history/parse.rs` 的 16,000 字符截断只作用于 **`tool_result.content`**（`parse.rs:304`），
`tool_use.input` 原样保留。所以打开历史会话后，`old_string` / `new_string` 仍然完整可用。
（例外：整行超过 `MAX_LINE_BYTES` = 1MB 的行会被跳过，那种超大 Write 连工具调用都不在流水里。）

### 2.4 审计查不到「重新打开的历史会话」

审计条目的归属字段是 `ccSessionId`（cc-bridge 内部会话 id，`cc_new_session` 铸发）。
重新打开一条历史会话会拿到**新的内部 id**，而审计里记的是当时的旧 id——两者之间没有桥。

审计里另有 `sessionId`，但那是 MCP 会话 id，不是 CLI 的 `~/.claude/projects/.../<uuid>.jsonl` 那个。

⇒ 结论：**实时 pane 能查审计，历史会话查不到**。要么接受这个限制（历史里只显示「当时有没有备份」看不出来），
要么给审计补一个 CLI session id 字段（见 §6 决策二）。

### 2.5 现有还原通道已经足够安全

`restore_file`（`backup_cmds.rs:345`）已做：备份路径范围校验、target 白名单、只读模式拒绝、扩展名白名单校验。
新命令只要复用同一套校验，安全语义不会退化。

## 三、数据模型

不改表结构，全部是**派生视图**：

```
CcApprovalPoint           一次审批 = 一次工具调用
├─ toolUseId              关联键（精确）
├─ toolName / input
├─ decision               allow / deny / cancel / 未决
├─ auto                   规则自动放行（不是用户点的）
├─ files[]                这次调用改的文件（0..n，batch 可能多个）
│   ├─ path
│   ├─ changeKind          edit / multi-edit / write / create / delete / move
│   ├─ revert               可还原手段
│   │   ├─ backup         有备份 → restore_file
│   │   ├─ patch          内置 Edit → 反向补丁
│   │   ├─ delete-created 内置 Write 且文件是本会话新建 → 删掉即可
│   │   └─ none           内置 Write 覆盖了已有文件（无旧内容，不可还原）
│   └─ reason             revert 为 none 时说清为什么
└─ messageId              跳转到流里那条工具卡
```

`decision === "deny"` 的点也要显示（显示为「已拒绝，无改动」）——那正是审计链比 checkpoint 多出来的信息：
**用户拒绝过什么**，也是审计的一部分。

## 四、界面（详见设计稿）

现在 `ChangesetPanel` 是「按文件聚合」的扁平列表。4-2 改成**按审批点分组的树**：

```
本会话改动  12 个文件 · 8 个审批点 · 3 个可整组还原
─────────────────────────────────────
✓ 允许 · Edit          src/a.rs            +12 −3   [撤销]
✓ 允许 · MultiEdit     src/b.rs  3 处      +40 −8   [撤销]
⚡ 自动放行 · Write     new/c.ts            +80      [撤销]
✗ 拒绝 · Edit          src/d.rs            —        （无改动）
✓ 允许 · Edit          src/e.rs            +5 −5    [撤销] ⚠ 无备份：可反向应用
                                                  [整组还原这 3 个点]
```

三层信息按需展开：审批点 → 文件 → diff（复用现有 `DiffBlock`）。

## 五、三条路线

| | A 只做有备份的 | B = A + 反向补丁 | C 只读不还原 |
|---|---|---|---|
| 覆盖内置 Edit/MultiEdit | ❌ | ✅ 反向应用 `new→old` | — |
| 覆盖桥工具 | ✅ | ✅ | — |
| 覆盖内置 Write | ❌ | ⚠️ 仅「新建的文件」可删 | — |
| 新增后端写路径 | 无 | **有**（`restore_edit_patch`） | 无 |
| 工作量 | 中 | 大 | 小 |
| 实际价值 | **低**：真实对话大多用内置 Edit，等于大部分不能还原 | **高**：覆盖最常用的改文件方式 | 低 |

**推荐 B，但拆两步交付**：B1 先落「分组视图 + 有备份的整组还原 + 无备份的如实标注」，
B2 再加 `restore_edit_patch`。这样 B1 单独就是完整可用的（只是覆盖率低），不做一个半成品。

### B2 的命令语义（这是 B 唯一的风险点）

```rust
restore_edit_patch(target_path, patches: [{old_string, new_string}])
```

- **逆序应用**：同一文件的多处编辑从最后一处往第一处撤（否则前面的位移会让后面的定位失效）
- **预检全过才动手**：每处 `new_string` 在当前文件里必须**恰好出现一次**。
  0 次 = 文件已被后续改动 / 内容不符；>1 次 = 歧义。任一不满足 ⇒ **整体拒绝，一个字不动**
- **写前备份**：复用现有备份机制（还原本身也是一次写，要能再撤销）
- **审计**：记一条 `tool: "restore_patch"`，参数里带 patches 的 hash 与目标路径
- 安全校验复用 `restore_file` 那套（白名单 / 只读 / 扩展名）

这不是「给前端一个任意文本替换 API」：它只接受「把某段已知文本换回另一段已知文本」，
且要求当前状态与预期完全吻合。冲突时宁可失败也不猜。

## 六、两个待拍板的决策

**决策一：路线选 A / B / C？**（推荐 B，分 B1 + B2）

**决策二：「整组」的粒度是什么？**

- ① 单个审批点（撤销「我点的那一下」）
- ② 一轮对话（撤销「从这句话到这句话」之间的全部改动）—— 更接近 CC checkpoint
- ③ 两者都要：单点 [撤销] + 区间 [整组还原]

②③ 需要确定「轮」的边界。事件流里有 `TurnEnd`，但审计与前端视图都**没有轮次号**（4-1 已确认这一点，
`context_tax.rs` 的注释里写着「不做本轮」）。所以「轮」只能由前端按 `TurnEnd` 切分消息序列来推，
不需要后端改字段——但要在界面上说清边界是「按对话轮次切分」而不是「按后端账」。

**决策三（可选）：要不要给审计补 CLI session id**，让重新打开的历史会话也能查备份。
不加的话，历史会话里所有改动都只能标「不可还原（不是当前会话的审计范围）」。

## 七、不做的事

- 不做快照（每轮存一份代码状态）：本项目的备份是**按次**的，快照会带来磁盘与清理策略的整套新问题
- 不拦截 CC 内置工具（那是改 CLI 行为，`~/.claude/*` 是红线）
- 不碰 `restore_file` 的安全语义（B2 复用，不改）
- 不做「还原后自动重跑对话」——那是回滚语义，别混进来

## 八、验收判据

1. 每个审批点显示：谁决定的（人工 / 规则自动）、允许还是拒绝、改了哪些文件、可不可以撤销
2. 有备份的改动能一键还原，且还原本身产生新备份（可再撤销）
3. 无备份的改动**明确说明原因**，不允许出现「点了没反应」或「假装能还原」
4. `decision === "deny"` 的点出现在列表里（审计链的独有价值）
5. 单测覆盖：分组归并、可还原性判定、反向补丁的冲突拒绝（0 次 / 多次匹配）
