- 审查日期：2026-11-01
- 审查范围：`desktop/src/components/ccgui/**`、`components/tabs/CcPane.tsx`、`CcGuiTab.tsx`、`hooks/useCc*.ts`、`hooks/useComposer*.ts`、`lib/ccReducer.ts`、`lib/ccMarkdown.ts`、`lib/ccHighlight.ts`
- 方法：逐文件通读源码 + 行号取证；`marked` 词法行为用 node 实跑验证；渲染/搜索同构关系按源码交叉核对；开源实现按技术社区 2026 年公开实践比对
- 本报告不含任何改动，只给判断与方案

## 一、结论摘要

对话 GUI 的**功能完整度**（多会话、审批、插话、分叉、搜索、导出、用量脚注）明显高于同类自研产品；**渲染安全**（lexer → React，无 `innerHTML`、链接白名单）与**状态机纪律**（`never` 穷尽检查、旁路数据三问）也做得比多数开源项目严。

问题集中在两处：**流式渲染的成本模型没有分层**（每来一个碎片就把整条会话重算一遍），以及**"卡住了"这条反馈链路整条是死的**（组件从未挂载，时间戳从未赋值）。

按严重度统计：

| 级别 | 数量 | 说明 |
|---|---|---|
| P0（数据/安全） | 0 | 未发现数据丢失、越权、XSS 面 |
| P1（体验断层） | 5 | 长回复卡顿、搜索雪崩、停滞无提示、格式渲染缺失 |
| P2（明确缺陷） | 7 | 任务列表丢勾选、tooltip 无效、快捷键语义冲突、布局缩进不一致 |
| P3（质量债） | 6 | 压行规避门禁、死代码、注释与实现矛盾 |

## 二、P1 问题（优先修）

### P1-1 流式渲染无节流，每个事件触发一次全量渲染

**位置**：`hooks/useCcEventStream.ts:93-103`

```ts
const apply = (p: CcEventPayload) => {
  if (p.seq < seqRef.current) return;
  ...
  dispatch({ type: "event", event: p.event });   // 每条事件一次渲染
```

**缺陷表现**：Tauri 的 `listen` 回调是独立宏任务，React 18 的 automatic batching 跨不过去 —— **每来一条 `text` 事件就是一次完整的 reducer + 整棵树 reconcile**。CLI 侧一个碎片一条事件，长回复就是几百次渲染。当前链路因为网关伪流式（整轮少量 `content_block_delta`）还没暴露，一旦上游改成真流式或打开 `--include-partial-messages`，卡顿会立刻显形。

**严重度**：高。这是后面 P1-2、P1-3 的放大器。

**修复建议**：在 `apply` 与 `dispatch` 之间加一层按帧/按时间窗合并的缓冲。

```ts
// 与现有 reconcile 防抖同址，不新增生命周期
let pending: CcEvent[] = [];
let flushTimer: ReturnType<typeof setTimeout> | undefined;
const flush = () => {
  flushTimer = undefined;
  const batch = pending; pending = [];
  dispatch({ type: "batch", events: batch });   // 新增一个 action
};
const apply = (p) => {
  ...
  pending.push(p.event);
  if (flushTimer === undefined) flushTimer = setTimeout(flush, 60);
};
```

`ccReducer` 加 `case "batch": for (const e of action.events) view = applyEvent(view, e)` —— 纯函数复用，穷尽检查会强制补分支，风险可控。

**社区同口径**：Chrome 团队关于"渲染流式 LLM 响应"的建议、以及多份 2026 年的工程笔记都收敛到 **50–100ms 一批**（人类阅读速度远低于模型输出速度，16ms/条是纯浪费）。

### P1-2 Markdown 每个 tick 全量重新词法，没有块级冻结

**位置**：`components/ccgui/MarkdownText.tsx:49`

```ts
const tokens = useMemo(() => (text ? lexMarkdown(text) : []), [text]);
```

**缺陷表现**：`text` 是整条回复的累计字符串，流式期间每个碎片都会变 ⇒ `useMemo` 每次都失效 ⇒ 对**整段已成文的内容**重新跑一次 `marked.lexer`，再重建整棵元素树。单条回复的累计代价随长度**平方增长**（长度 L，tick 数 ∝ L，每 tick O(L)）。

配合 P1-1，一次 3000 字的长回答 = 数百次 × 全量词法的开销。

**严重度**：高。

**修复建议**：按 top-level token 切块 + 每块 `memo`，只重解析最后一块。

```ts
// ccMarkdown.ts 增加
export function splitBlocks(text: string): Array<{ key: string; raw: string }> {
  return lexMarkdown(text).map((t, i) => ({ key: `${i}`, raw: (t as { raw?: string }).raw ?? "" }));
}
```
```ts
// MarkdownText 内
const blocks = useMemo(() => splitBlocks(text), [text]);
return blocks.map(b => <MemoBlock key={b.key} raw={b.raw} {...markMarksFor(b)} />);
```

关键点是 **`key` 用块序号是安全的**：流式期间只有追加，块边界不会重排。`marked.lexer` 的 `token.raw` 就是该块的原始源码，可以直接喂给一个 `memo` 的 `<MarkdownBlock>` 子组件。

⚠️ 有一个硬约束要一并处理：`seg` 游标（会话内搜索的叶子上标）目前是**整个 `text` 一次渲染期递增**的（`MarkdownText.tsx:53-55`）。拆成多块后，每块的起始 `seg` 必须显式传入并保持全局连续，否则搜索命中区间会整体错位 —— 这是 `lib/ccMarkdown.ts` 头注里"两边必须一起动"那条红线的直接延伸，`markdownLeaves` 也要同步改成按块累加。

**社区同口径**：Vercel AI SDK 的 memoized-markdown cookbook、llama.cpp PR #28460 的"只重算流式那一轮"、以及基于 mdast 的增量渲染实现（冻结已完成块、只重解析尾部 frontier）都是同一套思路。其中 mdast 方案对单个未闭合代码巨块会退化为全量重解析 —— 与我们改完后的最坏情况一致，不构成额外风险。

### P1-3 会话内搜索打开时，每个 tick 全量重建索引

**位置**：`hooks/useCcConvSearch.ts:23`

```ts
const hits = useMemo(() => (open ? buildConvHits(messages, query) : []), [open, messages, query]);
```

**缺陷表现**：`messages` 每 tick 都是新数组引用 ⇒ 依赖必然失效 ⇒ `buildConvHits` → `convSegments` → **对每一条消息跑 `marked.lexer`**（`summarize.ts:129-147` 走 `markdownLeaves`）+ 全文 `indexOf` 扫描。

后果是三重叠加：
1. 一条 200 屏的会话，搜索打开时每 tick 对它整体做一遍 markdown 词法；
2. `marksByMsg` 依赖 `hits` 也重算，产生新 `Map` ⇒ 所有 `MessageList` 子节点的 `marks` prop 引用变化；
3. 因此 `MessageText` / `ToolCard` / `UserMessageBubble` 的 `memo` 在这一刻全部失效 —— 本来只为流式那一条付的钱，变成整棵树付。

**严重度**：高（"搜索 + 生成中"是常见组合，正是找报错的时候）。

**修复建议**：索引按消息粒度缓存，只增不改。

```ts
// 以 msgId + 文本长度为 key，命中不重算
const segCache = useRef(new Map<string, { sig: string; segs: string[] }>());
function segsOf(m: CcMessage) {
  const sig = m.kind === "tool" ? JSON.stringify(m.tool) : (m.text ?? "").length + ":" + (m.text ?? "").slice(-16);
  const cur = segCache.current.get(m.id);
  if (cur && cur.sig === sig) return cur.segs;
  const segs = convSegments(m);
  segCache.current.set(m.id, { sig, segs });
  return segs;
}
```

再叠一层 debounce（流式期间 300ms 重算一次即可，人不会在读到之前就按下一处）。**注意**：debounce 只作用于「messages 变化」这条触发，查询词变化必须立即生效。

### P1-4 "卡住了"这条反馈链路整条是死的

**位置（两条独立缺陷叠加）**：

1. `components/ccgui/TurnActivity.tsx:22` 的 `<TurnActivity>` **组件从未被任何地方渲染** —— 全仓只有 `ConversationStream.tsx:14` import 了同文件里的纯函数 `turnActivity`，组件本体是死代码。
2. 即使挂上也不会工作：它靠 `Date.parse(m.at)` 算"最近收到记录多少秒前"（`TurnActivity.tsx:30-32`），而 **`ccReducer` 里所有消息的 `at` 恒为 `""`**（`ccReducer.ts:222, 240, 366, 402`）⇒ `Date.parse("")` = `NaN` ⇒ `age` 恒 `null` ⇒「最近收到记录 · N 秒前」与「暂未收到新进展」这两句**永远不会出现**。

**缺陷表现**：长任务（一次跑 30 个 Edit、或远端 SSH 抖动）时，界面上只有 `ScrollToBottom` 那句"本轮进行中"和一个 spinner。用户没有任何时间参照，30 秒后开始怀疑是不是挂了 —— 而这正是 `TurnActivity.tsx:5` 那句注释想解决的事。

**严重度**：高（用户明确关注的"反馈机制"，这里恰好是最薄弱的一环）。

**修复建议**（两步，都小）：
1. 给消息补真实时间戳：`applyEvent` 里 `at: new Date().toISOString()`（注意重放时历史流水应保留原时间，只有实时路径取 now —— 判据是 `action.type === "event"`）。
2. 把停滞提示并入已有出口，不再挂一个孤立组件：
   - `ConversationStream.tsx:192` 传给 `ScrollToBottom` 的 `activity` 已经是每 tick 计算的字符串，直接在这里拼"最近 42 秒无新记录"；
   - `ClawdWorkspace` 的 `.cc-clawd-note`（`ClawdWorkspace.tsx:94`）是常驻状态行，比浮动条更适合放"本轮 3 分 12 秒 · 最近 40 秒无新记录"。
3. 删掉 `TurnActivity.tsx` 里的死组件，或真正挂载它（二选一，不要留着）。

**开源同口径**：主流 agent 界面（Claude Code 自身 TUI、Cursor 的 agent 面板）都把"已运行时长 + 最后一次活动时间"作为静默期的唯一安抚手段；只给 spinner 是被公认的失败模式。

### P1-5 代码块无语法高亮，长代码只能内部滚动

**位置**：`MarkdownText.tsx:127-152`

```tsx
<pre data-cc-inset className="max-h-[240px] overflow-auto ... text-muted-foreground">
  {leaf(ct.text)}
</pre>
```

**缺陷表现**：
- 代码全是同色灰字，语言角标（`:134`）标了语言却不高亮，等于承诺了没兑现；
- 超过 240px 只能内部滚动 —— 与页面滚动形成**嵌套滚动**，触控板手势极易误滚到页面，读长代码时体验明显差；
- 没有"展开全文 / 折叠"控制。

**严重度**：高（对话 GUI 的主要产出就是代码和 diff；diff 已经做得相当讲究，代码块却仍是纯文本，反差很大）。

**修复建议**：
- 高亮用 **Shiki** 的按需加载（`createHighlighterCore` + 只预载常用 8–10 种语言，其余动态 import），或 `highlight.js` 的子集构建。不要引 Monaco（体积与这个页面的定位不匹配）。
- 长代码改成「默认折叠到 16 行 + 展开全文」，把内部滚动降级为兜底（与 `DiffBlock` 的 `compactDiff` 语汇一致）。

**开源同口径**：`markstream-vue`、`assistant-ui` 生态、llama.cpp 新版 chat UI 都是"Shiki 按需 + 折叠展开"的组合；没有一家在主聊天流里用 Monaco。

## 三、P2 问题（明确缺陷）

### P2-1 GFM 任务列表的勾选状态被完全吞掉

**位置**：`MarkdownText.tsx:159-172`（`list` 分支）与 `MarkdownText.tsx:219`（`default`）；`lib/ccMarkdown.ts:76-107`（`walkInlineLeaves` 缺 `checkbox`）

**证据**（node 实跑 `marked.lexer`，与 `ccMarkdown.ts:13` 的 options 一致）：

```
items[0] = { task: true, checked: false, tokens: [ "checkbox", "text" ] }
```

`blocks()` 的 switch **没有 `checkbox` 分支** ⇒ 落入 `default` ⇒ `any.text ?? ""` ⇒ 空串。`[ ]` / `[x]` 标记与 `checked` 状态双双丢失，用户只看到普通 `•` 列表。

**缺陷表现**：模型输出 TODO 清单（极常见）时，已完成项与未完成项看起来一模一样。

**严重度**：中（功能性格式丢失，且零测试覆盖 —— 全仓 `components/`、`lib/` 的测试里没有一条 `- [ ]` 用例）。

**修复建议**：
```tsx
case "checkbox": {
  const c = t as Tokens.Checkbox;
  return <span key={i} aria-label={c.checked ? "已完成" : "未完成"}
    className={...}>{c.checked ? "✓" : "○"} </span>;
}
```
同时在 `walkInlineLeaves` 里把 checkbox 的 `raw`（`"[x]"` / `[ ]`）纳入叶子 —— 否则搜索索引与渲染又分叉了（这是 `ccMarkdown.ts` 头注那条红线的第二个落点）。补两条测试钉住（紧凑 / 松列表各一）。

### P2-3 `Ctrl+Enter` 有两套语义，与发送键偏好冲突

**位置**：`Composer.tsx:252`

```tsx
if (running && onSendNow && event.key === "Enter" && (event.ctrlKey || event.metaKey) && !event.shiftKey && !event.altKey) {
  event.preventDefault(); void send("now"); return;
}
if (isSendKey(sendKey, event)) { event.preventDefault(); void send(); }
```

**缺陷表现**：用户把发送键设成 `ctrlEnter`（`lib/ccSendKey.ts` 的两档之一）后，运行中按 Ctrl+Enter 本意是"发送"，实际触发的是**软中断 + 立即重发**。发送键偏好在运行中被静默改写，且界面上没有任何提示。

**严重度**：中（`ccSendKey` 的头注专门强调"判据必须先拦 shiftKey"，说明这个交互已经被认真对待过一次，这里是漏掉的第二处）。

**修复建议**：`now` 档改用不与发送键冲突的组合（如 `Alt+Enter`），或仅在 `sendKey === "enter"` 时才让 `Ctrl+Enter` 承担 `now` 语义，并在 `ComposerFooter` 的提示里写清当前实际绑定。

### P2-5 `ExecutionSummary` 受控/非受控混用，搜索关闭会强制收起用户展开的分组

**位置**：`ExecutionSummary.tsx:10`

```tsx
<details className="cc-execution-summary" open={matches || verbosity === "v" ? true : undefined}>
```

**缺陷表现**：搜索命中时 `open={true}`，搜索关闭后变成 `undefined` ⇒ React 移除 `open` 属性 ⇒ **用户此刻正打开着的工具分组被强制收起**。反过来，用户在「详细」档手动折叠了某个分组，下一次 re-render 也不会记住他的选择。

**严重度**：中低（"我打开的分组自己关了"是可感知的失控感）。

**修复建议**：改成完全受控 —— `const [open, setOpen] = useState(...)` + `onToggle` 同步，`matches` 只作为"派生展开"（`const revealed = open || matches`），与 `ToolCard.tsx:194` 的 `reveal` 写法保持一套语义。

### P2-6 Clawd 角色用 76px 布局内边距占位，与项目自己的"浮层不占布局"红线冲突

**位置**：`clawd.css:51`

```css

```

**缺陷表现**：
- 含工具调用的消息整体右移 76px，而助手正文不缩进 ⇒ **正文左边缘与工具行左边缘不对齐**，一屏里两种左边距；
- 角色飘走（`data-landing="task"` 时它会移动到某条消息旁）后，这 76px 空白仍留在原处；
- 窄窗下正文实际可用宽度从 834px 掉到 758px，与 `@container(max-width:650px)` 的断点叠加后更紧。

**严重度**：中（这是"对话页看起来乱"的直接来源之一，性质与 `DiffBlock` 头注里"碎档字号是显得乱的主因"同源 —— 只不过这次是**左边距碎档**）。

**修复建议**：角色改为纯浮层（`position: absolute` + `pointer-events` 可控），需要避让时用 `transform: translateX()` 把正文推开一个动画帧，而不是在 CSS 里留永久坑位。这与项目既有红线「浮层一律不占布局」完全一致。

## 四、P3 问题（质量债）

### P3-1 300 行门禁被"压行"规避

**位置**（每条都是把两个语句塞进一行）：

- `components/tabs/CcPane.tsx:17`、`:20`（两个 import 挤在一个 import 语句后）
- `components/ccgui/Composer.tsx:18`、`:116`、`:121`
- `lib/... useCcSteering.ts:33`、`:50`、`useCcSendQueue.ts:65`、`:67`
- `components/ccgui/ClawdWorkspace.tsx:17`
- `TurnActivity.tsx:30`、`ClawdWorkspace.tsx:104-108`（双层 `records &&`）

## 六、专项二：流式渲染成本模型

单条 `text` 事件到达后实际发生的事（按调用顺序，n = 消息数，L = 当前回复长度）：

| # | 动作 | 位置 | 复杂度 |
|---|---|---|---|
| 1 | reducer `upsertText` 复制整条消息数组 | `ccReducer.ts:219-231` | O(n) |
| 2 | `clawdActivity(view, …)` | `ConversationStream.tsx:78` | O(n) |
| 3 | `pendingApprovals` 全量 filter（依赖 `view.messages` ⇒ 每 tick 失效） | `ConversationStream.tsx:86-89` | O(n) |
| 4 | `turnActivity` 全量遍历 + slice | `ConversationStream.tsx:192` | O(n) |
| 5 | `MessageList` 三次遍历（todo / user / 分组） | `MessageList.tsx:96-129` | O(n) |
| 6 | 流式那条 `MessageText` → `marked.lexer(全文)` | `MarkdownText.tsx:49` | **O(L)** |
| 7 | `useLayoutEffect` 写 `scrollTop = scrollHeight`（强制同步布局） | `useCcStreamScroll.ts:78-82` | O(布局) |
| 8 | 所有子节点元素重建（memo 能挡住渲染体，挡不住元素对象与协调） | `MessageList.tsx:137-241` | O(n) |

**总量**：每 tick ≈ O(n + L)；流式全程 ≈ O(tokens × (n + L)) —— 对长回复是**平方级**，而且第 7 步把第 6 步刚算完的布局又强制同步一次。

**已经做对的部分**（不要动）：
- `.cc-msgcol > *` 的 `content-visibility: auto + contain-intrinsic-size: auto 80px`（`index.css:1210`）—— 离屏节点的 paint/layout 已经跳过，这是正确的第一道闸；
- `ToolCard` / `DiffBlock` / `MessageText` / `ThinkingBlock` / `UserMessageBubble` 的 `memo` 边界；
- `ToolCard` 的 `reveal` 用派生值而不是 `setOpen` 的 effect（`:194`，这条是踩过坑写对的）。

**没做对的部分**：上述 6 个 O(n) 遍历没有一处是按"只有最后一条会变"来切分的，全部每 tick 重跑；第 6 步完全没有块级缓存。

**建议的量化目标**：单条 3000 字回复、会话 200 条消息时，流式期间每 tick 的主线程占用从当前量级压到 **< 4ms**（约 1 帧的一半）。可验收的代理指标：`performance.mark` 包住 reducer + `MessageList` 渲染，`PerformanceObserver` 统计流式全程的 long task（> 50ms）数量应趋近 0。

| 问题 | 开源做法 | 参考价值 |
|---|---|---|
| 流式 markdown 全量重解析（P1-2） | Vercel AI SDK 的 memoized-markdown cookbook：`marked.lexer` 按 top-level 块切分、`token.raw` 作块内容、块级 `memo`，只重解析最后一块 | **直接可用**，约 60 行改动，是投入产出比最高的一项 |
