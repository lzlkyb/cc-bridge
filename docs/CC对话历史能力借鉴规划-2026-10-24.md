# CC 对话历史能力：desktop-cc-gui 借鉴与落地规划

> 日期 2026-10-24（二次修订：补远端方案）。对象 `D:/AItool/research/desktop-cc-gui`（`af3537bee`）。
> 目的：cc-bridge 的 CC GUI 目前**没有任何历史能力**（关掉 app 连当前会话都看不到），
> 本文回答「别人怎么做的、哪些该学、怎么落到我们身上」。
> 阅读顺序：§一 结论 → §二 它的设计 → §三 学什么 → §四 不学什么 → §五 它没解决的 → **§六 远端（本期必做）** → §七 三期计划。

## 一、一句话结论

它把「历史对话」当成**索引问题**，不是「读文件问题」：

```
磁盘（CLI 自己的 jsonl，永不修改）
  ↓ 扫描（两级门禁 + stat 签名，增量）
SQLite 索引（元数据表 sessions + 全文表 messages_fts）
  ↓ 分页（一页 100 条，往前翻）
内存消息列表（与实时流共用同一个数组）
```

关键不是「怎么读 jsonl」，而是四件事：

1. **索引与转录分离** —— app 的数据（置顶/归档/重命名/模型）进自己的表，CLI 的转录一个字不动。
2. **两级门禁** —— 没变化时一次启动只做 readdir + stat，不解析任何文件。
3. **历史与实时同构** —— 打开历史 = 打开一个带 `sessionId` 的 tab。不写第二套渲染、第二套状态。
4. **远端是一等公民，不是加分项** —— 我们的主场景是 SSH 远端跑 claude，那里的转录**本机一行都没有**。只做本地等于主路径空白（详 §六）。

模块规模：`src-tauri/src/history/` 共 **11453 行**（extract 3146 / reader 2437 / scanner 1610 / discovery 1588 / search 1115）。这个体量是为 **11 个引擎**服务的，cc-bridge 只有 claude，能砍掉大半（见 §四）。加上远端后我们的实际量级 **2600~3200 行**（含测试）。

## 二、它的设计（只列对我们有决策价值的部分）

### 1. 数据模型：`sessions` 表不存正文

`db.rs:757-772`

```sql
CREATE TABLE sessions(
    engine, session_id, workspace_path,      -- 身份 + 分组
    file_path, file_size, file_mtime_ms,     -- ← 增量扫描的判据
    title, preview, created_at, updated_at, message_count,
    pinned, custom_title,                     -- 用户态（app 自己的数据）
    PRIMARY KEY(engine, session_id)
);
```

三件事值得注意：

- **`file_size + file_mtime_ms` 是索引的灵魂**。列表页只查这张表，一次 SQL 出全部会话，不碰任何 jsonl。
- **`pinned` / `custom_title` 和 CLI 的数据分表存在这里**。重命名不改标题生成逻辑，只是 `custom_title` 有值时覆盖显示。
- **`message_count`** 让列表能显示「12 条消息」，不用打开文件数。

`SessionMeta`（`history/mod.rs:56-91`）还多三个字段，理由写在注释里，对我们全部适用：

| 字段 | 它的理由 |
|---|---|
| `model` / `effort` / `provider` | **引擎转录只记裸模型名**。重开的会话若只看转录，恢复不了 provider 和模型 —— 尤其在手机、另一个窗口打开时 |
| `remote` / `remote_path` | 远端会话在本机没有转录，只有路径 |

### 2. 归档是 app 的标记，不是删文件

`db.rs:774-785` 的注释是整份代码里最值得抄的一句：

> App-owned archive markers. **CLI transcripts remain untouched**; the independent marker survives scanner upserts and workspace re-adds. The snapshot also covers plugin-fed remote sessions, which have no local row in `sessions`.

`session_archives` 存 `snapshot_json`（整条元数据快照）而不是外键，所以**即使 `sessions` 表被清空、工作区被移除再加回、远端会话本机根本没有行**，归档标记依然成立。恢复时从快照重建。

同一思路：`accepted_internal_frames`（内部帧身份）、`session_models`、`session_efforts` 全是**独立小表**，不塞进 `sessions` 一个 JSON 列里 —— 因为它们的生命周期不同（会话删了才一起删）。

### 3. 扫描：两级门禁（`scanner.rs:140-203`）

```
候选文件枚举（只 readdir，不读内容）
  ↓
Tier-1：全体 (path, size, mtime) + 工作区列表 + 缓存版本 → 一个 sha256
  ↓ 与 meta 表里上次的签名比较
  ├─ 相同 且 标题版本一致 → 直接返回，零解析（return Ok(None)）
  └─ 不同 → Tier-2：逐文件比对，各自决定 reparsed / reused
```

两个细节：

- **`TITLE_VERSION: &str = "10"`**（`scanner.rs:24`）。标题/预览的派生规则一改就 bump，于是**已索引但文件没变的会话也会重建一次**。注释说明了为什么不能靠「文件没变就不管」：旧标题里混着哪条规范化规则没生效，事后无法判断。
- **`ScanReport { scanned, reparsed, reused }`** 把「复用」显式计数。这是对增量的自证：如果 `reused` 一直是 0，说明门禁根本没生效。

对我们意味着：本机实测 63 个会话文件 / 24MB（单文件最大 1MB）。没有门禁，每次进对话页都要解析 24MB；有门禁，没事时只 readdir + stat。

### 4. 发现会话文件：cwd 编码有多重拼法（`discovery.rs:109-138`）

这段推翻了我之前的一个判断。我当时说「目录名是 cwd 的单向编码，从 cwd 正算就行」。它的注释是：

> Windows terminals disagree on drive-letter case, slash direction, and trailing separators, and **the CLI encodes whatever cwd spelling it saw**.

所以同一个工作区可能有多个编码目录，必须枚举：

1. 原始拼法（`workspace.to_string_lossy()`）
2. 去尾部斜杠的拼法
3. 两者的 `canonicalize` 结果（`strip_verbatim_prefix` 去掉 `\\?\`，因为 CLI 编码的是裸路径）

编码规则本身（`mod.rs:213-223`）：ASCII 字母数字和 `-` 保留，**其余一律变 `-`**。⇒ 含中文的路径会被整段抹平，不同路径可能撞到同一个目录名。它只靠「文件 stem 去重」兜底，没有解决 —— 我们也只能这样。

另外两个必抄的：

- **`CLAUDE_CONFIG_DIR`**：`engine_home(Some("CLAUDE_CONFIG_DIR"), ".claude")`。硬编码 `~/.claude` 会让改过配置目录的用户历史整个消失。
- **跳过 `history.jsonl`**：`if stem == "history"` 那个文件不是会话，混进列表会出一条点不开的条目。实测它在本机位于 `~/.claude/history.jsonl`（905KB，顶层），并不在 `projects/` 下 —— 我们的扫描限定在 `projects/` 内，所以这条只是冗余防御（见 §六.5）。

### 5. 标题派生：剥噪声（`mod.rs:424+`）

`strip_title_noise` 剥掉 `<file …>…</file>` 包裹（Claude Code 附文件内容时包在 user 消息里）、`[Image #N, WxH]` 占位符、`<local-command-*>`。**不剥的话，标题会变成"文件内容"而不是用户说的话。**

标题取「第一条非噪声的 user 正文」，截 80 字符；`preview` 取不到标题时的回退。这和我们的现状对得上 —— 实测每个 jsonl 首条 user 正文就是标题来源。

### 6. 打开历史：分页，而且复用实时渲染

`reader.rs:12-17` 的分页形状：

```rust
pub struct SessionPage {
    pub messages: Vec<Message>,
    pub next_before: Option<i64>,   // 上一页游标，None = 到头
    ...
}
```

- `limit` 默认 100，`clamp(1, 500)`；首次（`before_seq: None`）取**最后** limit 条（最新），往前翻。
- `load_session_page` 走 `spawn_blocking`（不能在 async 里做解析）。

**最关键的一点**（`features/chat/store.ts:49-79` + `store/`）：历史页灌进的是**同一份 `bySession[key].messages`**，实时流也写这份。所以：

- 历史消息和今天的流式消息用同一套 `MessageTimeline` 渲染，不需要"回放模式"。
- 发消息续聊时，`engine/claude.rs:209-212` 只是 `req.session_id` 有值就加 `--resume <id>`。**打开历史 = 打开一个带 sessionId 的 tab**，没有额外的"恢复会话"流程。

### 7. 远端历史：拉回来缓存（`reader.rs:657-760`）

对 cc-bridge 的 SSH 场景几乎是量身写的：

1. **路径形状白名单** `is_plausible_remote_session_path`：必须是绝对 `.jsonl` + 落在已知会话目录形态下（claude 是 `/projects/`）+ 拒绝 `..` 与 NUL。**挡住借 IPC 读任意文件**。
2. **先远端 `stat -c %s` 卡上限**（64MB），再 `base64` —— 避免 1.33× 膨胀后全量进内存。
3. 缓存到 `app_home()/remote-sessions/<sha256(workspace|engine|session|path)[:16]>`。
4. 缓存文件 **stat 签名不变就不重写**，翻页直接命中解析缓存。

⚠️ 它的 64MB 上限对我们**不能照抄**，我们自己的 helper 缓冲只有 4MB（§六.4）。

### 8. 搜索：中文必须用 trigram（`search.rs:1-45`）

这段是给我们的礼物，因为我们的用户是中文。它的原话：

> Tokenizer is `trigram`, not `porter unicode61`: **unicode61 treats a run of Chinese as one token, so CJK substring search is impossible**. trigram matches substrings (≥3 chars) across Chinese, English and punctuation alike. Queries containing any token shorter than 3 chars would silently drop that token in FTS5 (**verified: `"提交"` matches nothing, `"已生成" "提交"` matches as if only 已生成 were asked**), so they take the LIKE fallback with exact AND semantics instead.

两条硬结论：

1. FTS5 默认分词器对中文**不可用**，必须 `trigram`。
2. `trigram` 下 **< 3 字符的词会被静默丢弃** ⇒ 中文双字词（"提交"、"部署"）必须走 LIKE 兜底，且要显式 AND 语义。

其它两个细节：

- 外部内容 FTS（正文存 `session_messages`，`messages_fts` 只存索引，触发器同事务维护）—— 文本不存两遍。
- snippet 高亮用控制字符 `\u{1}` / `\u{2}` 当标记，**消息内容无法伪造出高亮**（对比 `agentsview` 用 `<mark>`，用户消息里写个 `<mark>` 就能伪造）。

### 9. 重启恢复：带版本的 localStorage + 草稿 tab

`features/chat/store/persistence.ts`：

- 键带版本：`ccgui-next.openTabs:v1`、`ccgui-next.activeSession:v1`；读到旧键做**一次性迁移**（写新键 + 删旧键）。
- `readStoredJson(key, validate)`，`validate` 逐字段判型 —— 坏数据不污染状态。
- `dedupeTabs`：同 `(engine, sessionId, workspacePath)` 去重（注释：重复会让 React key 相同，破坏 reconciliation）。
- **`sessionId: string | null` 表示草稿 tab**（还没发第一条消息），键是 `new:${engine}:${workspacePath}`；发首条消息时把草稿搬到真键。⇒ 用户打了一半字切走/重启，字不丢。

## 四、不该学什么

| 不学 | 理由 |
|---|---|
| 11 个引擎的统一抽象 | cc-bridge 只有 claude。`EngineEvent` 26 变体 + 归一化层在这里是纯负债。**但 `SessionMeta.engine` 字段留着**，将来加引擎不用改表 |
| worktree 子行 / 工作区分组（section）/ 拖拽排序 | 超出当前需求；我们的「工作区」就是一条 SSH 连接 + 本机 |
| 多 tab（`SessionTabStrip`） | 我们的页签是「对话/连接/终端」，会话在页内切换即可。多 tab 会和我们既有的 `TabsContent` 容器查询、浮层不占布局的规矩打架 |
| `history/` 全量 11453 行 | 按上面的清单挑，实际需要约 2600~3200 行（含测试、含远端） |
| 归档快照的 `snapshot_json`（第一版） | 它是为「工作区被移除再加回」设计的。我们先做普通归档（`archived_at` 标记），撞到问题再加快照 |
| 远端 64MB 上限 | 我们走 helper 通道，单条命令输出上限 4MB（`ssh_helper.rs:37`）。照抄会得到一个「永远失败的大文件」 |

## 五、它没解决、我们要做得更好的

### 1. 审批语义在历史里丢失（我们的差异化点）

它的 `Message` 只有 `role / text / path / args / result / todos / usage / model`。**没有「这条命令被拒绝过」这个概念** —— 因为它的产品里审批全被就地拒了，历史里只剩一条失败的工具结果。

cc-bridge 有真正的审批卡，所以回放必须多带一个字段：

```ts
verdict?: "allowed" | "denied" | "answered" | "skipped" | "expired"
```

否则用户回看三个月前的会话，看到 `Bash` 工具「失败」，无法区分是命令报错、还是当时自己拒了、还是 60s 超时。这是**只有我们能做对的部分**，也是审批卡作为差异化点的自然延伸。

⚠️ 实现前的待验证项：jsonl 里记 `tool_use`（带 `id`），但**不记审批结果**。要把 verdict 合并回去，需要在落盘时按 `tool_use_id` 关联我们自己的审批事件。远端会话的 verdict 只能存在本机索引里（远端 jsonl 不写），所以**跨机不会同步** —— 换一台电脑看同一条远端会话，verdict 会缺席。这是可接受的降级，但界面上要能区分「没记录」和「被拒」。

### 2. 进程复用后 `resume_id` 与历史的关系要理清

我们现在的实现是「进程复用 + 死了才 resume」（P0 探针推翻了它抄的「一轮一进程」）。这意味着：

- 当前会话的 `resume_id` 由 `system/init` 回填，纯内存。
- 落盘时**必须同时记 `resume_id` 和消息快照**：只记 `resume_id`，重启后 CLI 知道上下文但界面空白；只记消息，恢复后发消息又是新会话（CLI 那边断链）。

它的做法是「不落盘，永远从 jsonl 重建」（因为它是长驻渲染 + 打开即加载）。我们有进程复用，恢复时可以更快：**先读自己的快照秒开，再用 jsonl 对账**。

### 3. 它的 cwd 编码会让中文路径塌掉

`claude_encode_project_path` 把非 ASCII 字母数字全变 `-`，`D:\项目\a` 和 `D:\项目\b` 可能落到同一个目录名。它靠 stem 去重躲过冲突，但**会漏会话**（seed 里的会话 id 都在，只是可能混了别的项目的）。

我们至少要在「按 cwd 找目录」时，**用目录内 jsonl 里的真实 `cwd` 字段二次校验**再归到这个工作区，而不是只信目录名。

✅ 实测（本机 `021d92e5-…jsonl`）：第 4 行起的事件带 `cwd: C:\Users\19145` 和 `version: 2.1.296`；前 3 行（`last-prompt` / `mode` / `permission-mode` / `atis-latch`）不带。所以**校验时不能只看第一行**，要扫到第一条带 `cwd` 的事件为止。这对远端尤其关键 —— 见 §六.4。

## 六、远端历史：必须做，从期二开始

**已定方案 A：只读按需 + 本机缓存。** 不做后台全量镜像。

### 1. 为什么不能留在「可选」

`cc_start` 在远端模式下走的是 `ssh <dest> "echo <b64> | base64 -d | bash"` → 远端 `exec claude`（`cc_cmds.rs:254-269` + `channel.rs:116-147`）。转录只会落在**远端** `~/.claude/projects/`。

代码核查：整个仓库**没有任何一处**读取远端 `~/.claude`。`cc_reset` 只清 ring / resume / pending，不碰任何 jsonl。也就是说按原分期（远端排期三）做完期一+期二，远端用户打开对话页依然是空白 —— 功能对主路径不可用。

附带收益：终端页里手敲 `claude` 产生的会话也在这同一份目录里。历史列表做出来之后，**终端页和对话页共享一份历史**，这是本地-only 方案做不到的。

### 2. 实测与代码证据

| 结论 | 证据 |
|---|---|
| 远端 claude 由本机 ssh 拉起，非本机进程 | `cc_cmds.rs:241-269` 两个分支；`remote_command` 用 `exec` |
| 远端执行通道现成，且能零握手复用 | `ssh_cmds.rs:756 run_via_helper` + `ssh_helper.rs` 常驻会话（`HELPER_IDLE_TTL` 300s） |
| jsonl 自带真实 `cwd`，不用猜目录编码 | 本机实测 `cwd` / `version` 从第 4 行起出现 |
| 文件名就是 session id | `<uuid>.jsonl`，`--resume` 直接用 stem |
| 单个转录不大 | 本机 63 个 / 24MB / 最大 1MB |
| 远端链接参数可直接复用 | `ssh_cmds.rs:1662 ssh_link_args`（`pub(crate)`，已经是给 `cc_session` 用的） |
| 远端目录形态**未实测** | 本机唯一一条远端连接是**密码认证、没配密钥**，开发机无法免密登录，因此上面的脚本与上限都只在 GNU 环境验证过 |

### 3. 通道选型

| 方案 | 优点 | 致命点 |
|---|---|---|
| `ssh_sftp_get`（`ssh_cmds.rs:1739`） | 有 `.part` + rename、取消、进度事件 | 入参重（`transfer_id`/`app` 事件/`overwrite`），且走独立 scp = 一次完整握手；为「读一个 200KB 缓存文件」付这个代价不值 |
| 一次性 `ssh cat` | 简单 | 每次完整握手（`SSH_ONESHOT_TIMEOUT` 30s） |
| **helper + `base64`（选它）** | 零握手、一进一出、`MAX_BUF` 自带护栏 | 单条输出上限 4MB；PTY 会把 `\n` 变 `\r\n` |

结论：**列表扫描与正文读取都走 `run_via_helper`**，超过 2.5MB 的转录降级到 `ssh_sftp_get`。

### 4. 六个硬约束（每条都能让人踩一天）

1. **helper 的远端正是一个 `exec /bin/sh`，不是登录 shell**（`ssh_helper.rs:102`）。所以：
   - `$HOME` 可用（sshd 设的），`~/.claude` 没问题；
   - 但用户在 `.bashrc` / `.profile` 里 `export CLAUDE_CONFIG_DIR=…` 的情况**读不到**。
   - ⇒ 扫描脚本必须自己包一层 `bash -lc '…'`，与 `probe_script`（`channel.rs:150`）同源。
2. **helper 单条命令输出上限 4MB**（`ssh_helper.rs:37 MAX_BUF`），超出部分**静默丢弃** —— 表现是 base64 尾部被截断、解码失败。原文件上限要按最坏情况算：`base64 长度 = ceil(size/3)*4`，再加每 76 字符一个 `\r\n` 折行。

   | 原文件 | base64 | 含折行 | 判定 |
   |---|---|---|---|
   | 1.0MB | 1.40MB | 1.43MB | 安全（本机最大就是 1MB） |
   | 2.5MB | 3.50MB | 3.59MB | **取这个作上限** |
   | 3.0MB | 4.00MB | 4.10MB | ❌ 撞穿 4MB |

   ⇒ 卡 **2.5MB**，超过走 sftp 通道（scp 无此限制）。
3. **必须 base64，不能 `cat` 原始字节**。helper 是 PTY（`-tt`），裸二进制里的 `\x03` / `\x04` / `\x1a` 会被行规当信号或 EOF 处理，`\r` 会被改写。
4. **PTY 会把输出里的 `\n` 转成 `\r\n`**，base64 又默认每 76 字符换行。⇒ 解码前 `retain(|c| !c.is_whitespace())`，不要只 `replace("\r\n", "\n")`。这条不是推测：`ssh_helper.rs:80 scan_result` 里 `line.strip_suffix('\r')` 就是为它写的。
5. **`find -printf` 是 GNU 专有**，远端是 macOS/BSD 时直接报错。项目里 `ssh_sftp_list`（`ssh_cmds.rs:1674`）为同样的问题做了 GNU/BSD 双版 + `is_unknown_option_err` 降级，扫描器要照做：
   - GNU：`find … -exec stat --printf "%Y\t%s\t%n\n" {} +`（**`--printf` 不是 `-c`，`%n` 不是 `%p`**，见 §六.5 的实测）
   - BSD：`find … -exec stat -f "%m\t%z\t%N" {} +`（未实测）
6. **连接身份必须进主键**。同一个人可能为同一台机器存两条连接（不同 user/port），甚至两台机器上有同名 uuid 目录。⇒ 索引主键 `(connection_id, session_id)`，本机用 `NULL`/`""` 表示。**期一就必须这么建表**，否则期二要做数据迁移。

### 5. 扫描与读取

扫描（一次往返拿全量签名，绝不逐目录 `ls`）：

```sh
bash -lc '
cfg="${CLAUDE_CONFIG_DIR:-$HOME/.claude}"
[ -d "$cfg/projects" ] || { echo "__CCB_NO_DIR__"; exit 0; }
find "$cfg/projects" -type f -name "*.jsonl" ! -name "history.jsonl" \
  -exec stat --printf "%Y\t%s\t%n\n" {} + 2>/dev/null
'
```

🔴 **`-c` 必须写成 `--printf`，路径必须用 `%n`。** 我第一版写的是 `stat -c "%Y\t%s\t%p"`，实测（本机 MSYS/GNU stat）两个都错：

- `-c`（`--format`）**不解释反斜杠转义** ⇒ 输出的是字面反斜杠加 `t` 两个字符，按真 TAB 切分会切不开；只有 `--printf` 才解释。
- `%p` **不是 `stat` 的格式符**（它是 `find -printf` 的路径占位），实测输出一个字面 `?`。`stat` 里路径是 `%n`。

实测正确输出（`cat -A` 可见真 TAB）：`1792396953^I190701^I/c/Users/19145/.claude/projects/C--Users-19145/021d92e5-….jsonl$`

- 输出几十 KB（几百个会话），远在 4MB 内。
- 路径必须过 `shell_quote`（`channel.rs:155`）后再拼，虽然这里只有常量，但 `CLAUDE_CONFIG_DIR` 来自远端环境，不可信。
- 目录名解码 → 远端 cwd；**不做** cwd 二次校验（那需要读每个文件头，与「一次往返」冲突）。改在**打开时**校验：解析出的 `cwd` 与列表里的不一致就重写该行并记录。
- `! -name "history.jsonl"` 在本机实测是**冗余防御**：实测 `history.jsonl`（905KB）在 `~/.claude/` **顶层**，不在 `projects/` 下。留着是因为远端 CLI 版本可能不同，代价为零。
- `2>/dev/null` 会吞掉 `stat` 的失败（权限、文件在扫描与 stat 之间被删）。丢一个文件可接受；但它同时会吞 `stat` 不存在这种致命错误 —— 所以**空输出 + 退出码 0 + `[ -d ]` 已通过** 要判成「远端异常」而不是「没有历史」。
- **BSD/macOS 没有 `--printf`**：降级为 `stat -f "%m\t%z\t%N"`（BSD 的 `-f` 走 printf 风格，会解释 `\t`；⚠️ 这一条**未实测**，只在 GNU 上验证过）。判定方式与 `ssh_sftp_list` 相同 —— 先用 `is_unknown_option_err`（`ssh_cmds.rs:300`）识别，不要靠猜远端发行版。

读取（打开某条会话时）：

1. 远端 `stat -c %s <path>` 卡 2.5MB；
2. `base64 < <path>` 经 helper 取回；
3. 解 base64 → 落 `app_home()/remote-cc-sessions/<sha256(connection_id|path)[:16]>.jsonl`（先 `.part` 再 rename）；
4. 写索引行时一并存 `file_size` / `file_mtime_ms`；下次列表签名没变就直接命中本机缓存，**不再拉第二次**。

### 6. 缓存与降级链

远端条目按「能不能拿到正文」分三态，界面上必须能区分：

| 状态 | 触发 | 界面 |
|---|---|---|
| `cached` | 本机有缓存且签名一致 | 正常读，可续聊 |
| `remote-only` | 有元数据，正文未拉过 | 列表正常；点开才拉（首次有加载态） |
| `unavailable` | 连接被删/改名、远端目录消失、文件 >2.5MB 且 sftp 失败 | 列表**保留**（灰显 + 「正文不可用」），**绝不因为连接没了就删历史** |

最后一行是硬要求：连接是配置，历史是数据。用户删一条 SSH 连接不该把三个月的对话记录一起抹掉。

### 7. 安全

- **路径白名单**（抄 `is_plausible_remote_session_path`）：必须绝对路径、必须 `<cfg>/projects/` 前缀、必须 `.jsonl`、拒绝 `..` 与 NUL。**这是防「借 IPC 读远端任意文件」的唯一一道闸**。
- 前缀校验用**解码后的路径**，不用列表返回的原始字符串（原始串来自远端，不可信）。
- 拉取一律 `stat` 先行；不做「先 cat 再判大小」。
- 缓存目录权限沿用 `app_home()`，文件名用哈希而非原始路径（避免非法字符 + 长度问题）。

### 8. 明确不做（方案 A 的边界）

- **不做后台全量镜像**：不预取、不常驻同步、不在启动时扫远端。
- **不做远端全文搜索**（期三只搜已 `cached` 的）。
- **不写远端任何文件**：不删、不改名、不归档远端 jsonl。归档/置顶/重命名只存本机索引表。
- **不做跨机同步**：verdict、置顶、自定义标题都是本机的。

## 七、三期落地计划

### 期一：让「关掉就没了」消失（最小可用，约 1 天）

交付：**重开 app 能看到上次那条对话，能继续聊。**

1. 新表 `cc_sessions`（用 `cc_` 前缀，不沿用它的通用表名 `sessions`，避免以后真有第二个引擎时撞名）：

```sql
CREATE TABLE cc_sessions (
    id              INTEGER PRIMARY KEY AUTOINCREMENT,
    connection_id   TEXT NOT NULL DEFAULT '',   -- '' = 本机
    session_id      TEXT,                       -- init 之前是 NULL
    resume_id       TEXT,
    cwd             TEXT,
    claude_path     TEXT,                       -- 远端续聊必需
    model           TEXT,
    permission_mode TEXT,
    title           TEXT,
    preview         TEXT,
    message_count   INTEGER NOT NULL DEFAULT 0,
    created_at      INTEGER NOT NULL,
    updated_at      INTEGER NOT NULL,
    last_active_at  INTEGER NOT NULL,
    file_size       INTEGER,                    -- 期二用，期一留空
    file_mtime_ms   INTEGER,                    -- 期二用，期一留空
    source          TEXT NOT NULL DEFAULT 'local',
    dropped         INTEGER NOT NULL DEFAULT 0,
    events_json     TEXT
);
CREATE UNIQUE INDEX cc_sessions_ident
    ON cc_sessions(connection_id, session_id) WHERE session_id IS NOT NULL;
```

🔴 **主键必须是自增 `id`，不能是 `(connection_id, session_id)`** —— 我最初就是这么写的，实施时发现行不通：用户发出第一条消息的那一刻就要落盘，而 `session_id` 要等到 `system/init` 才出现，**那段时间根本没有键可写**。所以 `session_id` 只能是可空的业务列（`init` 到达后回填），唯一索引带 `WHERE session_id IS NOT NULL` 才不会互相冲突。内存侧对应 `Shared::row_id`
（`None` = 还没落过盘，下一轮插入新行）。

   - ⚠️ `file_size/file_mtime_ms` 与 `source`（`local`/`remote`）**期一就建好**，期二只填不用改表。`source` 是「从哪来」，与 §六.6 的 `cached`/`remote-only`/`unavailable`（正文当前能不能读）是两回事，别混成一个字段。
   - ⚠️ **`claude_path` 必须存**。远端续聊用的是非登录 bash，PATH 里没有 `~/.local/bin`，拿不到绝对路径就等于「远端没装 claude」（这正是期一前那次修复的原因）。它也是换了连接或重装后**唯一能自己纠错**的依据 —— 存的路径失效时重新 `cc_probe` 一次并更新该行。
2. 落盘时机：**每个 `TurnEnd` / `Exit` / 用户消息后各写一次**（不是每条事件），内容是 `ring` 的事件快照（JSON，一条会话几十 KB）。
   - 用户消息也写：发完就关 app 是最常见的丢内容场景，光等 `TurnEnd` 那句话就白打了。
   - 🔴 落盘在**独立 std 线程**里做，不能在 `TauriSink::emit` 里直接写 —— 那里跑在 claude 的 stdout 读线程上，一次慢查询就能把管道堵满、把对话冻住。
   - 🔴 线程内用代次计数器丢弃过期任务（`Shared::persist_gen`），且**检查必须在拿到 db 锁之后**：两次落盘可能乱序完成，锁外检查挡不住「先拿锁的是旧代次」。
   - `cc_reset` 时把当前会话标记结束而非删除，并 `mark_new_session()` —— 否则用户点了「新对话」、切页再回来，旧对话会自己冒出来（`ring.clear()` 把序号归零，和冷启动在流水上完全一样，必须另外记一个标志）。
3. 退出路径**必须同步落盘一次**（`RunEvent::Exit` 里、`cc.shutdown()` 之前）：异步任务是另一个线程，进程一退就被强杀，而「关掉 app 再看还在」正是这个功能存在的理由。用 `try_lock`，拿不到就跳过（退出时持有 db 的只可能是毫秒级查询）。
4. `cc_restore`：启动时取 `last_active_at` 最新的一条，返回 `{meta, events}`；前端先渲染事件快照，`resume_id` 用于下次 `--resume`。**`connection_id` / `cwd` / `claude_path` 必须一起回传** —— 否则恢复出来的会话不知道要在哪台机器、哪个目录、用哪个可执行文件续（`--resume` 只认 id，远端 resume 必须重新 ssh + cd 远端 cwd）。
   - 🔴 接管要写回内存三样：`row_id` / `facts` / `resume_id`。漏任何一样都是静默故障（分别对应「重开回到恢复那一刻」「消息发错目标」「发下一句变成新会话」），测试守住见 `restore_adopts_row_into_shared`。
5. 前端：`useCcSession` 挂载时先订阅、再 `cc_snapshot`、**仅当 `nextSeq === 0` 才** `cc_restore`（切页回来 / 热重载时 ring 里就是当前会话，它一定不比库里旧），最后用序号补漏。`CcGuiTab` 拿到 `restored` 后要把 `targetId` / `cwd` / `permissionMode` 一起切回去 —— 只还原消息的话，用户看到的是那段远端对话、发出去却落到本机新会话上。
   - `claudePath` **故意不采信**恢复值：可能已失效，重探一次更可靠（探测只要一次 `--version`）。
6. `cc_start` 里加了一道目标判定（`Shared::same_target`）：**换机器或换目录就必须先收掉旧进程并清 `resume_id` / 行号**。不收的后果是走「进程还活着 ⇒ 直接 send」那条快路径，把消息写进另一个目标的 claude 里 —— 界面正常、内容去了别处、没有任何报错。

验证：聊 3 轮 → 关 app → 重开 → 消息在、发第 4 轮能接上（`--resume` 生效）。**远端也要跑一遍**：`connection_id` + 远端 cwd + `claude_path` 三者缺一个就起不来，而这三个在本地测试里全是空值 —— 这是最容易被「本机通过」骗过去的一环。

| jsonl 是「对话转录」 | **混合日志**：`api-request-blob`(32)、`attachment`(66)、`file-history-snapshot`(8)、`mode`/`permission-mode`/`atis-latch`(各 15) 全在里面，真正的 `user`/`assistant` 只有 32/37 | 必须白名单。任何「除了 X 都算消息」的写法都会把钩子输出（`hook_success` 的几 KB stdout）渲染成聊天内容 |
| `ai-title` 是标题主来源 | **只覆盖 2/62** | 主来源改为首条用户消息，`ai-title` 只是「有就用」 |
| `block_id = {message_id}:{块下标}` 可复用 | 同一条 assistant 消息被**拆成多行**写入（同一 `message.id` 出现 2~5 次） | 改用**行号**拼 `block_id`。照实时流那条路写会让多行互相覆盖 —— 与 2026-10-24 修的「同一段回复渲染两遍」同源 |
| `thinking` 块可以照搬 | 存在 `redacted_thinking`，`data` 是 **5663 字符密文** | 跳过。渲染是乱码，存库白占几十 KB |

### 3. 打开历史 = 接管当前会话

沿用期一 `adopt` 的三件套，只是内容来源从「我们的落盘」换成「CLI 的 jsonl」：
`resume_id`（下一轮 `--resume`）+ `cwd` + `connection_id`。

前端还有一步**不能省**：把 `cwd` 写回工作目录输入框。`cc_start` 会拿它和内存里的
`facts.cwd` 比，不一致就判「换了目录」→ **清 resume id** → 打开的历史当场变成一条新会话，
模型忘光前面且不报错。顺序上 `saveCwd` 必须在 `setTargetId` **之前**（`targetId` 的
effect 会立刻重读 localStorage，晚一步被旧值覆盖）。

打开时不再逐条 emit 事件：后端直接写进 ring，前端用返回值 `replay` 一次。
逐条 emit 会让每条渲染两遍。

### 4. 远端为什么没写

不是漏了。是本机唯一那条远端连接（`10.0.19.194`）是**密码认证、没配密钥**，
开发机免密登录不通 —— 也就是说写出来的每一行都**无法跑一次**。

能做的部分（扫描脚本、`stat` 的 GNU/BSD 双版、base64 解码、PTY 的 `\r\n` 洗涤）
确实都是可单测的纯逻辑，但它们只占远端实现的一半，另一半是
`run_via_helper` 的接线与错误降级，而那部分只能真机验。按「安全/正确结论必须跑出来，
不能推出来」的规矩，宁可不写，也不交付一段看起来能跑、实际从未执行过的代码。

⇒ **需要一台能免密登录的远端机器**（或者给出一个可用的连接），届时按 §六 的六条约束接线。

### 5. verdict 没做的原因

§五.1 说「回放必须带 `verdict`」。第一版不做的理由不是省事，而是**数据源不存在**：
jsonl 不记审批结果，verdict 只存在我们自己的 `cc_sessions` 事件里。而绝大多数历史
（终端页手敲 `claude` 产生的）从没经过我们的审批卡 —— 强行关联只会得到一片「未记录」。

等对话页里跑过足够多会话之后，再按 `tool_use_id` 关联 `cc_sessions` 里的
`PermissionResolved` 才有意义。届时界面上要能区分「没记录」与「被拒」两种空。
