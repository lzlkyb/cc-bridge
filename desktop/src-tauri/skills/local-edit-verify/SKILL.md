# 在本地主机上改文件并验证

每多一趟往返，都要重发一遍整段上下文。目标是用最少的往返完成「改 → 验证」。

## 改文件

- 改已有文件用 `edit_files`，新建或整体覆盖用 `write_files`；不要用 shell 的重定向、`sed`、`cat` 去写文件。
- 回执默认只告诉你改了几行（如「+1/-1 行」），**不会**回显改动内容。需要核对再用 `read_files` 的 `startLine` / `endLine` 读那一小段，别整文件重读。
- `edit_files` 的旧文本用 `\n` 换行写即可；文件原有的编码和 CRLF 会被保留。GBK 文件传 `encoding:"gbk"`。
- 单个文件超过约 500 行时，先用 `search_files` 定位行号，再按行段读。

## 搜索

- `search_files` 默认返回 grep 风格纯文本（每个文件的路径只写一次，之后是 `行号:内容`）。需要结构化结果时才传 `format:"json"`。
- 搜索按 UTF-8 字节匹配：GBK 文件里的中文要传 `encoding:"gbk"`，否则会静默搜不到，不要据此下「不存在」的结论。

## 跑命令

- 预计 50 秒内结束的命令（单文件编译、单个测试、`git status`）直接前台跑，一趟拿到结果。
- 输出默认是不转义的文本块；命令输出可能很大时，先加 `include` / `exclude` / `tailLines` 在服务端过滤。
- 超过约 50 秒会自动转后台。支持任务的客户端会自行等待并在完成后给你结果；否则会得到一个 `handle`，用 `wait_command` 取结果（`timeoutSec` 不超过 55，可带 `untilPattern`），不要反复轮询 `get_command_output`。
- `wait_command` 超时只是不再等，命令仍在后台运行，没有被终止。
- 只有明知要跑好几分钟、且等待期间确有别的工具调用要做时，才主动用 `background:true`。

## 把顺序步骤合成一趟

中间不需要看结果的连续操作（改完文件紧接着编译、建目录再写文件、写完脚本就执行）放进**一个** `batch`：它按顺序执行，工具报错、写入失败或命令失败时默认停止后续步骤。互不依赖的操作则在同一条消息里并行调用。

## 通知

只有预计超过约 1 分钟的长任务（构建、全量测试、批量处理）完成后才调用 `push_notification`。简短的读改不要发，每发一次都多一趟完整上下文往返。
